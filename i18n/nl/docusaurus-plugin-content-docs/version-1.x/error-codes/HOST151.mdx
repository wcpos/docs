## Wat dit betekent {#what-this-means}

Een cache vóór de winkel speelt de API-antwoorden van één persoon af naar iedereen.

Een cachinglaag serveert opgeslagen REST API-antwoorden zonder te controleren wie erom vraagt: de app stuurde twee verschillend geauthenticeerde controles en ontving beide keren het antwoord op de eerste controle. Op een live winkel betekent dit dat de ene kassamedewerker de gegevens van een ander zou kunnen zien, dus verbinden wordt geblokkeerd totdat de cache de API van de winkel uitsluit. Dit is een probleem op de hostinglaag — WordPress zelf antwoordt altijd per gebruiker.

Voordat deze fout wordt gemeld, probeert de app het opnieuw met bij elk verzoek een unieke cachekey. Wanneer die nieuwe poging aantoont dat de sleutel de cache omzeilt, maakt de app verbinding en blijft de sleutel meesturen. Je ziet deze fout dus alleen wanneer ook met de nieuwe poging geen veilige verbinding kon worden vastgesteld.

## Je gegevens {#your-data}

Gegevens op dit apparaat kunnen gevaar lopen — wis geen lokale gegevens. Als dit aanhoudt, exporteer dan de diagnostiek en neem contact op met WCPOS-support.

## Probleemoplossing {#troubleshoot}

1. De app heeft het al opnieuw geprobeerd met bij elk verzoek een unieke cachekey, maar kon nog steeds geen veilige verbinding vaststellen. Daarom moet de cache op de host worden aangepast.
2. Sluit de REST API-paden van de winkel (/wp-json/ en /?rest_route=) uit van paginacaching — schakel op LiteSpeed REST-caching uit of voeg een no-cache-regel toe; breid op WP Engine de WooCommerce-uitsluiting uit naar /wp-json/wcpos; stel op Sucuri het cacheniveau in om Cache-Control te respecteren.
3. De API van de winkel stuurt al Cache-Control: no-store en Vary: Authorization — de cachelaag negeert deze; wijs de host op die headers.
4. Leeg na het wijzigen van de cache-instellingen de cache voordat je opnieuw verbinding maakt.
