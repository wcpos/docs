## Wat dit betekent {#what-this-means}

De server van de winkel blokkeert het inlogtoken via elk kanaal dat deze app kan gebruiken.

De app heeft bevestigd dat de winkel bereikbaar is, maar de server (of een firewall, proxy of beveiligingsplugin ervoor) verwijdert de Authorization-header en blokkeert het token ook wanneer het als URL-parameter wordt verzonden. Er is geen derde manier om een inlogtoken af te leveren, dus dit moet op de server worden opgelost.

## Je gegevens {#your-data}

Er zijn geen bestel- of productgegevens aangetast.

## Problemen oplossen {#troubleshoot}

**Voor je hostingprovider / server** — er is geen kanaal om het inlogtoken af te leveren totdat de server het doorlaat:

1. Laat de Authorization-header door naar WordPress — op Apache is hiervoor meestal één regel nodig: `SetEnvIf Authorization "(.*)" HTTP_AUTHORIZATION=$1`.
2. Als de site rewrites in `.htaccess` gebruikt, behoud dan de door WordPress gegenereerde RewriteRule-regel die `HTTP_AUTHORIZATION` doorgeeft — beveiligingsplugins verwijderen die soms.
3. Controleer bij een proxy of CDN de lijst met toegestane headers: de Authorization-verzoekheader moet worden doorgestuurd naar de oorspronkelijke server.
4. Als een webapplicatiefirewall (WAF) URL-parameters filtert, sta dan de authorization-parameter toe op `/wcpos/` REST-routes.
