**Administration WP :** les modèles se modifient dans `WP Admin → POS → Templates` ; cette page répertorie les champs qu’ils peuvent imprimer.

Pour imprimer un reçu ou l’envoyer par e-mail, consultez [Reçus et écran de paiement effectué](./at-checkout.mdx) ; pour choisir un modèle ou le faire modifier par l’IA, consultez [Personnaliser votre reçu](./customise.mdx).

Cette page explique comment modifier manuellement le code d’un modèle. Tous les modèles, HTML ou thermiques, utilisent les mêmes données de reçu pour l’impression : la boutique, la commande, les articles, les totaux et les paiements. Vous y trouverez comment imprimer un champ, trois exemples courants et la liste de tous les champs.

**Accès rapide :** [Trouver un champ](#field-reference) · [Exemples courants](#common-recipes) · [En cas de problème](#if-something-goes-wrong)

## Imprimer un champ {#print-a-field}

1. Ouvrez le modèle dans **WP Admin → PDV → Modèles** (consultez [Modifier manuellement](./customise.mdx#option-3--edit-it-by-hand) pour les détails).
2. À l’endroit où le champ doit être imprimé, saisissez son chemin entre doubles accolades, par exemple `{{store.name}}`, `{{order.number}}` ou `{{totals.total_display}}`, ou insérez-le depuis la liste des champs à côté du code.
3. Vérifiez l’aperçu sous le code, puis cliquez sur **Mettre à jour** pour enregistrer.

Pour une liste, comme celle des articles, placez la ligne dans une section : elle se répétera une fois par article :

```mustache
{{#lines}}
  {{name}} x {{qty}} —
  {{line_total_display}}
{{/lines}}
```

Une section omet aussi son contenu lorsque le champ est vide, nul ou faux. Ainsi, `{{#customer.id}}…{{/customer.id}}` ne s’imprime que pour un client identifié. Pour imprimer un montant, utilisez le champ se terminant par `_display` ; consultez [Champs monétaires](#currency-fields).

Les reçus s’impriment aussi hors ligne : l’application crée une copie des données du reçu à partir de la commande présente sur l’appareil.

<Accordion>
  <AccordionItem question="Pourquoi les reçus peuvent différer">

### D’où viennent les données {#where-the-data-comes-from}

Le serveur de votre boutique crée les données du reçu pour chaque commande, et l’application en crée une version réduite à partir de la commande présente sur l’appareil : celle-ci ne contient ni `cashier`, ni horaires d’ouverture, notes ou conditions de la boutique, ni `totals.paid_total` ou `totals.change_total`. Un modèle HTML ou thermique s’ouvre immédiatement à partir de la copie de l’appareil, puis utilise celle du serveur dès qu’elle arrive ; hors ligne, c’est la copie de l’appareil qui s’imprime, et ces champs restent donc vides. Avec WCPOS Pro, la copie de l’appareil contient aussi le logo de la boutique ; sans Pro, le logo arrive avec la copie du serveur. Le rendu d’un ancien modèle PHP est toujours effectué par le serveur. C’est pourquoi un modèle utilise les champs ci-dessous et jamais les méthodes PHP des commandes. Certains champs ne s’impriment que lorsque le serveur effectue le rendu du modèle, comme pour un téléchargement PDF ; ils sont répertoriés dans [En cas de problème](#if-something-goes-wrong).

</Accordion>

## Le reçu en détail {#receipt-map}

Chaque partie d’un reçu imprimé provient d’une section des données du reçu. Pointez sur une partie du reçu ou sur sa fiche pour mettre les deux en surbrillance ; cliquez ou appuyez sur l’une ou l’autre pour accéder aux champs de cette section. Sur un téléphone, les fiches suivent le reçu dans le même ordre, de haut en bas.

Le reçu ci-dessous, les deux premiers exemples et la décomposition des prix utilisent la même commande d’exemple. Les montants de ses articles sont ceux d’avant application du coupon (`line_subtotal_display`) ; les modèles de reçu de la galerie les impriment après son application (`line_total_display`, 26.10 pour l’espresso).

## Référence des champs {#field-reference}

Dépliez une section pour voir ses champs. La première entrée répertorie toutes les sections et leur type.

<Accordion>
  <AccordionItem question="Toutes les sections et leurs types">

### Sections de premier niveau {#top-level-sections}

| Section | Contenu |
|---------|---------------|
| `order` (objet) | Identité, statut, dates, note de la commande et informations sur l’URL de paiement |
| `store` (objet) | Identité, adresse, coordonnées, identifiants fiscaux, logo, horaires et texte de pied de page de la boutique |
| `cashier` (objet) | Utilisateur ayant traité la commande |
| `customer` (objet) | Nom d’affichage, adresses et identifiants fiscaux du client |
| `lines` (tableau) | Lignes de produits |
| `fees` (tableau) | Lignes de frais |
| `shipping` (tableau) | Lignes de livraison |
| `discounts` (tableau) | Lignes de coupons/remises |
| `totals` (objet) | Totaux de la commande, totaux des paiements, récapitulatif des remboursements et nombre d’articles |
| `tax` (objet) | Indicateurs du mode d’affichage des taxes pour conditionner les sections |
| `tax_summary` (tableau) | Lignes récapitulatives des taxes par taux |
| `has_tax_summary` (booléen) | Condition pratique pour `tax_summary` |
| `payments` (tableau) | Lignes de paiements |
| `refunds` (tableau) | Enregistrements des remboursements appliqués à la commande |
| `fiscal` (objet) | Champs de l’instantané fiscal renseignés par les intégrations fiscales |
| `register` (objet) | Caisse ayant enregistré la vente : `id` et `name`. Chaînes vides si elle est inconnue |
| `software` (objet) | Logiciel ayant émis le reçu : `name` (`WCPOS`), `plugin_version`, `app_version`, `app_build`, `platform` |
| `presentation_hints` (objet) | Indications de mise en forme et de rendu |
| `i18n` (objet) | Libellés traduits pour les modèles fournis et personnalisés |

  </AccordionItem>

### order {#order}

| Champ | Type | Exemple / description |
|-------|------|-----------------------|
| `order.id` | nombre | `1042` |
| `order.number` | chaîne | Numéro de commande destiné à l’utilisateur, par ex. `"1042"` |
| `order.currency` | chaîne | Code ISO de la devise, par ex. `"USD"` |
| `order.customer_note` | chaîne | Note du client/de la commande |
| `order.wc_status` | chaîne | Identifiant brut du statut WooCommerce, par ex. `"processing"` |
| `order.status_label` | chaîne | Libellé localisé du statut, y compris pour les statuts personnalisés |
| `order.created_via` | chaîne | Source/canal, par ex. `"woocommerce-pos"` |
| `order.needs_payment` | booléen | Indique si une section de paiement doit être affichée |
| `order.payment_url` | chaîne | URL de paiement de la commande, si disponible |
| `order.created` | objet date | Date de création de la commande |
| `order.paid` | objet date | Date du paiement, chaînes vides si la commande n’est pas payée |
| `order.completed` | objet date | Date de fin, chaînes vides si la commande n’est pas terminée |
| `order.printed` | objet date | Horodatage d’impression/réimpression au moment du rendu |

| Champ | Type | Exemple / description |
|-------|------|-----------------------|
| `store.id` | nombre | ID de la boutique, ou ID historique pour les boutiques supprimées |
| `store.name` | chaîne | Nom d’affichage de la boutique |
| `store.address.address_1` | chaîne | Ligne 1 de l’adresse postale |
| `store.address.address_2` | chaîne | Complément d’adresse (bureau/appartement) |
| `store.address.city` | chaîne | Ville/localité |
| `store.address.state` | chaîne | État/région |
| `store.address.postcode` | chaîne | Code postal |
| `store.address.country` | chaîne | Code ISO du pays |
| `store.address_lines` | tableau | Lignes d’adresse préformatées ; recommandées pour la plupart des modèles |
| `store.tax_ids` | tableau | Identifiants fiscaux structurés de l’entreprise ; parcourez ce tableau en boucle plutôt que d’utiliser un seul identifiant fiscal |
| `store.phone` | chaîne | Téléphone de la boutique |
| `store.email` | chaîne | E-mail de la boutique |
| `store.logo` | chaîne/null | URL ou URI de données du logo de la boutique : son propre logo ou, à défaut, celui du site WordPress, sauf si la boutique désactive cette option. `null` si aucun des deux n’existe |
| `store.opening_hours` | chaîne/null | Texte compact des horaires d’ouverture |
| `store.opening_hours_vertical` | chaîne/null | Bloc des horaires d’ouverture sur plusieurs lignes |
| `store.opening_hours_inline` | chaîne/null | Horaires d’ouverture séparés par des virgules |
| `store.opening_hours_notes` | chaîne/null | Notes libres sur les horaires d’ouverture |
| `store.personal_notes` | chaîne/null | Pied de page du reçu/note personnelle |
| `store.policies_and_conditions` | chaîne/null | Texte sur les remboursements, les retours ou les conditions |
| `store.footer_imprint` | chaîne/null | Mentions légales en pied de page |

### Objets d’identifiants fiscaux {#tax-id-objects}

`store.tax_ids` et `customer.tax_ids` contiennent des objets de même structure :

| Champ | Type | Description |
|-------|------|-------------|
| `type` | chaîne | Identifiant tel que `eu_vat`, `de_steuernummer`, `au_abn`, `br_cpf`, `us_ein` ou `other` |
| `value` | chaîne | Valeur de l’identifiant fiscal à imprimer |
| `country` | chaîne/null | Code ISO du pays ; null pour `eu_vat` et `other` |
| `label` | chaîne | Libellé d’affichage localisé, déterminé avant le rendu |

Exemple :

```mustache
{{#store.tax_ids}}
  {{label}}: {{value}}
{{/store.tax_ids}}
```

### customer {#customer}

| Champ | Type | Exemple / description |
|-------|------|-----------------------|
| `customer.id` | nombre/null | ID du client, ou `null` pour les invités |
| `customer.name` | chaîne | Nom d’affichage du client, ou libellé pour les invités |
| `customer.first_name` | chaîne | Prénom de facturation, pour un message comme « Merci, Nia ». Vide pour les invités qui n’en ont pas renseigné |
| `customer.billing_address.*` | objet | Champs de l’adresse de facturation WooCommerce |
| `customer.shipping_address.*` | objet | Champs de l’adresse de livraison WooCommerce |
| `customer.tax_ids` | tableau | Identifiants fiscaux structurés du client, enregistrés dans un instantané à partir de la commande |

Les clés d’adresse courantes comprennent `first_name`, `last_name`, `company`, `address_1`, `address_2`, `city`, `state`, `postcode`, `country`, `email` et `phone`.

### Afficher le prix normal et les économies {#displaying-regular-price-and-savings}

Pour une mise en page avec prix unitaires, affichez le prix normal enregistré, le prix de vente et l’économie ainsi :

```mustache
{{#lines}}
  {{#unit_savings}}
    <span style="text-decoration: line-through;">{{regular_price_display}}</span>
    <span>{{selling_price_display}}</span>
    <span>{{i18n.savings}}: -{{unit_savings_display}}</span>
  {{/unit_savings}}
{{/lines}}
```

Utilisez les champs de total de ligne lorsque la quantité compte :

```mustache
{{#lines}}
  {{#line_savings}}
    <span style="text-decoration: line-through;">{{line_regular_total_display}}</span>
    <span>{{i18n.savings}}: -{{line_savings_display}}</span>
  {{/line_savings}}
{{/lines}}
```

`selling_price` est le prix avant les coupons. Utilisez `unit_price` ou `line_total` pour le montant final après les remises WooCommerce.

:::note Réimpression des commandes créées avant la v1.9.0
Les anciennes commandes WCPOS peuvent déjà inclure la réduction entre le prix normal et le prix de vente dans `discounts`. Si votre modèle personnalisé imprime à la fois les économies et les remises de chaque ligne, utilisez `savings_in_discounts` pour éviter d’afficher deux fois la même réduction :

```mustache
{{#lines}}
  {{#line_savings}}
    <span style="text-decoration: line-through;">{{line_regular_total_display}}</span>
    {{^savings_in_discounts}}
      <span>{{i18n.savings}}: -{{line_savings_display}}</span>
    {{/savings_in_discounts}}
  {{/line_savings}}
  {{#discounts}}
    <span>{{i18n.discount}}: -{{discounts_display}}</span>
  {{/discounts}}
{{/lines}}
```

Si le modèle n’imprime pas de ligne `discounts` pour chaque article, continuez à afficher `line_savings` même lorsque `savings_in_discounts` est vrai. Les modèles fournis gèrent automatiquement cette distinction.
:::

## Les relations entre les prix {#price-model}

Un article sur le reçu comporte plusieurs prix ; leurs noms sont plus faciles à comprendre en regardant les montants eux-mêmes. Voici la ligne de café espresso de la commande d’exemple : un produit à $17.00 en promotion à $14.50, avec un coupon de 10% supplémentaire :

<PriceFlow
  caption="Café en grains espresso — une unité (la commande en contient deux)"
  scaleLabel="prix normal 17.00"
  segments={[
    { kind: 'paid', amount: 13.05, label: "13.05 payés" },
    { kind: 'coupon', amount: 1.45, label: "1.45" },
    { kind: 'savings', amount: 2.5, label: "2.50" },
  ]}
  summary={[
    { label: "Économies promotionnelles sur toute la commande", value: '`totals.sale_savings_total` = 5.00' },
    { label: "Toutes les remises par coupon sur la commande", value: '`totals.discount_total` = 5.28' },
    { label: "Économies + remises, doublons des anciennes commandes éliminés", value: '`totals.total_saved` = 10.28' },
  ]}
/>

Une économie promotionnelle est l’écart entre le prix normal et le prix de vente. Une remise est le montant déduit par un coupon, tel que WooCommerce le calcule. Les totaux de commande et les rapports WooCommerce ne contiennent que les remises : `total_saved` additionne donc les deux pour présenter un seul montant au client.

### Objets date {#date-objects}

Chaque date est fournie dans plusieurs formats prêts à l’emploi : le modèle n’a donc jamais à la formater lui-même.

| Champ | Description |
|-------|-------------|
| `datetime`, `date`, `time` | Chaînes de date/heure par défaut |
| `datetime_short`, `datetime_long`, `datetime_full` | Formats combinés adaptés aux paramètres régionaux |
| `date_short`, `date_long`, `date_full` | Formats de date seule adaptés aux paramètres régionaux |

| `weekday_short`, `weekday_long` | Noms des jours |

## Étendre les données du reçu {#extending}

Une extension peut ajouter ses propres champs aux données du reçu grâce au filtre `wcpos_receipt_data`.

<Accordion>
  <AccordionItem question="Le filtre — ses arguments, les six modes et un exemple">

WCPOS ne place aucune donnée propre à une extension dans les champs ci-dessus. Lorsqu’une extension a besoin que le reçu contienne une information que WooCommerce ne modélise pas, elle l’ajoute elle-même via le filtre `wcpos_receipt_data`, de la même manière que les extensions filtrent les totaux de commande de WooCommerce. Le filtre s’exécute pour chaque reçu créé par le serveur : reçus en direct, instantanés fiscaux au moment du paiement, téléchargements PDF et anciens modèles PHP. Avant WCPOS 2.0, ce filtre s’appelait `woocommerce_pos_receipt_data` ; ce nom fonctionne encore, mais il est obsolète depuis la version 2.0 et sera supprimé au plus tôt dans la version 2.2 (voir [Nommage des hooks](../extensions/index.mdx#hook-naming)).

Le troisième argument, `$mode`, indique le document en cours de création : `live`, `fiscal`, `refund`, `preview` (reçus d’exemple dans l’éditeur de modèles et la galerie), `closure` ou `xreport` (documents de clôture de caisse et rapports X). En mode `preview`, `closure` et `xreport`, la commande n’est pas enregistrée et son ID est `0` ; une extension qui nécessite une commande enregistrée doit renvoyer `$data` sans modification lorsque `$order->get_id()` vaut `0`.

```php
add_filter( 'wcpos_receipt_data', function ( array $data, WC_Abstract_Order $order, string $mode ) {
    foreach ( $data['discounts'] as &$row ) {
        if ( 'smart_coupon' === $row['discount_type'] ) {
            $row['gift_card'] = true;
        }
    }
    return $data;
}, 10, 3 );
```

Un modèle peut alors utiliser la nouvelle clé comme condition, comme pour toute autre section :

```
{{#discounts}}
  {{#gift_card}}Gift Card{{/gift_card}}{{^gift_card}}{{i18n.discount}}{{/gift_card}}{{#label}}: {{label}}{{/label}}
{{/discounts}}
```

Les clés définies dans le schéma doivent conserver leurs types documentés. Les clés ajoutées ne font pas partie du schéma : elles n’apparaissent donc pas dans le sélecteur de champs de l’éditeur de modèles, et les instantanés fiscaux ne contiennent que ce que le filtre a ajouté au moment du paiement de la commande. Le filtre est disponible depuis WCPOS 1.10.8.

  </AccordionItem>

  <AccordionItem question="Quels reçus impriment une clé ajoutée">

Toutes les clés ajoutées parviennent aux reçus dont le serveur effectue lui-même le rendu : téléchargements PDF et anciens modèles PHP. Les modèles HTML et thermiques dont le rendu est effectué dans l’application PDV reconstruisent d’abord les données : une clé ajoutée dans `order`, `store`, `cashier` ou `customer` est transmise, mais une clé ajoutée ailleurs, comme sur la ligne de remises ci-dessus, est omise. {/* pending: monorepo#3363 */} Sur un reçu en direct disposant d’un instantané fiscal, l’identité fiscale, `register` et `software` sont copiés depuis l’instantané après l’exécution du filtre ; les modifier dans ce filtre n’a donc aucun effet. Enrichissez plutôt l’instantané.

  </AccordionItem>
</Accordion>

## En cas de problème {#if-something-goes-wrong}

**Une ligne imprime `$0.00` sur un reçu et rien sur un autre.** Certains champs `_display`, tels que `totals.change_total_display`, `totals.refund_total_display` et `payments[].tendered_display`, sont vides lorsque le montant est nul si le serveur effectue le rendu du reçu, et valent `$0.00` si c’est l’application qui s’en charge. Placez plutôt la ligne dans une section conditionnée par le nombre, afin de l’omettre dans les deux cas : `{{#totals.change_total}}…{{/totals.change_total}}`.

**La ligne Total économisé est absente.** `totals.total_saved_complete` est faux : au moins un article n’a pas de prix normal enregistré, ce qui empêche de calculer l’économie. C’est généralement le cas des commandes encaissées avant WCPOS 1.9.0.

**Le total est inférieur au montant payé par le client.** La boutique affiche les prix hors taxes : `totals.total` correspond donc au total avant taxes. Imprimez `totals.total_incl_display` pour obtenir le montant facturé. L’ancien reçu PHP fourni avec WCPOS imprime ce montant.

**Un champ s’imprime dans le PDF téléchargé, mais pas dans le PDV.** Les modèles dont le rendu est effectué dans l’application reconstruisent d’abord les données et omettent certains champs, qui ne s’impriment que dans les téléchargements PDF et les anciens modèles PHP. N’imprimez un champ de la liste ci-dessous que dans ces derniers, ou conditionnez-le avec une section pour que le reçu du PDV l’omette. {/* pending: monorepo#3363 */}

<Accordion>
  <AccordionItem question="Champs qui diffèrent entre les reçus PDF et ceux du PDV">

- `lines[].attributes`, `lines[].total_refunded_display` et `lines[].unit_subtotal_display` (avec ses variantes `_incl` et `_excl`)
- `software.platform`
- `presentation_hints` autres que `display_tax`, `prices_entered_with_tax`, `rounding_mode`, `locale` et `order_barcode_type`
- identifiants fiscaux des clients de types allemand, néerlandais, français, entreprise britannique et suisse
- clés qu’une extension ajoute en dehors de `order`, `store`, `cashier` et `customer` ; voir [Étendre les données du reçu](#extending)

</AccordionItem>
</Accordion>

## Versions {#versions}

Les données du reçu ont leur propre numéro de version, distinct de celui de l’extension. Les champs récents sont absents des anciens reçus, par exemple d’un instantané fiscal créé avant leur existence : conditionnez-les donc avec une section.

| Version | Ajouts |
|---------|-------|
| 1.1 | Prix normal, prix de vente et économies pour chaque article, ainsi que les totaux d’économies de la commande, dont **Total économisé**. Aucun de ces champs ne modifie les totaux de commande ni les rapports WooCommerce |
| 1.2 | `discounts[].discount_type` |
| 1.3 | `customer.first_name` et les libellés d’affichage du client dans `i18n` |
| 1.4 | `register`, `software`, les champs du document fiscal (`fiscal.document_type`, les indicateurs `is_…`, `sale_time`, `received_at`, `sale_tz`, `sale_counter`, `corrects`) et leurs libellés `i18n` |
