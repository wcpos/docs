Cette page explique l’architecture technique de WCPOS aux développeurs et aux utilisateurs avancés.

## Système en deux parties {#two-part-system}

WCPOS est conçu comme un système en deux parties :

1. **Extension PHP :** hébergée sur votre serveur, cette extension relativement petite étend l’[API REST de WooCommerce](/1.x/reference/wc-rest-api) avec des points de terminaison spécifiques au PDV.

2. **Client JavaScript :** il fonctionne localement dans votre navigateur, dans l’application de bureau ou dans les applications iOS/Android.

Vous pouvez le considérer comme deux mondes séparés :

- Le _monde PHP_ est celui où la gestion des données se fait à l’aide de WordPress et WooCommerce.
- Le _monde JavaScript_ conserve une copie locale, utilisable hors ligne, des données de boutique dont vos caisses ont besoin, optimisée pour une recherche rapide et une réponse instantanée.

## Synchronisation des données {#data-synchronization}

:::info Modifié dans la v1.10.0
La v1.10.0 remplace la précédente couche de réplication par un **moteur de synchronisation** dédié. Le résumé ci-dessous en est la version courte — l’explication complète se trouve dans [Fonctionnement du moteur de synchronisation](/1.x/reference/sync-engine).
:::

Le client privilégie le fonctionnement local : chaque écran lit et écrit dans la base de données locale de l’appareil, et un moteur de synchronisation en arrière-plan fait converger cette base et WooCommerce. Le moteur ne reproduit **pas** aveuglément l’intégralité de votre boutique — il part de ce dont vos écrans ont réellement besoin :

- **Détection des changements :** le PDV interroge un journal des changements léger au moyen de requêtes conditionnelles ; une boutique inactive répond par un unique `304` sans corps.
- **Besoin déclaré :** un écran déclare ce qu’il affiche, et le moteur décide si cela nécessite une requête ou si la réponse existe déjà localement.
- **Amorçages et voies :** un amorçage limité du catalogue, une fenêtre de commandes récentes et des voies de maintenance exécutées pendant les temps morts remplissent et vérifient les données locales selon des planifications réglables par appareil.
- **Écritures durables :** les ventes et les modifications sont mises en file d’attente localement puis envoyées à WooCommerce, avec des possibilités de récupération visibles pour tout ce que le serveur refuse.

Éléments synchronisés : produits et variations, catégories/étiquettes/marques, clients, taux de taxe, coupons (Pro) et commandes. Les passerelles de paiement sont récupérées au moment du paiement.

## Avantages et inconvénients de l’architecture {#architecture-pros-and-cons}

| Avantages 😊 | Inconvénients 😟 |
| ------------------------------------------------------------------ | -------------------------------------------------------- |
| La recherche dans les données locales est instantanée | Maintenir les données synchronisées est complexe |
| Les données mises en cache sont disponibles hors ligne | Limité par l’API REST de WooCommerce |
| Possibilité de créer de meilleures applications natives pour ordinateur, iOS et Android | Les thèmes et hooks WordPress ne peuvent pas personnaliser l’application PDV |

## Base de données locale {#local-database}

Le client stocke les données dans une base de données locale sur chaque appareil — les applications web et de bureau utilisent un **stockage OPFS (Origin Private File System) exécuté dans un worker**, et les applications mobiles utilisent le même format sur disque via un moteur de système de fichiers. Toutes les plateformes partagent le même format de stockage et les mêmes outils de récupération. Cela offre :

- **Persistance :** les données sont conservées après les redémarrages du navigateur et de l’appareil
- **Performance :** des requêtes rapides sans latence réseau — le filtrage, le tri et la pagination s’exécutent dans la couche de stockage, de sorte que seule la page de lignes visible parvient à l’interface
- **Navigation hors ligne :** les données mises en cache restent accessibles sans Internet

Chaque combinaison site + boutique + caissier dispose de sa propre base de données locale, de sorte que les caissiers et les boutiques ne partagent jamais de données locales sur un même appareil. Les mises à jour ne migrent jamais une base de données locale sur place — l’application retélécharge les données depuis le serveur, qui conserve toujours la copie de référence.

## Architecture de paiement {#checkout-architecture}

Le processus de paiement utilise une iframe/webview qui charge la page de paiement de commande de WooCommerce. Cette approche :

- **Tire parti des passerelles de paiement existantes :** toute passerelle de paiement WooCommerce peut fonctionner dans le PDV
- **Maintient la sécurité :** le traitement des paiements passe par l’infrastructure sécurisée de WooCommerce
- **Réduit la complexité :** pas besoin de réimplémenter les intégrations des passerelles de paiement

## Extensions de l’API {#api-extensions}

L’extension PHP étend l’API REST de WooCommerce avec des points de terminaison supplémentaires pour les fonctionnalités propres au PDV, enregistrés sous les espaces de noms dédiés `wcpos/v1` et `wcpos/v2` — `wcpos/v2` regroupe les fonctions de synchronisation de la v1.10.0, ce qui explique que les versions de l’application et de l’extension soient publiées de pair. Consultez l’[API REST de WooCommerce](/1.x/reference/wc-rest-api) pour une introduction.

### L’espace de noms `wcpos/v2` {#wcpos-v2-namespace}

La v1.10 introduit l’espace de noms REST `wcpos/v2`. La synchronisation y réside, et les services PDV partagés qui étaient auparavant servis depuis `wcpos/v1` sont désormais servis depuis `wcpos/v2` (les routes de service `wcpos/v1` sont des relais vers leurs implémentations v2). Les routes `wcpos/v1` sont toujours enregistrées pour assurer la rétrocompatibilité, mais elles sont **figées** — le client actuel ne les appelle plus.

Points importants si vous développez une intégration avec ces points de terminaison :

- **Les routes v2 sont toujours enregistrées.** L’ancienne option `woocommerce_pos_sync_api_enabled` a été supprimée ; il n’existe plus d’indicateur qui active ou désactive l’API.
- **Points de terminaison publics.** `wcpos/v2/site`, `wcpos/v2/ping` et `wcpos/v2/echo` sont publics (utilisés pour tester les capacités et la connectivité, y compris les [solutions de repli du transport](/1.x/error-codes) pour les hébergeurs restrictifs).
- **Les commandes ont l’UUID comme identifiant principal.** L’identité d’une commande sur le réseau est l’UUID ; l’ancien champ `wooOrderId` a été retiré de l’enveloppe de récupération des commandes. Les métadonnées de commande sont typées lors des échanges réseau à l’aide d’un normaliseur unique.
- **Le stockage des prix par ligne d’article est documenté** pour assurer la compatibilité avec les systèmes de synchronisation tiers — consultez [Comment les modifications de prix PDV sont stockées](/1.x/reference/pos-discounts#how-pos-price-overrides-are-stored).
- **Le tri par défaut des produits** dans le PDV est désormais **par nom croissant** (auparavant `menu_order, id`).
- **Suppression de méthodes héritées.** Plusieurs méthodes héritées du contrôleur `API\Settings` (par exemple `get_general_settings()`, `update_access_settings()`, `get_general_endpoint_args()`, `remove_license_transient()`) ont été supprimées ; l’alias de classe subsiste, mais pas ces méthodes.

:::note Pro suit la même séparation
WCPOS Pro suit la même séparation V1/V2 — ses services partagés passent à `wcpos/v2` tandis que ses données de commande restent figées en v1. La tarification des produits par boutique s’exécute sur la voie v2, et la boutique associée à la caisse est transmise lors de l’écriture des commandes afin que les prix et les taxes des commandes multi-boutiques soient calculés pour la bonne boutique. Consultez [Pro](/1.x/getting-started/free-vs-pro).
:::
