## Ce que cela signifie {#what-this-means}

La route de la boutique WCPOS n’est pas disponible.

Demandez à l’administrateur du site de vérifier qu’aucune extension de sécurité ou de proxy ne supprime les en-têtes de requête WCPOS.

## Que faire {#what-to-do}

Une modification des réglages est nécessaire avant que cela fonctionne. Réessayez après avoir effectué la modification ci-dessus ; sans elle, la nouvelle tentative échouera de la même manière.

## Vos données {#your-data}

Aucune donnée de commande ou de produit n’est affectée. Si le problème persiste, demandez de l’aide à la personne qui gère votre site WordPress.

## Résolution des problèmes {#troubleshoot}

1. Vérifiez que WCPOS est actif sur le site : WP Admin → Extensions.
2. Testez directement la route : ouvrez l’adresse /wp-json/ de votre boutique dans un navigateur — une page HTML ou une erreur 404 à la place de JSON signifie que l’API REST elle-même est bloquée.
3. Demandez à l’administrateur du site si une extension de sécurité, un proxy ou un CDN supprime les en-têtes de requête WCPOS ou bloque /wp-json/ — les règles de pare-feu et les options de renforcement désactivant l’API REST sont les causes habituelles.
4. Chez certains hébergeurs, enregistrer à nouveau les permaliens (Réglages → Permaliens → Enregistrer) restaure les routes REST manquantes.

## Où chercher {#where-to-look}

Chaque occurrence de ce code est enregistrée sur l’appareil qui l’a générée. Ouvrez **Santé de la boutique → Journaux** (l’icône de pulsation cardiaque en bas du panneau de navigation), recherchez l’entrée marquée de ce code et développez-la : la ligne développée affiche la raison en langage clair ainsi que le contexte capturé au moment de l’échec — pour tout ce qui impliquait une requête vers votre boutique, cela inclut le propre code d’erreur du serveur (`serverCode`), le `status` HTTP et l’`endpoint`. Lorsque vous signalez un problème, utilisez **Copier les informations de débogage** en haut de l’écran Journaux (**Partager les informations de débogage** sur les téléphones et tablettes) plutôt que des captures d’écran : ces informations regroupent la version de l’application, l’état de la connexion et les erreurs les plus récentes. Les journaux sont conservés au maximum 30 jours ; recueillez-les donc tant que le problème est récent.

Au-delà du journal intégré à l’application, cet échec peut laisser des traces dans :

- **Inspecteur réseau** (web et bureau) : ouvrez les outils de développement — appuyez sur F12 dans le navigateur, ou choisissez **Avancé → Afficher/masquer les outils de développement** dans le menu de l’application de bureau — sélectionnez l’onglet **Réseau** et répétez l’action. La requête en échec affiche le statut HTTP et le corps de réponse brut, y compris les pages d’erreur qui n’atteignent jamais le journal POS.
- **WooCommerce → État → Journaux** : sur le site WordPress, vérifiez le plus récent `fatal-errors-*.log` pour détecter les plantages PHP, ainsi que toute source de journal portant le nom d’une extension impliquée dans l’échec. Une erreur de classe 500 provenant de la boutique y laisse presque toujours sa cause.

## Détails {#details}

- **Code :** `AUTH311` (`REST_ROUTE_MISSING`)
- **Gravité :** erreur
- **Introduit dans :** WCPOS 1.10.0
