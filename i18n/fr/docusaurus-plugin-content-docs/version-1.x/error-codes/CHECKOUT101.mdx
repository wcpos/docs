## Signification {#what-this-means}

Le paiement n’a pas abouti, et le panier peut toujours être réessayé en toute sécurité.

Vérifiez le panier et réessayez le paiement ; le contenu actuel du panier a été préservé.

## Que faire {#what-to-do}

Réessayez l’action. WCPOS ne la réessaie pas automatiquement ; réessayez lorsque vous êtes prêt.

## Vos données {#your-data}

La commande elle-même est préservée et inchangée.

## Résolution des problèmes {#troubleshoot}

1. Vérifiez le panier — il n’a pas été modifié — puis réessayez de finaliser la commande.
2. Si le problème persiste de la même manière, développez l’entrée du journal : serverCode et status indiquent si la boutique a refusé la commande et pourquoi.
3. Un échec répété avec un statut de classe 500 indique un problème du site — vérifiez WooCommerce → État → Journaux afin de repérer une erreur PHP au moment de l’échec.
4. Si la raison mentionne un article précis, retirez-le, terminez la vente, puis examinez ce produit ultérieurement.

## Où chercher {#where-to-look}

Chaque occurrence de ce code est enregistrée sur l’appareil qui l’a générée. Ouvrez **État du point de vente → Journaux** (l’icône de fréquence cardiaque en bas du tiroir de navigation), recherchez l’entrée marquée de ce code et développez-la : la ligne développée affiche la raison en langage clair et le contexte capturé au moment de l’échec — pour tout élément impliquant une requête vers votre boutique, cela inclut le propre code d’erreur du serveur (`serverCode`), le `status` HTTP et l’`endpoint`. Pour signaler un problème, utilisez **Copier les informations de débogage** en haut de l’écran Journaux (**Partager les informations de débogage** sur les téléphones et tablettes) plutôt que des captures d’écran : cette option regroupe la version de l’application, l’état de la connexion et les erreurs les plus récentes. Les journaux sont conservés pendant 30 jours au maximum ; collectez-les donc tant que le problème est récent.

Au-delà du journal intégré à l’application, cet échec peut laisser des traces dans :

- **Inspecteur réseau** (web et ordinateur) : ouvrez les outils de développement — appuyez sur F12 dans le navigateur, ou sélectionnez **Avancé → Afficher/Masquer les outils de développement** dans le menu de l’application de bureau — puis sélectionnez l’onglet **Réseau** et répétez l’action. La requête en échec affiche le statut HTTP et le corps brut de la réponse, y compris les pages d’erreur qui n’atteignent jamais le journal POS.
- **Journaux POS côté serveur** : dans WP Admin, ouvrez **POS → Réglages → Outils → Journaux**. Cette page enregistre les avertissements et erreurs liés au POS générés sur le serveur lui-même, qui peuvent ne jamais apparaître dans l’application. Un badge rouge sur le menu indique des erreurs côté serveur non lues.
- **WooCommerce → État → Journaux** : sur le site WordPress, consultez le plus récent `fatal-errors-*.log` pour repérer les plantages PHP, ainsi que toute source de journal portant le nom d’une extension impliquée dans l’échec. Une erreur de classe 500 provenant de la boutique y laisse presque toujours sa cause.
