## Ce que cela signifie {#what-this-means}

Un autre plugin d’authentification empêche WCPOS de se connecter.

Demandez à l’administrateur du site de résoudre le conflit avec le plugin indiqué avant de vous reconnecter.

## Que faire {#what-to-do}

Une modification des réglages est nécessaire avant que cela fonctionne. Réessayez après avoir effectué la modification ci-dessus ; sans elle, la nouvelle tentative échouera de la même manière.

## Vos données {#your-data}

Aucune donnée de commande ou de produit n’est affectée. Si le problème persiste, contactez la personne qui gère votre site WordPress.

## Résolution des problèmes {#troubleshoot}

1. Développez l’entrée du journal : elle indique le plugin en conflit signalé par la boutique.
2. Demandez à l’administrateur du site de vérifier les réglages de ce plugin : la plupart des plugins d’authentification peuvent exempter les routes REST de WCPOS au lieu d’être entièrement désactivés.
3. Après la modification, reconnectez-vous depuis la caisse.
4. S’il n’est pas évident de déterminer quel plugin est en conflit, effectuez un test sur une copie de préproduction en désactivant les plugins de sécurité et de connexion un par un.

## Où chercher {#where-to-look}

Chaque occurrence de ce code est enregistrée sur l’appareil qui l’a générée. Ouvrez **État de la boutique → Journaux** (l’icône de pouls cardiaque en bas du tiroir de navigation), trouvez l’entrée marquée avec ce code et développez-la : la ligne développée affiche la raison en langage simple et le contexte capturé au moment de l’échec — pour tout ce qui impliquait une requête vers votre boutique, cela comprend le propre code d’erreur du serveur (`serverCode`), le `status` HTTP et le `endpoint`. Pour signaler un problème, utilisez **Copier les informations de débogage** en haut de l’écran Journaux (**Partager les informations de débogage** sur les téléphones et tablettes) plutôt que des captures d’écran : cette option regroupe la version de l’application, l’état de connexion et les erreurs les plus récentes. Les journaux sont conservés au maximum 30 jours ; collectez-les donc tant que le problème est récent.

Au-delà du journal dans l’application, cet échec peut laisser des traces dans :

- **Inspecteur réseau** (web et ordinateur) : ouvrez les outils de développement — appuyez sur F12 dans le navigateur, ou sur **Avancé → Afficher/masquer les outils de développement** dans le menu de l’application de bureau — sélectionnez l’onglet **Réseau** et répétez l’action. La requête en échec affiche le statut HTTP et le corps brut de la réponse, y compris les pages d’erreur qui n’atteignent jamais le journal POS.
- **Journaux POS côté serveur** : dans WP Admin, ouvrez **POS → Réglages → Outils → Journaux**. Cette page enregistre les avertissements et erreurs liés au POS générés sur le serveur lui-même, qui peuvent ne jamais apparaître dans l’application. Un badge rouge dans le menu indique des erreurs côté serveur non lues.
- **WooCommerce → État → Journaux** : sur le site WordPress, consultez le fichier `fatal-errors-*.log` le plus récent pour détecter les plantages PHP, ainsi que toute source de journal nommée d’après un plugin impliqué dans l’échec. Une erreur de classe 500 provenant de la boutique laisse presque toujours sa cause ici.

## Détails {#details}

- **Code :** `AUTH301` (`AUTH_PLUGIN_CONFLICT`)
- **Gravité :** erreur
- **Introduit dans :** WCPOS 1.10.0
