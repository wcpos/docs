## Ce que cela signifie {#what-this-means}

Le serveur de la boutique bloque le jeton de connexion sur tous les canaux que cette application peut utiliser.

L’application a confirmé que la boutique est accessible, mais le serveur (ou un pare-feu, un proxy ou une extension de sécurité placé devant lui) supprime l’en-tête Authorization et bloque également le jeton lorsqu’il est envoyé comme paramètre d’URL. Il n’existe pas de troisième moyen de transmettre un jeton de connexion ; ce problème doit donc être corrigé sur le serveur.

## Que faire {#what-to-do}

Exportez les diagnostics et contactez l’assistance. Réessayez après avoir effectué la modification ci-dessus ; sans elle, la nouvelle tentative échouera de la même manière.

## Vos données {#your-data}

Aucune donnée de commande ou de produit n’est affectée.

## Résolution des problèmes {#troubleshoot}

1. Demandez à votre hébergeur d’autoriser l’en-tête Authorization jusqu’à WordPress — sur Apache, cela se résume généralement à une ligne : SetEnvIf Authorization "(.*)" HTTP_AUTHORIZATION=$1.
2. Si le site utilise des réécritures .htaccess, conservez la ligne RewriteRule générée par WordPress qui transmet HTTP_AUTHORIZATION — les extensions de sécurité la suppriment parfois.
3. Derrière un proxy ou un CDN, vérifiez sa liste d’autorisation des en-têtes : l’en-tête de requête Authorization doit être transmis au serveur d’origine.
4. Si un pare-feu d’application web (WAF) filtre les paramètres d’URL, demandez à l’hébergeur d’autoriser le paramètre d’autorisation sur les routes REST /wcpos/.

## Où chercher {#where-to-look}

Lorsque WCPOS peut enregistrer cette erreur, elle est consignée sur l’appareil qui l’a générée. Ouvrez **État de santé de la boutique → Journaux** (l’icône de fréquence cardiaque en bas du volet de navigation), trouvez l’entrée portant ce code et développez-la : la ligne développée affiche la raison en langage clair et le contexte capturé au moment de l’échec. Pour une requête de boutique, ce contexte peut inclure le propre code d’erreur du serveur (`serverCode`), le `status` HTTP ou l’`endpoint` ; les champs affichés dépendent de l’endroit où l’échec s’est produit. Pour signaler un problème, utilisez **Copier les informations de débogage** en haut de l’écran Journaux (**Partager les informations de débogage** sur les téléphones et tablettes) plutôt que des captures d’écran : cela regroupe la version de l’application, l’état de la connexion et les erreurs les plus récentes. Les journaux sont conservés pendant 30 jours au maximum ; collectez-les donc tant que le problème est récent. Copiez également toute erreur de la console du navigateur apparue avant que le POS ait pu écrire sa propre entrée de journal.
