## Signification {#what-this-means}

La boutique n’a renvoyé aucun résultat de paiement. Le statut de la commande est donc inconnu.

Vérifiez si la commande a été créée avant de tenter à nouveau le paiement.

## Marche à suivre {#what-to-do}

Vérifiez les détails ci-dessous avant de réessayer. Ne relancez pas le paiement tant que vous n’avez pas confirmé ce qui s’est réellement passé : une nouvelle tentative à l’aveugle peut créer un débit ou une commande en double.

## Vos données {#your-data}

Le résultat n’a pas pu être confirmé : vérifiez-le avant de réessayer. Si le problème persiste, exportez les diagnostics et contactez l’assistance WCPOS.

## Résolution des problèmes {#troubleshoot}

1. Vérifiez WooCommerce → Commandes dans WP Admin avant toute autre chose — une réponse vide signifie souvent que la commande a été créée, mais que la confirmation n’est jamais arrivée.
2. L’inspecteur réseau affiche la requête de passage en caisse : un statut de réussite avec un corps vide ou tronqué indique qu’une extension ou un tampon du serveur interrompt la réponse prématurément.
3. Vérifiez WooCommerce → État → Journaux afin de détecter une erreur fatale lors du passage en caisse — un plantage PHP après la création de la commande produit exactement ce résultat.
4. Ne réessayez le passage en caisse qu’après avoir confirmé qu’aucune commande n’a été créée.

## Où chercher {#where-to-look}

Chaque occurrence de ce code est enregistrée sur l’appareil qui l’a générée. Ouvrez **Santé de la boutique → Journaux** (l’icône de pouls en bas du tiroir de navigation), recherchez l’entrée marquée de ce code et développez-la : la ligne développée affiche la raison en langage clair et le contexte capturé au moment de l’échec — pour tout ce qui impliquait une requête vers votre boutique, cela inclut le propre code d’erreur du serveur (`serverCode`), le `status` HTTP et l’`endpoint`. Lorsque vous signalez un problème, utilisez **Copier les informations de débogage** en haut de l’écran Journaux (**Partager les informations de débogage** sur les téléphones et tablettes) plutôt que des captures d’écran : cette option regroupe la version de l’application, l’état de connexion et les erreurs les plus récentes. Les journaux sont conservés pendant 30 jours au maximum ; collectez-les donc tant que le problème est récent.

Au-delà du journal de l’application, cet échec peut laisser des traces dans :

- **Inspecteur réseau** (web et bureau) : ouvrez les outils de développement — appuyez sur F12 dans le navigateur ou sélectionnez **Avancé → Afficher les outils de développement** dans le menu de l’application de bureau —, sélectionnez l’onglet **Réseau**, puis répétez l’action. La requête en échec affiche le statut HTTP et le corps brut de la réponse, y compris les pages d’erreur qui n’atteignent jamais le journal POS.
- **WooCommerce → État → Journaux** : sur le site WordPress, consultez le fichier `fatal-errors-*.log` le plus récent pour détecter les plantages PHP, ainsi que toute source de journal portant le nom d’une extension impliquée dans l’échec. Une erreur de la classe 500 provenant de la boutique y laisse presque toujours sa cause.
- **Journal des erreurs PHP du site** : si la page des journaux de WooCommerce n’affiche rien pour l’heure de l’échec, demandez le journal des erreurs PHP à l’hébergeur — certaines erreurs fatales ne sont enregistrées qu’au niveau du serveur.
