يؤثر أداء الخادم مباشرةً في سرعة تطبيق WCPOS واستجابته. يُجري POS العديد من استدعاءات REST API، لذا فإن **وقت استجابة الخادم هو عنق الزجاجة الأساسي** — إذ تعتمد سرعة POS بدرجة كبيرة على جودة الاستضافة. يساعدك هذا الدليل على مراقبة أداء الخادم وتشخيصه وتحسينه باستخدام المقاييس المضمنة وتقنيات استكشاف الأخطاء وإصلاحها.

## الحد الأدنى لمتطلبات الخادم {#minimum-server-requirements}

للحصول على POS سريع الاستجابة في بيئة الإنتاج، نوصي على الأقل بما يلي:

<RequirementsList>
  <RequirementItem label="CPU">4+ نوى CPU</RequirementItem>
  <RequirementItem label="RAM">4 جيجابايت أو أكثر</RequirementItem>
  <RequirementItem label="PHP">PHP 7.4+ (يُوصى بالإصدار 8.x)</RequirementItem>
  <RequirementItem label="قاعدة البيانات">MySQL 8.0+ أو MariaDB 11.x</RequirementItem>
  <RequirementItem label="التخزين">SSD أو NVMe</RequirementItem>
  <RequirementItem label="SSL">HTTPS مطلوب — لن تعمل REST API الخاصة بـ WooCommerce بدونه</RequirementItem>
</RequirementsList>

:::warning غالبًا ما تكون الاستضافة المشتركة غير كافية
غالبًا ما توفر الاستضافة المشتركة عددًا قليلًا جدًا من عمليات PHP العاملة وذاكرة غير كافية لأحمال عمل POS، التي تُجري العديد من استدعاءات API المتزامنة. لاستخدام POS في بيئة الإنتاج، يُوصى بشدة باستخدام **VPS أو استضافة WordPress مُدارة**. ومن المعروف أيضًا أن استضافة `WordPress.com` المُدارة تواجه مشكلات توافق مع REST API (لا يرى بعض المستخدمين سوى 9–10 منتجات من الكتالوجات الكبيرة) — لذا يُوصى باستخدام `WordPress.org` المُستضاف ذاتيًا لضمان التوافق الكامل.
:::

### حزمة تحسينات اختبرها المجتمع {#community-validated-optimisation-stack}

أفاد المستخدمون بأنهم يحصلون على أفضل أداء لـ POS باستخدام هذه التركيبة:

- **MariaDB 11.4** (أسرع من MySQL لأحمال عمل WooCommerce)
- **تفعيل HPOS** (انظر أدناه)
- التخزين المؤقت للكائنات باستخدام **LiteSpeed أو Redis**
- تخزين **NVMe**
- تفعيل **PHP OPcache**

## أخطاء 503 {#503-errors}

:::important أخطاء 503 تنشأ دائمًا من جانب الخادم
الخطأ `503 Service Unavailable` **ليس خللًا في POS** — بل يعني أن الخادم لم يتمكن من معالجة الطلب. تحقّق مما يلي:

1. حمل الخادم والموارد المتاحة
2. عمليات PHP العاملة (قد تكون جميعها مشغولة)
3. حد ذاكرة PHP — ارفعه إلى **256 ميجابايت أو أكثر**
4. سجلات الخادم لدى مزود الاستضافة (تواصل معه؛ إذ يمكنه الاطلاع على ما لا يستطيع التطبيق رؤيته)
:::

## توافق إصدارات WooCommerce {#woocommerce-version-compatibility}

قد يؤدي تحديث WooCommerce أحيانًا إلى تعطيل POS. حدّث WooCommerce دائمًا على [موقع تجريبي](/1.x/support/troubleshooting/plugin-conflicts#before-you-start-use-a-staging-site) أولًا، واحرص على تحديث WCPOS ليشمل أحدث إصلاحات التوافق.

المشكلات المعروفة:

- **WooCommerce 10.5.0** — عطّل تحميل المنتجات في POS (العَرَض: ظهور ~10 منتجات فقط؛ توقف مسح الباركود والبحث عن العمل) وأدخل ذاكرة تخزين مؤقت تجريبية للمنتجات يمكن أن تسبب **تضخم postmeta** واستنفاد الذاكرة. **الإصلاح:** قم بتحديث WCPOS إلى أحدث إصدار (يتضمن الإصلاح وعملية ترحيل للتنظيف)، أو قم بالتراجع عن WooCommerce إلى [10.4.3](https://downloads.wordpress.org/plugin/woocommerce.10.4.3.zip).

إذا أدى تحديث WooCommerce إلى تعطيل POS، فأعد WooCommerce إلى الإصدار السابق (من علامة التبويب **متقدم** في صفحة الإضافة على WordPress.org) وأبلغ عن المشكلة.

## فهم مقاييس الخادم {#understanding-server-metrics}

يجمع WCPOS تلقائيًا مقاييس أداء الخادم مع كل عملية جلب بيانات (المنتجات والطلبات والعملاء وغيرها).

بدءًا من **v1.10.0**، يتوفر العرض الإجمالي في **صحة المتجر → الأداء**: عدد الطلبات المنفذة، وحجم البيانات المنقولة، وزمن الاستجابة المعتاد خلال آخر 24 ساعة، إلى جانب شريط زمن التشغيل بالساعة (انظر [صحة المتجر](/1.x/support/store-health#performance)). انتبه إلى أمرين عند قراءته: حجم البيانات المنقولة يمثل حدًا أدنى (تُحتسب الاستجابات التي لا تعلن عن حجمها بصفر)، وتقدير *~N طلب في اليوم* بجوار مؤشر المزامنة هو معدل اسمي مشتق من الفاصل الزمني المضبوط، وليس سقفًا أو عددًا فعليًا. قد يزيد التفاوت العشوائي في التوقيت العدد أو ينقصه، وتُحتسب استجابة `304` طلبًا أيضًا، ولا يخفض تباطؤ الخمول العدد إلا للإعدادات المسبقة ذات الفواصل الأقصر من 60 ثانية. وتظهر مقاييس الطلبات الفردية في **صحة المتجر → السجلات**.

### مقاييس الخادم النموذجية {#typical-server-metrics}

```json
{
  "total": "24692",
  "execution_time": "76.64 ms",
  "server_load": "[15.20605469,16.16357422,16.76806641]"
}
```

**التفصيل:**
- **`total`** - عدد السجلات التي تمت معالجتها (24,692 معرّف منتج)
- **`execution_time`** - الوقت المستغرق لإكمال العملية (76.64 مللي ثانية)
- **`server_load`** - متوسطات حمل الخادم خلال 1 و5 و15 دقيقة

## شرح حمل الخادم {#server-load-explained}

يمثل حمل الخادم متوسط حمل النظام خلال فترات زمنية مختلفة:

- **القيمة الأولى** - المتوسط خلال 1 دقيقة (15.21)
- **القيمة الثانية** - المتوسط خلال 5 دقائق (16.16)
- **القيمة الثالثة** - المتوسط خلال 15 دقيقة (16.77)

### تفسير الحمل {#load-interpretation}

قد تكون قيم حمل الخادم مضللة، وينبغي تفسيرها بعناية:

:::warning قد تكون قيم الحمل مضللة
لا ترتبط متوسطات حمل الخادم دائمًا بالأداء ارتباطًا مباشرًا. فقد يكون الخادم ذو قيم الحمل المرتفعة (15+) سريع الاستجابة للغاية إذا كانت موارده كافية وإعداداته محسّنة جيدًا. **ركّز على أوقات التنفيذ بدلًا من قيم الحمل وحدها.**
:::

**إرشادات عامة:**
- **الحمل بالنسبة إلى نوى CPU** - حمل قدره 8.0 على خادم ذي 8 نوى يعني الاستخدام الكامل
- **المستمر مقابل المؤقت** - الارتفاعات العابرة طبيعية، لكن استمرار الحمل المرتفع قد يشير إلى مشكلات
- **الأداء أكثر أهمية** - الخادم سريع الاستجابة ذو الحمل المرتفع أفضل من الخادم البطيء ذي الحمل المنخفض

**ما ينبغي مراقبته:**
- **ازدياد أوقات التنفيذ** بمرور الوقت
- **تزايد الحمل باستمرار** دون تفسير
- **ارتفاع الحمل وبطء أوقات التنفيذ** معًا

## معايير الأداء {#performance-benchmarks}

### إرشادات أوقات التنفيذ {#execution-time-guidelines}

| العملية | جيد | مقبول | ضعيف | حرج |
|-----------|------|------------|------|----------|
| **جلب المنتجات** | < 100ms | 100-500ms | 500ms-2s | > 2s |
| **إنشاء الطلب** | < 200ms | 200-800ms | 800ms-3s | > 3s |

### اعتبارات عدد السجلات {#record-count-considerations}

ينبغي أن يتناسب وقت التنفيذ بصورة معقولة مع عدد السجلات:

```json
// Good scaling examples
{"total": "100", "execution_time": "15.2 ms"}    // 0.15ms per record
{"total": "1000", "execution_time": "89.4 ms"}   // 0.09ms per record
{"total": "10000", "execution_time": "234.1 ms"} // 0.02ms per record

// Poor scaling examples
{"total": "100", "execution_time": "500.0 ms"}   // 5.0ms per record
{"total": "1000", "execution_time": "8000.0 ms"} // 8.0ms per record
```

## تشخيص مشكلات الأداء {#diagnosing-performance-issues}

### الخطوة 1: مراقبة السجلات {#step-1-monitor-the-logs}

1. افتح **صحة المتجر** من درج التنقل وراجع علامة التبويب **الأداء** للاطلاع على أداء آخر 24 ساعة (زمن الاستجابة المعتاد هو الرقم الأهم)
2. نفّذ العملية البطيئة (مزامنة المنتجات، إنشاء طلب، وما إلى ذلك)
3. ابحث عن الإدخال المقابل في علامة التبويب **السجلات**
4. وسّع الصف للاطلاع على المقاييس

### الخطوة 2: تحليل المقاييس {#step-2-analyse-the-metrics}

**وقت تنفيذ مرتفع + حمل خادم مرتفع = مشكلة في موارد الخادم**
```json
{
  "total": "5000",
  "execution_time": "3500.0 ms",
  "server_load": "[12.45, 11.23, 10.87]"
}
```
*الحل: زيادة موارد الخادم أو تحسين إعداداته*

**وقت تنفيذ مرتفع + حمل خادم طبيعي = مشكلة في الإضافات/قاعدة البيانات**
```json
{
  "total": "1000",
  "execution_time": "2800.0 ms",
  "server_load": "[1.23, 1.45, 1.67]"
}
```
*الحل: تحديد الإضافات البطيئة أو تحسين استعلامات قاعدة البيانات*

**وقت تنفيذ طبيعي + حمل خادم مرتفع = حمل عام زائد على الخادم**
```json
{
  "total": "2000",
  "execution_time": "150.0 ms",
  "server_load": "[8.90, 9.12, 8.45]"
}
```
*الحل: تقليل الحمل الذي تسببه العمليات الأخرى على الخادم أو ترقية الموارد*

## مشكلات الأداء الشائعة {#common-performance-problems}

### 1. عدم كفاية موارد الخادم {#1-insufficient-server-resources}

**الأعراض:**
- حمل خادم مرتفع باستمرار (> 4.0 على معظم الخوادم)
- أوقات تنفيذ طويلة في جميع العمليات
- انتهاء مهلة الطلبات بشكل متكرر

**الحلول:**
- **ترقية CPU** - زيادة عدد النوى تحسّن معالجة الطلبات المتزامنة
- **زيادة RAM** - تقلل عمليات الإدخال والإخراج على القرص وتحسّن التخزين المؤقت
- **استخدام تخزين SSD** - يحسّن أداء قاعدة البيانات بدرجة كبيرة
- **تحسين إعدادات PHP** - زيادة memory_limit وmax_execution_time

### 2. بطء استعلامات قاعدة البيانات {#2-slow-database-queries}

**الأعراض:**
- أوقات تنفيذ مرتفعة مع حمل خادم طبيعي
- بطء ملحوظ في جلب المنتجات/الطلبات
- ظهور أكواد أخطاء متعلقة بقاعدة البيانات في السجلات

**الحلول:**
- **تفعيل WooCommerce HPOS** - أكبر تحسين منفرد لأداء قاعدة البيانات
- **استخدام التخزين المؤقت للكائنات** - Redis أو Memcached إذا كان مزود الاستضافة يتيحهما
- **الحفاظ على تحديث WordPress** - غالبًا ما تتضمن تحديثات النواة تحسينات لقاعدة البيانات
- **الحد من مراجعات المقالات** - أضف `define('WP_POST_REVISIONS', 3);` إلى wp-config.php

### 3. تداخل الإضافات {#3-plugin-interference}

**الأعراض:**
- تدهور مفاجئ في الأداء بعد تحديث الإضافات
- عمليات معينة أبطأ بكثير من غيرها
- أوقات تنفيذ مرتفعة مع حمل خادم طبيعي

**استكشاف الأخطاء وإصلاحها:**
1. **الاختبار على موقع تجريبي** - عطّل جميع الإضافات باستثناء WooCommerce وWCPOS
2. **قياس الأداء المرجعي** - سجّل أوقات التنفيذ مع أقل عدد ممكن من الإضافات
3. **التفعيل تدريجيًا** - أضف الإضافات واحدة تلو الأخرى لتحديد المسببة للمشكلة
4. **فحص خطافات الإضافات** - ابحث عن الإضافات المرتبطة بإجراءات WooCommerce

**إضافات شائعة قد تسبب مشكلات:**
- إضافات SEO التي تستهلك موارد كثيرة أثناء عمليات المنتجات
- أنظمة إدارة المخزون المعقدة
- إضافات التحليلات/التتبع في الوقت الفعلي
- إضافات مخصصة ذات برمجة رديئة

### 4. إعدادات WordPress/WooCommerce {#4-wordpresswoocommerce-configuration}

**الأعراض:**
- أداء غير مستقر
- أخطاء متعلقة بالذاكرة في السجلات
- بطء لوحة تحكم الإدارة

**قائمة فحص التحسين:**
- **إصدار PHP** - استخدم PHP 8.0+ للحصول على أداء أفضل
- **WooCommerce HPOS** - فعّل تخزين الطلبات عالي الأداء (انظر أدناه)
- **التخزين المؤقت في WordPress** - فعّل التخزين المؤقت للكائنات إذا كان متاحًا
- **إعدادات WooCommerce** - حسّن أحجام صور المنتجات

### تخزين الطلبات عالي الأداء في WooCommerce (HPOS) {#woocommerce-high-performance-order-storage-hpos}

:::tip أكبر تحسين للأداء
**يُعد HPOS أحد أهم تحسينات الأداء التي يمكنك تطبيقها على WooCommerce.** فهو يخزّن الطلبات في جداول مخصصة بقاعدة البيانات بدلًا من جدول مقالات WordPress، مما يحسّن الأداء بدرجة كبيرة في المتاجر ذات الطلبات الكثيرة.
:::

**الفوائد:**
- **استعلامات طلبات أسرع** - تخزين الطلبات في بنية محسّنة لقاعدة البيانات
- **تقليل حمل قاعدة البيانات** - فصل الطلبات عن المقالات/الصفحات
- **قابلية توسع أفضل** - التعامل بكفاءة مع أعداد كبيرة من الطلبات
- **تحسين أداء الإدارة** - شاشات أسرع لإدارة الطلبات

**كيفية التفعيل:**
1. انتقل إلى `WooCommerce > الإعدادات > Advanced > Features`
2. فعّل «تخزين الطلبات عالي الأداء»
3. اتبع عملية الترحيل (خطوة بخطوة: [التبديل إلى HPOS](/1.x/support/performance/order-storage#switch-to-hpos))

**لمعرفة المزيد:**
- [وثائق HPOS لـ WooCommerce](https://woocommerce.com/document/high-performance-order-storage/)
- [دليل ترحيل HPOS](https://woocommerce.com/document/high-performance-order-storage/#section-3)

## أفضل ممارسات مراقبة الخادم {#server-monitoring-best-practices}

### 1. فحوصات الأداء الدورية {#1-regular-performance-checks}

- **مراجعات أسبوعية** - راجع السجلات لتحديد اتجاهات الأداء
- **قياسات مرجعية** - سجّل أوقات التنفيذ الطبيعية
- **مراقبة أوقات الذروة** - راقب الأداء خلال فترات الزيارات الكثيفة

### 2. إعداد تنبيهات الأداء {#2-set-performance-alerts}

راقب العلامات التحذيرية التالية:
- أوقات تنفيذ > 1000ms باستمرار
- حمل خادم > 5.0 لفترات طويلة
- أخطاء متكررة لانتهاء المهلة في السجلات

### 3. تخطيط السعة {#3-capacity-planning}

تتبّع اتجاهات النمو:
- **نمو عدد السجلات** - المنتجات والطلبات والعملاء
- **تدهور الأداء** - كيفية تزايد وقت التنفيذ
- **استخدام الموارد** - CPU والذاكرة واستخدام القرص

## استراتيجيات تحسين الخادم {#server-optimisation-strategies}

### 1. أفضل ممارسات WordPress/WooCommerce {#1-wordpresswoocommerce-best-practices}

**تفعيل HPOS:**
- التحسين المنفرد الأكثر تأثيرًا في أداء WooCommerce
- راجع قسم HPOS أعلاه لمعرفة التفاصيل

**إعدادات PHP (استشر مزود الاستضافة):**
```ini
memory_limit = 512M
max_execution_time = 300
max_input_vars = 3000
```

**إعدادات WordPress:**
```php
// In wp-config.php - limit post revisions
define('WP_POST_REVISIONS', 3);

// Enable WordPress debug logging if needed
define('WP_DEBUG_LOG', true);
```

### 2. تحسينات على مستوى الاستضافة {#2-hosting-level-optimizations}

**التخزين المؤقت للكائنات:**
- اسأل مزود الاستضافة عن توفر Redis أو Memcached
- يوفر العديد من مزودي استضافة WordPress المُدارة هذه الميزة تلقائيًا

**إصدار PHP:**
- استخدم PHP 8.0+ للحصول على تحسينات كبيرة في الأداء
- يتيح معظم مزودي الاستضافة تغيير إصدار PHP بسهولة

**موارد الخادم:**
- تأكد من توفر RAM كافية (1GB كحد أدنى، ويُفضّل 2GB+)
- يوفر تخزين SSD أداءً لقاعدة البيانات أفضل بكثير من الأقراص التقليدية

## ملاحظات خاصة بمزودي الاستضافة {#hosting-specific-notes}

يحتاج بعض مزودي الاستضافة وشبكات CDN إلى إعدادات تتيح لـ POS الوصول إلى REST API الخاصة بـ WooCommerce:

| مزود الاستضافة / الخدمة | المشكلة | الحل |
| --- | --- | --- |
| **GoDaddy** | يحظر جدار حماية الموقع استدعاءات REST API إلى `/wp-json/` (أخطاء مثل _«تم استلام 'undefined'»_) | `Website Security > Firewall > الإعدادات > Access Control > Allow URL Paths` → أضف `/wp-json/` |
| **WP Engine** | يجب تفعيل REST API صراحةً | فعّل REST API؛ وأضف نقاط نهاية API إلى قائمة السماح في جدار الحماية عند الحاجة |
| **Cloudflare** | تحظر فحوصات الأمان (وضع مكافحة الروبوتات، ووضع التعرض لهجوم، وتحديات WAF) طلبات REST API، وقد تقدم ذاكرة التخزين المؤقت استجابات API قديمة | اتبع [دليل Cloudflare](/1.x/support/troubleshooting/cloudflare): أضف قاعدة **تخطي** في WAF للمسار `/wp-json/` وقاعدة تخزين مؤقت من أجل **تجاوز ذاكرة التخزين المؤقت** للمسارات نفسها |
| **WordPress.com** | مشكلات توافق REST API / تحميل المنتجات (ظهور 9–10 منتجات فقط) | استخدم WordPress.org المُستضاف ذاتيًا لضمان التوافق الكامل |
| **الاستضافة المشتركة** | عدد غير كافٍ من عمليات PHP العاملة / ذاكرة قليلة لاستدعاءات POS المتزامنة | انتقل إلى VPS أو استضافة WordPress مُدارة |

يمكن لإضافات الأمان (Wordfence وغيرها) حظر REST API بطرق مماثلة — راجع [تعارضات الإضافات](/1.x/support/troubleshooting/plugin-conflicts) للاطلاع على القائمة الكاملة والحلول.

### HTTP 414 — عنوان URI طويل جدًا {#http-414-uri-too-long}

قد تتجاوز سلال التسوق الكبيرة، أو رمز الوصول المضمن في عنوان URL الخاص بالدفع، حد طول URL على الخادم (يستخدم طلب الدفع `GET`). وقد تحدث المشكلة في متصفحات معينة، وتزيد ذاكرة التخزين المؤقت للمتصفح من حدتها.

**حل مؤقت:** امسح ذاكرة التخزين المؤقت للمتصفح أولًا، ثم ارفع حد طول URL على الخادم:

- **Apache:** أضف `LimitRequestLine 65536` في `httpd.conf`
- **Nginx:** أضف `large_client_header_buffers 4 65536;` في `nginx.conf`
- إذا لم يكن لديك وصول إلى الإعدادات، فاطلب من مزود الاستضافة تعديلها.

## متى تطلب المساعدة {#when-to-seek-help}

تواصل مع مزود الاستضافة أو مطور WordPress في الحالات التالية:

- **حمل الخادم > 8.0 باستمرار** رغم جهود التحسين
- **أوقات التنفيذ > 5000ms** للعمليات البسيطة
- ظهور **أخطاء في الذاكرة** بشكل متكرر في السجلات
- **استعلامات قاعدة البيانات تستغرق > 2 ثانية** باستمرار

زوّدهم بما يلي:
- مقاييس الخادم من سجلاتك
- قائمة الإضافات النشطة
- مواصفات الخادم (CPU وRAM ونوع التخزين)
- إصدارات WordPress وWooCommerce
