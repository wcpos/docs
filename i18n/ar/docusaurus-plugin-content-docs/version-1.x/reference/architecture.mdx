توضح هذه الصفحة الهيكلية الفنية لـ WCPOS للمطورين والمستخدمين المتقدمين.

## نظام ذو جزءين {#two-part-system}

صُمّم WCPOS كنظام ذي جزءين:

1. **إضافة PHP:** مستضافة على خادمك، وهي إضافة صغيرة نسبيًا توسّع [واجهة REST API الخاصة بـ WooCommerce](/1.x/reference/wc-rest-api) بنقاط نهاية خاصة بنقطة البيع.

2. **عميل JavaScript:** يعمل محليًا في متصفحك أو تطبيق سطح المكتب أو تطبيقات iOS/Android.

يمكنك التفكير فيه كعالمين منفصلين:

- في _عالم PHP_، تُدار البيانات باستخدام WordPress وWooCommerce.
- يحتفظ _عالم JavaScript_ بنسخة محلية قابلة للعمل دون اتصال من بيانات المتجر التي تحتاجها نقاط البيع لديك، محسّنة للبحث السريع والاستجابة الفورية.

## مزامنة البيانات {#data-synchronization}

:::info تغيّر في v1.10.0
يستبدل v1.10.0 طبقة النسخ المتماثل السابقة بـ **محرك مزامنة** مخصص. والملخص أدناه هو النسخة المختصرة — أما الشرح الكامل فتجده في [كيف يعمل محرك المزامنة](/1.x/reference/sync-engine).
:::

يعتمد العميل على البيانات المحلية أولًا: فكل شاشة تقرأ من قاعدة البيانات المحلية للجهاز وتكتب إليها، ويحافظ محرك مزامنة يعمل في الخلفية على تقارب بيانات تلك القاعدة وWooCommerce. والمحرك **لا** ينسخ متجرك بالكامل دون تمييز — بل ينطلق مما تحتاجه شاشاتك فعليًا:

- **اكتشاف التغييرات:** تستعلم نقطة البيع دوريًا عن سجل تغييرات خفيف بطلبات شرطية؛ ويردّ المتجر الخامل باستجابة `304` واحدة بلا محتوى.
- **الطلب المُعلَن:** تعلن الشاشة عمّا تعرضه، ويقرر المحرك ما إذا كان ذلك يستلزم طلبًا أم أن البيانات المطلوبة متوفرة محليًا بالفعل.
- **البذور والمسارات:** تملأ بذرة كتالوج محدودة ونافذة للطلبات الحديثة ومسارات صيانة تعمل في أوقات الخمول البيانات المحلية وتتحقق منها وفق جداول يمكنك ضبطها لكل جهاز.
- **عمليات كتابة دائمة:** تُدرَج المبيعات والتعديلات في قائمة انتظار محلية ثم تُرسل إلى WooCommerce، مع آلية استعادة ظاهرة للمستخدم لكل ما يرفضه الخادم.

تُزامَن المنتجات والبدائل، والفئات/الوسوم/العلامات التجارية، والعملاء، ومعدّلات الضريبة، والكوبونات (Pro)، والطلبات. أما بوابات الدفع فتُجلب عند الدفع.

## مزايا الهيكلية وعيوبها {#architecture-pros-and-cons}

| جيد 😊 | سيئ 😟 |
| ------------------------------------------------------------------ | -------------------------------------------------------- |
| البحث في البيانات المحلية فوري | الحفاظ على تزامن البيانات يمثّل تحديًا |
| البيانات المخبأة متاحة دون اتصال | مقيّد بواجهة REST API الخاصة بـ WooCommerce |
| القدرة على إنشاء تطبيقات أصلية أفضل لسطح المكتب وiOS وAndroid | لا يمكن لسمات WordPress وخطافاتها تخصيص تطبيق نقطة البيع |

## قاعدة البيانات المحلية {#local-database}

يخزّن العميل البيانات في قاعدة بيانات محلية على كل جهاز — إذ يستخدم تطبيقا الويب وسطح المكتب **تخزين OPFS (نظام الملفات الخاص بالأصل) العامل داخل worker**، وتستخدم تطبيقات الجوال التنسيق نفسه على القرص عبر محرك نظام ملفات. وتشترك جميع المنصات في تنسيق تخزين واحد وأدوات استعادة واحدة. وهذا يوفّر:

- **الاستمرارية:** تبقى البيانات محفوظة بعد إعادة تشغيل المتصفح وإعادة تشغيل الجهاز
- **الأداء:** استعلامات سريعة دون تأخير الشبكة — إذ تعمل التصفية والفرز والتقسيم إلى صفحات داخل طبقة التخزين، فلا يصل إلى الواجهة إلا صفوف الصفحة المرئية
- **التصفح دون اتصال:** تبقى البيانات المخبأة متاحة دون إنترنت

يحصل كل مزيج من الموقع + المتجر + أمين الصندوق على قاعدة بيانات محلية خاصة به، فلا يتشارك أمناء الصندوق ولا المتاجر البيانات المحلية على جهاز واحد أبدًا. ولا تُرحّل الترقيات قاعدة البيانات المحلية في مكانها — بل يعيد التطبيق تنزيلها من الخادم، الذي يحتفظ دائمًا بالنسخة المعتمدة.

## هيكلية الدفع {#checkout-architecture}

تستخدم عملية الدفع إطار iframe/webview يحمّل صفحة دفع الطلب الخاصة بـ WooCommerce. هذه الطريقة:

- **تستفيد من بوابات الدفع الموجودة:** يمكن لأي بوابة دفع خاصة بـ WooCommerce العمل في نقطة البيع
- **تحافظ على الأمان:** تتم معالجة الدفع من خلال البنية التحتية الآمنة لـ WooCommerce
- **تقلّل التعقيد:** لا حاجة إلى إعادة تنفيذ تكاملات بوابات الدفع

## توسيعات واجهة API {#api-extensions}

توسّع إضافة PHP واجهة REST API الخاصة بـ WooCommerce بنقاط نهاية إضافية لوظائف خاصة بنقطة البيع، مسجّلة ضمن مساحتَي الأسماء المخصصتين `wcpos/v1` و`wcpos/v2` — وتضم `wcpos/v2` واجهة المزامنة الخاصة بـ v1.10.0، ولهذا تصدر نسخ التطبيق والإضافة معًا. راجع [واجهة REST API الخاصة بـ WooCommerce](/1.x/reference/wc-rest-api) للاطلاع على مقدمة.

### مساحة الأسماء `wcpos/v2` {#wcpos-v2-namespace}

يقدّم v1.10 مساحة أسماء REST باسم `wcpos/v2`. توجد المزامنة هنا، وخدمات نقطة البيع المشتركة التي كانت تُقدَّم سابقًا من `wcpos/v1` تُقدَّم الآن من `wcpos/v2` (تمرّر مسارات خدمة `wcpos/v1` الطلبات إلى تنفيذاتها في v2). ولا تزال مسارات `wcpos/v1` تُسجّل للتوافق مع الإصدارات السابقة لكنها **مجمّدة** — فالعميل الحالي لم يعد يستدعيها.

نقاط مهمة إذا كنت تتكامل مع نقاط النهاية هذه:

- **مسارات v2 تُسجَّل دائمًا.** أُزيل خيار `woocommerce_pos_sync_api_enabled` القديم؛ فلم يعد هناك خيار يشغّل API أو يوقفها.
- **نقاط نهاية عامة.** إن `wcpos/v2/site` و`wcpos/v2/ping` و`wcpos/v2/echo` عامة (تُستخدم لفحص القدرات والاتصال، بما في ذلك [الحلول الاحتياطية للنقل](/1.x/error-codes) لدى جهات الاستضافة التي تفرض قيودًا).
- **تعتمد الطلبات على UUID كمعرّف أساسي.** هوية الطلب عند نقله عبر الشبكة هي UUID؛ وقد أُلغي الحقل القديم `wooOrderId` من بنية استجابة سحب الطلبات. وتُحدّد أنواع البيانات الوصفية للطلب عند نقلها عبر الشبكة باستخدام أداة توحيد واحدة.
- **تخزين تسعير البنود موثّق** من أجل توافق المزامنة مع الجهات الخارجية — راجع [كيفية تخزين تعديلات أسعار POS](/1.x/reference/pos-discounts#how-pos-price-overrides-are-stored).
- **الفرز الافتراضي للمنتجات** في نقطة البيع أصبح الآن **حسب الاسم تصاعديًا** (وكان سابقًا `menu_order, id`).
- **إزالة طرق قديمة.** أُزيلت عدة طرق قديمة من المتحكم `API\Settings` (مثل `get_general_settings()` و`update_access_settings()` و`get_general_endpoint_args()` و`remove_license_transient()`)؛ ويبقى الاسم البديل للفئة، لكن تلك الطرق لم تعد موجودة.

:::note يتبع Pro التقسيم نفسه
يتبع WCPOS Pro تقسيم V1/V2 نفسه — إذ تُنقل خدماته المشتركة إلى `wcpos/v2` بينما تبقى بيانات طلباته مجمّدة عند v1. ويعمل تسعير المنتجات المحدّد بنطاق المتجر على مسار v2، ويُضمَّن نطاق متجر نقطة البيع في عمليات كتابة الطلبات بحيث تُحتسب أسعار الطلبات متعددة المتاجر وضرائبها وفق المتجر الصحيح. راجع [Pro](/1.x/getting-started/free-vs-pro).
:::
