## معنى هذا الخطأ {#what-this-means}

قد تعيد ذاكرة التخزين المؤقت لدى مزود الاستضافة تقديم بيانات المتجر الخاصة بشخص إلى شخص آخر.

لم تُفقد أي بيانات على هذا الجهاز. اطلب من مزود الاستضافة إيقاف التخزين المؤقت لـ API الخاصة بالمتجر (لعناوين `/wp-json/` و`?rest_route=` معاً). إذا لم يتصل WCPOS، فأعد الاتصال بعد ذلك.

تقدّم طبقة تخزين مؤقت استجابات REST API المحفوظة دون التحقق من هوية طالبها: أرسل التطبيق طلبي فحص ببيانات مصادقة مختلفة، وتلقى رد الفحص الأول في المرتين. في متجر يعمل فعلياً، يعني هذا أن أمين صندوق قد يرى بيانات أمين صندوق آخر. هذه مشكلة في طبقة الاستضافة — أما WordPress نفسه فيرد دائماً بحسب المستخدم.

عند حدوث ذلك، يعيد التطبيق المحاولة بمفتاح تخزين مؤقت فريد في كل طلب. إذا ثبت أن المفتاح يتجاوز ذاكرة التخزين المؤقت، يتصل WCPOS ويستمر في إرسال المفتاح — ويصبح هذا الإدخال تحذيراً بأن التخزين المؤقت ما زال يحتاج إلى إصلاح. وإذا تعذر إثبات أمان الاتصال، فلن يتصل WCPOS حتى يُصلح التخزين المؤقت.

## بياناتك {#your-data}

لم تُفقد أي بيانات على هذا الجهاز. إذا تعذر على WCPOS إثبات أمان الاتصال، فلن يتصل حتى لا يخاطر بعرض بيانات شخص لآخر؛ وتبقى كل البيانات الموجودة على هذا الجهاز محفوظة فيه وتُرسَل بمجرد الاتصال.

## استكشاف الأخطاء وإصلاحها {#troubleshoot}

**لمزود الاستضافة أو مسؤول الموقع** — يجب إصلاح التخزين المؤقت لدى مزود الاستضافة، حتى لو اتصل WCPOS بعد تجاوز المشكلة:

1. استثنِ مسارات REST API الخاصة بالمتجر (/wp-json/ و/?rest_route=) من التخزين المؤقت للصفحات — على LiteSpeed، عطّل التخزين المؤقت لـ REST أو أضف قاعدة تمنع التخزين المؤقت؛ وعلى WP Engine، وسّع استثناء WooCommerce ليشمل /wp-json/wcpos والصيغة ?rest_route=؛ وعلى Sucuri، اضبط مستوى التخزين المؤقت ليلتزم بـ Cache-Control.
2. ترسل API الخاصة بالمتجر بالفعل Cache-Control: no-store وVary: Authorization — لكن طبقة التخزين المؤقت تتجاهلهما؛ وجّه مزود الاستضافة إلى هاتين الترويستين.
3. بعد تغيير إعدادات التخزين المؤقت، امسح ذاكرته. إذا لم يتصل WCPOS، فأعد الاتصال.
