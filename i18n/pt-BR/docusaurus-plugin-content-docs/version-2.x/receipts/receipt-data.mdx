**WP Admin:** os modelos são editados em `WP Admin → POS → Templates`; esta página lista os campos que eles podem imprimir.

Para imprimir ou enviar um recibo por e-mail, consulte [Recibos e a tela de pagamento concluído](./at-checkout.mdx); para escolher um modelo ou pedir à IA que altere um para você, consulte [Personalize seu recibo](./customise.mdx).

Esta página é voltada à edição manual do código de um modelo. Todos os modelos, HTML ou térmicos, imprimem a partir dos mesmos dados do recibo: a loja, o pedido, os itens, os totais e os pagamentos. A página mostra como imprimir um campo, apresenta três exemplos comuns e lista todos os campos.

**Ir para:** [Encontrar um campo](#field-reference) · [Exemplos comuns](#common-recipes) · [Se algo der errado](#if-something-goes-wrong)

## Imprimir um campo {#print-a-field}

1. Abra o modelo em **WP Admin → POS → Modelos** (consulte os detalhes em [Editar manualmente](./customise.mdx#option-3--edit-it-by-hand)).
2. No local em que o campo deve ser impresso, digite seu caminho entre chaves duplas, como `{{store.name}}`, `{{order.number}}` ou `{{totals.total_display}}`, ou insira-o pela lista de campos ao lado do código.
3. Confira a prévia abaixo do código e clique em **Atualizar** para salvar.

Para uma lista, como a de itens, envolva a linha em uma seção para que ela se repita uma vez por item:

```mustache
{{#lines}}
  {{name}} x {{qty}} —
  {{line_total_display}}
{{/lines}}
```

Uma seção também omite seu conteúdo quando o campo está vazio, é zero ou falso. Assim, `{{#customer.id}}…{{/customer.id}}` só imprime para um cliente identificado. Para imprimir valores monetários, use o campo que termina em `_display`; consulte [Campos monetários](#currency-fields).

Os recibos também podem ser impressos offline: o aplicativo cria uma cópia dos dados do recibo a partir do pedido no dispositivo.

<Accordion>
  <AccordionItem question="Por que os recibos podem ser diferentes">

### De onde vêm os dados {#where-the-data-comes-from}

O servidor da sua loja gera os dados do recibo de cada pedido, e o aplicativo cria uma cópia reduzida a partir do pedido no dispositivo: ela não inclui `cashier`, horários de funcionamento, observações ou políticas da loja, nem `totals.paid_total` ou `totals.change_total`. Um modelo HTML ou térmico abre imediatamente com a cópia do dispositivo e passa a usar a do servidor quando ela chega; offline, a cópia do dispositivo é a que será impressa, então esses campos ficam vazios. Com o WCPOS Pro, a cópia do dispositivo também inclui o logotipo da loja; sem o Pro, o logotipo chega com a cópia do servidor. Um modelo PHP legado é sempre renderizado pelo servidor. Por isso, um modelo usa os campos abaixo, nunca métodos PHP de pedidos. Alguns campos só são impressos quando o servidor renderiza o modelo, como no download de um PDF; eles estão listados em [Se algo der errado](#if-something-goes-wrong).

  </AccordionItem>
</Accordion>

## Referência de campos {#field-reference}

Expanda uma seção para ver seus campos. O primeiro item lista todas as seções e seus tipos.

### Seções de nível superior {#top-level-sections}

| Seção | Conteúdo |
|---------|---------------|
| `order` (objeto) | Identificação, status, datas, observação e informações da URL de pagamento do pedido |
| `store` (objeto) | Identificação, endereço, dados de contato, identificações fiscais, logotipo, horários e texto de rodapé da loja |
| `cashier` (objeto) | Usuário que processou o pedido |
| `customer` (objeto) | Nome de exibição, endereços e identificações fiscais do cliente |
| `lines` (array) | Itens de produto do pedido |
| `fees` (array) | Linhas de taxas adicionais |
| `shipping` (array) | Linhas de frete |
| `discounts` (array) | Linhas de cupons/descontos |
| `totals` (objeto) | Totais do pedido, totais de pagamentos, resumo de reembolsos e contagens de itens |
| `tax` (objeto) | Indicadores do modo de exibição de impostos para condições de seções |
| `tax_summary` (array) | Linhas de resumo de impostos por alíquota |
| `has_tax_summary` (booleano) | Condição auxiliar para `tax_summary` |
| `payments` (array) | Linhas de pagamentos |
| `refunds` (array) | Registros de reembolsos aplicados ao pedido |
| `fiscal` (objeto) | Campos do snapshot fiscal preenchidos por integrações fiscais |
| `register` (objeto) | O caixa que registrou a venda: `id` e `name`. Strings vazias quando desconhecido |
| `software` (objeto) | O software que emitiu o recibo: `name` (`WCPOS`), `plugin_version`, `app_version`, `app_build`, `platform` |
| `presentation_hints` (objeto) | Orientações de formatação e renderização |
| `i18n` (objeto) | Rótulos traduzidos para modelos incluídos e personalizados |

### Objetos de identificação fiscal {#tax-id-objects}

`store.tax_ids` e `customer.tax_ids` contêm objetos com a mesma estrutura:

| Campo | Tipo | Descrição |
|-------|------|-------------|
| `type` | string | Identificador como `eu_vat`, `de_steuernummer`, `au_abn`, `br_cpf`, `us_ein` ou `other` |
| `value` | string | Valor da identificação fiscal a imprimir |
| `country` | string/null | Código ISO do país; null para `eu_vat` e `other` |
| `label` | string | Rótulo de exibição traduzido, resolvido antes da renderização |

Exemplo:

```mustache
{{#store.tax_ids}}
  {{label}}: {{value}}
{{/store.tax_ids}}
```

### Exibir o preço normal e a economia {#displaying-regular-price-and-savings}

Para um layout com preços unitários, exiba o preço normal registrado, o preço de venda e a economia assim:

```mustache
{{#lines}}
  {{#unit_savings}}
```

```mustache
    <span>{{i18n.savings}}: -{{line_savings_display}}</span>
  {{/line_savings}}
{{/lines}}
```

`selling_price` é o preço antes dos cupons. Use `unit_price` ou `line_total` para obter o valor final após os descontos do WooCommerce.

:::note Reimpressão de pedidos criados antes da v1.9.0
Pedidos antigos do WCPOS podem já incluir a redução do preço normal para o preço de venda em `discounts`. Se o seu modelo personalizado imprime tanto a economia quanto os descontos da linha, use `savings_in_discounts` para evitar exibir a mesma redução duas vezes:

```mustache
{{#lines}}
  {{#line_savings}}
    <span style="text-decoration: line-through;">{{line_regular_total_display}}</span>
    {{^savings_in_discounts}}
      <span>{{i18n.savings}}: -{{line_savings_display}}</span>
    {{/savings_in_discounts}}
  {{/line_savings}}
  {{#discounts}}
    <span>{{i18n.discount}}: -{{discounts_display}}</span>
  {{/discounts}}
{{/lines}}
```

Se o modelo não imprime uma linha de `discounts` por item, continue exibindo `line_savings` mesmo quando `savings_in_discounts` for verdadeiro. Os modelos incluídos tratam essa distinção automaticamente.
:::

## Como os preços se relacionam {#price-model}

Um item no recibo tem vários preços, e fica mais fácil entender os nomes olhando os próprios valores. Esta é a linha do café espresso do pedido de exemplo — um produto de $17.00 em promoção por $14.50, com um cupom de 10% aplicado adicionalmente:

<PriceFlow
  caption="Café espresso em grãos — uma unidade (o pedido tem duas)"
  scaleLabel="preço normal 17.00"
  segments={[
    { kind: 'paid', amount: 13.05, label: "13.05 pagos" },
    { kind: 'coupon', amount: 1.45, label: "1.45" },
    { kind: 'savings', amount: 2.5, label: "2.50" },
  ]}
  summary={[
    { label: "Economia em promoções no pedido inteiro", value: '`totals.sale_savings_total` = 5.00' },
    { label: "Todos os descontos de cupons no pedido inteiro", value: '`totals.discount_total` = 5.28' },
    { label: "Economia + descontos, sem a sobreposição dos pedidos antigos", value: '`totals.total_saved` = 10.28' },
  ]}
/>

A economia na promoção é a diferença entre o preço normal e o preço de venda. O desconto é o valor deduzido por um cupom, conforme calculado pelo WooCommerce. Os totais de pedidos e os relatórios do WooCommerce contêm apenas os descontos, então `total_saved` soma os dois em um único valor para o cliente.

## Estender os dados do recibo {#extending}

Um plugin pode adicionar seus próprios campos aos dados do recibo por meio do filtro `wcpos_receipt_data`.

<Accordion>
  <AccordionItem question="O filtro — seus argumentos, os seis modos e um exemplo">

O WCPOS mantém os campos acima livres de dados específicos de plugins. Quando um plugin precisa que o recibo tenha uma informação que o WooCommerce não representa em seu modelo de dados, ele próprio a adiciona pelo filtro `wcpos_receipt_data`, da mesma forma que os plugins filtram os totais de pedidos do próprio WooCommerce. O filtro é executado em todos os recibos gerados pelo servidor: recibos em tempo real, snapshots fiscais no momento do pagamento, downloads de PDF e modelos PHP legados. Antes do WCPOS 2.0, esse filtro se chamava `woocommerce_pos_receipt_data`; esse nome ainda funciona, mas está obsoleto desde a versão 2.0 e será removido, no mínimo, na versão 2.2 (consulte [Nomenclatura de hooks](../extensions/index.mdx#hook-naming)).

O terceiro argumento, `$mode`, indica qual documento está sendo gerado: `live`, `fiscal`, `refund`, `preview` (recibos de exemplo no editor de modelos e na galeria), `closure` ou `xreport` (documentos de fechamento de caixa e relatório X). Em `preview`, `closure` e `xreport`, o pedido ainda não foi salvo e seu ID é `0`; um plugin que precisa de um pedido salvo deve retornar `$data` sem alterações quando `$order->get_id()` for `0`.

```php
add_filter( 'wcpos_receipt_data', function ( array $data, WC_Abstract_Order $order, string $mode ) {
    foreach ( $data['discounts'] as &$row ) {
        if ( 'smart_coupon' === $row['discount_type'] ) {
            $row['gift_card'] = true;
        }
    }
    return $data;
}, 10, 3 );
```

O modelo pode então usar a nova chave como condição, como em qualquer outra seção:

```
{{#discounts}}
  {{#gift_card}}Gift Card{{/gift_card}}{{^gift_card}}{{i18n.discount}}{{/gift_card}}{{#label}}: {{label}}{{/label}}
{{/discounts}}
```

As chaves definidas no esquema devem manter os tipos documentados. As chaves adicionadas não fazem parte do esquema, então não aparecem no seletor de campos do editor de modelos, e os snapshots fiscais só contêm o que o filtro adicionou no momento em que o pedido foi pago. O filtro está disponível a partir do WCPOS 1.10.8.

  </AccordionItem>

  <AccordionItem question="Quais recibos imprimem uma chave adicionada">

Toda chave adicionada chega aos recibos que o próprio servidor renderiza: downloads de PDF e modelos PHP legados. Modelos HTML e térmicos renderizados no aplicativo POS reconstroem os dados primeiro: uma chave adicionada dentro de `order`, `store`, `cashier` ou `customer` é mantida, mas uma chave adicionada em qualquer outro lugar, como na linha de descontos acima, é omitida. {/* pending: monorepo#3363 */} Em um recibo em tempo real com um snapshot fiscal, a identificação fiscal, `register` e `software` são copiados do snapshot após a execução do filtro. Por isso, alterá-los nesse filtro não tem efeito; em vez disso, acrescente as informações ao snapshot.

  </AccordionItem>
</Accordion>

## Se algo der errado {#if-something-goes-wrong}

**Uma linha imprime `$0.00` em um recibo e nada em outro.** Alguns campos `_display`, como `totals.change_total_display`, `totals.refund_total_display` e `payments[].tendered_display`, ficam vazios quando o valor é zero e o servidor renderiza o recibo, mas exibem `$0.00` quando o aplicativo faz a renderização. Coloque a linha dentro de uma seção baseada no número para que ela seja omitida em ambos os casos: `{{#totals.change_total}}…{{/totals.change_total}}`.

**A linha Total economizado não aparece.** `totals.total_saved_complete` é falso: pelo menos um item não tem preço normal registrado, então não é possível calcular a economia. Isso costuma acontecer com pedidos registrados antes do WCPOS 1.9.0.

**O total é menor do que o cliente pagou.** A loja exibe os preços sem impostos, então `totals.total` é o total antes dos impostos. Imprima `totals.total_incl_display` para mostrar o valor cobrado. O recibo PHP legado incluído no WCPOS imprime esse valor.

**Um campo é impresso no PDF baixado, mas não no POS.** Os modelos renderizados no aplicativo reconstroem os dados primeiro e omitem alguns campos, que só são impressos em downloads de PDF e modelos PHP legados. Imprima os campos da lista abaixo apenas nesses casos ou condicione sua exibição a uma seção para que o recibo do POS os omita. {/* pending: monorepo#3363 */}

<Accordion>
  <AccordionItem question="Campos que diferem entre recibos PDF e do POS">

- `lines[].attributes`, `lines[].total_refunded_display` e `lines[].unit_subtotal_display` (com suas variantes `_incl` e `_excl`)
- `software.platform`
- `presentation_hints`, exceto `display_tax`, `prices_entered_with_tax`, `rounding_mode`, `locale` e `order_barcode_type`
- identificações fiscais de clientes dos tipos alemão, holandês, francês, de empresa do Reino Unido e suíço
- chaves que um plugin adiciona fora de `order`, `store`, `cashier` e `customer`; consulte [Estender os dados do recibo](#extending)

</AccordionItem>
</Accordion>

## Versões {#versions}

Os dados do recibo têm seu próprio número de versão, separado do número do plugin. Os campos mais recentes não estão presentes em recibos antigos, como um snapshot fiscal capturado antes de o campo existir, então condicione sua exibição a uma seção.

| Versão | Adições |
|---------|-------|
| 1.1 | Preço normal, preço de venda e economia de cada item, além dos totais de economia do pedido, incluindo **Total economizado**. Nenhum deles altera os totais do pedido ou os relatórios do WooCommerce |
| 1.2 | `discounts[].discount_type` |
| 1.3 | `customer.first_name` e os rótulos de exibição do cliente em `i18n` |
| 1.4 | `register`, `software`, os campos de documento fiscal (`fiscal.document_type`, os indicadores `is_…`, `sale_time`, `received_at`, `sale_tz`, `sale_counter`, `corrects`) e seus rótulos em `i18n` |
