服务器性能直接影响 WCPOS 应用的速度和响应能力。POS 会发起大量 REST API 调用，因此 **服务器响应时间是首要瓶颈**——POS 的速度很大程度上取决于主机质量。本指南介绍如何利用内置指标和故障排除方法监控、诊断并优化服务器性能。

## 最低服务器要求 {#minimum-server-requirements}

为确保生产环境中的 POS 响应迅速，我们建议至少满足以下要求：

<RequirementsList>
  <RequirementItem label="CPU">4+ 个 CPU 核心</RequirementItem>
  <RequirementItem label="RAM">4 GB 或更多</RequirementItem>
  <RequirementItem label="PHP">PHP 7.4+（推荐 8.x）</RequirementItem>
  <RequirementItem label="数据库">MySQL 8.0+ 或 MariaDB 11.x</RequirementItem>
  <RequirementItem label="存储">SSD 或 NVMe</RequirementItem>
  <RequirementItem label="SSL">必须使用 HTTPS，否则 WooCommerce REST API 无法工作</RequirementItem>
</RequirementsList>

:::warning 共享主机往往无法满足需求
共享主机的 PHP 工作进程和内存往往不足以应对 POS 工作负载所产生的大量并发 API 调用。在生产环境中使用 POS 时，强烈建议选择 **VPS 或托管式 WordPress 主机**。`WordPress.com` 托管服务也存在已知的 REST API 兼容性问题（部分用户的大型产品目录仅显示 9–10 个产品），建议使用自托管的 `WordPress.org` 以获得完整兼容性。
:::

### 经社区验证的优化组合 {#community-validated-optimisation-stack}

据用户反馈，以下组合可带来最佳 POS 性能：

- **MariaDB 11.4**（处理 WooCommerce 工作负载时比 MySQL 更快）
- **启用 HPOS**（见下文）
- **LiteSpeed 或 Redis** 对象缓存
- **NVMe** 存储
- 启用 **PHP OPcache**

## 503 错误 {#503-errors}

:::important 503 错误始终来自服务器端
`503 Service Unavailable` **不是 POS 的程序错误**，而是表示服务器无法处理请求。请检查：

1. 服务器负载和可用资源
2. PHP 工作进程（可能已全部占用）
3. PHP 内存限制——提高至 **256 MB 或更多**
4. 主机服务商的服务器日志（请联系服务商，他们能查看应用无法获取的信息）
:::

## WooCommerce 版本兼容性 {#woocommerce-version-compatibility}

WooCommerce 更新偶尔会导致 POS 无法正常工作。请务必先在[暂存站点](/1.x/support/troubleshooting/plugin-conflicts#before-you-start-use-a-staging-site)上更新 WooCommerce，并将 WCPOS 保持为最新版本，以获得最新的兼容性修复。

已知问题：

- **WooCommerce 10.5.0**——破坏了 POS 中的产品加载（症状：仅显示约 10 个产品；条形码扫描和搜索停止工作），并引入了一个实验性产品缓存，可能导致 **postmeta 膨胀** 和内存耗尽。**修复方法：** 将 WCPOS 更新到最新版本（它包含该修复和一个清理迁移），或将 WooCommerce 回滚到 [10.4.3](https://downloads.wordpress.org/plugin/woocommerce.10.4.3.zip)。

如果 WooCommerce 更新导致 POS 无法正常工作，请通过插件 WordPress.org 页面上的 **高级** 选项卡将 WooCommerce 回滚至上一版本，并报告问题。

## 了解服务器指标 {#understanding-server-metrics}

WCPOS 会在每次获取数据（产品、订单、客户等）时自动收集服务器性能指标。

从 **v1.10.0** 起，汇总视图位于 **店铺健康 → 性能**，显示过去 24 小时的请求数、数据传输量和典型响应时间，以及按小时显示的运行状况条（参见[店铺健康](/1.x/support/store-health#performance)）。解读时需注意两点：数据传输量为下限值（未声明大小的响应计为零）；同步调节项旁的 *每天约 N 次请求* 是根据配置间隔推算的名义速率，并非上限或实际计数。抖动会使计数上下浮动，`304` 也计为一次请求，而空闲衰减仅会降低间隔短于 60 秒的预设的请求量。单次请求指标可在 **店铺健康 → 日志** 中查看。

### 典型服务器指标 {#typical-server-metrics}

```json
{
  "total": "24692",
  "execution_time": "76.64 ms",
  "server_load": "[15.20605469,16.16357422,16.76806641]"
}
```

**指标说明：**
- **`total`** - 已处理的记录数（24,692 个产品 ID）
- **`execution_time`** - 完成操作所需的时间（76.64 毫秒）
- **`server_load`** - 1、5 和 15 分钟的服务器平均负载

## 服务器负载说明 {#server-load-explained}

服务器负载表示不同时间段内的系统平均负载：

- **第一个值** - 1 分钟平均值（15.21）
- **第二个值** - 5 分钟平均值（16.16）
- **第三个值** - 15 分钟平均值（16.77）

### 负载解读 {#load-interpretation}

服务器负载数值可能具有误导性，应谨慎解读：

:::warning 负载数值可能具有误导性
服务器平均负载并不总是与性能直接相关。只要资源充足且优化得当，负载较高（15+）的服务器仍可响应迅速。**应关注执行时间，而非仅看负载数值。**
:::

**一般原则：**
- **结合 CPU 核心数看负载** - 8 核服务器的负载为 8.0 时，意味着资源已充分利用
- **区分持续与暂时的高负载** - 短暂峰值属于正常现象，持续高负载可能意味着存在问题
- **实际性能更重要** - 负载高但响应迅速的服务器，优于负载低却响应缓慢的服务器

**需要关注的现象：**
- **执行时间增加**，且随时间推移不断加长
- **负载持续增长**，原因不明
- **高负载与执行缓慢**同时出现

## 性能基准 {#performance-benchmarks}

### 执行时间参考 {#execution-time-guidelines}

| 操作 | 良好 | 可接受 | 较差 | 严重 |
|-----------|------|------------|------|----------|
| **产品获取** | < 100ms | 100-500ms | 500ms-2s | > 2s |
| **订单创建** | < 200ms | 200-800ms | 800ms-3s | > 3s |

### 记录数量的影响 {#record-count-considerations}

执行时间应随记录数量合理增长：

```json
// Good scaling examples
{"total": "100", "execution_time": "15.2 ms"}    // 0.15ms per record
{"total": "1000", "execution_time": "89.4 ms"}   // 0.09ms per record
{"total": "10000", "execution_time": "234.1 ms"} // 0.02ms per record

// Poor scaling examples
{"total": "100", "execution_time": "500.0 ms"}   // 5.0ms per record
{"total": "1000", "execution_time": "8000.0 ms"} // 8.0ms per record
```

## 诊断性能问题 {#diagnosing-performance-issues}

### 第 1 步：监控日志 {#step-1-monitor-the-logs}

1. 从导航抽屉打开 **店铺健康**，查看 **性能** 选项卡以了解过去 24 小时的整体情况（典型响应时间是关键指标）
2. 执行响应缓慢的操作（同步产品、创建订单等）
3. 在 **日志** 选项卡中查找对应条目
4. 展开该行以查看指标

### 第 2 步：分析指标 {#step-2-analyse-the-metrics}

**执行时间长 + 服务器负载高 = 服务器资源问题**
```json
{
  "total": "5000",
  "execution_time": "3500.0 ms",
  "server_load": "[12.45, 11.23, 10.87]"
}
```
*解决方案：增加服务器资源或优化服务器配置*

**执行时间长 + 服务器负载正常 = 插件或数据库问题**
```json
{
  "total": "1000",
  "execution_time": "2800.0 ms",
  "server_load": "[1.23, 1.45, 1.67]"
}
```
*解决方案：找出响应缓慢的插件或优化数据库查询*

**执行时间正常 + 服务器负载高 = 服务器整体过载**
```json
{
  "total": "2000",
  "execution_time": "150.0 ms",
  "server_load": "[8.90, 9.12, 8.45]"
}
```
*解决方案：减少其他进程产生的服务器负载或升级资源*

## 常见性能问题 {#common-performance-problems}

### 1. 服务器资源不足 {#1-insufficient-server-resources}

**症状：**
- 服务器负载持续偏高（多数服务器上 > 4.0）
- 所有操作的执行时间都很长
- 频繁超时

**解决方案：**
- **升级 CPU** - 更多核心可更好地处理并发请求
- **增加 RAM** - 减少磁盘 I/O 并改善缓存效果
- **使用 SSD 存储** - 显著提升数据库性能
- **优化 PHP 设置** - 提高 memory_limit、max_execution_time

### 2. 数据库查询缓慢 {#2-slow-database-queries}

**症状：**
- 执行时间长，但服务器负载正常
- 获取产品或订单时尤其缓慢
- 日志中出现数据库相关错误代码

**解决方案：**
- **启用 WooCommerce HPOS** - 对数据库性能提升最大的一项措施
- **使用对象缓存** - 若主机服务商支持，可使用 Redis 或 Memcached
- **保持 WordPress 更新** - 核心更新通常包含数据库优化
- **限制文章修订版本数** - 在 wp-config.php 中添加 `define('WP_POST_REVISIONS', 3);`

### 3. 插件干扰 {#3-plugin-interference}

**症状：**
- 插件更新后性能突然下降
- 某些操作明显比其他操作慢
- 执行时间长，但服务器负载正常

**故障排除：**
1. **在暂存环境中测试** - 禁用 WooCommerce 和 WCPOS 以外的所有插件
2. **测量基线** - 记录仅启用必要插件时的执行时间
3. **逐步启用** - 逐一启用插件以找出问题来源
4. **检查插件钩子** - 查找挂接到 WooCommerce 动作的插件

**常见的问题插件：**
- 在产品操作过程中消耗大量资源的 SEO 插件
- 复杂的库存管理系统
- 实时分析或跟踪插件
- 代码质量不佳的自定义插件

### 4. WordPress/WooCommerce 配置 {#4-wordpresswoocommerce-configuration}

**症状：**
- 性能不稳定
- 日志中出现内存相关错误
- 管理后台响应缓慢

**优化检查清单：**
- **PHP 版本** - 使用 PHP 8.0+ 以获得更好的性能
- **WooCommerce HPOS** - 启用高性能订单存储（见下文）
- **WordPress 缓存** - 如支持，请启用对象缓存
- **WooCommerce 设置** - 优化产品图片尺寸

### WooCommerce 高性能订单存储（HPOS） {#woocommerce-high-performance-order-storage-hpos}

:::tip 最显著的性能提升
**启用 HPOS 是提升 WooCommerce 性能最有效的措施之一。** 它将订单存储在自定义数据库表中，而非 WordPress 文章表中，可显著提升订单量较大的店铺的性能。
:::

**优势：**
- **订单查询更快** - 订单存储在经过优化的数据库结构中
- **降低数据库负载** - 将订单与文章和页面分开存储
- **更好的可扩展性** - 高效处理大量订单
- **提升管理后台性能** - 订单管理界面响应更快

**启用方法：**
1. 前往 `WooCommerce > 设置 > Advanced > Features`
2. 启用高性能订单存储
3. 按迁移流程操作（详细步骤请参见[切换到 HPOS](/1.x/support/performance/order-storage#switch-to-hpos)）

**了解更多：**
- [WooCommerce HPOS 文档](https://woocommerce.com/document/high-performance-order-storage/)
- [HPOS 迁移指南](https://woocommerce.com/document/high-performance-order-storage/#section-3)

## 服务器监控最佳实践 {#server-monitoring-best-practices}

### 1. 定期检查性能 {#1-regular-performance-checks}

- **每周检查** - 查看日志中的性能趋势
- **基线测量** - 记录正常情况下的执行时间
- **高峰时段监控** - 在流量高峰期间进行监控

### 2. 设置性能警报 {#2-set-performance-alerts}

留意以下预警信号：
- 执行时间持续 > 1000ms
- 服务器负载长时间 > 5.0
- 日志中频繁出现超时错误

### 3. 容量规划 {#3-capacity-planning}

跟踪增长趋势：
- **记录数量增长** - 产品、订单、客户
- **性能下降** - 执行时间随数据量增长的变化
- **资源利用率** - CPU、内存、磁盘使用情况

## 服务器优化策略 {#server-optimisation-strategies}

### 1. WordPress/WooCommerce 最佳实践 {#1-wordpresswoocommerce-best-practices}

**启用 HPOS：**
- 对 WooCommerce 性能提升最大的一项措施
- 详情请参见上文的 HPOS 部分

**PHP 配置（请咨询主机服务商）：**
```ini
memory_limit = 512M
max_execution_time = 300
max_input_vars = 3000
```

**WordPress 配置：**
```php
// In wp-config.php - limit post revisions
define('WP_POST_REVISIONS', 3);

// Enable WordPress debug logging if needed
define('WP_DEBUG_LOG', true);
```

### 2. 主机层面的优化 {#2-hosting-level-optimizations}

**对象缓存：**
- 向主机服务商询问是否支持 Redis 或 Memcached
- 许多托管式 WordPress 主机会自动提供此功能

**PHP 版本：**
- 使用 PHP 8.0+ 可显著提升性能
- 大多数主机都支持便捷地切换 PHP 版本

**服务器资源：**
- 确保 RAM 充足（至少 1GB，建议 2GB+）
- 与传统硬盘相比，SSD 存储可显著提升数据库性能

## 特定主机服务的说明 {#hosting-specific-notes}

部分主机和 CDN 需要进行配置，才能让 POS 访问 WooCommerce REST API：

| 主机 / 服务 | 问题 | 解决方法 |
| --- | --- | --- |
| **GoDaddy** | 网站防火墙阻止 `/wp-json/` REST API 调用（例如出现 _“收到 'undefined'”_ 错误） | `Website Security > Firewall > 设置 > Access Control > Allow URL Paths` → 添加 `/wp-json/` |
| **WP Engine** | 必须明确启用 REST API | 启用 REST API；必要时在其防火墙中将 API 端点加入白名单 |
| **Cloudflare** | 安全检查（机器人对抗模式、遭受攻击模式、WAF 质询）阻止 REST API 请求，缓存也可能返回过时的 API 响应 | 按照 [Cloudflare 指南](/1.x/support/troubleshooting/cloudflare)操作：为 `/wp-json/` 添加 WAF **跳过** 规则，并为相同路径添加 **绕过缓存** 规则 |
| **WordPress.com** | REST API / 产品加载兼容性问题（仅显示 9–10 个产品） | 使用自托管的 WordPress.org 以获得完整兼容性 |
| **共享主机** | PHP 工作进程太少或内存不足，无法应对 POS 的并发调用 | 迁移至 VPS 或托管式 WordPress 主机 |

安全插件（如 Wordfence）也可能以类似方式阻止 REST API。完整列表和解决方法请参见[插件冲突](/1.x/support/troubleshooting/plugin-conflicts)。

### HTTP 414 — URI 过长 {#http-414-uri-too-long}

购物车内容过多，或结账 URL 中包含的访问令牌，都可能导致 URL 超过服务器的长度限制（结账请求使用 `GET`）。此问题可能仅在特定浏览器中出现，浏览器缓存也可能使问题加重。

**临时解决方法：** 先清除浏览器缓存，再提高服务器的 URL 长度限制：

- **Apache：** 在 `httpd.conf` 中设置 `LimitRequestLine 65536`
- **Nginx：** 在 `nginx.conf` 中设置 `large_client_header_buffers 4 65536;`
- 如果您没有配置访问权限，请让主机服务商进行调整。

## 何时寻求帮助 {#when-to-seek-help}

出现以下情况时，请联系主机服务商或 WordPress 开发人员：

- 已经尝试优化，但 **服务器负载仍持续 > 8.0**
- 简单操作的 **执行时间 > 5000ms**
- 日志中频繁出现 **内存错误**
- **数据库查询耗时 > 2 秒** 的情况持续出现

请向他们提供：
- 日志中的服务器指标
- 已启用插件列表
- 服务器配置（CPU、RAM、存储类型）
- WordPress 和 WooCommerce 版本
