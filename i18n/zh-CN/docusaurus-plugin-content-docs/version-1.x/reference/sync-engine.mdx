本页描述的是 **WCPOS v1.10.0** 中引入的同步引擎。更早的版本使用另一种按屏幕划分的复制模型——请参见本页末尾的 [v1.10.0 有哪些变化](#what-changed-in-v1100)。
:::

WCPOS 是本地优先的：每个屏幕都读写设备上的一个数据库，而 **同步引擎** 在后台让该数据库与您的 WooCommerce 商店保持收敛。本页解释引擎如何决定获取什么、何时获取，以及您的销售数据如何回到服务器——这一层次的细节对开发者、集成商以及希望了解 POS 对其主机做了什么的店主很有用。

## 每个商店和收银员各一个引擎 {#one-engine-per-scope}

在每台设备上，POS 为 **每个站点 + 商店 + 收银员的组合运行一个同步引擎**。该引擎拥有自己的本地数据库，因此切换商店或收银员切换的是整个数据平面，而不是在同一堆共享记录上做筛选。按收银员隔离是有意为之：同一台设备上的两名收银员绝不会共享本地数据。

切换范围采用**事务式**处理：新店铺或收银员的数据层完成加载后才会提交；如发生错误，会明确提示，而不会让您处于两个店铺之间、只切换了一半的状态。

升级时，本地数据库绝不会就地迁移——应用会启动一个全新的数据库并从服务器重新下载，服务器始终持有权威副本（参见 [从 v1.9 升级](#upgrading-from-v19)）。

在 Pro 多店铺安装中，每个同步请求都会标明所属店铺，因此在收银台修改价格时，更新的是该店铺的价格，而不是网店的价格。

## 后台运行的内容 {#sync-lanes}

引擎按计划执行的每一项工作都是一个**通道**——一个有名称、工作量有限的后台工作单元。通道分为三组：

| 分组 | 通道 | 默认频率 |
| --- | --- | --- |
| **拉取** | 变更检查（变更信号） | 10 秒 – 5 分钟，由您的[同步预设](/1.x/support/store-health#sync-presets)决定 |
| | 最近订单、产品目录预填充、参考数据预填充 | 约 5 分钟 |
| | 客户涓流下载（仅在空闲时） | 约 5 分钟 |
| **推送** | 写入排空——发送已排队的本地更改 | 约 10 秒 |
| **维护** | 完整性与删除审计、服务器总数刷新 | 每隔几分钟到约 17 分钟 |

每个通道都满足以下两点：

- **每个通道都声明单次运行的请求上限。** 任何通道都不得在一次运行中发出数量不受限的请求；较大的任务使用带可恢复游标的有界批次。这是设计中必须始终满足的核心约束，[同步性能](/1.x/reference/sync-performance)中有详细介绍。
- **维护工作让位于收银员。** 审计和后台预热会在让收银台准备好销售的交互性工作完成之后运行，绝不会抢在前面；一旦服务器出现压力迹象，它们也会最先暂停。

上述频率都是默认值。商家可以在 POS 的**店铺健康 → 性能**中，按设备调整检查间隔和每次请求的记录数——请参阅[店铺健康](/1.x/support/store-health)。

## POS 如何得知发生了变更 {#change-signal}

引擎不会通过重新下载数据来判断数据是否变化。服务器维护一份变更日志，POS 则轮询一个轻量的**变更检查**，只回答一个问题：自上次记录的位置以来，是否有任何变动？

- **一次检查覆盖八个集合**——产品、变体、税率、客户、优惠券、分类、品牌和标签。订单被有意排除在变更检查之外；订单的时效性由独立的最近订单通道负责，因此产品更新和订单更新可能以不同频率到达。
- **空闲的收银台几乎不产生开销。** 引擎发送条件请求：当没有任何变化时，服务器仅返回一个无正文的 `304 Not Modified` 响应。没有业务活动的店铺会稳定在每次检查一个极小响应的水平。
- **检查带有 ±20% 的抖动**，使同一站点的多台收银机错开请求时间，避免同时向服务器发起突发请求。
- **空闲衰减：** 在 10 分钟无交互之后，检查间隔会拉长（至少为 60 秒）。任何实际活动——触摸、按键或一次被接受的条形码扫描——都会立即恢复正常频率，并马上触发一次追赶检查。衰减只会拉长间隔，绝不会让轮询频率高于配置值。
- **停用数天的收银台会重新建立基线，而不是回放历史。** 如果变更日志已远远超出收银台上次记录的位置，逐条回放就会耗费数百次请求。引擎会改为将游标跳到最新位置，重新检查设备已有数据在服务器上的当前状态——因此开销取决于本地副本的规模，而不是收银台停用了多久。

## 屏幕如何获得数据 {#declared-demand}

在 v1.10.0 中，屏幕不再自行运行同步。**屏幕只声明正在显示的内容——搜索词、筛选条件、排序和页码——由引擎决定是否需要发起请求。** 每次声明会得到以下三种结果之一：

- **已获取**——引擎已通过网络获取所需数据。
- **本地满足**——设备已有所需数据，或近期一次相同的获取已覆盖该需求。
- **被取代**——屏幕内容已变化（您滚动了页面或更改了筛选条件），更新的声明取代了原有声明。这是正常现象，不是错误。

只能在本地处理的筛选条件不会发送到服务器。此外，声明得到满足并不意味着某个集合已完整下载——完整性会单独跟踪（见下一节）。

并非所有内容都会提前下载，启动时设备上已有的数据也因集合而异：

1. **预填充**——产品通过有界的目录预填充逐步下载；税率在启动时拉取（没有税率，POS 就无法完成购物车计算）。
2. **按需下载，外加空闲涓流**——客户数据不会提前预填充。客户涓流下载会在每个空闲间隔下载一小批数据，只要收银员处于活动状态就完全跳过；新增或变更的客户则通过变更检查获取。
3. **首次打开时获取**——分类、标签、品牌和优惠券会在收银员首次打开时拉取。无人打开的集合始终不会产生请求。

此外，变体选择器每次打开时都会刷新一次价格和库存，因此本地已有的变体可以立即显示，同时不会显示数天前的过期库存。

## “是否全部下载完了？”——如实呈现覆盖率 {#coverage}

像 *“5,000 件产品中的 1,240 件”* 这样的读数，需要以**服务器端**总数作为分母。引擎为每个集合维护一个总数（大约每 15 分钟刷新一次，通常没有额外开销——实际的同步响应已包含总数，因此很少需要专门发起请求），并严格遵守如实呈现的约定：

- 过期或缺失的服务器总数会显示为*正在检查…*，绝不会悄悄用本地计数替代。若以本地计数作分母，就总会显示 100%，恰好掩盖了该数字本应揭示的差距。
- 当引擎无法确认完整性时，结果为*未知*，界面会将该数字标注为本地计数。
- 订单覆盖率条以服务器上的**整个**订单历史为基准，而收银台有意只保留未结和最近的订单，因此正常的收银台在这里也会显示为部分覆盖，这是设计预期。

这些数字显示在**店铺健康 → 数据库**中，同时还有一个*可开始销售*里程碑：设备上有了第一件产品后，该里程碑就会达成。离线不会阻止它，因为离线销售正是其目的。请参阅[店铺健康](/1.x/support/store-health)。

## 更改如何回到您的店铺 {#write-path}

每次本地写入——一笔销售、一次产品编辑或一次客户更新——都会先进入设备上的**持久化出站队列**，然后由排空通道每隔几秒将队列推送到 WooCommerce。这使离线销售有了保障：断网时录入的销售会留在队列中，并在连接恢复后发出。

需要了解的细节：

- **购物车写入按订单串行化。** 扫描枪连续快速扫描时，数据会逐条应用；重复添加会合并到已有的同一行项目，而不是排队生成第二行。
- **订单确认会采纳服务器的副本。** WooCommerce 在创建订单时会为订单行项目分配 ID；引擎会采纳已确认的订单，使后续更新能匹配这些行，而不是追加重复项。采纳过程采取保守策略：绝不会覆盖尚未发送到服务器的本地编辑，且只适用于订单。
- **订单写入冲突会自动恢复一次。** 如果订单写入与较新的服务器副本冲突，引擎会协调数据并重试一次；如果仍然失败，就会显示冲突供您处理，而不会静默地反复重试。
- **服务器永久拒绝的写入绝不会被静默重试。** 此类写入会连同服务器给出的原因一起被搁置，并在**店铺健康 → 数据库**中显示为*“从未送达服务器的更改”*，提供两个明确的操作：**重新发送**（根据记录当前的状态重新构建请求，因此之后的修正会生效）和**放弃**。这里没有自动重试循环——恢复始终是一次可见、由用户主动执行的操作。面向商家的操作说明请参阅[店铺健康](/1.x/support/store-health#database)。

### 多个浏览器标签页 {#multi-tab}

支持在多个浏览器标签页中运行同一店铺的 Web 版 POS。每个标签页都可以开单，写入会追加到共享队列，但对每个店铺 + 收银员作用域，**由一个选出的标签页负责发送**。如果该标签页关闭，浏览器会自动选择下一个接替。以不同收银员身份登录的两个标签页属于不同作用域，各自管理自己的队列。

## 本地存储 {#local-storage}

Web 版和桌面版应用通过 **OPFS（源私有文件系统）工作线程**存储数据；iOS 和 Android 应用通过文件系统引擎使用相同的磁盘格式。四个平台共用一种存储格式和同一套损坏恢复工具。（早期版本在 Web 端使用 IndexedDB，在原生端使用 SQLite。）

如果本地存储变得**无法读取**，WCPOS 会阻止结账并提示重新加载，避免在数据损坏的情况下继续销售并丢失销售记录。此时条形码扫描也会明确报错，而不是无声失败，确保在恢复工具重建本地存储之前，损坏的数据不会悄悄吞掉一笔销售。

查询在数据库层内执行，包括选择器、排序和分页，因此只有当前可见页的数据会传入应用。在包含 10,000 笔订单的合成测试数据上，这种查询下推使实时订阅下每次写入的更新开销从约 27 毫秒降至约 0.06 毫秒。

## 从 v1.9 升级 {#upgrading-from-v19}

v1.10.0 不迁移本地数据库，而是执行一次**冷重新同步**：

1. 首次启动时，应用会打开一个全新的本地数据库，并从您的店铺重新下载数据。每台设备都需要进行一次完整的重新下载。
2. 数据不会丢失：WooCommerce 服务器保存着所有已同步数据的权威副本。待发送的更改会在旧数据清理**之前**发出或明确显示，升级不会销毁未发送的销售记录。
3. **应用与插件同步发布。** v1.10.0 客户端使用插件的 v2 同步 API。如果只升级其中一端，请求会因 `rest_no_route` 错误而失败——这个错误意味着“请更新另一端”，而不是安装损坏。

## v1.10.0 有哪些变化 {#what-changed-in-v1100}

| | v1.9.x | v1.10.0 |
| --- | --- | --- |
| 同步单位 | 每个已挂载的屏幕查询对应一条复制流 | 每个站点 + 店铺 + 收银员对应一个引擎 |
| 获取数据的触发条件 | 屏幕挂载 | 屏幕声明所需数据 |
| 变更检测 | 定期轮询 + 每小时全量审计 | 变更日志游标配合条件式 `304` 响应 |
| 服务器总数 | 不跟踪 | 各集合的总数，并以*正在检查…*状态如实反映情况 |
| 失败的写入 | 重试过程不透明 | 持久化队列、可见的恢复面板、无静默重试 |
| Web 多标签页 | 无协调机制 | 每个作用域选出一个发送方 |
| 本地搜索 | 按词首匹配 | 子串匹配（最少 3 个字符） |
| 存储 | IndexedDB（Web）、SQLite（原生） | 所有平台均采用 OPFS 格式存储 |
| 同步调优 | 固定 | 店铺健康中按设备提供预设和调节项 |

有关引擎的性能设计理念——请求上限、服务器压力下的退避以及实测数据——请参阅[同步性能](/1.x/reference/sync-performance)。
