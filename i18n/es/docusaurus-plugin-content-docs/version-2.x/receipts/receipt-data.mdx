**Administración de WP:** las plantillas se editan en `WP Admin → POS → Templates`; esta página enumera los campos que pueden imprimir.

Para imprimir un recibo o enviarlo por correo electrónico, consulte [Recibos y pantalla de pago completado](./at-checkout.mdx); para elegir una plantilla o pedir a la IA que la modifique, consulte [Personalizar el recibo](./customise.mdx).

Esta página está dirigida a quienes editan manualmente el código de una plantilla. Todas las plantillas, tanto HTML como térmicas, imprimen a partir de los mismos datos del recibo: la tienda, el pedido, los artículos, los totales y los pagos. La página explica cómo imprimir un campo, ofrece tres ejemplos habituales y enumera todos los campos.

**Ir a:** [Buscar un campo](#field-reference) · [Ejemplos habituales](#common-recipes) · [Si algo sale mal](#if-something-goes-wrong)

## Imprimir un campo {#print-a-field}

1. Abra la plantilla en **WP Admin → POS → Plantillas** (en [Editar manualmente](./customise.mdx#option-3--edit-it-by-hand) encontrará los detalles).
2. Donde deba imprimirse el campo, escriba su ruta entre llaves dobles, como `{{store.name}}`, `{{order.number}}` o `{{totals.total_display}}`, o insértelo desde la lista de campos situada junto al código.
3. Revise la vista previa debajo del código y haga clic en **Actualizar** para guardar.

Para una lista, como la de artículos, incluya la fila dentro de una sección para que se repita una vez por artículo:

```mustache
{{#lines}}
  {{name}} x {{qty}} —
  {{line_total_display}}
{{/lines}}
```

Una sección también omite su contenido cuando el campo está vacío, es cero o es falso, por lo que `{{#customer.id}}…{{/customer.id}}` solo se imprime para un cliente identificado. Para imprimir importes, utilice el campo que termina en `_display`; consulte [Campos monetarios](#currency-fields).

Los recibos también se imprimen sin conexión: la aplicación genera una copia de los datos del recibo a partir del pedido almacenado en el dispositivo.

<Accordion>
  <AccordionItem question="Por qué pueden diferir los recibos">

### De dónde proceden los datos {#where-the-data-comes-from}

El servidor de su tienda genera los datos del recibo de cada pedido, y la aplicación genera una copia reducida a partir del pedido almacenado en el dispositivo: no incluye `cashier`, ni horarios, notas o políticas de la tienda, ni `totals.paid_total` o `totals.change_total`. Las plantillas HTML y térmicas se abren de inmediato con la copia del dispositivo y pasan a utilizar la del servidor cuando llega; sin conexión, se imprime la copia del dispositivo, por lo que esos campos quedan vacíos. Con WCPOS Pro, la copia del dispositivo también incluye el logotipo de la tienda; sin Pro, el logotipo llega con la copia del servidor. Las plantillas PHP heredadas siempre se renderizan en el servidor. Por eso las plantillas utilizan los campos siguientes y nunca métodos PHP del pedido. Algunos campos solo se imprimen cuando el servidor renderiza la plantilla, como ocurre al descargar un PDF; se enumeran en [Si algo sale mal](#if-something-goes-wrong).

</Accordion>

## Mapa del recibo {#receipt-map}

Cada parte de un recibo impreso procede de una sección de los datos del recibo. Pase el puntero por una parte del recibo o por su tarjeta para resaltar ambas; haga clic o pulse cualquiera de ellas para ir a los campos de esa sección. En un teléfono, las tarjetas aparecen después del recibo en el mismo orden, de arriba abajo.

## Referencia de campos {#field-reference}

Despliegue una sección para ver sus campos. El primer apartado enumera todas las secciones y sus tipos.

### Secciones de nivel superior {#top-level-sections}

| Sección | Contenido |
|---------|---------------|
| `order` (objeto) | Identificación, estado, fechas, nota e información de la URL de pago del pedido |
| `store` (objeto) | Identificación, dirección, datos de contacto, identificadores fiscales, logotipo, horarios y texto del pie del recibo de la tienda |
| `cashier` (objeto) | Usuario que procesó el pedido |
| `customer` (objeto) | Nombre para mostrar, direcciones e identificadores fiscales del cliente |
| `lines` (matriz) | Líneas de productos |
| `fees` (matriz) | Filas de cargos |
| `shipping` (matriz) | Filas de envío |
| `discounts` (matriz) | Filas de cupones/descuentos |
| `totals` (objeto) | Totales del pedido, totales de pagos, resumen de reembolsos y recuentos de artículos |
| `tax` (objeto) | Indicadores del modo de visualización de impuestos para las condiciones de las secciones |
| `tax_summary` (matriz) | Filas de resumen de impuestos por tipo impositivo |
| `has_tax_summary` (booleano) | Condición auxiliar para `tax_summary` |
| `payments` (matriz) | Filas de pagos |
| `refunds` (matriz) | Registros de reembolso aplicados al pedido |
| `fiscal` (objeto) | Campos de la instantánea fiscal que rellenan las integraciones fiscales |
| `register` (objeto) | La caja que registró la venta: `id` y `name`. Cadenas vacías cuando se desconoce |
| `software` (objeto) | El software que emitió el recibo: `name` (`WCPOS`), `plugin_version`, `app_version`, `app_build`, `platform` |
| `presentation_hints` (objeto) | Indicaciones de formato y renderizado |
| `i18n` (objeto) | Etiquetas traducidas para las plantillas incluidas y las personalizadas |

### Objetos de identificadores fiscales {#tax-id-objects}

`store.tax_ids` y `customer.tax_ids` contienen objetos con la misma estructura:

| Campo | Tipo | Descripción |
|-------|------|-------------|
| `type` | cadena | Identificador como `eu_vat`, `de_steuernummer`, `au_abn`, `br_cpf`, `us_ein` u `other` |
| `value` | cadena | Valor del identificador fiscal que se imprimirá |
| `country` | cadena/nulo | Código ISO del país; nulo para `eu_vat` y `other` |
| `label` | cadena | Etiqueta de visualización traducida, resuelta antes del renderizado |

Ejemplo:

```mustache
{{#store.tax_ids}}
  {{label}}: {{value}}
{{/store.tax_ids}}
```

```mustache

    <span>{{i18n.savings}}: -{{line_savings_display}}</span>
  {{/line_savings}}
{{/lines}}

`selling_price` es el precio antes de los cupones. Utilice `unit_price` o `line_total` para el importe final después de los descuentos de WooCommerce.

:::note Reimpresión de pedidos creados antes de v1.9.0

  {{#discounts}}
    <span>{{i18n.discount}}: -{{discounts_display}}</span>
  {{/discounts}}
{{/lines}}
```

Si la plantilla no imprime una fila `discounts` por línea, siga mostrando `line_savings` aunque `savings_in_discounts` sea verdadero. Las plantillas incluidas gestionan esta distinción automáticamente.

## Cómo se relacionan los precios {#price-model}

Un artículo del recibo tiene varios precios, y sus nombres se entienden mejor al ver los propios importes. Esta es la línea de café espresso del pedido de ejemplo: un producto de $17.00 en oferta a $14.50, con un cupón adicional del 10%:

<PriceFlow
  caption="Café espresso en grano — una unidad (el pedido tiene dos)"
  scaleLabel="precio normal 17.00"
  segments={[
    { kind: 'paid', amount: 13.05, label: "13.05 pagados" },
    { kind: 'coupon', amount: 1.45, label: "1.45" },
    { kind: 'savings', amount: 2.5, label: "2.50" },
  ]}
  summary={[
    { label: "Ahorro por ofertas en todo el pedido", value: '`totals.sale_savings_total` = 5.00' },
    { label: "Todos los descuentos de cupones del pedido", value: '`totals.discount_total` = 5.28' },
    { label: "Ahorro + descuentos, sin duplicaciones de versiones anteriores", value: '`totals.total_saved` = 10.28' },
  ]}
/>

El ahorro por oferta es la diferencia entre el precio normal y el precio de venta. El descuento es lo que resta un cupón según el cálculo de WooCommerce. Los totales de pedidos y los informes de WooCommerce solo contienen los descuentos, por lo que `total_saved` suma ambos conceptos en una única cifra para el cliente.

### Objetos de fecha {#date-objects}

Cada fecha se ofrece ya formateada de varias maneras, por lo que la plantilla nunca necesita darle formato.

| Campo | Descripción |

| `datetime_short`, `datetime_long`, `datetime_full` | Formatos combinados adaptados a la configuración regional |

## Ampliar los datos del recibo {#extending}

Un plugin puede añadir sus propios campos a los datos del recibo mediante el filtro `wcpos_receipt_data`.

<Accordion>
  <AccordionItem question="El filtro: sus argumentos, los seis modos y un ejemplo">

WCPOS mantiene los campos anteriores libres de datos específicos de plugins. Cuando un plugin necesita que el recibo contenga información que WooCommerce no contempla, la añade mediante el filtro `wcpos_receipt_data`, del mismo modo que los plugins filtran los propios totales de pedidos de WooCommerce. El filtro se ejecuta en cada recibo que genera el servidor: recibos en tiempo real, instantáneas fiscales en el momento del pago, descargas de PDF y plantillas PHP heredadas. Antes de WCPOS 2.0, este filtro se llamaba `woocommerce_pos_receipt_data`; ese nombre sigue funcionando, pero está obsoleto desde 2.0 y se eliminará como pronto en 2.2 (consulte [Nombres de los hooks](../extensions/index.mdx#hook-naming)).

El tercer argumento, `$mode`, indica qué documento se está generando: `live`, `fiscal`, `refund`, `preview` (recibos de ejemplo del editor de plantillas y la galería), `closure` o `xreport` (documentos de cierre de caja e informe X). En `preview`, `closure` y `xreport`, el pedido no está guardado y su ID es `0`; un plugin que necesite un pedido guardado debe devolver `$data` sin cambios cuando `$order->get_id()` sea `0`.

```php
add_filter( 'wcpos_receipt_data', function ( array $data, WC_Abstract_Order $order, string $mode ) {
    foreach ( $data['discounts'] as &$row ) {
        if ( 'smart_coupon' === $row['discount_type'] ) {
            $row['gift_card'] = true;
        }
    }
    return $data;
}, 10, 3 );
```

La plantilla puede entonces utilizar la nueva clave como condición, igual que en cualquier otra sección:

```
{{#discounts}}
  {{#gift_card}}Gift Card{{/gift_card}}{{^gift_card}}{{i18n.discount}}{{/gift_card}}{{#label}}: {{label}}{{/label}}
{{/discounts}}
```

Las claves definidas en el esquema deben conservar sus tipos documentados. Las claves añadidas no forman parte del esquema, por lo que no aparecen en el selector de campos del editor de plantillas, y las instantáneas fiscales solo contienen lo que el filtro añadió en el momento del pago del pedido. El filtro está disponible desde WCPOS 1.10.8.

  </AccordionItem>

  <AccordionItem question="Qué recibos imprimen una clave añadida">

Todas las claves añadidas llegan a los recibos que renderiza el propio servidor: descargas de PDF y plantillas PHP heredadas. Las plantillas HTML y térmicas renderizadas en la aplicación WCPOS reconstruyen primero los datos: una clave añadida dentro de `order`, `store`, `cashier` o `customer` se conserva, pero una añadida en cualquier otro lugar, como en la fila de descuentos anterior, se omite. {/* pending: monorepo#3363 */} En un recibo en tiempo real con una instantánea fiscal, la identificación fiscal, `register` y `software` se copian de la instantánea después de ejecutar el filtro, por lo que modificarlos en este filtro no tiene efecto; amplíe la instantánea en su lugar.

  </AccordionItem>
</Accordion>

## Si algo sale mal {#if-something-goes-wrong}

**Una fila imprime `$0.00` en un recibo y nada en otro.** Algunos campos `_display`, como `totals.change_total_display`, `totals.refund_total_display` y `payments[].tendered_display`, están vacíos cuando su valor es cero si el servidor renderiza el recibo, y muestran `$0.00` si lo hace la aplicación. Incluya la fila en una sección condicionada por el número para que se omita en ambos casos: `{{#totals.change_total}}…{{/totals.change_total}}`.

**Falta la fila Total ahorrado.** `totals.total_saved_complete` es falso: al menos un artículo no tiene un precio normal registrado, por lo que no puede calcularse el ahorro. Suele ocurrir con pedidos registrados antes de WCPOS 1.9.0.

**El total es inferior a lo que pagó el cliente.** La tienda muestra los precios sin impuestos, por lo que `totals.total` es el total antes de impuestos. Imprima `totals.total_incl_display` para mostrar el importe cobrado. El recibo PHP heredado incluido en WCPOS imprime ese importe.

**Un campo se imprime en la descarga de PDF, pero no en WCPOS.** Las plantillas renderizadas en la aplicación reconstruyen primero los datos y omiten algunos campos, que solo se imprimen en las descargas de PDF y las plantillas PHP heredadas. Imprima los campos de la lista siguiente solo en esos casos, o condiciónelos con una sección para que el recibo de WCPOS los omita. {/* pending: monorepo#3363 */}

<Accordion>
  <AccordionItem question="Campos que difieren entre los recibos en PDF y los de WCPOS">

- `lines[].attributes`, `lines[].total_refunded_display` y `lines[].unit_subtotal_display` (con sus variantes `_incl` y `_excl`)
- `software.platform`
- `presentation_hints` salvo `display_tax`, `prices_entered_with_tax`, `rounding_mode`, `locale` y `order_barcode_type`
- identificadores fiscales del cliente de tipo alemán, neerlandés, francés, de empresa del Reino Unido y suizo
- claves que un plugin añade fuera de `order`, `store`, `cashier` y `customer`; consulte [Ampliar los datos del recibo](#extending)

</AccordionItem>
</Accordion>

## Versiones {#versions}

Los datos del recibo tienen su propio número de versión, independiente del plugin. Los recibos antiguos, como una instantánea fiscal capturada antes de que existiera un campo, carecen de los campos más recientes; por eso deben condicionarse con una sección.

| Versión | Incorporaciones |
|---------|-------|
| 1.1 | Precio normal, precio de venta y ahorro de cada artículo, y totales de ahorro del pedido, incluido **Total ahorrado**. Ninguno modifica los totales del pedido ni los informes de WooCommerce |
| 1.2 | `discounts[].discount_type` |
| 1.3 | `customer.first_name` y las etiquetas de visualización del cliente en `i18n` |
| 1.4 | `register`, `software`, los campos del documento fiscal (`fiscal.document_type`, los indicadores `is_…`, `sale_time`, `received_at`, `sale_tz`, `sale_counter`, `corrects`) y sus etiquetas `i18n` |
