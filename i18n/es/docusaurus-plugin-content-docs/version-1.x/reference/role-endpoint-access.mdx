Esta página documenta qué endpoints REST de WCPOS son accesibles para cada uno de los tres roles predeterminados utilizados en los flujos de trabajo del POS:

- `administrator`
- `shop_manager`
- `cashier`

Para configurar los roles y las capacidades desde la interfaz de usuario, consulte [Acceso al POS](/1.x/settings/wp-admin/access).

## Resumen {#summary}

El modelo de acceso predeterminado es:

- **`administrator`** — acceso completo al POS y a la gestión.
- **`shop_manager`** — acceso completo al POS y a la gestión, excepto las acciones de extensión de plugins que requieren capacidades de instalación de plugins.
- **`cashier`** — acceso normal al flujo de trabajo de venta del POS, pero sin acceso a la gestión, los ajustes, los registros ni la administración de la tienda.

La matriz de endpoints se verifica mediante pruebas de integración que utilizan la misma ruta de autenticación que la aplicación POS (tokens de acceso de portador de WCPOS, no solo `wp_set_current_user()`). Las aserciones sobre los endpoints permitidos confirman que un rol no recibe `401` ni `403`. Algunos endpoints pueden devolver datos normales o errores de negocio como `400` o `404` cuando la prueba utiliza un conjunto mínimo de datos de prueba; esas respuestas también demuestran que el usuario superó la capa de autenticación y permisos.

## Cobertura de expiración de tokens {#token-expiry-coverage}

| Escenario | Administrador | Gestor de la tienda | Cajero | Resultado esperado |
|---|---:|---:|---:|---|
| Token de acceso válido | ✅ probado | ✅ probado | ✅ probado | Los endpoints permitidos no devuelven `401` ni `403` |
| Token de acceso expirado | ✅ probado | ✅ probado | ✅ probado | La solicitud falla en el control de autenticación de WCPOS con el usuario `0` |
| Token de actualización válido tras expirar el de acceso | ✅ probado | ✅ probado | ✅ probado | Se emite un nuevo token de acceso y se restablece el acceso |
| Token de actualización expirado | ✅ probado | ✅ probado | ✅ probado | No se puede generar un nuevo token de acceso |

## Diagnóstico de fallos {#diagnosing-failures}

Si un `shop_manager` con la configuración predeterminada ve un error como:

> La solicitud sigue sin autorización después de actualizar el token; vuelva a iniciar sesión

La matriz de endpoints indica que esto **no** se debe a que el rol `shop_manager` predeterminado carezca de acceso al POS por definición. Causas probables que conviene investigar:

1. Corrupción de roles o capacidades específica del sitio.
2. Un endpoint no cubierto por la matriz.
3. Comportamiento del cliente al reintentar con un token de acceso obsoleto o expirado.
4. Interferencia de un plugin de seguridad o autenticación de terceros.
5. Reglas de acceso Pro o específicas de la tienda, o código personalizado.

### Fallo de permisos frente a fallo de token {#permission-failure-vs-token-failure}

La interfaz del POS puede mostrar el mismo error de actualización de token en ambos casos tras recibir un `401` o `403`, intentar actualizar el token y comprobar que el reintento sigue sin estar autorizado. Los dos tipos de fallo presentan diferencias en el servidor:

Un **fallo real de rol o capacidad** suele tener este aspecto:

```text
status: 403
current_user: <actual user id>
access token expired: false
```

Un **fallo de token o autenticación** suele tener este aspecto:

```text
status: 403
current_user: 0
access token expired: true or invalid
```

Utilice esta distinción al diagnosticar problemas de acceso al POS: un `current_user` distinto de cero apunta a las capacidades, mientras que `current_user: 0` apunta a la capa de autenticación y tokens.
