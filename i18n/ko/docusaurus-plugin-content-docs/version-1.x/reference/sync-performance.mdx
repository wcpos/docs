:::info v1.10.0 신규 기능
이 페이지는 **WCPOS v1.10.0**에서 도입된 동기화 엔진을 설명합니다. 엔진의 기술적인 작동 방식은 [동기화 엔진의 작동 방식](/1.x/reference/sync-engine)에서 먼저 확인하세요.
:::

대부분의 WCPOS 매장은 공유 PHP 호스팅에서 운영됩니다. 소수의 PHP 워커를 사용하고, 모든 REST 요청마다 WordPress 전체 초기화가 이루어지며, 보안 플러그인이 순간적인 요청 폭주를 제한하는 환경입니다. 클라이언트가 비용이 없다고 여기는 요청은 온라인 매장을 느리게 하고 요청 제한을 유발하며 캐셔의 트래픽과 자원을 두고 경쟁합니다. 이러한 부하는 실행 중인 모든 계산대와 브라우저 탭 수만큼 늘어납니다.

v1.10.0 동기화 엔진은 이를 사후 고려 사항이 아닌 설계 제약으로 다룹니다. **판매자의 호스팅을 보호하는 것도 동기화 엔진의 역할입니다.** 이 페이지에서는 엔진이 따르는 규칙과 그 근거가 되는 측정값을 설명합니다.

## 항상 적용되는 네 가지 규칙 {#the-four-rules}

엔진의 모든 예약 동기화 동작은 네 가지 불변식을 따릅니다:

1. **비용은 카탈로그 크기가 아니라 변경된 양에 비례합니다.** 대량 가져오기 전에는 항상 비용이 적은 다이제스트나 조기 종료 확인을 수행합니다. 변경 사항이 없는 제품 50,000개 매장을 동기화 상태로 유지하는 비용은 변경 사항이 없는 제품 500개 매장과 거의 같습니다.
2. **요청을 무제한으로 늘리지 않습니다.** 모든 백그라운드 레인은 실행당 요청 상한을 선언하고 자동화된 테스트로 이를 강제합니다. 큰 작업은 재개 가능한 커서를 사용해 크기가 제한된 배치로 실행되므로 전체 순회가 한꺼번에 몰리지 않고 실행 일정에 걸쳐 분산됩니다.
3. **유지 관리는 캐셔를 방해하지 않습니다.** 계산대가 판매를 시작할 수 있게 하는 요청이 먼저 실행되고 무결성 감사와 백그라운드 사전 준비 작업은 이후 유휴 시간에 실행됩니다.
4. **부하가 걸리면 유지 관리부터 늦춥니다.** 서버가 부하 신호를 보내면 엔진은 캐셔가 사용하는 기능에 영향을 주기 전에 자체 백그라운드 작업부터 늦춥니다.

## 동기화가 서버에 주는 비용 {#request-budgets}

정상 상태의 비용은 **매장 상태 → 성능**에서 기기별로 선택하는 **동기화 프리셋**이 결정합니다:

| 프리셋 | 확인 간격 | 요청당 레코드 수 | 하루 명목 확인 횟수 |
| --- | --- | --- | --- |
| 에코 | 5분 | 25 | 288 |
| 균형(기본값) | 60초 | 50 | 1,440 |
| 실시간 | 10초 | 75 | 8,640 |

두 설정 모두 중요하며 공유 호스팅에 실제 부담을 주는 것은 대개 페이지 크기입니다. 레코드가 많은 페이지는 서버 처리 시간을 소모하고 확인 빈도가 높을수록 그 비용도 늘어납니다. 최대치인 100개 레코드 페이지를 사용하는 프리셋은 없습니다. 이 값은 사용자 지정 슬라이더(간격 5초–5분, 레코드 10–100개)로만 설정할 수 있습니다.

프리셋 외에 다음 사항이 적용됩니다:

- **유휴 상태의 확인은 비용이 적습니다.** 엔진이 조건부 요청을 보내므로 변경 사항이 없으면 본문 없는 `304 Not Modified` 하나로 응답합니다. 여전히 요청 한 건이지만 페이로드가 없고 서버 작업도 최소화됩니다.
- **확인 간격에는 ±20%의 지터가 적용되므로** 여러 계산대의 요청이 동시에 몰리지 않고 분산됩니다.
- **유휴 계산대에는 감쇠가 적용되어** 10분 동안 조작이 없으면 주기가 느려지고, 바코드 스캔을 포함한 활동이 발생하면 즉시 원래 주기로 돌아옵니다.
- **백그라운드 유지 관리에는 상한이 있습니다.** 편차가 없는 무결성 확인에는 비용이 적은 집계 페이지 몇 개만 필요하며 상세 조회는 **전혀** 하지 않습니다. 서버와 일치한다고 확인된 버킷은 아예 건너뜁니다. 편차가 발견되면 상세 조회는 **실행당 두 건**으로 제한하고 저장된 커서로 이어서 처리하므로 요청이 한꺼번에 몰리지 않습니다. 전체 삭제 감사는 **실행당 11건의 요청**, 다이제스트 사전 준비는 실행당 5개 청크로 제한됩니다. 이 상한은 코드에 선언되어 있으며 CI에서 강제됩니다.

:::note 앱에 표시되는 ‘하루 요청 수’는 명목값입니다
매장 상태는 설정된 간격을 바탕으로 *하루 약 N건의 요청* 추정치를 산출합니다. 이를 상한이나 예측치가 아닌 명목 확인 빈도로 이해하세요. ±20% 지터로 인해 실제 횟수가 늘거나 줄 수 있으며 `304`도 요청 한 건으로 계산됩니다. 유휴 감쇠는 최소 간격인 60초보다 빠른 프리셋에서만 횟수를 줄이며 기본값인 균형 프리셋을 더 느리게 하지는 않습니다.
:::

## 서버 부하 시 백오프 {#server-pressure}

엔진이 받는 모든 응답은 매장별 부하 모니터에 전달됩니다. 모니터는 다음에 반응합니다:

- HTTP `429`(즉시),
- 반복되는 `5xx` 오류 또는 전송 실패(최근 일 분 동안 세 번),
- 지속적인 지연(응답 시간 중앙값이 2초 초과),
- 다음 확인까지의 최소 대기 시간으로 강제 적용되는 `Retry-After` 헤더.

이 중 하나라도 감지되면 엔진은 단계적으로 **변경 확인 간격을 두 배로 늘리고** 유지 관리 레인은 실행을 완전히 건너뜁니다. 검색, 바코드 조회, 결제 등 캐셔가 유발하는 요청은 제한하지 않습니다. 판매를 늦추지 않고 미룰 수 있는 부하를 줄이는 것이 목적입니다.

복구 방식은 의도적으로 비대칭입니다. 백오프는 즉시 적용되지만 **연속으로 정상 응답을 열 번** 받은 뒤에야 간격을 단계적으로 줄입니다. 따라서 불안정한 서버가 빠른 주기와 느린 주기 사이를 오가지 않습니다. 판매자가 더 빠른 프리셋을 선택해도 부하 상태는 유지됩니다. 보호 기능은 어떤 단계를 설정해도 그 아래에서 작동하며 설정으로 끌 수 없습니다.

## 기기의 응답성 유지 {#device-responsiveness}

성능의 나머지 절반은 계산대 자체입니다. 백그라운드 동기화 때문에 UI가 끊겨서는 안 됩니다.

- **감사는 이벤트 루프에 양보합니다.** 무결성 감사는 작업을 여러 청크로 나누고 청크 사이에 실행을 양보하여 중단 없이 실행되는 가장 긴 구간을 약 **30 ms**로 유지합니다. 이는 사람이 지연을 느끼는 약 100 ms 임계값보다 짧습니다. 로컬 제품 10,000개에서 측정한 전체 감사의 연산 시간은 약 **68 ms**이며 17회 이상 실행을 양보하며 분산 처리합니다. 제품 50,000개에서는 300 ms 미만입니다.
- **부하가 있어도 첫 결과는 빠르게 나옵니다.** 대량 적용이나 전체 감사가 동시에 실행되는 중에도 첫 결과까지의 시간 기준을 CI에서 고정해 검증합니다. 벤치마크 환경의 일반적인 카탈로그 크기에서는 한 자릿수 밀리초입니다.
- **화면에 보이는 페이지만 앱으로 전달됩니다.** 필터, 정렬, 페이지 처리 같은 쿼리 작업은 저장소 계층 내부에서 실행되므로 화면 업데이트 시 만 개가 아니라 열 개의 행만 전달합니다.

이 수치는 CI에서 격리 실행되는 엔진의 고정 성능 기준 테스트 모음에서 나온 것입니다. 허용 한도는 정상 상태의 실측값보다 약 열 배 높게 설정되어 있습니다. 느린 실행 환경에서 실패하게 하려는 것이 아니라 성능이 자릿수 단위로 악화되는 회귀를 잡아내기 위한 설계입니다.

## 실제 매장에서 검증 {#live-verification}

서버를 배려하는 규칙은 단위 테스트로만 확인하지 않습니다. 실제 WordPress 매장을 대상으로 한 종단 간 검증을 통해 실제 호스팅에서 가장 중요한 불변식을 확인합니다:

- 매장을 열 때 제품 카탈로그가 표시되기 전에는 유지 관리 요청(무결성 또는 다이제스트 트래픽)이 **전혀 없습니다**.
- 매장을 연 직후 대기 시간이 지난 뒤에도 비용이 적은 집계 페이지 몇 개와 최대 두 건의 상세 조회만 발생합니다.

이 시나리오는 실제 회귀 문제를 바탕으로 만들어졌습니다. 이전 개발 빌드의 감사는 매장을 열 때마다 기기당 약 41건(1.2 MB)의 요청을 보냈습니다. 이를 대체한 다이제스트 기반 설계에서는 편차가 없는 감사에 집계 페이지만 필요합니다. 이제 이런 유형의 버그는 검토자의 주의력에 의존하지 않고 CI에 선언된 상한으로 방지합니다.

## 주장하지 않는 내용 {#honest-limits}

아직 근거를 제시할 수 있는 수치가 없어 이 페이지에서 의도적으로 언급하지 않는 내용이 있습니다:

- **‘초기 동기화에 X분 걸린다’는 전체 소요 시간 수치는 없습니다.** 초기 다운로드 시간은 주로 서버 응답 시간과 카탈로그 크기에 좌우됩니다. 기기에서 레코드를 적용하는 비용은 적으며(제품 10,000개를 일괄 적용하는 연산 시간은 10 ms 미만으로 측정됩니다), 대부분의 시간은 네트워크와 서버에서 소요됩니다.
- **‘v1.9보다 X% 빠르다’고 주장하지 않습니다.** 두 아키텍처의 차이가 커서 하나의 비교 수치는 정보를 전달하기보다 오해를 부를 수 있습니다. 구조적 차이는 [v1.10.0에서 달라진 점](/1.x/reference/sync-engine#what-changed-in-v1100)에 정리되어 있습니다.
- 위 벤치마크 수치는 엔진의 테스트 환경(메모리 내 저장소, 격리된 실행 환경)에서 얻은 값입니다. 실제 기기와 매장마다 결과가 다르므로 **매장 상태 → 성능**에서는 예상치 대신 지난 24시간 동안 계산대의 실제 요청 수와 일반적인 응답 시간을 보여 줍니다. 크기가 명시되지 않은 응답은 데이터량에 영으로 반영되므로 표시되는 데이터량은 하한값입니다.

호스팅 요구 사항, HPOS, 캐싱, 느린 응답 진단 등 서버 측 조정은 [서버 성능](/1.x/support/performance/server)을 참조하세요.
