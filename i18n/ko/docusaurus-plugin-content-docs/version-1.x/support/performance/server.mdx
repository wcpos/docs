서버 성능은 WCPOS 애플리케이션의 속도와 반응성에 직접적인 영향을 미칩니다. POS는 많은 REST API 호출을 수행하므로 **서버 응답 시간이 주요 병목 지점**이며, POS 속도는 호스팅 품질에 크게 좌우됩니다. 이 가이드는 내장 메트릭과 문제 해결 기법을 활용하여 서버 성능을 모니터링, 진단 및 최적화하는 방법을 설명합니다.

## 최소 서버 요구 사항 {#minimum-server-requirements}

운영 환경에서 POS가 빠르게 반응하도록 다음과 같은 최소 사양을 권장합니다:

<RequirementsList>
  <RequirementItem label="CPU">CPU 코어 4개 이상</RequirementItem>
  <RequirementItem label="RAM">4 GB 이상</RequirementItem>
  <RequirementItem label="PHP">PHP 7.4+ (8.x 권장)</RequirementItem>
  <RequirementItem label="데이터베이스">MySQL 8.0+ 또는 MariaDB 11.x</RequirementItem>
  <RequirementItem label="스토리지">SSD 또는 NVMe</RequirementItem>
  <RequirementItem label="SSL">HTTPS는 필수입니다 — HTTPS 없이는 WooCommerce REST API가 작동하지 않습니다</RequirementItem>
</RequirementsList>

:::warning 공유 호스팅만으로는 부족한 경우가 많습니다
공유 호스팅은 많은 API 호출을 동시에 수행하는 POS 작업을 처리하기에 PHP 워커 수와 메모리가 부족한 경우가 많습니다. 실제 운영에 POS를 사용한다면 **VPS 또는 관리형 WordPress 호스트**를 강력히 권장합니다. `WordPress.com` 관리형 호스팅에도 REST API 호환성 문제가 있는 것으로 알려져 있습니다(일부 사용자에게는 대규모 카탈로그의 상품 중 9–10개만 표시됩니다). 완전한 호환성을 위해 자체 호스팅 `WordPress.org`를 권장합니다.
:::

### 커뮤니티에서 검증한 최적화 구성 {#community-validated-optimisation-stack}

사용자들은 다음 조합에서 POS 성능이 가장 좋다고 보고합니다:

- **MariaDB 11.4** (WooCommerce 작업 처리 시 MySQL보다 빠름)
- **HPOS 활성화** (아래 참조)
- **LiteSpeed 또는 Redis** 객체 캐싱
- **NVMe** 스토리지
- **PHP OPcache** 활성화

## 503 오류 {#503-errors}

:::important 503 오류는 항상 서버 측 문제입니다
`503 Service Unavailable`은 **POS 버그가 아닙니다** — 서버가 요청을 처리하지 못했다는 뜻입니다. 다음을 확인하세요:

1. 서버 부하 및 가용 리소스
2. PHP 워커 (가용 워커가 모두 소진되었을 수 있음)
3. PHP 메모리 제한 — **256 MB 이상**으로 늘리세요
4. 웹 호스트의 서버 로그 (호스트에 문의하세요. 애플리케이션에서 확인할 수 없는 정보도 호스트는 확인할 수 있습니다)
:::

## WooCommerce 버전 호환성 {#woocommerce-version-compatibility}

WooCommerce 업데이트로 POS가 작동하지 않는 경우가 있습니다. 항상 [스테이징 사이트](/1.x/support/troubleshooting/plugin-conflicts#before-you-start-use-a-staging-site)에서 먼저 WooCommerce를 업데이트하고, 최신 호환성 수정 사항이 포함되도록 WCPOS를 최신 상태로 유지하세요.

알려진 문제:

- **WooCommerce 10.5.0** — POS에서 상품 로딩이 손상됨(증상: 약 10개 상품만 표시됨, 바코드 스캔 및 검색이 작동 중지) 및 **postmeta 부풀림**과 메모리 소진을 유발할 수 있는 실험적 상품 캐시를 도입함. **해결책:** WCPOS를 최신 버전으로 업데이트(수정 사항 및 정리 마이그레이션 포함)하거나 WooCommerce를 [10.4.3](https://downloads.wordpress.org/plugin/woocommerce.10.4.3.zip)으로 롤백하세요.

WooCommerce 업데이트 후 POS가 작동하지 않으면 플러그인의 WordPress.org 페이지에 있는 **고급** 탭에서 WooCommerce를 이전 버전으로 되돌리고 문제를 보고하세요.

## 서버 메트릭 이해하기 {#understanding-server-metrics}

WCPOS는 데이터를 가져오는 작업(상품, 주문, 고객 등)을 수행할 때마다 서버 성능 메트릭을 자동으로 수집합니다.

**v1.10.0**부터 집계 보기는 **매장 상태 → 성능**에서 확인할 수 있습니다. 지난 24시간 동안의 요청 수, 전송된 데이터, 일반적인 응답 시간과 시간별 가동 시간 표시줄을 제공합니다([매장 상태](/1.x/support/store-health#performance) 참조). 해석할 때는 두 가지에 유의하세요. 전송된 데이터 수치는 하한값입니다(크기를 명시하지 않은 응답은 집계에 포함되지 않습니다). 동기화 다이얼 옆의 *하루 약 N건의 요청* 추정치는 설정된 간격에서 산출한 명목상의 빈도이며, 상한이나 실제 요청 수가 아닙니다. 지터에 따라 요청 수는 늘거나 줄 수 있고, `304`도 요청으로 계산됩니다. 유휴 상태에서의 빈도 감소는 60초보다 간격이 짧은 프리셋에서만 요청 수를 줄입니다. 개별 요청 메트릭은 **매장 상태 → 로그**에서 확인할 수 있습니다.

### 일반적인 서버 메트릭 {#typical-server-metrics}

```json
{
  "total": "24692",
  "execution_time": "76.64 ms",
  "server_load": "[15.20605469,16.16357422,16.76806641]"
}
```

**세부 사항:**
- **`total`** - 처리된 레코드 수 (상품 ID 24,692개)
- **`execution_time`** - 작업 완료에 걸린 시간 (76.64밀리초)
- **`server_load`** - 1, 5, 15분 동안의 서버 부하 평균

## 서버 부하 설명 {#server-load-explained}

서버 부하는 각 시간 구간의 평균 시스템 부하를 나타냅니다:

- **첫 번째 값** - 1분 평균 (15.21)
- **두 번째 값** - 5분 평균 (16.16)
- **세 번째 값** - 15분 평균 (16.77)

### 부하 해석 {#load-interpretation}

서버 부하 값은 오해의 소지가 있으므로 주의 깊게 해석해야 합니다:

:::warning 부하 값은 오해의 소지가 있습니다
서버 부하 평균이 항상 성능과 직접적인 관계가 있는 것은 아닙니다. 부하 값이 높은 서버(15+)도 리소스가 충분하고 잘 최적화되어 있다면 매우 빠르게 반응할 수 있습니다. **부하 값만 보지 말고 실행 시간에 중점을 두세요.**
:::

**일반 지침:**
- **CPU 코어 수 대비 부하** - 8코어 서버에서 부하가 8.0이면 처리 용량을 모두 사용하고 있다는 뜻입니다
- **지속적인 부하와 일시적인 부하** - 잠깐 급증하는 것은 정상이지만, 높은 부하가 지속되면 문제가 있을 수 있습니다
- **성능이 더 중요함** - 부하가 높아도 빠르게 반응하는 서버가 부하는 낮지만 느린 서버보다 낫습니다

**주의해서 살펴볼 사항:**
- 시간이 지날수록 **실행 시간이 증가함**
- 뚜렷한 이유 없이 **부하가 지속적으로 증가함**
- **높은 부하와 긴 실행 시간**이 동시에 나타남

## 성능 기준 {#performance-benchmarks}

### 실행 시간 지침 {#execution-time-guidelines}

| 작업 | 우수 | 허용 가능 | 나쁨 | 심각 |
|-----------|------|------------|------|----------|
| **상품 가져오기** | < 100ms | 100-500ms | 500ms-2s | > 2s |
| **주문 생성** | < 200ms | 200-800ms | 800ms-3s | > 3s |

### 레코드 수 고려 사항 {#record-count-considerations}

레코드 수가 늘어날 때 실행 시간도 합리적인 수준으로 증가해야 합니다:

```json
// Good scaling examples
{"total": "100", "execution_time": "15.2 ms"}    // 0.15ms per record
{"total": "1000", "execution_time": "89.4 ms"}   // 0.09ms per record
{"total": "10000", "execution_time": "234.1 ms"} // 0.02ms per record

// Poor scaling examples
{"total": "100", "execution_time": "500.0 ms"}   // 5.0ms per record
{"total": "1000", "execution_time": "8000.0 ms"} // 8.0ms per record
```

## 성능 문제 진단하기 {#diagnosing-performance-issues}

### 단계 1: 로그 모니터링 {#step-1-monitor-the-logs}

1. 내비게이션 서랍에서 **매장 상태**를 열고 **성능** 탭에서 24시간 현황을 확인하세요(일반적인 응답 시간이 핵심 수치입니다)
2. 느린 작업을 수행하세요(상품 동기화, 주문 생성 등)
3. **로그** 탭에서 해당 항목을 찾으세요
4. 행을 펼쳐 메트릭을 확인하세요

### 단계 2: 메트릭 분석 {#step-2-analyse-the-metrics}

**긴 실행 시간 + 높은 서버 부하 = 서버 리소스 문제**
```json
{
  "total": "5000",
  "execution_time": "3500.0 ms",
  "server_load": "[12.45, 11.23, 10.87]"
}
```
*해결책: 서버 리소스를 늘리거나 서버 구성을 최적화하세요*

**긴 실행 시간 + 정상 서버 부하 = 플러그인/데이터베이스 문제**
```json
{
  "total": "1000",
  "execution_time": "2800.0 ms",
  "server_load": "[1.23, 1.45, 1.67]"
}
```
*해결책: 느린 플러그인을 찾거나 데이터베이스 쿼리를 최적화하세요*

**정상 실행 시간 + 높은 서버 부하 = 전반적인 서버 과부하**
```json
{
  "total": "2000",
  "execution_time": "150.0 ms",
  "server_load": "[8.90, 9.12, 8.45]"
}
```
*해결책: 다른 프로세스가 유발하는 서버 부하를 줄이거나 리소스를 업그레이드하세요*

## 일반적인 성능 문제 {#common-performance-problems}

### 1. 서버 리소스 부족 {#1-insufficient-server-resources}

**증상:**
- 지속적으로 높은 서버 부하 (대부분의 서버에서 > 4.0)
- 모든 작업에서 긴 실행 시간
- 잦은 시간 초과

**해결책:**
- **CPU 업그레이드** - 코어가 많을수록 동시 요청을 더 잘 처리합니다
- **RAM 증설** - 디스크 I/O를 줄이고 캐싱 성능을 개선합니다
- **SSD 스토리지 사용** - 데이터베이스 성능을 크게 향상합니다
- **PHP 설정 최적화** - memory_limit, max_execution_time을 늘리세요

### 2. 느린 데이터베이스 쿼리 {#2-slow-database-queries}

**증상:**
- 정상 서버 부하에서도 긴 실행 시간
- 상품/주문 가져오기가 특히 느림
- 로그에 데이터베이스 관련 오류 코드가 나타남

**해결책:**
- **WooCommerce HPOS 활성화** - 데이터베이스 성능을 가장 크게 개선하는 방법입니다
- **객체 캐싱 사용** - 호스트에서 제공한다면 Redis 또는 Memcached를 사용하세요
- **WordPress를 최신 상태로 유지** - 코어 업데이트에는 데이터베이스 최적화가 포함되는 경우가 많습니다
- **게시물 수정본 수 제한** - wp-config.php에 `define('WP_POST_REVISIONS', 3);`를 추가하세요

### 3. 플러그인 간섭 {#3-plugin-interference}

**증상:**
- 플러그인 업데이트 후 갑작스러운 성능 저하
- 특정 작업이 다른 작업보다 훨씬 느림
- 정상 서버 부하에서도 긴 실행 시간

**문제 해결:**
1. **스테이징에서 테스트** - WooCommerce와 WCPOS를 제외한 모든 플러그인을 비활성화하세요
2. **기준 측정** - 최소한의 플러그인만 활성화한 상태에서 실행 시간을 기록하세요
3. **점진적으로 활성화** - 플러그인을 하나씩 추가하여 문제의 원인을 찾으세요
4. **플러그인 훅 확인** - WooCommerce 작업에 훅을 연결하는 플러그인을 확인하세요

**문제를 자주 일으키는 플러그인:**
- 상품 관련 작업 중 부하가 큰 SEO 플러그인
- 복잡한 재고 관리 시스템
- 실시간 분석/추적 플러그인
- 코드 품질이 낮은 사용자 지정 플러그인

### 4. WordPress/WooCommerce 구성 {#4-wordpresswoocommerce-configuration}

**증상:**
- 일관되지 않은 성능
- 로그에 메모리 관련 오류가 나타남
- 느린 관리자 대시보드

**최적화 체크리스트:**
- **PHP 버전** - 성능 향상을 위해 PHP 8.0+를 사용하세요
- **WooCommerce HPOS** - 고성능 주문 저장소를 활성화하세요(아래 참조)
- **WordPress 캐싱** - 사용할 수 있다면 객체 캐싱을 활성화하세요
- **WooCommerce 설정** - 상품 이미지 크기를 최적화하세요

### WooCommerce 고성능 주문 저장소(HPOS) {#woocommerce-high-performance-order-storage-hpos}

:::tip 가장 큰 성능 향상
**HPOS는 WooCommerce 성능을 가장 크게 개선할 수 있는 방법 중 하나입니다.** 주문을 WordPress 게시물 테이블 대신 전용 데이터베이스 테이블에 저장하여 주문이 많은 매장의 성능을 크게 향상합니다.
:::

**이점:**
- **더 빠른 주문 쿼리** - 최적화된 데이터베이스 구조에 주문을 저장합니다
- **데이터베이스 부하 감소** - 주문을 게시물/페이지와 분리합니다
- **향상된 확장성** - 많은 주문을 효율적으로 처리합니다
- **관리자 성능 개선** - 주문 관리 화면이 더 빠르게 작동합니다

**활성화 방법:**
1. `WooCommerce > 설정 > Advanced > Features`으로 이동하세요
2. "고성능 주문 저장소"를 활성화하세요
3. 마이그레이션 절차를 따르세요(단계별 안내: [HPOS로 전환](/1.x/support/performance/order-storage#switch-to-hpos))

**자세히 알아보기:**
- [WooCommerce HPOS 문서](https://woocommerce.com/document/high-performance-order-storage/)
- [HPOS 마이그레이션 가이드](https://woocommerce.com/document/high-performance-order-storage/#section-3)

## 서버 모니터링 모범 사례 {#server-monitoring-best-practices}

### 1. 정기적인 성능 점검 {#1-regular-performance-checks}

- **주간 검토** - 로그에서 성능 추세를 확인하세요
- **기준 측정** - 정상적인 실행 시간을 기록하세요
- **피크 시간 모니터링** - 트래픽이 많은 시간대에 모니터링하세요

### 2. 성능 경고 설정 {#2-set-performance-alerts}

다음 경고 신호를 살펴보세요:
- 실행 시간이 지속적으로 > 1000ms
- 서버 부하가 장시간 > 5.0
- 로그에 시간 초과 오류가 자주 나타남

### 3. 용량 계획 {#3-capacity-planning}

증가 추세를 추적하세요:
- **레코드 수 증가** - 상품, 주문, 고객
- **성능 저하** - 데이터가 늘어날 때 실행 시간이 어떻게 증가하는지
- **리소스 사용률** - CPU, 메모리, 디스크 사용량

## 서버 최적화 전략 {#server-optimisation-strategies}

### 1. WordPress/WooCommerce 모범 사례 {#1-wordpresswoocommerce-best-practices}

**HPOS 활성화:**
- WooCommerce 성능을 가장 크게 개선하는 방법입니다
- 자세한 내용은 위의 HPOS 섹션을 참조하세요

**PHP 구성 (호스트에 문의하세요):**
```ini
memory_limit = 512M
max_execution_time = 300
max_input_vars = 3000
```

**WordPress 구성:**
```php
// In wp-config.php - limit post revisions
define('WP_POST_REVISIONS', 3);

// Enable WordPress debug logging if needed
define('WP_DEBUG_LOG', true);
```

### 2. 호스팅 수준의 최적화 {#2-hosting-level-optimizations}

**객체 캐싱:**
- Redis 또는 Memcached를 사용할 수 있는지 호스트에 문의하세요
- 많은 관리형 WordPress 호스트가 이를 자동으로 제공합니다

**PHP 버전:**
- 성능을 크게 향상하려면 PHP 8.0+를 사용하세요
- 대부분의 호스트에서는 PHP 버전을 쉽게 전환할 수 있습니다

**서버 리소스:**
- 충분한 RAM을 확보하세요(최소 1GB, 권장 2GB+)
- SSD 스토리지는 기존 드라이브보다 훨씬 뛰어난 데이터베이스 성능을 제공합니다

## 호스팅별 참고 사항 {#hosting-specific-notes}

일부 호스트와 CDN에서는 POS가 WooCommerce REST API에 접근할 수 있도록 설정해야 합니다:

| 호스트 / 서비스 | 문제 | 해결책 |
| --- | --- | --- |
| **GoDaddy** | 웹사이트 방화벽이 `/wp-json/` REST API 호출을 차단함(_"'undefined'를 수신했습니다"_ 같은 오류) | `Website Security > Firewall > 설정 > Access Control > Allow URL Paths` → `/wp-json/` 추가 |
| **WP Engine** | REST API를 명시적으로 활성화해야 함 | REST API를 활성화하고, 필요한 경우 방화벽의 허용 목록에 API 엔드포인트 추가 |
| **Cloudflare** | 보안 검사(봇 차단 모드, 공격 방어 모드, WAF 챌린지)가 REST API 요청을 차단하며, 캐시가 오래된 API 응답을 제공할 수 있음 | [Cloudflare 가이드](/1.x/support/troubleshooting/cloudflare)에 따라 `/wp-json/`에 대한 WAF **건너뛰기** 규칙과 같은 경로에 대한 **캐시 우회** 규칙 추가 |
| **WordPress.com** | REST API / 상품 로딩 호환성 문제(상품이 9–10개만 표시됨) | 완전한 호환성을 위해 자체 호스팅 WordPress.org 사용 |
| **공유 호스팅** | 동시 POS 호출을 처리하기에 PHP 워커 수 / 메모리가 부족함 | VPS 또는 관리형 WordPress 호스트로 이전 |

보안 플러그인(Wordfence 등)도 비슷한 방식으로 REST API를 차단할 수 있습니다. 전체 목록과 해결책은 [플러그인 충돌](/1.x/support/troubleshooting/plugin-conflicts)을 참조하세요.

### HTTP 414 — URI가 너무 깁니다 {#http-414-uri-too-long}

장바구니에 담긴 항목이 많거나 결제 URL에 액세스 토큰이 포함된 경우 서버의 URL 길이 제한을 초과할 수 있습니다(결제 요청은 `GET`을 사용합니다). 특정 브라우저에서만 발생할 수도 있으며, 브라우저 캐시 때문에 문제가 더 심해질 수 있습니다.

**해결 방법:** 먼저 브라우저 캐시를 지운 다음 서버의 URL 길이 제한을 늘리세요:

- **Apache:** `httpd.conf`에 `LimitRequestLine 65536` 설정
- **Nginx:** `nginx.conf`에 `large_client_header_buffers 4 65536;` 설정
- 설정에 접근할 수 없다면 호스팅 제공업체에 조정을 요청하세요.

## 도움을 요청해야 할 때 {#when-to-seek-help}

다음과 같은 경우 호스팅 제공업체 또는 WordPress 개발자에게 문의하세요:

- 최적화했는데도 **서버 부하가 지속적으로 > 8.0**
- 간단한 작업의 **실행 시간이 > 5000ms**
- 로그에 **메모리 오류**가 자주 나타남
- **데이터베이스 쿼리 소요 시간이 지속적으로 > 2초**

다음 정보를 제공하세요:
- 로그의 서버 메트릭
- 활성 플러그인 목록
- 서버 사양 (CPU, RAM, 스토리지 유형)
- WordPress 및 WooCommerce 버전
