모든 계산대는 하루 종일 WordPress 사이트와 통신하며 변경 사항을 확인하고, 판매 내역을 전송하고, 캐셔가 조회하는 정보를 가져옵니다. 서버의 응답 속도가 POS의 체감 속도를 결정합니다. 서버가 버거워하면 각 계산대는 자체적으로 확인 빈도를 낮추고 자동으로 복구합니다. 이 페이지에서는 이러한 동작을 어디에서 확인할 수 있는지, 무엇을 의미하는지, 호스팅에서 무엇을 변경해야 하는지 설명합니다.

화면에 표시된 내용 때문에 이 페이지를 찾으셨나요?

- **시간에 따른 서버 상태** 아래에 [**확인 빈도 낮춤** 또는 **…까지 일시 중지**](#pace)가 표시됩니다. 판매는 계속할 수 있습니다. 백그라운드 확인만 느려지므로 다른 계산대의 변경 사항이 표시되기까지 더 오래 걸릴 수 있습니다. 거의 매일 표시된다면 먼저 [부하가 더 적은 사전 설정을 선택하세요](#fix).
- [**503**, **429** 또는 **414** 오류](#503-errors)가 발생합니다. 각 코드에 대한 간단한 설명이 먼저 나오며, 웹사이트 관리자를 위한 자세한 내용은 그 아래에 접혀 있습니다.
- [모든 계산대에서 검색과 판매 처리가 느립니다](#fix). 확인 빈도를 낮추는 기능은 검색과 판매 속도에 영향을 주지 않으므로 계산대보다 서버를 먼저 살펴보세요. 웹사이트 관리자에게 [호스팅 업체에 전달할 정보](#when-to-seek-help)를 전달하세요.

## 서버의 처리 상태 확인하기 {#store-health}

메뉴 하단의 맥박 아이콘에서 **매장 상태**를 연 다음 **성능**을 선택하세요. 수치는 현재 계산대에만 해당합니다.

<JourneyShot manifest={manifest} device="tablet" step={1} offsets={[[50, 0], [160, 0], [370, 0], [480, 26], [180, 0], [470, 0]]} alt="매장 상태의 성능 탭: 지난 24시간의 요청, 데이터, 일반적인 응답 시간을 보여 주는 상태 표시줄, 시간별 가동 상태 막대, 절약·균형·실시간 사전 설정">

1. **매장 상태** — 메뉴 하단의 맥박 아이콘입니다.
2. **성능** — 현재 계산대가 매장을 확인하는 빈도와 서버의 처리 상태를 보여 줍니다.
3. **지난 24시간** — **정상**은 현재 계산대가 온라인 상태이며 동기화 중임을 뜻합니다. 그다음에는 요청, 데이터, 밀리초 단위의 **일반적인 응답 시간**이 표시됩니다. 여기서 2347은 약 2.3초입니다. 거의 매일 2000을 넘는다면 [호스팅 업체에 전달할 정보](#when-to-seek-help)에 포함하세요.
4. **엔진 가동 시간** — 셀 하나가 한 시간에 해당합니다. 황색은 해당 시간에 요청이 하나 이상 실패했다는 뜻입니다. 셀 위에 마우스를 올리거나 셀을 탭하면 횟수를 볼 수 있습니다.
5. **절약** — **균형**, **실시간**과 함께 제공되는 세 가지 사전 설정 중 부하가 가장 적습니다. 다른 계산대의 판매 내역을 빠르게 확인할 필요가 없는 계산대에서 선택하세요. 웹사이트 관리자가 권하지 않는 한 **실시간**은 선택하지 마세요. [동기화 사전 설정](../store-health.mdx#sync-presets)을 참조하세요.
6. **현재** — 다음 확인 예정 시간을 보여 줍니다. 시간당 요청 수는 설정에 따른 정기 확인 횟수입니다. 계산대가 확인 빈도를 낮추는 동안에는 요청 수가 줄어들므로, 여기서는 다음 확인까지 ~2분이 남아 있습니다.

</JourneyShot>

## “시간에 따른 서버 상태” 읽기 {#server-load}

같은 탭에서 아래로 스크롤하세요. **시간에 따른 서버 상태**는 계산대의 확인 속도와 지난 24시간의 차트를 보여 줍니다.

<JourneyShot manifest={manifest} device="tablet" step={2} maxWidth={710} offsets={[[400, -204], [430, 0], [110, -84], [120, -84]]} alt="확인 빈도를 낮춘 계산대의 시간에 따른 서버 상태: 서버가 높은 부하를 보고하여 확인 빈도를 2× 낮췄음을 알리는 황색 속도 표시줄, 오전 3:00에 59.1까지 상승하는 서버 부하 차트, 하락하는 POS 요청 차트">

1. **시간에 따른 서버 상태** — 서버 부하에는 POS뿐 아니라 웹사이트, 백업, 같은 호스트의 다른 사이트 등 서버에서 실행되는 모든 작업이 포함됩니다.
2. **속도** — 여기서는 **확인 빈도 낮춤 — 확인 빈도 2× 감소: 서버가 높은 부하를 보고했습니다**가 황색으로 표시됩니다. 현재 계산대는 매분 대신 2분마다 확인하며, 서버가 복구되면 자동으로 원래 주기로 돌아갑니다. [속도 표시줄의 의미](#pace)를 참조하세요.
3. **서버 부하** — 각 시간대에 서버가 보고한 가장 높은 부하입니다. 제목 옆 수치는 가장 최근 시간대의 값입니다. 숫자를 직접 판단할 필요는 없습니다. 서버가 부하를 상승 또는 높음으로 보고하면 속도 표시줄에 표시됩니다.
4. **POS 요청** — 현재 계산대가 매시간 매장에 보낸 모든 요청입니다. 정기 확인뿐 아니라 변경 사항 다운로드, 판매 내역 전송, 검색도 포함됩니다. 따라서 설정에 따른 시간당 요청 수를 크게 웃돌 수 있습니다.

</JourneyShot>

두 차트를 함께 살펴보세요. 부하가 POS 요청과 함께 오르내린다면 계산대도 원인 중 하나일 수 있습니다. 부하만 증가한다면 웹사이트, 백업, 같은 호스트의 다른 사이트 등 서버의 다른 작업이 바쁜 것입니다. 이 화면에서는 자정 이후 두 선이 함께 내려갑니다. 오전 2:00 이후에는 현재 계산대의 요청이 계속 줄어드는데도 부하가 59.1까지 올라갑니다. 즉, 다른 작업이 바쁜 상태이며 계산대는 서버 부담을 덜기 위해 확인 빈도를 낮춘 것입니다.

어느 경우든 호스팅 업체에는 두 차트가 모두 담긴 스크린샷을 보내야 합니다. 부하가 낮은데도 **일반적인 응답 시간**이 길다면 서버의 처리 능력이 부족한 것은 아닙니다. 주문 저장 방식과 플러그인을 먼저 살펴보세요([서버가 계속 버거워하는 경우](#fix)의 2단계와 3단계).

### 속도 표시줄의 의미 {#pace}

표시줄에는 다음 중 하나가 표시됩니다. 이는 탭 상단의 **정상** 상태와는 별개입니다. 계산대가 확인 빈도를 낮추는 중에도 상단 상태는 정상으로 유지될 수 있습니다.

- **정상 속도** — 계산대가 설정된 주기로 확인합니다.
- **정상 속도 — 서버가 부하 상승을 보고합니다**(또는 **높은 부하**) — 서버가 바쁘다고 보고했지만 계산대는 여전히 설정된 주기로 확인합니다. 바쁘다는 응답이 한 번 왔다고 확인 빈도를 낮추지는 않습니다. 부하가 지속될 때도 계산대는 확인 빈도를 낮춥니다. 최근 열 번의 응답 중 대부분이 높은 부하를 보고하면 응답이 빠르게 왔더라도 표시줄이 **확인 빈도 낮춤**으로 바뀝니다([각 사유의 의미](#reasons) 참조). 거의 매일 표시되는 것이 아니라면 조치할 필요가 없습니다.
- **확인 빈도 낮춤 — 확인 빈도 N× 감소: …** — 계산대가 확인 빈도를 낮추고 콜론 뒤에 사유를 표시합니다. 아래의 [각 사유의 의미](#reasons)를 참조하세요.
- **…까지 일시 중지** — 서버가 다시 요청할 시간을 지정하여 계산대가 그때까지 기다립니다. 기다리는 동안에도 판매는 계속할 수 있습니다.

계산대가 확인 빈도를 낮추거나 일시 중지하면 표시줄의 색상이 바뀝니다. 두 상태 모두 서버가 복구되면 자동으로 해제됩니다. 거의 매일 표시된다면 [서버가 계속 버거워하는 경우](#fix)를 참조하세요.

:::note 백그라운드 확인만 느려집니다
계산대의 정기적인 변경 사항 확인과 백그라운드 확인만 느려집니다. 검색, 바코드 조회, 판매 요청은 서버로 즉시 전송됩니다. 확인 빈도를 낮추는 동안에는 다른 계산대와 WooCommerce에서 발생한 변경 사항이 현재 계산대에 표시되기까지 더 오래 걸립니다.
:::

<Accordion>
<AccordionItem question="각 사유의 의미, 확인 빈도가 줄어드는 정도, 복구 방식">

<Anchor id="reasons" />

- **서버가 POS에 요청 빈도를 낮추도록 요청했습니다** — 서버 또는 서버 앞단의 방화벽이 “요청이 너무 많음”(**429**)을 한 번 응답했습니다.
- **서버가 오류를 반환했습니다** 또는 **서버 요청 시간이 초과되었습니다** — 일 분 이내에 서버 오류(**5xx**) 또는 시간 초과가 세 번 발생했습니다. 사유에는 세 번 중 마지막에 발생한 문제가 표시됩니다.
- **서버의 응답이 느렸습니다** — 최근 열 번의 응답에 대한 일반적인 응답 시간(중앙값)이 두 초를 초과했습니다.
- **서버가 높은 부하를 보고했습니다** — 계산대가 정상 속도로 확인하는 동안 최근 열 번의 응답 중 대부분이 높은 서버 부하를 보고했거나, 부하가 1 이상인 상태에서 연속된 두 번의 부하 측정값이 서버의 평소 부하보다 최소 두 배 높았습니다.

매번 확인 빈도를 이전의 절반으로 줄입니다. 확인 간격은 최대 5분이며, 설정된 간격의 두 배가 더 길면 그 값을 적용합니다. **절약**에서는 10분마다 확인합니다. 서버가 직접 대기 시간(**Retry-After** 헤더)을 지정하면 최대 15분까지 따릅니다.

복구는 의도적으로 더 천천히 진행됩니다. 마지막으로 확인 빈도를 낮춘 후 최소 일 분이 지나고 정상 응답을 열 번 받으면 대기 시간을 다시 절반으로 줄입니다. 부하 급증은 예외입니다. 연속된 두 번의 부하 측정값이 서버의 평소 부하에서 사분의 일 이내 차이로 돌아올 때까지 확인 빈도를 절반으로 유지하며, 그보다 더 낮추지는 않습니다. 계산대를 다시 시작하면 설정된 주기로 돌아갑니다.

WCPOS 자체도 짧은 일시 중지를 요청합니다. 사이트에서 플러그인을 업데이트하는 동안에는 5초, 동기화 테이블을 설치하는 동안에는 30초입니다. 이때 **…까지 일시 중지**가 잠시 표시될 수 있습니다.

이 동작의 기반이 되는 엔진 규칙은 [동기화 성능](../../reference/sync-performance.mdx#server-pressure)을 참조하세요.

</AccordionItem>
<AccordionItem question="부하 수치의 출처">

서버는 동기화 응답마다 평균 부하를 보고합니다. 이는 지난 일 분 동안 실행 중이거나 프로세서를 기다리던 프로세스 수의 평균입니다. 서버의 프로세서 코어 수와 비교하세요. 4코어 서버에서 부하가 4이면 처리 능력을 모두 사용 중이라는 뜻이지만, 16코어 서버에서는 가벼운 부하입니다.

**상승**과 **높음**이라는 표시가 이를 대신 판단해 줍니다. WCPOS는 부하를 코어 수로 나눕니다. 코어당 0.9 미만은 낮음, 1.8까지는 상승, 그보다 높으면 높음입니다. 공유 호스팅에서는 내 사이트뿐 아니라 해당 서버의 모든 사이트가 수치에 포함됩니다.

PHP가 평균 부하를 읽을 수 없으면 차트 대신 **서버가 부하를 보고하지 않습니다. 이 페이지의 나머지 기능은 정상적으로 작동합니다.** 문구가 표시됩니다. Windows 서버나 해당 함수를 비활성화한 호스팅에서는 정상적인 현상입니다. 계산대가 오류와 응답 시간도 확인하므로 부하 정보가 없어도 속도 표시줄은 작동합니다.

</AccordionItem>
</Accordion>

## 서버가 계속 버거워하는 경우 {#fix}

이 목록을 위에서부터 순서대로 진행하세요. 아래 단계로 갈수록 비용이 커집니다. 1단계는 계산대를 사용하는 누구나 할 수 있습니다. 2단계부터 4단계까지는 매장 소유자, 개발자, 호스팅 업체 등 웹사이트 관리자가 수행해야 합니다.

1. **부하가 더 적은 사전 설정을 선택하세요.** 다른 계산대의 판매 내역을 수초 이내에 확인할 필요가 없는 계산대에서는 **매장 상태 › 성능**을 열고 **절약**을 선택하세요. 웹사이트 관리자가 권하지 않는 한 **실시간**은 선택하지 마세요. 사전 설정은 계산대별로 저장됩니다. [동기화 사전 설정](../store-health.mdx#sync-presets)을 참조하세요.
2. 기존 주문 저장 방식을 사용하고 있다면 **WooCommerce를 HPOS로 전환하세요**. 주문이 많은 매장에서 단일 조치로 얻을 수 있는 가장 큰 개선입니다. 매장이 기존 저장 방식을 사용하는 동안에는 WP Admin의 **POS → 설정 → 결제** 상단에 이를 알리는 경고와 WooCommerce 설정 링크가 표시됩니다. [주문 저장소(HPOS)](./order-storage.mdx#switch-to-hpos)를 참조하세요.
3. **모든 요청을 느리게 만드는 플러그인을 찾으세요.** 스테이징 사이트에서 WooCommerce와 WCPOS만 활성화한 상태로 테스트한 다음 플러그인을 하나씩 다시 활성화하세요. [플러그인 충돌](../troubleshooting/plugin-conflicts.mdx#step-2-the-plugin-elimination-method)을 참조하세요.
4. 객체 캐싱(Redis 또는 Memcached), PHP 워커 및 메모리 증설, 공유 호스팅에서 다른 환경으로의 이전을 **호스팅 업체에 요청하세요**. [호스팅 업체에 전달할 정보](#when-to-seek-help)를 참조하세요.

## 호스팅 업체에 전달할 정보 {#when-to-seek-help}

**확인 빈도 낮춤** 또는 **…까지 일시 중지**가 거의 매일 표시되거나, 일반적인 응답 시간이 계속 2초를 넘거나, 호스팅 업체의 로그에 메모리 오류가 나타나면 호스팅 업체 또는 WordPress 개발자에게 문의하세요.

계산대에서 다음 정보를 보내세요.

- **매장 상태 → 성능**에서 **시간에 따른 서버 상태**까지 스크롤한 화면의 스크린샷.
- **매장 상태 → 로그 → 디버그 정보 복사**에서 가져온 디버그 보고서(휴대폰 및 태블릿 앱에서는 **디버그 정보 공유**). 여기에는 WordPress, WooCommerce, WCPOS 버전이 이미 포함되어 있습니다. [로그](../store-health.mdx#logs)를 참조하세요.

웹사이트 관리자는 다음 정보도 추가하세요.

- WP Admin의 **플러그인**에서 확인한 활성 플러그인 목록.
- 호스팅 계정에서 확인한 서버 사양: 코어 수, 메모리, 저장 장치 유형.

이 페이지의 나머지 내용은 웹사이트 관리자를 위한 것입니다. **503**, **429**, **414** 코드 때문에 이 페이지를 찾았다면 [서버가 보내는 오류](#503-errors)에서 각 코드의 간단한 설명을 먼저 확인할 수 있습니다.


## 서버 요구 사항 {#minimum-server-requirements}

WCPOS는 PHP 7.4, WordPress 5.6, WooCommerce 9.0이라는 [플러그인의 최소 요구 사항](../../getting-started/installation.mdx#server-requirements)을 충족하는 모든 사이트에 설치할 수 있습니다. 매일 판매하는 매장에는 더 높은 사양이 필요합니다. 호스팅 업체에 전달할 수치는 아래와 같습니다.

<Accordion>
<AccordionItem question="호스팅 업체에 전달할 서버 요구 사항">

매일 판매하는 매장에는 최소한 다음 사양을 권장합니다.

<RequirementsList>
  <RequirementItem label="CPU">4코어 이상</RequirementItem>
  <RequirementItem label="RAM">4 GB 이상</RequirementItem>
  <RequirementItem label="PHP">PHP 8.x, OPcache 활성화</RequirementItem>
  <RequirementItem label="데이터베이스">MySQL 8.0 이상 또는 MariaDB 11</RequirementItem>
  <RequirementItem label="저장 장치">SSD 또는 NVMe</RequirementItem>
  <RequirementItem label="SSL">유효한 인증서를 사용하는 HTTPS</RequirementItem>
</RequirementsList>

</AccordionItem>
</Accordion>

:::warning 공유 호스팅은 충분하지 않은 경우가 많습니다
공유 호스팅은 여러 계산대가 동시에 확인하기에 PHP 워커 수와 메모리가 부족한 경우가 많습니다. 매일 판매하는 매장에는 VPS 또는 관리형 WordPress 호스팅을 사용하세요. WordPress.com 호스팅에서는 대규모 카탈로그에서 상품이 9개 또는 10개만 로드되는 등의 REST API 문제가 있었습니다. 자체 호스팅 WordPress를 사용하면 이러한 문제를 피할 수 있습니다.
:::

<Accordion>
<AccordionItem question="매장에서 가장 빠르다고 보고한 구성">

매장 소유자들은 다음 조합에서 POS 속도가 가장 좋았다고 보고합니다.

- **MariaDB 11.4**
- 주문에 **HPOS** 사용([주문 저장소](./order-storage.mdx))
- **Redis** 또는 LiteSpeed 객체 캐싱
- **NVMe** 저장 장치
- **PHP OPcache** 활성화

</AccordionItem>
</Accordion>

## 서버가 보내는 오류 {#503-errors}

### 503 서비스 이용 불가 {#503}

서버 또는 서버 앞단의 구성 요소가 요청을 처리하지 못했습니다. 계산대는 백그라운드 확인 간격을 늘리고 자동으로 다시 시도합니다. 사이트에서 WCPOS를 업데이트하거나 테이블을 설치하는 동안 503이 잠깐 발생하는 것은 정상입니다. 계산대는 5~30초 기다린 후 계속 진행합니다. 반복해서 발생하면 웹사이트 관리자에게 [호스팅 업체에 전달할 정보](#when-to-seek-help)를 전달하세요.

<Accordion>
<AccordionItem question="웹사이트 관리자용: 503 발생 시 확인할 사항">

서버 부하와 여유 메모리, PHP 워커가 모두 사용 중인지, PHP 메모리 제한이 **256 MB** 이상인지 확인하세요. 호스팅 업체의 오류 로그에서는 POS에서 볼 수 없는 정보를 확인할 수 있습니다.

</AccordionItem>
</Accordion>

### 429 요청이 너무 많음 {#429}

호스팅 업체 또는 방화벽이 하나의 주소에서 사이트를 호출하는 빈도를 제한하고 있습니다. 계산대는 즉시 확인 빈도를 낮추고 나중에 다시 시도합니다. 매장의 공유기 하나에 연결된 여러 계산대는 같은 주소를 공유하므로, 다른 계산대의 판매 내역을 빠르게 확인할 필요가 없는 계산대에서는 **절약**을 선택하세요. 반복해서 발생하면 웹사이트 관리자에게 [호스팅 업체에 전달할 정보](#when-to-seek-help)를 전달하세요.

<Accordion>
<AccordionItem question="웹사이트 관리자용: POS에 더 많은 요청 허용하기">

매장 주소에서 POS가 호출하는 경로인 `/wp-json/`으로 더 많은 요청을 보낼 수 있도록 호스팅 업체에 요청하거나 방화벽 설정을 변경하세요.

</AccordionItem>
</Accordion>

### 414 URI가 너무 김 {#http-414-uri-too-long}

결제 화면의 **레거시** 탭에 있는 결제 페이지에서 발생합니다. 해당 페이지는 주소에 로그인 정보를 포함하여 열리는데, 서버가 허용하는 주소 길이가 너무 짧기 때문입니다. 웹사이트 관리자 또는 호스팅 업체에 제한을 늘려 달라고 요청하세요.

<Accordion>
<AccordionItem question="웹사이트 관리자용: 주소 길이 제한 늘리기">

- **Apache:** `httpd.conf`에 `LimitRequestLine 65536` 설정
- **Nginx:** `nginx.conf`에 `large_client_header_buffers 4 65536;` 설정

</AccordionItem>
</Accordion>

## WooCommerce 안전하게 업데이트하기 {#woocommerce-version-compatibility}

WooCommerce 업데이트로 POS가 정상 작동하지 않는 경우가 간혹 있습니다. 먼저 [스테이징 사이트](../troubleshooting/plugin-conflicts.mdx#before-you-start-use-a-staging-site)에서 WooCommerce를 업데이트하고, 최신 호환성 수정 사항이 적용되도록 WCPOS도 최신 상태로 유지하세요. WCPOS 2.0에는 WooCommerce 9.0 이상이 필요합니다.

업데이트 후 POS가 작동하지 않으면 [Discord](https://wcpos.com/discord)로 알려 주시고, 웹사이트 관리자에게 이전 버전으로 되돌리는 방법을 문의하세요. 업데이트로 매장 데이터베이스가 변경될 수 있으므로 관리자는 이를 먼저 확인하고 업데이트 전 백업을 확보해야 합니다.

<Accordion>
<AccordionItem question="웹사이트 관리자용: WooCommerce 이전 버전으로 되돌리기">

WordPress.org의 WooCommerce 페이지에서 **고급 보기** 링크를 클릭하면 이전 버전 목록을 볼 수 있습니다. 업데이트로 데이터베이스가 변경되었다면 업데이트 전에 만든 백업으로 복원하세요. 그렇지 않다면 이전에 사용하던 버전을 설치하세요. 먼저 스테이징 환경에서 시도하세요.

</AccordionItem>
</Accordion>

## 주문 저장소(HPOS) {#woocommerce-high-performance-order-storage-hpos}

WooCommerce의 **고성능 주문 저장소**는 주문을 글과 함께 저장하는 대신 전용 테이블에 저장합니다. 주문이 많은 매장에서는 판매 내역 저장 속도가 훨씬 빨라집니다. 매장에서 사용하는 저장 방식을 확인하고 WooCommerce 자체 도구로 전환하세요. [주문 저장소(HPOS)](./order-storage.mdx)를 참조하세요. WooCommerce의 안내는 [고성능 주문 저장소](https://woocommerce.com/document/high-performance-order-storage/)에서 확인할 수 있습니다.

<Accordion>
<AccordionItem question="호스팅 업체에 문의할 PHP 및 WordPress 설정">

다음 설정은 출발점으로 참고할 값이며 필수 규칙은 아닙니다. 서버에서 허용하는 설정은 호스팅 업체가 알고 있습니다.

```ini
memory_limit = 512M
max_execution_time = 300
max_input_vars = 3000
```

`wp-config.php`에서 보관할 글 수정본 수를 줄이면 데이터베이스 크기를 줄일 수 있습니다.

```php
define('WP_POST_REVISIONS', 3);
```

모든 요청을 느리게 만드는 경우가 많은 플러그인으로는 상품 저장 시 실행되는 무거운 SEO 플러그인, 복잡한 재고 시스템, 실시간 분석 및 추적 기능, WooCommerce에 훅으로 연결된 사용자 정의 코드가 있습니다. [플러그인 충돌](../troubleshooting/plugin-conflicts.mdx)을 참고하여 원인을 찾으세요.

</AccordionItem>
</Accordion>

## 호스팅별 참고 사항 {#hosting-specific-notes}

일부 호스팅 업체와 CDN은 POS가 사이트의 REST API에 접근할 수 있도록 설정을 변경해야 합니다. 사용 중인 서비스를 펼쳐 보세요.

<Accordion>
<AccordionItem question="GoDaddy">

웹사이트 방화벽이 `/wp-json/`을 차단하여 _“'undefined' 수신”_ 같은 오류가 발생합니다. **웹사이트 보안 › 방화벽 › 설정 › 액세스 제어 › URL 경로 허용**에 `/wp-json/`을 추가하세요.

</AccordionItem>
<AccordionItem question="WP Engine">

REST API를 활성화해야 합니다. REST API를 활성화하고, 필요하면 WP Engine 방화벽에서 해당 경로를 허용하세요.

</AccordionItem>
<AccordionItem question="Cloudflare">

봇 차단 모드, 공격 방어 모드 또는 WAF 챌린지가 REST 요청을 차단하고, 캐시가 오래된 응답을 제공할 수 있습니다. [Cloudflare 안내](../troubleshooting/cloudflare.mdx)에 따라 `/wp-json/`에 대한 WAF **건너뛰기** 규칙과 **캐시 우회** 규칙을 추가하세요.

</AccordionItem>
<AccordionItem question="WordPress.com">

대규모 카탈로그에서 상품이 9개 또는 10개만 표시되는 등 상품을 제대로 불러오지 못할 수 있습니다. 자체 호스팅 WordPress를 사용하세요.

</AccordionItem>
<AccordionItem question="공유 호스팅">

여러 계산대를 운영하기에는 PHP 워커 수와 메모리가 부족합니다. VPS 또는 관리형 WordPress 호스팅으로 이전하세요.

</AccordionItem>
</Accordion>

Wordfence 같은 보안 플러그인도 같은 방식으로 REST API를 차단할 수 있습니다. [플러그인 충돌](../troubleshooting/plugin-conflicts.mdx)을 참조하세요.
