1. 메뉴 하단의 맥박 아이콘에서 **매장 상태**를 여세요.
2. **성능**을 누르세요.
3. 기본값인 **균형**을 선택한 상태로 두세요. 서버가 자주 버거워하고 속도 표시줄에 **속도 조절 중** 또는 **…까지 일시 중지**가 자주 표시되면 **절약**을 누르세요.

이 설정은 이 기기의 현재 매장에 대해서만 저장되므로 계산대마다 설정하세요. 사전 설정별 비교는 [동기화가 서버에 주는 부담](#request-budgets)을 참고하세요.

## 성능 메시지 이해하기 {#troubleshooting}

성능 탭에는 다음 네 가지 상태가 표시될 수 있습니다. 앞의 두 가지는 조치가 필요하고, 뒤의 두 가지는 정상입니다.

<Accordion>
<AccordionItem question="속도 조절 중 또는 …까지 일시 중지가 거의 매일 표시되는 경우 — 절약을 선택한 다음 서버를 점검하세요">

서버가 계산대의 요청을 자주 거부하거나, 오류를 반환하거나, 느리게 응답하고 있습니다. [속도 표시줄](#server-pressure)에 그 원인이 표시됩니다. 각 계산대에서 **절약**을 선택하고, 호스팅·플러그인·방화벽·느린 응답 점검 방법은 [서버 성능](../support/performance/server.mdx)을 참고하세요.

</AccordionItem>
<AccordionItem question="⚠ 확인 필요 — 이 계산대의 연결과 동기화 작업을 확인하세요">

</AccordionItem>

7. **요청당 레코드 수** — 다운로드하는 각 페이지의 처리량으로, 10에서 100까지 설정할 수 있습니다. 일반적으로 공유 서버에 가장 큰 부담을 주는 요소입니다. [페이지당 처리량](#page-weight)을 참고하세요.
8. **현재 상태** — 다음 확인 시점과 현재 설정에서 발생하는 대략적인 시간당 요청 수입니다. 이 수치는 추정치입니다. [시간당 요청 수](#nominal-rate)를 참고하세요.

## 동기화가 서버에 주는 부담 {#request-budgets}

지속적인 서버 부담은 두 가지 설정에 따라 결정됩니다. 계산대가 얼마나 자주 확인하는지, 요청당 레코드를 몇 개 가져오는지입니다.

- **절약** — 서버가 자주 버거워할 때 선택하세요. 5분마다 확인하며, 요청당 레코드 25개를 가져옵니다.
- **균형** (기본값) — 대부분의 매장에 적합합니다. 60초마다 확인하며, 요청당 레코드 50개를 가져옵니다.
- **실시간** — 서버에 여유가 있고 가장 빠른 업데이트가 필요할 때 선택하세요. 10초마다 확인하며, 요청당 레코드 75개를 가져옵니다.
- **사용자 지정** — 두 슬라이더를 직접 설정하려면 선택하세요.

<Accordion>
<AccordionItem question="시간당 확인 횟수와 사용자 지정 범위">

**절약**은 시간당 12회, **균형**은 60회, **실시간**은 360회 확인하므로 실시간 설정이 서버에 가장 큰 부담을 줍니다. **사용자 지정**에서는 확인 주기를 5초부터 5분까지 5초 단위로, 요청당 레코드 수를 10개부터 100개까지 5개 단위로 설정합니다. 확인 횟수는 시간당 720회부터 12회까지입니다.

</AccordionItem>
</Accordion>

슬라이더 중 하나라도 움직이면 **사용자 지정**으로 바뀝니다. **균형으로 초기화**를 누르면 기본값으로 돌아갑니다.

### 페이지당 처리량 {#page-weight}

요청당 레코드 수는 다운로드 한 번에 서버가 처리해야 하는 작업량을 결정합니다. 상품 100개가 담긴 페이지는 빠른 서버에서도 몇 초가 걸릴 수 있으며, 확인 주기가 짧을수록 부담이 커집니다. 따라서 각 사전 설정은 두 설정을 함께 조정하며, 최대값인 레코드 100개를 사용하는 사전 설정은 없습니다. 서버가 감당할 수 있다고 확신하는 경우 **사용자 지정**에서 이 값을 사용할 수 있습니다.

### 변경이 없는 매장의 동기화 부담이 적은 이유 {#cheap-checks}

변경 사항이 없는 매장은 동기화 유지에 드는 부담이 적습니다. 응답이 비어 있고, 계산대별 확인 시점이 분산되며, 빠른 설정에서도 사용하지 않는 계산대는 확인 빈도를 낮춥니다.

<Accordion>
<AccordionItem question="빈 응답, 확인 시점 분산, 유휴 계산대 자세히 알아보기">

- **변경 사항이 없는 매장은 빈 응답을 반환합니다.** 계산대가 마지막으로 확인한 상태를 보내면 서버는 본문 없이 `304 Not Modified`로 응답합니다. 이 경우에도 요청 한 건으로 계산됩니다.
- **확인 시점을 분산합니다.** 매번 대기하는 시간은 설정값의 80%에서 120% 사이이므로 여러 계산대가 동시에 요청하지 않습니다. 이 때문에 **현재 상태**의 남은 시간이 설정값과 정확히 일치하는 경우는 드뭅니다.
- 확인 주기가 한 분보다 짧게 설정되어 있으면 **사용하지 않는 계산대는 속도를 낮춥니다.** 터치, 키 입력, 바코드 스캔 없이 10분이 지나면 확인 주기가 30초, 이후 60초로 늘어납니다. 앱이 숨겨지면 바로 60초로 바뀝니다. 계산대를 다시 사용하면 원래 주기로 돌아가 즉시 확인합니다. 단, 서버 문제로 계산대가 속도를 낮춘 경우는 예외입니다. **균형**과 **절약**은 이미 주기가 한 분 이상이므로 바뀌지 않습니다.

</AccordionItem>
</Accordion>

### 백그라운드 유지 관리 {#maintenance-budgets}

변경 사항 확인 외에도 몇 가지 백그라운드 작업이 계산대의 데이터 사본을 완전하고 정확하게 유지합니다. 서버에서 삭제된 레코드를 찾고, 아직 다운로드하지 않은 데이터를 채워 오프라인에서도 판매할 수 있게 합니다. 각 실행에는 정해진 상한이 있습니다. 요청은 최대 11건이며, 추가 다운로드 작업은 1건입니다.

미결제 주문도 확인합니다. 계산대를 시작할 때와 이후 5분마다, 계산대에 보관된 [미결제 주문](../pos/cart/open-orders.mdx) 중 서버에 이미 저장된 각 주문의 상태를 서버에 요청합니다. 요청 한 건에는 최대 **요청당 레코드 수**만큼의 주문을 포함합니다. WP Admin에서 휴지통으로 이동하거나 삭제한 미결제 주문은 계산대에서도 제거됩니다. 아직 서버에 전송하지 않은 변경 사항이 있는 주문은 그대로 유지됩니다.

<Accordion>
<AccordionItem question="각 백그라운드 작업과 상한">

| 작업 | 대략적인 실행 주기 | 실행당 최대 요청 수 |
| --- | --- | --- |
| 삭제 감사 | 17분 | 11 |
| 삭제 감사, 계산대가 이미 동기화된 상태 | 17분 | 요약 페이지만 요청(최대 9개), 상세 요청 없음 |
| 계산대에 이미 있는 레코드의 지문 확인(요청당 ID 100개) | 15분 | 5 |
| 상품 추가 다운로드, 상품 목록의 정렬 순서대로 한 페이지 | 5분 | 1 |
| 고객 추가 다운로드 | 5분 | 1 |
| 옵션 상품 다운로드 | 5분 | 1 |
| 매장 상태에 표시할 서버 합계(요청당 집계값 하나, 오래된 경우 갱신) | 30초마다 확인 | 11 |

</AccordionItem>
<AccordionItem question="삭제 감사가 요청 11건 이내로 유지되는 방식">

감사는 계산대의 레코드를 묶음별로 서버와 비교합니다. 요약 페이지를 최대 9개(확인하는 레코드 종류당 3개) 읽고, 요약이 일치하는 묶음은 모두 건너뜁니다. 다른 묶음에만 상세 요청을 보내며, 실행당 최대 2건으로 제한합니다. 확인할 항목이 더 있으면 한꺼번에 처리하지 않고 진행 위치를 저장한 뒤 다음 실행에서 이어갑니다. 서버 부하가 높으면 실행당 레코드 종류별 요약 페이지 1개와 상세 요청 1건으로 줄어듭니다.

</AccordionItem>
</Accordion>

### 시간당 요청 수 {#nominal-rate}

**현재 설정: 시간당 약 N건의 요청**은 **변경 사항 확인** 설정만으로 계산한, 이 계산대의 변경 사항 확인 빈도 추정치입니다. 모든 요청에 적용되는 상한이 아닙니다. 탭 상단의 **지난 24시간**에 표시되는 수치가 실제 합계입니다.

<Accordion>
<AccordionItem question="실제 요청 수가 다른 이유">

확인 시점 분산으로 실제 요청 수는 늘거나 줄 수 있고, `304`도 요청에 포함됩니다. 빠른 설정에서도 사용하지 않는 계산대는 요청을 줄이며, 서버 문제로 계산대가 속도를 낮추면 더 줄어듭니다. 여기에 백그라운드 유지 관리와 캐셔가 직접 수행한 작업의 요청(검색, 주문 저장)이 추가됩니다.

</AccordionItem>
</Accordion>

## 엔진이 따르는 네 가지 원칙 {#the-four-rules}

위의 서버 부담과 아래의 속도 조절은 네 가지 원칙에 따릅니다. 부담은 변경량에 비례하고, 백그라운드 작업에는 상한이 있으며, 캐셔가 우선이고, 부하가 높으면 백그라운드 작업이 먼저 양보합니다.

<Accordion>
<AccordionItem question="각 원칙의 작동 방식">

모든 계산대가 매장의 변경 사항을 계속 확인하므로 POS는 서버의 처리 시간을 신중하게 사용합니다. 이 페이지의 나머지 부분에서는 매장 운영자와 개발자를 위해 이러한 원칙의 근거가 되는 수치를 설명합니다. 탭 전체에 대한 안내는 [매장 상태 › 성능](../support/store-health.mdx#performance)을 참고하세요.

1. **부담은 카탈로그 크기가 아니라 변경량에 비례합니다.** 모든 확인은 부담이 적은 요청으로 시작하며, 변경 사항이 없는 매장은 빈 응답을 반환합니다. 변경이 없는 상품 50,000개 규모의 매장과 상품 500개 규모의 매장은 동기화 유지에 드는 부담이 거의 같습니다.
2. **백그라운드 작업에는 상한이 있습니다.** 모든 백그라운드 유지 관리 작업은 한 번의 실행에서 보낼 수 있는 최대 요청 수를 선언하며, 이를 초과하면 엔진 테스트가 실패합니다. 큰 작업은 작은 단위로 나누어 실행하고 다음 실행에서 중단한 지점부터 이어갑니다.
3. **캐셔가 우선입니다.** 계산대를 판매 가능한 상태로 만드는 요청이 먼저 실행됩니다. 감사는 상품의 첫 페이지가 다운로드된 뒤에도 한 분을 더 기다립니다. 앱이 숨겨져 있거나 백그라운드에 있으면 유지 관리는 대기합니다.
4. **부하가 높으면 백그라운드 작업이 먼저 양보합니다.** 서버가 버거워하면 계산대는 변경 사항 확인 빈도를 낮추고 유지 관리를 미룹니다. 검색, 바코드 조회, 판매 저장은 지연시키지 않습니다.

</AccordionItem>
<AccordionItem question="서버의 처리 시간이 소중한 이유">

대부분의 매장은 공유 호스팅을 사용합니다. 계산대에서 보내는 요청마다 WordPress가 처음부터 시작되고, 웹사이트 방문자의 요청과 자원을 나누어 써야 하며, 보안 플러그인의 요청 빈도 제한에 걸릴 수 있습니다. 계산대가 늘 때마다 각각의 확인 요청도 추가됩니다.

</AccordionItem>
</Accordion>

## 서버가 버거워할 때 속도 조절하기 {#server-pressure}

계산대가 받는 모든 응답은 이 기기에서 웹사이트별로 수행하는 부하 판단에 반영됩니다. 부하 조건에 해당하면 **시간에 따른 서버 상태** 아래의 속도 표시줄에 그 사실과 원인이 표시됩니다. **속도 조절 중** 또는 **…까지 일시 중지**가 거의 매일 표시되면 [성능 메시지 이해하기](#troubleshooting)를 참고하세요.

<JourneyShot manifest={manifest} device="tablet" step={2} offsets={[[527, 0], [91, -84], [106, -84], [165, 0]]} alt="시간에 따른 서버 상태: 정상 속도, 서버가 높은 부하를 보고한다는 속도 표시줄, 아직 데이터를 수집 중인 서버 부하 및 POS 요청 차트, 문서에서 자세히 알아보기 링크">

1. **속도** — 서버 상태에 대응하여 계산대가 취하는 동작으로, 아래 확대 화면에서 자세히 볼 수 있습니다.
2. **서버 부하** — 서버가 보고하는 부하로, POS뿐 아니라 서버에서 실행되는 모든 작업을 포함합니다. 서버가 이 정보를 보내지 않으면 **서버가 부하를 보고하지 않습니다**가 표시되며, 탭의 나머지 기능은 계속 작동합니다.
3. **POS 요청** — 지난 24시간 동안 이 계산대가 보낸 요청을 시간별로 표시합니다. 계산대가 일정 시간 실행되기 전까지는 화면처럼 두 차트 모두 **아직 데이터가 부족합니다**로 표시됩니다.
4. **문서에서 자세히 알아보기** — 문서의 [매장 상태 › 성능](../support/store-health.mdx#performance)을 엽니다.

</JourneyShot>

<JourneyShot manifest={manifest} device="tablet" step={3} maxWidth={586} offsets={[[534, 0]]} alt="시간에 따른 서버 상태 확대 화면: 정상 속도, 서버가 높은 부하를 보고하지만 서버 응답이 느려질 때만 계산대도 속도를 낮춘다는 속도 표시줄">

1. **속도 표시줄** — **정상 속도**: 설정을 그대로 두세요. 서버가 높은 부하를 보고하지만 여전히 빠르게 응답하고 있습니다.

</JourneyShot>

계산대가 실제로 속도를 낮추면 속도 표시줄에 원인이 표시됩니다. **속도 조절 중 — 확인 간격 2× 증가** 뒤에 다음 중 하나가 표시되며, 단계가 올라갈 때마다 숫자가 커집니다.

- **… 서버가 POS에 속도를 낮추도록 요청했습니다** — 요청이 너무 많아 서버가 요청을 거부했습니다.
- **… 서버가 오류를 반환했습니다** — 한 분 내에 서버에서 여러 요청이 실패했습니다.
- **… 서버 요청 시간이 초과되었습니다** — 여러 요청이 제한 시간 내에 응답을 받지 못했습니다.
- **… 서버가 느리게 응답했습니다** — 일반적인 응답에 2초 넘게 걸리고 있습니다.
- **… 서버가 높은 부하를 보고했습니다** — 최근 응답 대부분에 높은 부하 상태라는 표시가 있거나, 서버가 보고하는 부하가 두 배로 늘었습니다.

**…까지 일시 중지 — 서버가 POS에 대기를 요청했습니다**는 서버가 요청을 거부하면서 다시 시도할 시점을 알렸다는 뜻입니다. 계산대는 요청받은 대로 최대 15분까지 기다립니다.

기기가 오프라인일 때 발생한 오류는 계산하지 않습니다. 서버 문제가 아니라 연결 문제이기 때문입니다.

<Accordion>
<AccordionItem question="각 속도 메시지가 표시되는 정확한 조건">

| 속도 표시줄 끝부분 | 서버 상태 | 계산대의 반응 시점 |
| --- | --- | --- |
| POS에 속도를 낮추도록 요청했습니다 | `429 Too Many Requests`로 응답 | 즉시 |
| 오류를 반환했습니다 | `5xx` 오류 반환 | 한 분 내 3회 발생 후 |
| 요청 … 시간이 초과되었습니다 | 제한 시간 내에 응답하지 않음 | 한 분 내 3회 발생 후 |
| 느리게 응답했습니다 | 느리게 응답 | 최근 10회 응답 시간의 중앙값이 2초를 초과할 때 |
| 높은 부하를 보고했습니다 | 응답에 `X-WCPOS-Pressure: high` 표시 | 최근 10회 중 약 6회 해당할 때 |
| 높은 부하를 보고했습니다 | 평소의 두 배 이상이면서 1 이상인 부하 보고 | 2회 연속 측정 후, 최대 2× |
| …까지 일시 중지 | 요청 거부와 함께 `Retry-After` 전송 | 즉시, 최대 15분 동안 |

서버가 응답에 `elevated` 또는 `high`를 표시하더라도 계속 빠르게 응답하면, 위 확대 화면처럼 **정상 속도 — 서버가 높은 부하를 보고합니다. 서버 응답이 느려질 때만 계산대도 속도를 낮춥니다**가 표시됩니다(더 낮은 단계에서는 **증가한 부하**로 표시). 이 헤더가 속도 조절을 시작하게 할 수는 있지만, 헤더만으로 속도 조절을 계속 유지하지는 않습니다. 계산대는 서버의 실제 응답 속도를 기준으로 판단합니다.

</AccordionItem>
</Accordion>

### 속도 조절이 의미하는 것 {#back-off-steps}

- **계산대가 변경 사항을 덜 자주 확인합니다.** 단계마다 확인 간 대기 시간이 두 배로 늘어납니다. 조절 가능한 범위는 설정에 따라 다릅니다. **균형**과 **실시간**에서는 약 5분까지, **절약**에서는 10분까지 늘어납니다. 사용자 지정 설정과 일시 중지에 대해서는 아래 세부 내용을 참고하세요.
- **백그라운드 유지 관리는 대기합니다.** 오래 대기한 작업은 서버가 POS에 대기를 요청한 경우를 제외하고 소규모로 한 번 실행됩니다.
- **POS는 캐셔의 작업을 지연시키지 않습니다.** 검색, 바코드 조회, 레코드 열기, 판매 저장은 속도 조절의 영향을 받지 않습니다. 다만 서버가 버거워하면 해당 요청에도 느리게 응답할 수 있습니다.

<Accordion>
<AccordionItem question="설정별 속도 조절 범위와 계속 실행되는 유지 관리 작업">

- **단계마다 확인 간 대기 시간이 두 배로 늘어나며,** 약 5분까지 증가합니다. **실시간**은 최대 32×, **균형**은 8×, **절약**은 2×(10분까지)로 늘어날 수 있습니다. 사용자 지정 설정은 5분까지 늘어나며, 자체 주기의 두 배가 그보다 길면 해당 시간까지 늘어납니다. `Retry-After`에 따른 일시 중지는 이 한도를 넘어 최대 15분까지 지속될 수 있습니다.
- **백그라운드 유지 관리는 대기합니다.** [백그라운드 작업](#maintenance-budgets)은 실행을 미룹니다. 평소 주기의 두 배만큼(삭제 감사와 지문 작업은 한 주기만큼) 대기한 작업은 서버가 POS에 대기를 요청한 경우가 아니면 상한 내에서 한 번 실행됩니다. 삭제 감사는 실행당 레코드 종류별 요약 페이지 1개와 상세 요청 1건으로 줄어듭니다.

</AccordionItem>
</Accordion>

### 원래 속도로 복귀하기 {#recovery}

서버가 다시 정상적으로 응답하면 계산대는 자동으로 한 단계씩 원래 설정으로 돌아갑니다(서버가 보고하는 높은 부하에는 아래에 설명하는 별도 규칙이 적용됩니다). 직접 바꿀 필요는 없습니다. 속도를 낮추는 것은 즉시 이루어지지만, 높이는 것은 점진적으로 이루어집니다. 따라서 불안정한 서버에서 속도가 빠르게 오르내리는 일을 방지합니다.

<Accordion>
<AccordionItem question="사전 설정, 매장 전환, 재시작과 서버 부하">

- **속도를 한 단계 높이려면 정상 응답이 10회 연속 필요하며,** 마지막으로 속도를 낮춘 뒤 한 분이 지났고 `Retry-After` 일시 중지가 진행 중이지 않아야 합니다. 32× 상태에서 원래 설정으로 돌아가려면 정상 응답 50회가 필요합니다.
- **사전 설정을 바꿔도 속도 조절은 유지되며,** 새 사전 설정의 한도에 맞게 줄어듭니다. 이 기능은 끌 수 없습니다. **사용자 지정**을 포함한 모든 사전 설정에서 작동합니다.
- **같은 웹사이트에서 매장이나 캐셔를 바꿔도 유지됩니다.** 기기의 각 웹사이트별로 별도의 속도 조절 상태를 유지합니다.
- **앱을 닫으면 초기화됩니다.** 계산대는 지정한 설정으로 시작하고, 서버가 여전히 버거워하면 다시 속도를 낮춥니다.
- **서버 부하는 별도로 작동합니다.** 서버가 보고하는 부하가 두 번의 측정에서 평소의 두 배 이상이면서 1 이상이면, 계산대는 확인 빈도를 절반으로 줄입니다. 이후 두 번의 측정에서 부하가 평소의 1.25배 미만으로 내려갈 때까지 이를 유지합니다.

</AccordionItem>
</Accordion>

## 계산대의 빠른 응답 유지하기 {#device-responsiveness}

백그라운드 동기화 때문에 화면이 끊겨서는 안 됩니다. 감사는 짧은 단위로 작업하고 중간에 쉬어 화면이 응답할 수 있게 합니다. 엔진 테스트에서 감사가 실행되는 동안에도 목록의 첫 결과는 십분의 일 초보다 훨씬 빠르게 도착합니다. 또한 데이터베이스가 목록을 직접 필터링하고 정렬할 수 있으면 화면에 표시할 행만 데이터베이스에서 가져옵니다.

<Accordion>
<AccordionItem question="측정 수치">

- **감사는 화면이 응답할 수 있도록 중간에 쉽니다.** 삭제 감사는 작업을 나누어 처리하며, 각 작업은 약 **30 ms**를 넘지 않습니다. 사람이 지연을 느끼는 100 ms보다 훨씬 짧습니다. 계산대에 상품이 10,000개 있으면 전체 감사의 실제 작업 시간은 약 **68 ms**이며, 중간에 17회 또는 18회 쉽니다. 상품이 50,000개인 경우에도 300 ms 미만입니다.
- **동기화 중에도 첫 결과는 빠르게 도착합니다.** 상품 10,000개를 감사하는 동안 쿼리의 첫 결과는 약 **7–10 ms** 안에 도착하며, 상품 50,000개를 감사하는 동안에는 약 **40–54 ms**가 걸립니다.
- 데이터베이스 내부에서 필터링과 정렬이 가능하면 **화면에 보이는 행만 데이터베이스에서 가져오므로,** 화면을 갱신할 때 만 개가 아니라 열 개의 행만 이동합니다. 검색과 데이터베이스가 직접 실행할 수 없는 필터는 계산대에서 처리합니다.

이 수치는 데이터베이스를 메모리에 둔 컴퓨터 한 대에서 측정한 엔진 성능 테스트 결과입니다.

</AccordionItem>
<AccordionItem question="수치 측정 방법">

테스트는 데이터베이스를 메모리에 둔 Apple silicon 컴퓨터에서 실행되며, 동기화 엔진이 변경될 때마다 CI에서도 단독으로 실행됩니다. 허용 한도는 측정값의 약 11–18배(30 ms 작업 단위의 경우 3배)이며, CI에서는 여기에 다시 세 배를 적용합니다. 따라서 느린 테스트 장비가 아니라 해당 규모의 성능 저하를 감지합니다.

</AccordionItem>
</Accordion>

## 실제 매장에서 검증 {#live-verification}

위 원칙은 릴리스 배포 후 실제 WordPress 매장에서도 수동으로 확인합니다. 계산대는 상품 목록이 처음 표시되기 전에는 감사 요청을 **전혀** 보내지 않으며, 그 이후에도 감사 상한을 지킵니다.

<Accordion>
<AccordionItem question="실제 환경 테스트의 확인 항목과 도입 배경">

테스트는 감사 실행 시점이 된 상태에서 POS를 다시 불러오고 다음을 확인합니다.

- 상품 목록이 처음 표시되기 전에는 계산대가 감사 요청을 **전혀** 보내지 않는지, 그리고
- 한 분의 대기 후 감사가 요약 페이지를 최대 **9**개, 상세 요청을 최대 **2**건만 요청하는지 확인합니다.

이 테스트는 실제 회귀 문제를 계기로 도입되었습니다. 초기 개발 빌드에서는 계산대가 레코드를 재구성할 때 감사 한 번에 상세 요청 **41**건(**1.2 MB**)을 보냈습니다. 이를 대체한 설계는 요약을 먼저 확인하고 상세 요청을 위의 상한 이내로 유지합니다. 엔진 테스트는 변경할 때마다 이 상한을 지키는지 확인합니다.

</AccordionItem>
</Accordion>

## 수치만으로 알 수 없는 것 {#honest-limits}

- **최초 다운로드에 걸리는 시간.** 이는 거의 전적으로 서버 응답 시간과 카탈로그 크기에 달려 있습니다. 테스트에서 다운로드한 상품 10,000개를 계산대 데이터베이스에 쓰는 데는 10 ms 미만이 걸립니다. 나머지 시간은 네트워크와 서버에서 소요됩니다.
- **WCPOS 1.x보다 얼마나 빠른지.** 두 설계의 차이가 너무 커서 하나의 수치로 공정하게 비교하기 어렵습니다. 차이점은 [동기화 엔진의 작동 방식](./sync-engine.mdx)에서 설명합니다.
- **실제 매장에서 나타날 결과.** 테스트 수치는 데이터베이스를 메모리에 둔 컴퓨터 한 대에서 측정한 것입니다. 그래서 성능 탭은 예측값 대신 이 계산대가 지난 24시간 동안 실제로 수행한 작업을 보여 줍니다. 데이터 수치는 크기가 명시된 응답만 집계하므로 실제 트래픽보다 낮게 표시되거나 **0.0 MB**로 표시될 수도 있습니다.
