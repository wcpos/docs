POS 메뉴를 열고 메뉴 하단의 **설정**과 **지원** 바로 위에 있는 [**매장 상태**](../support/store-health.mdx)를 선택하면 이 페이지에서 설명하는 내용을 사용 중인 계산대에서 확인할 수 있습니다. 계산대에서 확인하려는 항목에 따라 다음 내용을 참고하세요:

- **전송 대기 중인 변경 사항 확인.** **매장 상태 → 데이터베이스**를 열고 **전송 대기 중인 변경 사항**을 확인하세요. 이 계산대에서 매장으로 아직 보내야 하는 항목입니다. [데이터베이스](../support/store-health.mdx#database)를 참고하세요. 수치가 계속 0보다 크면 ["전송 대기 중인 변경 사항"이 줄어들지 않음](../support/store-health.mdx#waiting-to-send)을 참고하세요. 전송 방식은 [변경 사항이 매장으로 전송되는 방식](#write-path)에서 설명합니다.
- **다운로드된 항목 확인.** **매장 상태 → 데이터베이스**를 열고 표에서 매장 데이터가 이 기기에 얼마나 저장되어 있는지 확인하세요. [이 기기에 저장된 항목](../support/store-health.mdx#coverage)을 참고하세요. 다운로드 수량을 계산하는 방식은 [모두 다운로드되었나요?](#coverage)에서 설명합니다.
- **WooCommerce에서 변경한 내용은 언제 계산대에 반영되나요?** [POS가 변경 사항을 감지하는 방식](#change-signal)을 참고하세요.
- **판매 또는 수정 내용이 매장에 전달되지 않았습니다.** [서버에 전달되지 못한 변경 사항](../support/store-health.mdx#refused-changes)을 참고하세요.
- **"다른 탭에서 POS가 열려 있습니다."** [하나의 탭에서 POS 실행](#multi-tab)을 참고하세요.
- **"로컬 데이터베이스를 사용할 수 없습니다."** **앱 다시 로드**를 누르세요. [로컬 저장소](#local-storage)를 참고하세요.
- **2.0으로 업데이트.** [업데이트를 누르기 전에](../getting-started/upgrading-to-2.mdx#before-you-click-update)를 참고하세요.

:::warning 업데이트를 누르기 전에
모든 계산대에서 **매장 상태 → 데이터베이스**를 열고 **전송 대기 중인 변경 사항**이 0이 될 때까지 기다린 다음 업데이트하세요. 계산대에 대기 중인 변경 사항은 업데이트 후 전송되지 않습니다. 수치가 줄어들지 않으면 아직 업데이트하지 말고 ["전송 대기 중인 변경 사항"이 줄어들지 않음](../support/store-health.mdx#waiting-to-send)을 참고하세요. 자세한 내용은 [2.0으로 업그레이드](#upgrading)에서 확인하세요.
:::

WCPOS는 로컬 우선 방식으로 동작합니다. 모든 화면은 기기의 데이터베이스에서 데이터를 읽고 쓰며, **동기화 엔진**이 백그라운드에서 이 데이터베이스와 WooCommerce 매장의 데이터를 일치시킵니다. 이 페이지의 나머지 부분에서는 POS가 호스팅에 어떤 요청을 보내는지 알고 싶은 개발자, 통합 담당자, 매장 운영자를 위해 엔진이 언제 무엇을 가져오고 판매 내역을 어떻게 매장에 전송하는지 설명합니다.

## 매장과 캐셔별 데이터베이스 {#one-engine-per-scope}

기기에서는 매장과 캐셔 조합마다 별도의 로컬 데이터베이스를 사용합니다. 하나의 기기를 사용하는 두 캐셔는 로컬 데이터를 공유하지 않습니다.

- **전환은 완전히 이루어지거나 아예 이루어지지 않습니다.** 새 매장이나 캐셔의 데이터베이스를 먼저 불러온 뒤 준비가 완료되면 전환합니다. 문제가 생기면 오류가 표시되며, 계산대가 일부만 전환된 상태로 남지 않습니다.
- **모든 요청에는 대상 매장이 명시됩니다.** 여러 매장을 운영하는 WCPOS Pro에서는 계산대에서 가격을 변경하면 온라인 매장이 아닌 해당 매장의 가격이 업데이트됩니다.
- **새 버전은 새 데이터베이스로 시작합니다.** 기존 데이터베이스를 그대로 마이그레이션하지 않습니다. [2.0으로 업그레이드](#upgrading)를 참고하세요.

<Accordion>
<AccordionItem question="엔진과 범위의 구성">

각 기기는 **사이트마다 하나의 동기화 엔진**을 실행합니다. 엔진 안에서 매장과 캐셔의 각 조합은 자체 로컬 데이터베이스를 가진 **범위**가 됩니다. 매장이나 캐셔를 전환하면 같은 엔진에서 범위와 해당 데이터베이스 전체가 전환됩니다. 다른 사이트에 연결하면 엔진이 교체됩니다.

</AccordionItem>
</Accordion>

## 백그라운드에서 실행되는 작업 {#sync-lanes}

계산대의 **변경 확인**은 **균형** 설정에서 60초마다 매장에 변경 사항이 있는지 묻습니다. [동기화 사전 설정](../support/store-health.mdx#sync-presets)을 통해 주기를 10초(**실시간**)부터 5분(**절약**)까지 설정할 수 있습니다.

- **백그라운드 작업은 캐셔의 작업이 끝나기를 기다립니다.** 상품, 고객, 옵션 상품의 추가 다운로드는 계산대를 사용하는 사람이 없고 데이터를 기다리는 화면도 없는 상태가 60초 동안 지속된 후에만 실행되며, 매장이 응답에 어려움을 겪는 동안에는 보류됩니다. 삭제된 레코드와 매장의 전체 수량을 확인하는 백그라운드 작업도 마찬가지입니다.

<Accordion>
<AccordionItem question="각 작업 경로의 주기와 요청 상한">

엔진이 타이머로 실행하는 모든 작업은 **작업 경로**에 속합니다. 작업 경로는 이름과 작업 한도가 정해진 백그라운드 작업 단위입니다. 이 중 변경 확인의 주기를 조정할 수 있습니다. 기기에서 발생한 변경 사항은 약 0.3초 후에 전송됩니다.

초기 데이터 요청, 점진적 다운로드, 전체 수량 확인, 점검 작업은 각각 한 번 실행할 때 보낼 수 있는 요청 수를 선언합니다. 캐셔가 완료를 기다리는 세 경로(변경 확인, 쓰기 대기열 처리, 데이터 수요 대기열 처리)에는 아직 상한이 없습니다. 요청 한도는 [동기화 성능](sync-performance.mdx)에 나와 있습니다.

| 작업 경로 | 주기 | 실행당 요청 수 |
| --- | --- | --- |
| 변경 확인 | 사전 설정: 10초(실시간), 60초(균형), 5분(절약); 사용자 지정은 5초부터 | 아직 상한 없음 |
| 쓰기 대기열 처리 | 각 변경 후 약 0.3초, 누락 확인은 10초마다 | 아직 상한 없음 |
| 데이터 수요 대기열 처리(화면에서 선언한 데이터 가져오기) | 30초 | 아직 상한 없음 |
| 최근 주문, 상품, 참조 데이터의 초기 요청 | 5분 | 0(데이터 수요 대기열에 작업 추가) |
| 고객, 상품, 옵션 상품의 점진적 다운로드 | 60초 동안 유휴 상태일 때 5분마다 | 1 |
| 서버 전체 수량 확인 재시도 | 30초 | 11 |
| 다운로드 범위 정보 압축 | 60초 | 0 |
| 존재 여부 초기 확인 | 15분 | 5 |
| 삭제 여부 점검 | 17분 | 11 |

주문은 변경 확인 대상이 아니므로, 최근 주문의 초기 요청이 실행될 때마다 기기의 진행 중인 장바구니 중 매장에도 사본이 있고 전송 대기 중인 변경 사항이 없는 모든 장바구니를 다시 확인합니다. 매장에서 삭제했거나 휴지통으로 옮긴 장바구니는 기기에서도 제거됩니다. 특정 주문을 가져올 때도 마찬가지입니다. 매장에 더 이상 없는 주문은 가져오기 실패로 처리하지 않고 제거합니다. 단, 이 기기에 해당 주문의 전송 대기 중인 변경 사항이 남아 있으면 제거하지 않습니다.

</AccordionItem>
</Accordion>

2. **엔진 가동 시간** — 지난 24시간을 시간당 한 칸으로 표시합니다. 녹색: 요청이 있었고 오류는 없었습니다. 황색: 하나 이상의 요청이 실패했습니다. 빈칸: 앱이 종료되어 있었습니다.
3. **절약** — 5분마다 변경 사항을 확인하며, 요청당 25개의 레코드를 가져옵니다.
4. **균형** — 기본값으로, 60초마다 50개의 레코드를 가져옵니다.
5. **실시간** — 10초마다 75개의 레코드를 가져옵니다.
6. **변경 사항 확인** — 변경 확인 주기를 5초부터 5분까지 설정합니다.
7. **요청당 레코드 수** — 한 번에 가져올 레코드 수를 10개부터 100개까지 설정합니다.
8. **현재 상태** — 다음 확인 예정 시간과 현재 설정에서 시간당 발생하는 대략적인 요청 수를 표시합니다.

## POS가 변경 사항을 감지하는 방식 {#change-signal}

POS는 변경 사항을 찾기 위해 카탈로그를 다시 다운로드하지 않습니다. 변경 확인 때마다 매장에 지난번 이후 달라진 것이 있는지만 간단히 묻습니다. **균형** 설정에서는 연결된 계산대가 대략 매분 가격과 재고 변경 사항을 확인합니다. 매장이 응답에 어려움을 겪으면 확인 간격이 더 길어질 수 있습니다. 주문은 별도의 일정에 따라 처리됩니다.

<Accordion>
<AccordionItem question="변경 확인의 작동 방식">

매장은 **변경 로그**를 유지하며, POS는 로그에서 마지막으로 확인한 위치 이후 변경 사항이 있는지 묻습니다.

- **한 번의 확인으로 여덟 종류의 레코드를 확인합니다:** 상품, 옵션 상품, 세율, 고객, 쿠폰, 카테고리, 브랜드, 태그입니다. 주문은 포함되지 않습니다. 진행 중인 주문과 최근 주문에는 별도의 작업 경로가 있으므로 상품과 주문의 업데이트 주기는 서로 다릅니다.
- **변경이 없는 매장에는 부하가 거의 발생하지 않습니다.** 조건부 요청을 사용하므로 변경 사항이 없으면 매장은 본문 없이 `304 Not Modified`로 응답합니다.
- **확인 시점을 ±20% 범위로 분산하여,** 같은 사이트의 여러 계산대가 동시에 요청하지 않고 서로 다른 시점에 요청하도록 합니다.
- **사용하지 않는 계산대는 확인 주기를 조금 늦춥니다.** 터치, 키 입력, 정상적으로 처리된 스캔이 10분 동안 없으면 확인 간격이 최소 30초로, 이후 최소 60초로 늘어납니다. 숨겨진 창은 곧바로 60초로 늘어납니다. **균형**과 **절약** 설정에서는 달라지는 것이 없습니다. 매장이 POS에 요청 속도를 늦추도록 요청한 상태가 아니라면, 다음 터치 시 즉시 확인하고 원래 주기로 돌아갑니다. 유휴 상태의 확인 주기가 설정한 주기보다 빨라지지는 않습니다.
- **며칠 동안 꺼져 있던 계산대는 현재 시점부터 시작합니다.** 변경 사항이 5,000개 넘게 쌓였거나 매장이 로그를 정리하여 계산대의 마지막 위치 이후 기록까지 삭제했다면, 엔진은 로그의 최신 위치로 이동하고 기기에 이미 저장된 데이터를 다시 확인합니다. 부하는 사용하지 않은 기간이 아니라 로컬 사본의 크기에 따라 달라집니다.

</AccordionItem>
</Accordion>

## 화면이 데이터를 가져오는 방식 {#declared-demand}

화면에는 기기에 이미 저장된 데이터가 항상 즉시 표시됩니다. 처음 가져온 상품 범위를 넘어 검색하는 경우처럼 아직 기기에 없는 레코드가 필요하면, 계산대가 온라인 상태일 때 엔진이 매장에서 해당 데이터를 가져옵니다. 처음부터 모든 데이터가 기기에 저장되는 것은 아니며, 레코드 종류에 따라 다릅니다:

1. **세율**은 시작 시 가장 먼저 가져옵니다. 세율이 없으면 장바구니 금액을 계산할 수 없기 때문입니다.
2. **상품:** 시작 시 기본 정렬 순서의 첫 100개를 가져옵니다. 나머지는 화면에서 요청할 때 가져오며, 유휴 상태에서도 캐셔의 정렬 순서에 따라 추가로 다운로드합니다.
3. **고객**은 시작 시 가져오지 않습니다. 화면에서 요청하면 가져오고, 유휴 상태에서는 10개씩 추가로 다운로드하며, 변경 확인을 통해 신규 및 수정된 고객을 가져옵니다.
4. **카테고리, 태그, 브랜드, 쿠폰**도 시작 시 가져오지 않습니다. 처음 열 때 불러오며(15초 이내에 다시 열면 재요청하지 않음), 매장에 해당 데이터가 있다고 확인되면 백그라운드에서 추가로 가져옵니다. 30분마다 새로 고치며 변경 확인에도 반영됩니다.

계산대가 온라인 상태일 때 옵션 상품 선택기를 열면 가격과 재고를 새로 고칩니다. 그동안 기기에 이미 저장된 옵션 상품은 즉시 표시됩니다.

<Accordion>
<AccordionItem question="화면이 데이터를 요청하는 방식">

화면 자체는 동기화하지 않습니다. **화면이 표시할 내용(검색, 필터, 정렬, 페이지)을 선언하면 엔진이 요청이 필요한지 판단합니다.** 각 선언은 다음 세 가지 중 하나로 끝납니다:

- **로컬에서 제공됨** — 필요한 모든 레코드가 이미 기기에 있습니다.
- **가져옴** — 엔진이 매장에서 데이터를 가져왔습니다.
- **해제됨** — 화면이 해당 선언을 해제했습니다. 보통 스크롤하거나 필터를 변경하여 새 선언으로 대체된 경우입니다. 이는 일반적인 동작이며 오류가 아닙니다.

매장에서 처리할 수 없는 필터는 기기에서 적용합니다. 쿼리의 나머지 부분은 여전히 매장으로 보낼 수 있습니다. 선언이 처리되었다고 해서 해당 종류의 레코드가 모두 다운로드되었다는 뜻은 아닙니다. 다운로드 완료 여부는 [아래](#coverage)에서 설명하는 방식으로 별도 추적합니다.

</AccordionItem>
</Accordion>

## 모두 다운로드되었나요? {#coverage}

**매장 상태 → 데이터베이스**에는 각 레코드 종류별로 기기에 저장된 수량, 매장의 전체 수량, 다운로드 범위 막대가 표시됩니다. [이 기기에 저장된 항목](../support/store-health.mdx#coverage)을 참고하세요. 여기에 표시되는 전체 수량을 기기에 저장된 데이터로 추정하지는 않습니다:

- **전체 수가 오래되었거나 없으면 *확인 중…* 표시가 나타납니다.** 오래된 경우에는 매장에서 마지막으로 받은 수치가 옆에 남아 있습니다. 기기에 저장된 개수를 기준으로 하면 항상 100%로 표시되어, 이 수치로 보여 주려는 차이가 가려집니다.
- **주문은 설계상 일부만 다운로드된 것으로 표시됩니다.** 막대는 매장의 모든 주문을 기준으로 하지만 계산대에는 진행 중인 주문과 최근 주문만 보관합니다(**진행 중인 주문 + 최근 주문은 기기에 유지 · 이전 주문은 조회 시 다운로드**).
- **판매 준비는 일찍 완료됩니다.** 첫 상품이 기기에 저장되는 즉시 판매 준비 상태가 되며, 오프라인이어도 준비 완료를 막지 않습니다. 오프라인 판매를 지원하기 위한 동작입니다.

<Accordion>
<AccordionItem question="다운로드 전체 수량을 확인하는 방식">

*상품 5,000개 중 1,240개*와 같은 수치를 표시하려면 기준이 되는 매장의 전체 수량이 필요합니다. 엔진은 레코드 종류별로 전체 수량을 유지합니다. 종류마다 페이지당 레코드 하나만 요청하여 WooCommerce의 `X-WP-Total` 헤더를 읽는 가벼운 별도 요청을 사용하며, 각 종류에 대해 약 15분에 최대 한 번만 요청합니다.

</AccordionItem>
</Accordion>

## 변경 사항이 매장으로 전송되는 방식 {#write-path}

기기에서 발생하는 모든 변경 사항(판매, 상품 수정, 신규 고객)은 먼저 기기에 저장되고 약 한 초 이내에 매장으로 전송됩니다. 진행 중인 장바구니는 예외로, **결제**를 누를 때 전송됩니다. **오프라인에서 기록한 판매는 기기에서 대기하다가 연결이 복구되면 전송됩니다.** 대부분의 변경 사항은 별도 조치가 필요하지 않습니다. 두 가지 경우에는 **매장 상태 → 데이터베이스**에서 선택해야 하며, 세 번째 경우는 자동으로 처리됩니다:

- **충돌이 발생한 주문은 한 번 재시도합니다.** 매장에 더 최신인 주문 사본이 있으면 엔진이 데이터를 조정하여 한 번 더 전송합니다. 다시 실패하거나 주문이 아닌 레코드라면 변경 사항을 보류하고 **다시 보내기** 또는 **서버 버전 사용**을 선택할 때까지 기다립니다. [매장에 더 최신 버전이 있어 보류된 변경 사항](../support/store-health.mdx#held-changes)을 참고하세요.
- **매장에서 거부한 변경 사항은 자동으로 재시도하지 않습니다.** 단, 다음에 설명하는 매장에서 삭제한 주문은 예외입니다. 거부된 변경 사항은 매장이 보낸 사유와 함께 보관되며 **매장 상태 → 데이터베이스**에 **서버에 전달되지 못한 변경 사항**으로 표시됩니다. **다시 보내기**는 현재 기기에 저장된 레코드로 변경 사항을 다시 구성하고, **버리기**는 해당 변경 사항을 삭제합니다. [서버에 전달되지 못한 변경 사항](../support/store-health.mdx#refused-changes)을 참고하세요.
- **매장에서 삭제된 주문.** 계산대에서 주문을 계속 업데이트하는 동안 매장에서 해당 주문을 삭제하거나 휴지통으로 옮겼다면 POS가 묻지 않고 처리합니다. 진행 중인 장바구니는 보관했다가 다음에 **결제**를 누르면 새 번호의 새 주문으로 다시 전송합니다. 그 외 주문은 이 기기에서 제거합니다. **매장에서 삭제된 주문**이라는 제목의 메시지가 한 번 표시되어 어떤 처리가 이루어졌는지 알려 줍니다:
  - 진행 중인 장바구니: **매장에서 주문 #1234가 삭제되었습니다. 장바구니는 새 주문으로 보관되었습니다.**
  - 그 외 주문: **매장에서 주문 #1234가 삭제되어 이 기기에서도 제거되었습니다.**

  로그에는 [SYNC203](../error-codes/SYNC203.mdx)이 기록됩니다.

<Accordion>
<AccordionItem question="변경 사항을 전송하는 방식">

- **영구 저장되는 대기열에 먼저 기록합니다.** 각 변경 사항은 전송에 앞서 기기의 대기열에 저장됩니다. 약 0.3초 후 쓰기 대기열 처리 작업이 이를 전송하며, 전송을 촉발하는 신호가 놓친 항목은 10초마다 실행되는 폴링이 처리합니다.
- **장바구니 변경 사항은 주문별로 하나씩 처리합니다.** 빠르게 연속 스캔해도 순서대로 적용됩니다. 장바구니에 이미 정확히 한 줄로 들어 있는 상품을 추가하면 새 줄을 추가하는 대신 기존 줄의 수량을 늘립니다.
- **매장이 반환한 데이터를 보관합니다.** 매장이 변경 사항을 수락하면 기기는 매장의 사본을 받아 이후 수정의 기준으로 삼습니다. 주문에서는 WooCommerce가 부여한 항목 ID를 유지하므로 업데이트할 때 중복 항목이 추가되지 않습니다. 매장에 아직 전달되지 않은 로컬 수정 사항은 덮어쓰지 않습니다.
- **삭제된 주문은 POS가 처리합니다.** 매장은 더 이상 존재하지 않는 주문의 업데이트 요청에 `404`로 응답합니다. POS는 대기열의 변경 사항을 버립니다. 진행 중인 장바구니라면 그동안 수정한 내용까지 포함하여 새 주문으로 대기열에 다시 추가합니다.

</AccordionItem>
</Accordion>

## 하나의 탭에서 POS 실행 {#multi-tab}

웹 브라우저에서는 **사이트당 하나의 탭만 POS를 실행합니다**. 같은 사이트의 두 번째 탭은 어떤 매장이나 캐셔를 사용하든 이 화면에서 멈춥니다. 로컬 데이터베이스를 열지 않으므로 판매를 기록하거나 데이터를 전송할 수 없으며, 첫 번째 탭의 동작에는 영향을 주지 않습니다.

<JourneyShot manifest={manifest} device="tablet" step={5} offsets={[[637, 37], [334, 0]]} alt="POS의 두 번째 브라우저 탭: 다른 탭에서 POS가 열려 있습니다, 하나의 탭에서만 계산대를 실행할 수 있습니다, 여기서 이어서 사용 버튼">

1. **다른 탭에서 POS가 열려 있습니다** — 이 탭은 대기 상태입니다. **하나의 탭에서만 계산대를 실행할 수 있습니다.**
2. **여기서 이어서 사용** — 다른 탭에 제어권을 넘겨 달라고 요청합니다. 다른 탭은 진행 중인 결제를 마치고 저장을 최대 15초 동안 기다린 다음 대기 상태로 전환되며, 이 탭이 POS를 불러옵니다.

</JourneyShot>

- **대기 중인 탭은 저절로 활성화되지 않습니다.** 활성 탭을 닫아도 다른 탭은 **여기서 이어서 사용**을 누르거나 다시 로드할 때까지 대기 상태로 남습니다.
- **"다른 탭이 응답하지 않습니다"** — 활성 탭이 제어권을 넘기지 않았습니다. 이 탭에서 계속하려면 기존 활성 탭을 닫거나 다시 로드하세요.
- **이전 탭이 계산대 제어권을 넘긴 뒤 시작하려는 결제**는 전송 전에 거부되며 [CLIENT161](../error-codes/CLIENT161.mdx)로 기록됩니다. 제어권을 넘기기 전에 시작한 결제는, 전환 과정에서 저장을 기다리는 동안 시작했더라도, 완료된 후에 제어권을 넘깁니다.
- **데스크톱 및 모바일 앱**에는 탭도, 탭 실행 제한도 없습니다. 탭 간 조정을 할 수 없는 브라우저(Web Locks 미지원)는 이 확인 없이 모든 탭을 실행합니다.

## 로컬 저장소 {#local-storage}

2.0에서는 모든 계산대가 기기 자체의 데이터베이스에 데이터를 보관합니다.

배너에 **로컬 데이터베이스를 사용할 수 없습니다 — 앱을 다시 로드할 때까지 스캔, 결제, 저장 및 취소가 차단됩니다**라고 표시되면 **앱 다시 로드**를 누르세요. 다시 로드하기 전까지는 환불도 차단되며, 스캔하면 아무 반응 없이 넘어가는 대신 **스캔을 사용할 수 없습니다**가 표시됩니다. 기기의 데이터베이스가 응답하지 않거나 로컬 저장이 멈추면 POS는 판매 데이터 손실로 이어질 수 있는 모든 작업을 중단합니다. 오류 코드는 [SYNC161](../error-codes/SYNC161.mdx)입니다.

<Accordion>
<AccordionItem question="플랫폼별 데이터 저장 위치">

데이터베이스는 RxDB Premium을 통해 실행되는 SQLite입니다:

| 플랫폼 | 데이터 저장 위치 |
| --- | --- |
| 웹 | 전용 워커 하나에서 실행되는 SQLite-wasm, 브라우저의 비공개 파일 시스템(OPFS)에 저장 |
| 데스크톱 | 앱의 메인 프로세스에서 실행되는 SQLite |
| iOS 및 Android | expo-sqlite를 통해 실행되는 SQLite |

필터링, 정렬, 페이지 처리는 데이터베이스 내부에서 수행됩니다. 화면에 표시할 행만 앱으로 전달됩니다.

</AccordionItem>
</Accordion>

## 2.0으로 업그레이드 {#upgrading}

2.0은 로컬 데이터를 마이그레이션하지 않습니다. 모든 기기가 **모든 데이터를 다시 다운로드합니다**:

1. **모든 기기가 새 데이터베이스로 시작**하여 매장에서 데이터를 한 번씩 다시 다운로드합니다. 매장에는 동기화된 모든 데이터의 전체 사본이 보관되어 있습니다.
2. **업데이트 전에 대기열에 있던 변경 사항은 전송되지 않습니다.** 모든 계산대에서 **매장 상태 → 데이터베이스**의 **전송 대기 중인 변경 사항**이 0이 될 때까지 기다린 다음 업데이트하세요. [업데이트를 누르기 전에](../getting-started/upgrading-to-2.mdx#before-you-click-update)를 참고하세요. 매장의 판매 준비가 완료되면 기존 1.x 데이터베이스가 삭제됩니다.
3. **앱과 플러그인은 함께 업데이트해야 합니다.** 2.0 앱에는 WCPOS 2.0 플러그인이 필요합니다. 한쪽만 업데이트하면 앱이 어느 쪽이 오래된 버전인지 알려 줍니다. 플러그인이 오래된 경우 [AUTH331](../error-codes/AUTH331.mdx), 앱이 오래된 경우 [SYNC341](../error-codes/SYNC341.mdx)이 표시됩니다.

| 거부된 변경 사항 | 사용자에게 알리지 않고 재시도 | 영구 저장 대기열, 복구 패널, 알림 없는 재시도 없음 | 동일 |
| 브라우저 탭 | 조정 없음 | 모든 탭 활성, 선택된 탭 하나가 전송 | 사이트당 활성 탭 하나, 나머지는 대기 |
| 저장소 | IndexedDB(웹), SQLite(앱) | 파일 시스템 저장소(웹에서는 OPFS) | 모든 플랫폼에서 SQLite |
| 동기화 조정 | 고정 | 매장 상태의 사전 설정과 슬라이더 | 동일 |
| 로컬 검색 | 단어 접두사 일치 | 부분 문자열 일치 | 길이에 관계없이 레코드 내 어느 위치에서든 모든 검색 단어 일치 |

</AccordionItem>
</Accordion>

요청 한도, 매장이 응답에 어려움을 겪을 때의 요청 속도 조절, 측정 수치는 [동기화 성능](sync-performance.mdx)을 참고하세요.
