**WP Admin:** Vorlagen werden unter `WP Admin → POS → Templates` bearbeitet; diese Seite listet die Felder auf, die sie drucken können.

Wie Sie einen Beleg drucken oder per E-Mail versenden, erfahren Sie unter [Belege und der Bildschirm nach der Zahlung](./at-checkout.mdx). Wie Sie eine Vorlage auswählen oder von KI anpassen lassen, erfahren Sie unter [Ihren Beleg anpassen](./customise.mdx).

Diese Seite richtet sich an alle, die den Code einer Vorlage von Hand bearbeiten. Jede Vorlage, ob HTML oder Thermodruck, verwendet dieselben Belegdaten: Filiale, Bestellung, Artikel, Summen und Zahlungen. Die Seite zeigt, wie Sie ein Feld drucken, stellt drei häufige Beispiele vor und listet alle Felder auf.

**Direkt zu:** [Feld finden](#field-reference) · [Häufige Beispiele](#common-recipes) · [Wenn etwas schiefgeht](#if-something-goes-wrong)

## Ein Feld drucken {#print-a-field}

1. Öffnen Sie die Vorlage unter **WP Admin → POS → Vorlagen** (Einzelheiten finden Sie unter [Von Hand bearbeiten](./customise.mdx#option-3--edit-it-by-hand)).
2. Geben Sie an der Stelle, an der das Feld gedruckt werden soll, seinen Pfad in doppelten geschweiften Klammern ein, etwa `{{store.name}}`, `{{order.number}}` oder `{{totals.total_display}}`, oder fügen Sie es aus der Feldliste neben dem Code ein.
3. Prüfen Sie die Vorschau unter dem Code und klicken Sie dann zum Speichern auf **Aktualisieren**.

Bei einer Liste, etwa den Artikeln, umschließen Sie die Zeile mit einem Abschnitt. Sie wird dann einmal pro Artikel wiederholt:

```mustache
{{#lines}}
  {{name}} x {{qty}} —
  {{line_total_display}}
{{/lines}}
```

Ein Abschnitt lässt seinen Inhalt auch weg, wenn das Feld leer, null oder falsch ist. Daher wird `{{#customer.id}}…{{/customer.id}}` nur für einen namentlich bekannten Kunden gedruckt. Verwenden Sie für Geldbeträge das Feld, das auf `_display` endet; siehe [Währungsfelder](#currency-fields).

Belege lassen sich auch offline drucken: Die App erstellt aus der Bestellung auf dem Gerät eine Kopie der Belegdaten.

<Accordion>
  <AccordionItem question="Warum Belege voneinander abweichen können">

### Woher die Daten stammen {#where-the-data-comes-from}

Der Server Ihrer Filiale erstellt die Belegdaten für jede Bestellung, und die App erstellt aus der Bestellung auf dem Gerät eine verkürzte Kopie: Diese enthält weder `cashier` noch Öffnungszeiten, Hinweise oder Bedingungen der Filiale und auch kein `totals.paid_total` oder `totals.change_total`. Eine HTML- oder Thermodruckvorlage öffnet sich sofort mit der Kopie vom Gerät und wechselt zur Serverkopie, sobald diese eintrifft. Offline wird die Kopie vom Gerät gedruckt, sodass diese Felder leer bleiben. Mit WCPOS Pro enthält die Kopie auf dem Gerät auch das Filiallogo; ohne Pro kommt das Logo mit der Serverkopie. Eine ältere PHP-Vorlage wird immer vom Server gerendert. Deshalb verwendet eine Vorlage die unten aufgeführten Felder und niemals PHP-Bestellmethoden. Einige Felder werden nur gedruckt, wenn der Server die Vorlage rendert, etwa bei einem PDF-Download; sie sind unter [Wenn etwas schiefgeht](#if-something-goes-wrong) aufgeführt.

</Accordion>

Klicken oder tippen Sie auf einen der beiden, um zu den Feldern dieses Abschnitts zu springen. Auf einem Smartphone folgen die Karten unter dem Beleg in derselben Reihenfolge von oben nach unten.

## Feldreferenz {#field-reference}

Klappen Sie einen Abschnitt auf, um seine Felder zu sehen. Der erste Eintrag listet alle Abschnitte und ihre Typen auf.

<Accordion>
  <AccordionItem question="Alle Abschnitte und ihre Typen">

### Abschnitte auf oberster Ebene {#top-level-sections}

| Abschnitt | Inhalt |
|---------|---------------|
| `order` (Objekt) | Bestellkennung, Status, Datumsangaben, Notiz und Informationen zur Zahlungs-URL |
| `store` (Objekt) | Filialkennung, Adresse, Kontaktdaten, Steuer-IDs, Logo, Öffnungszeiten und Fußzeilentext |
| `cashier` (Objekt) | Benutzer, der die Bestellung bearbeitet hat |
| `customer` (Objekt) | Anzeigename, Adressen und Steuer-IDs des Kunden |
| `lines` (Array) | Produktpositionen |
| `fees` (Array) | Gebührenzeilen |
| `shipping` (Array) | Versandzeilen |
| `discounts` (Array) | Gutschein-/Rabattzeilen |
| `totals` (Objekt) | Bestellsummen, Zahlungssummen, Rückerstattungsübersicht und Artikelanzahlen |
| `tax` (Objekt) | Kennzeichen für die Steueranzeige als Abschnittsbedingungen |
| `tax_summary` (Array) | Zeilen der Steuerübersicht je Steuersatz |
| `has_tax_summary` (boolescher Wert) | Einfache Bedingung für `tax_summary` |
| `payments` (Array) | Zahlungszeilen |
| `refunds` (Array) | Der Bestellung zugeordnete Rückerstattungsdatensätze |
| `fiscal` (Objekt) | Felder des Fiskaldaten-Snapshots, die von Fiskalintegrationen befüllt werden |
| `register` (Objekt) | Die Kasse, an der der Verkauf erfolgte: `id` und `name`. Leere Zeichenfolgen, wenn unbekannt |
| `software` (Objekt) | Die Software, die den Beleg ausgestellt hat: `name` (`WCPOS`), `plugin_version`, `app_version`, `app_build`, `platform` |
| `presentation_hints` (Objekt) | Hinweise zur Formatierung und zum Rendering |
| `i18n` (Objekt) | Übersetzte Beschriftungen für mitgelieferte und benutzerdefinierte Vorlagen |

  </AccordionItem>

### Steuer-ID-Objekte {#tax-id-objects}

`store.tax_ids` und `customer.tax_ids` enthalten Objekte mit derselben Struktur:

| Feld | Typ | Beschreibung |
|-------|------|-------------|
| `type` | Zeichenfolge | Kennung wie `eu_vat`, `de_steuernummer`, `au_abn`, `br_cpf`, `us_ein` oder `other` |
| `value` | Zeichenfolge | Zu druckender Steuer-ID-Wert |
| `country` | Zeichenfolge/null | ISO-Ländercode; null für `eu_vat` und `other` |
| `label` | Zeichenfolge | Lokalisierte Anzeigebezeichnung, die vor dem Rendern ermittelt wird |

Beispiel:

```mustache
{{#store.tax_ids}}
  {{label}}: {{value}}
{{/store.tax_ids}}
```

    <span>{{i18n.savings}}: -{{line_savings_display}}</span>

{{/lines}}

:::note Vor v1.9.0 erstellte Bestellungen erneut drucken
Bei älteren WCPOS-Bestellungen kann die Reduzierung vom regulären Preis auf den Verkaufspreis bereits in `discounts` enthalten sein. Wenn Ihre benutzerdefinierte Vorlage sowohl Positionsersparnisse als auch Positionsrabatte druckt, verwenden Sie `savings_in_discounts`, damit dieselbe Reduzierung nicht doppelt angezeigt wird:

```mustache
{{#lines}}
  {{#line_savings}}
    <span style="text-decoration: line-through;">{{line_regular_total_display}}</span>
    {{^savings_in_discounts}}
      <span>{{i18n.savings}}: -{{line_savings_display}}</span>
    {{/savings_in_discounts}}
  {{/line_savings}}
  {{#discounts}}
    <span>{{i18n.discount}}: -{{discounts_display}}</span>
  {{/discounts}}
{{/lines}}
```

Wenn die Vorlage keine `discounts`-Zeile auf Positionsebene druckt, zeigen Sie `line_savings` weiterhin an, auch wenn `savings_in_discounts` wahr ist. Die mitgelieferten Vorlagen berücksichtigen diesen Unterschied automatisch.
:::

## Wie die Preise zusammenhängen {#price-model}

Ein Artikel auf dem Beleg hat mehrere Preise. Die Bezeichnungen lassen sich am besten anhand der Beträge nachvollziehen. Dies ist die Espresso-Position aus der Beispielbestellung — ein Produkt für $17.00, das im Angebot $14.50 kostet, mit einem zusätzlichen Gutschein über 10%:

  caption="Espressobohnen — eine Einheit (die Bestellung enthält zwei)"
  scaleLabel="regulärer Preis 17.00"
  segments={[
    { kind: 'paid', amount: 13.05, label: "13.05 bezahlt" },
    { kind: 'coupon', amount: 1.45, label: "1.45" },

Eine Angebotspreisersparnis ist die Differenz zwischen regulärem Preis und Verkaufspreis. Ein Rabatt ist der von WooCommerce berechnete Gutscheinabzug. Die Bestellsummen und Berichte von WooCommerce enthalten nur die Rabatte. Daher fasst `total_saved` beides zu einer Zahl für den Kunden zusammen.

## Regeln für die Ausgabe {#rendering-rules}

So werden Geldbeträge, Preise mit oder ohne Steuer und Datumsangaben gedruckt. Öffnen Sie den benötigten Abschnitt.

  <AccordionItem question="Geldbeträge drucken und Nullbeträge ausblenden">

### Währungsfelder {#currency-fields}

Geldfelder bleiben Zahlen. Jedes erhält ein `_display`-Feld, das in der Sprache und Währung der Filiale formatiert ist:

| Numerisches Feld | Anzeigefeld |
|---------------|---------------|
| `totals.total` | `totals.total_display` |
| `lines[].line_total` | `lines[].line_total_display` |
| `payments[].amount` | `payments[].amount_display` |
| `tax_summary[].tax_amount` | `tax_summary[].tax_amount_display` |

Drucken Sie das `_display`-Feld. Verwenden Sie die Zahl nur für einen Abschnitt oder für maschinenlesbare Ausgaben: `{{#totals.change_total}}…{{/totals.change_total}}` lässt die zugehörige Zeile weg, wenn der Betrag null ist.

### Datumsobjekte {#date-objects}

Jedes Datum liegt bereits in mehreren Formaten vor, sodass eine Vorlage Datumsangaben nie selbst formatieren muss.

| Feld | Beschreibung |
|-------|-------------|
| `datetime`, `date`, `time` | Standardzeichenfolgen für Datum/Uhrzeit |
| `datetime_short`, `datetime_long`, `datetime_full` | Kombinierte Formate gemäß Gebietsschema |
| `date_short`, `date_long`, `date_full` | Reine Datumsformate gemäß Gebietsschema |
| `date_ymd`, `date_dmy`, `date_mdy` | Datumsformate mit fester Reihenfolge |

## Belegdaten erweitern {#extending}

Ein Plugin kann über den Filter `wcpos_receipt_data` eigene Felder zu den Belegdaten hinzufügen.

<Accordion>
  <AccordionItem question="Der Filter — seine Argumente, die sechs Modi und ein Beispiel">

WCPOS hält die oben genannten Felder frei von pluginspezifischen Daten. Wenn ein Plugin auf dem Beleg Informationen benötigt, die WooCommerce nicht abbildet, fügt es diese selbst über den Filter `wcpos_receipt_data` hinzu — genauso, wie Plugins die Bestellsummen von WooCommerce filtern. Der Filter wird bei jedem Beleg ausgeführt, den der Server erstellt: aktuellen Belegen, Fiskaldaten-Snapshots zum Zahlungszeitpunkt, PDF-Downloads und älteren PHP-Vorlagen. Vor WCPOS 2.0 hieß dieser Filter `woocommerce_pos_receipt_data`; dieser Name funktioniert weiterhin, ist aber seit 2.0 veraltet und wird frühestens in 2.2 entfernt (siehe [Hook-Benennung](../extensions/index.mdx#hook-naming)).

Das dritte Argument, `$mode`, gibt an, welches Dokument erstellt wird: `live`, `fiscal`, `refund`, `preview` (Beispielbelege im Vorlageneditor und in der Galerie), `closure` oder `xreport` (Kassenabschluss- und X-Bericht-Dokumente). Bei `preview`, `closure` und `xreport` handelt es sich um eine ungespeicherte Bestellung mit der ID `0`. Ein Plugin, das eine gespeicherte Bestellung benötigt, sollte `$data` unverändert zurückgeben, wenn `$order->get_id()` den Wert `0` hat.

```php
add_filter( 'wcpos_receipt_data', function ( array $data, WC_Abstract_Order $order, string $mode ) {
    foreach ( $data['discounts'] as &$row ) {
        if ( 'smart_coupon' === $row['discount_type'] ) {
            $row['gift_card'] = true;
        }
    }
    return $data;
}, 10, 3 );
```

Eine Vorlage kann den neuen Schlüssel dann wie jeden anderen Abschnitt als Bedingung verwenden:

```
{{#discounts}}
  {{#gift_card}}Gift Card{{/gift_card}}{{^gift_card}}{{i18n.discount}}{{/gift_card}}{{#label}}: {{label}}{{/label}}
{{/discounts}}
```

Im Schema definierte Schlüssel sollten ihre dokumentierten Typen beibehalten. Hinzugefügte Schlüssel sind nicht Teil des Schemas und erscheinen daher nicht in der Feldauswahl des Vorlageneditors. Fiskaldaten-Snapshots enthalten nur das, was der Filter zum Zahlungszeitpunkt der Bestellung hinzugefügt hat. Der Filter ist ab WCPOS 1.10.8 verfügbar.

  </AccordionItem>

  <AccordionItem question="Welche Belege einen hinzugefügten Schlüssel drucken">

Jeder hinzugefügte Schlüssel steht den Belegen zur Verfügung, die der Server selbst rendert: PDF-Downloads und älteren PHP-Vorlagen. HTML- und Thermodruckvorlagen, die in der POS-App gerendert werden, bauen die Daten zunächst neu auf: Ein innerhalb von `order`, `store`, `cashier` oder `customer` hinzugefügter Schlüssel wird übernommen. Ein an anderer Stelle hinzugefügter Schlüssel, etwa in der Rabattzeile oben, wird dagegen weggelassen. {/* pending: monorepo#3363 */} Bei einem aktuellen Beleg mit Fiskaldaten-Snapshot werden die Fiskalkennung, `register` und `software` nach Ausführung des Filters aus dem Snapshot kopiert. Änderungen an diesen Werten in diesem Filter haben daher keine Wirkung; erweitern Sie stattdessen den Snapshot.

  </AccordionItem>
</Accordion>

## Wenn etwas schiefgeht {#if-something-goes-wrong}

**Eine Zeile druckt auf einem Beleg `$0.00` und auf einem anderen nichts.** Einige `_display`-Felder wie `totals.change_total_display`, `totals.refund_total_display` und `payments[].tendered_display` bleiben bei null leer, wenn der Server den Beleg rendert, und zeigen `$0.00`, wenn die App ihn rendert. Umschließen Sie die Zeile stattdessen mit einem Abschnitt, der die Zahl als Bedingung verwendet, damit sie in beiden Fällen entfällt: `{{#totals.change_total}}…{{/totals.change_total}}`.

**Die Zeile „Insgesamt gespart“ fehlt.** `totals.total_saved_complete` ist falsch: Für mindestens einen Artikel ist kein regulärer Preis gespeichert, sodass sich die Ersparnis nicht berechnen lässt. Das betrifft üblicherweise Bestellungen, die vor WCPOS 1.9.0 an der Kasse erfasst wurden.

**Die Gesamtsumme ist niedriger als der vom Kunden bezahlte Betrag.** Die Filiale zeigt Preise exklusive Steuer an, daher ist `totals.total` die Summe vor Steuer. Drucken Sie `totals.total_incl_display` für den berechneten Betrag. Der mit WCPOS gelieferte ältere PHP-Beleg druckt diesen Betrag.

**Ein Feld wird im PDF-Download gedruckt, aber nicht im POS.** In der App gerenderte Vorlagen bauen die Daten zunächst neu auf und lassen dabei einige Felder weg, die nur in PDF-Downloads und älteren PHP-Vorlagen gedruckt werden. Drucken Sie ein Feld aus der folgenden Liste nur dort, oder umschließen Sie es mit einem Abschnitt, damit der POS-Beleg es weglässt. {/* pending: monorepo#3363 */}

<Accordion>
  <AccordionItem question="Felder, die sich zwischen PDF- und POS-Belegen unterscheiden">

- `lines[].attributes`, `lines[].total_refunded_display` und `lines[].unit_subtotal_display` (mit seinen Varianten `_incl` und `_excl`)
- `software.platform`
- `presentation_hints` außer `display_tax`, `prices_entered_with_tax`, `rounding_mode`, `locale` und `order_barcode_type`
- Kunden-Steuer-IDs der deutschen, niederländischen, französischen und schweizerischen Typen sowie des Typs für britische Unternehmen
- Schlüssel, die ein Plugin außerhalb von `order`, `store`, `cashier` und `customer` hinzufügt; siehe [Belegdaten erweitern](#extending)

</AccordionItem>
</Accordion>

## Versionen {#versions}

Die Belegdaten haben eine eigene Versionsnummer, unabhängig von der des Plugins. Neuere Felder fehlen in älteren Belegen, etwa in einem Fiskaldaten-Snapshot, der vor Einführung des Feldes erstellt wurde. Umschließen Sie sie daher mit einem Abschnitt.

| Version | Hinzugefügt |
|---------|-------|
| 1.1 | Regulärer Preis, Verkaufspreis und Ersparnis für jeden Artikel sowie die Ersparnissummen der Bestellung, einschließlich **Insgesamt gespart**. Keines dieser Felder verändert die Bestellsummen oder WooCommerce-Berichte |
| 1.2 | `discounts[].discount_type` |
| 1.3 | `customer.first_name` und die Kunden-Anzeigebezeichnungen in `i18n` |
| 1.4 | `register`, `software`, die fiskalischen Dokumentfelder (`fiscal.document_type`, die `is_…`-Kennzeichen, `sale_time`, `received_at`, `sale_tz`, `sale_counter`, `corrects`) und ihre `i18n`-Beschriftungen |
