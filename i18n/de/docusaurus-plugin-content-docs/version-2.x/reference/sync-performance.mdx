So legen Sie fest, wie stark eine Kasse Ihren Server beansprucht:

1. Öffnen Sie **Filialstatus** über das Pulssymbol unten im Menü.
2. Tippen Sie auf **Leistung**.
3. Lassen Sie **Ausgewogen** ausgewählt: Das ist die Standardeinstellung. Wenn Ihr Server regelmäßig an seine Grenzen stößt und die Tempoanzeige oft **Gedrosselt** oder **Pausiert bis …** anzeigt, tippen Sie stattdessen auf **Eco**.

Die Einstellung wird nur auf diesem Gerät für die aktuell ausgewählte Filiale gespeichert. Stellen Sie daher jede Kasse einzeln ein. Einen Vergleich der Voreinstellungen finden Sie unter [Wie stark die Synchronisierung Ihren Server belastet](#request-budgets).

## Die Meldungen im Tab „Leistung“ verstehen {#troubleshooting}

Vier mögliche Anzeigen im Tab „Leistung“. Bei den ersten beiden müssen Sie handeln; die letzten beiden sind normal.

<Accordion>
<AccordionItem question="An den meisten Tagen „Gedrosselt“ oder „Pausiert bis …“ — wählen Sie Eco und prüfen Sie dann Ihren Server">

Ihr Server weist die Kasse regelmäßig ab, gibt Fehler zurück oder antwortet langsam. Die [Tempoanzeige](#server-pressure) nennt den jeweiligen Grund. Wählen Sie auf jeder Kasse **Eco**. Unter [Serverleistung](../support/performance/server.mdx) finden Sie Prüfungen für Hosting, Plugins, Firewall und langsame Antworten.

</AccordionItem>
<AccordionItem question="⚠ Handlungsbedarf — prüfen Sie die Verbindung und die Synchronisierungsaufgaben dieser Kasse">

Die Kasse ist offline, die Synchronisierung ist blockiert, ein erster Download ist fehlgeschlagen oder der letzte Lauf einer Synchronisierungsaufgabe ist fehlgeschlagen. Siehe [Filialstatus](../support/store-health.mdx#performance).

</AccordionItem>
<AccordionItem question="Ihr Server meldet seine Auslastung nicht — die übrigen Messwerte funktionieren weiterhin">

Es liegt kein Problem vor. Die Tempoanzeige und die Anzahl der Anfragen funktionieren weiterhin.

</AccordionItem>
<AccordionItem question="0.0 MB neben vielen Anfragen — Größen, die Ihr Server nicht angibt, zählen als 0">

Ihr Server gibt die Größe seiner Antworten nicht an, daher zählen sie als 0. Siehe [Was die Zahlen nicht aussagen](#honest-limits).

</AccordionItem>
</Accordion>

## Wie stark die Synchronisierung Ihren Server belastet {#request-budgets}

Zwei Einstellungen bestimmen die dauerhafte Belastung: wie oft die Kasse prüft und wie viele Datensätze sie pro Anfrage abruft.

- **Eco** — wählen Sie diese Einstellung, wenn Ihr Server regelmäßig an seine Grenzen stößt. Eine Prüfung alle 5 Minuten, 25 Datensätze pro Anfrage.
- **Ausgewogen** (die Standardeinstellung) — für die meisten Filialen geeignet. Eine Prüfung alle 60 Sekunden, 50 Datensätze pro Anfrage.
- **Echtzeit** — wählen Sie diese Einstellung für die schnellsten Aktualisierungen, wenn Ihr Server noch Kapazität hat. Eine Prüfung alle 10 Sekunden, 75 Datensätze pro Anfrage.
- **Benutzerdefiniert** — wählen Sie diese Einstellung, um die beiden Schieberegler selbst einzustellen.

<Accordion>
<AccordionItem question="Prüfungen pro Stunde und die benutzerdefinierten Einstellbereiche">

**Eco** führt 12 Prüfungen pro Stunde durch, **Ausgewogen** 60 und **Echtzeit** 360 — die höchste Belastung für Ihren Server. **Benutzerdefiniert** prüft alle 5 Sekunden bis 5 Minuten, einstellbar in Schritten von 5 Sekunden, mit 10 bis 100 Datensätzen pro Anfrage in Schritten von 5: von 720 Prüfungen pro Stunde bis hinunter zu 12.

</AccordionItem>
</Accordion>

Wenn Sie einen der Schieberegler bewegen, wechselt die Einstellung zu **Benutzerdefiniert**; **Auf Ausgewogen zurücksetzen** stellt den Standard wieder her.

### Belastung pro Seite {#page-weight}

Die Anzahl der Datensätze pro Anfrage bestimmt, wie viel Arbeit jeder Download für Ihren Server bedeutet. Eine Seite mit 100 Produkten kann selbst auf einem schnellen Server Sekunden dauern, und das Prüfintervall vervielfacht diese Belastung nur. Deshalb verändert jede Voreinstellung beide Werte gemeinsam, und keine nutzt das Maximum von 100 Datensätzen: Dieses steht unter **Benutzerdefiniert** für Server zur Verfügung, von denen Sie wissen, dass sie damit zurechtkommen.

### Warum ein Shop ohne Änderungen wenig Last verursacht {#cheap-checks}

Einen Shop ohne Änderungen synchron zu halten, verursacht wenig Last: Seine Antworten sind leer, die Prüfungen der Kassen sind zeitlich verteilt, und bei schnellen Einstellungen prüft eine unbenutzte Kasse seltener.

<Accordion>
<AccordionItem question="Leere Antworten, verteilte Prüfungen und unbenutzte Kassen im Detail">

- **Ein unveränderter Shop gibt eine leere Antwort zurück.** Die Kasse sendet ihren zuletzt bekannten Stand, und der Server antwortet mit `304 Not Modified` ohne Antwortinhalt. Das zählt weiterhin als eine Anfrage.
- **Prüfungen werden zeitlich verteilt.** Jede Wartezeit liegt zwischen 80% und 120% Ihrer Einstellung, damit mehrere Kassen nicht alle gleichzeitig anfragen. Deshalb entspricht der Countdown unter **Aktuell** selten genau Ihrer Einstellung.
- **Eine unbenutzte Kasse drosselt ihr Tempo,** wenn ein Intervall unter einer Minute eingestellt ist. Nach 10 Minuten ohne Antippen, Tastendruck oder Barcode-Scan prüft sie zunächst alle 30 Sekunden, dann alle 60 Sekunden. Eine ausgeblendete App wechselt direkt zu 60 Sekunden. Jede Bedienung stellt das ursprüngliche Tempo wieder her und löst sofort eine Prüfung aus, sofern Ihr Server die Kasse nicht gedrosselt hat. **Ausgewogen** und **Eco** liegen bereits bei einer Minute oder darüber und ändern sich daher nicht.

</AccordionItem>
</Accordion>

### Wartung im Hintergrund {#maintenance-budgets}

Zusätzlich zu den Änderungsprüfungen halten einige Hintergrundaufgaben die Datenkopie auf der Kasse vollständig und korrekt: Sie finden auf dem Server gelöschte Datensätze und laden nach, was die Kasse noch nicht heruntergeladen hat, damit sie offline verkaufen kann. Jeder Lauf hat eine feste Obergrenze: höchstens 11 Anfragen; die Nachladeaufgaben benötigen 1.

Auch offene Bestellungen werden geprüft. Beim Start der Kasse und danach alle 5 Minuten fragt sie Ihren Server nach jeder [offenen Bestellung](../pos/cart/open-orders.mdx), die sie lokal vorhält und die dort bereits gespeichert ist. Pro Anfrage werden höchstens so viele Bestellungen abgefragt, wie unter **Datensätze pro Anfrage** eingestellt sind. Eine offene Bestellung, die jemand in WP Admin in den Papierkorb verschoben oder gelöscht hat, wird dann von der Kasse entfernt; eine Bestellung mit noch nicht an Ihren Server gesendeten Änderungen bleibt erhalten.

<Accordion>
<AccordionItem question="Alle Hintergrundaufgaben und ihre Obergrenzen">

| Aufgabe | Läuft ungefähr alle | Maximale Anfragen pro Lauf |
| --- | --- | --- |
| Löschprüfung | 17 min | 11 |
| Löschprüfung, Kasse bereits auf aktuellem Stand | 17 min | nur Übersichtsseiten (höchstens 9), keine Detailanfragen |
| Fingerabdrücke für bereits auf der Kasse vorhandene Datensätze (100 IDs pro Anfrage) | 15 min | 5 |
| Produkte nachladen, eine Seite in der Sortierreihenfolge der Produktliste | 5 min | 1 |
| Kunden nachladen | 5 min | 1 |
| Varianten herunterladen | 5 min | 1 |
| Gesamtzahlen vom Server für den Filialstatus (ein Zählwert pro Anfrage, Abruf bei veralteten Werten) | Prüfung alle 30 s | 11 |

</AccordionItem>
<AccordionItem question="Wie die Löschprüfung mit höchstens 11 Anfragen auskommt">

Die Prüfung vergleicht die Datensätze der Kasse gruppenweise mit dem Server. Sie liest höchstens 9 Übersichtsseiten (3 für jede geprüfte Datensatzart) und überspringt jede Gruppe, deren Zusammenfassung übereinstimmt. Nur für eine abweichende Gruppe wird eine Detailanfrage gestellt, höchstens 2 pro Lauf. Wenn noch mehr zu prüfen ist, merkt sich die Prüfung ihre Position und setzt beim nächsten Lauf dort fort, statt alles auf einmal nachzuholen. Bei hoher Serverbelastung wird ein Lauf auf 1 Übersichtsseite pro Art und 1 Detailanfrage reduziert.

</AccordionItem>
</Accordion>

### Die Angabe der Anfragen pro Stunde {#nominal-rate}

**Bei diesen Einstellungen: ~N Anfragen pro Stunde** schätzt, wie oft diese Kasse auf Änderungen prüft, allein anhand von **Auf Änderungen prüfen**. Das ist keine Obergrenze für alle Anfragen. Die Zahl unter **Letzte 24 h** oben im Tab ist die tatsächliche Gesamtzahl.

<Accordion>
<AccordionItem question="Warum die tatsächliche Anzahl abweicht">

Die zeitliche Verteilung kann die tatsächliche Anzahl erhöhen oder verringern, ein `304` zählt weiterhin mit, eine unbenutzte Kasse mit einer schnellen Einstellung fragt seltener an, und eine vom Server gedrosselte Kasse noch seltener. Wartung im Hintergrund und die eigenen Anfragen des Kassierers (Suchen, Speichern von Bestellungen) kommen hinzu.

</AccordionItem>
</Accordion>

## Vier Regeln, denen die Engine folgt {#the-four-rules}

Die oben beschriebene Belastung und die unten erläuterte Drosselung beruhen auf vier Regeln: Die Belastung richtet sich nach den Änderungen, Hintergrundarbeit hat eine Obergrenze, der Kassierer hat Vorrang, und unter Last wird zuerst die Hintergrundarbeit zurückgestellt.

<Accordion>
<AccordionItem question="Wie die einzelnen Regeln funktionieren">

Jede Kasse prüft Ihren Shop fortlaufend auf Änderungen. Deshalb geht der POS sparsam mit der Rechenzeit Ihres Servers um. Der Rest dieser Seite liefert Shop-Betreibern und Entwicklern die Zahlen hinter diesen Regeln. Eine Erläuterung des gesamten Tabs finden Sie unter [Filialstatus › Leistung](../support/store-health.mdx#performance).

1. **Die Belastung richtet sich nach den Änderungen, nicht nach der Größe Ihres Katalogs.** Jede Prüfung beginnt mit einer wenig aufwendigen Abfrage, auf die ein unveränderter Shop eine leere Antwort zurückgibt. Einen unveränderten Shop mit 50,000 Produkten synchron zu halten, verursacht ungefähr dieselbe Last wie bei einem unveränderten Shop mit 500 Produkten.
2. **Hintergrundarbeit hat eine Obergrenze.** Jede Wartungsaufgabe im Hintergrund legt fest, wie viele Anfragen sie pro Lauf höchstens stellen darf. Die Tests der Engine schlagen fehl, wenn sie mehr stellt. Größere Aufgaben laufen in kleinen Paketen und machen beim nächsten Mal dort weiter, wo sie aufgehört haben.
3. **Der Kassierer hat Vorrang.** Die Anfragen, die eine Kasse verkaufsbereit machen, werden zuerst ausgeführt. Prüfungen warten, bis die erste Produktseite heruntergeladen ist, und dann noch eine weitere Minute. Solange die App ausgeblendet ist oder im Hintergrund läuft, wartet die Wartung.
4. **Unter Last wird zuerst die Hintergrundarbeit zurückgestellt.** Wenn Ihr Server an seine Grenzen stößt, prüft die Kasse seltener auf Änderungen und verschiebt die Wartung. Suchen, Barcode-Abfragen und das Speichern eines Verkaufs werden nie zurückgehalten.

</AccordionItem>
<AccordionItem question="Warum die Rechenzeit Ihres Servers kostbar ist">

Die meisten Shops laufen auf Shared Hosting. Dort startet jede Anfrage einer Kasse WordPress von Grund auf neu, konkurriert mit den Besuchern Ihrer Website um Ressourcen und kann das Anfragelimit eines Sicherheitsplugins auslösen. Jede Kasse bringt zusätzliche eigene Prüfungen mit.

</AccordionItem>
</Accordion>

## Drosselung bei Serverproblemen {#server-pressure}

Jede Antwort an die Kasse fließt in eine Belastungsprüfung ein, die auf diesem Gerät pro Website geführt wird. Wenn sie anschlägt, zeigt die Tempoanzeige unter **Ihr Server im Zeitverlauf** dies samt Grund an. Wenn an den meisten Tagen **Gedrosselt** oder **Pausiert bis …** erscheint, siehe [Die Meldungen im Tab „Leistung“ verstehen](#troubleshooting).

<JourneyShot manifest={manifest} device="tablet" step={2} offsets={[[527, 0], [91, -84], [106, -84], [165, 0]]} alt="Ihr Server im Zeitverlauf: die Tempoanzeige mit „Normales Tempo, Ihr Server meldet eine hohe Auslastung“, die beiden noch nicht vollständig gefüllten Diagramme „Serverauslastung“ und „POS-Anfragen“ sowie der Link „Mehr in der Dokumentation erfahren“">

1. **Tempo** — wie die Kasse auf Ihren Server reagiert, unten in der Nahaufnahme gezeigt.
2. **Serverauslastung** — die von Ihrem Server gemeldete Auslastung, einschließlich aller darauf laufenden Vorgänge, nicht nur des POS. Wenn ein Server sie nicht übermittelt, erscheint **Ihr Server meldet seine Auslastung nicht**. Der Rest des Tabs funktioniert weiterhin.
3. **POS-Anfragen** — die Anfragen dieser Kasse, stundenweise für die letzten 24 Stunden. Beide Diagramme zeigen **Noch nicht genügend Daten**, bis die Kasse eine Weile gelaufen ist, wie hier zu sehen.
4. **Mehr in der Dokumentation erfahren** — öffnet [Filialstatus › Leistung](../support/store-health.mdx#performance) in der Dokumentation.

</JourneyShot>

<JourneyShot manifest={manifest} device="tablet" step={3} maxWidth={586} offsets={[[534, 0]]} alt="Nahaufnahme von „Ihr Server im Zeitverlauf“: die Tempoanzeige mit „Normales Tempo, Ihr Server meldet eine hohe Auslastung; die Kasse wird erst langsamer, wenn auch seine Antworten langsamer werden“">

1. **Tempoanzeige** — **Normales Tempo**: Lassen Sie Ihre Einstellung unverändert. Ihr Server meldet eine hohe Auslastung, antwortet aber weiterhin schnell.

</JourneyShot>

Wenn die Kasse ihr Tempo drosselt, nennt die Tempoanzeige den Grund. Auf **Gedrosselt — Prüfung 2× seltener** folgt eine dieser Meldungen; die Zahl steigt mit jeder Stufe:

- **… Ihr Server hat den POS aufgefordert, langsamer zu arbeiten** — Ihr Server hat eine Anfrage abgewiesen, weil es zu viele waren.
- **… Ihr Server hat Fehler zurückgegeben** — mehrere Anfragen sind innerhalb einer Minute auf dem Server fehlgeschlagen.
- **… bei Anfragen an Ihren Server wurde das Zeitlimit überschritten** — mehrere Anfragen wurden nicht rechtzeitig beantwortet.
- **… Ihr Server hat langsam geantwortet** — typische Antworten dauern länger als 2 Sekunden.
- **… Ihr Server hat eine hohe Auslastung gemeldet** — die meisten der letzten Antworten waren als unter hoher Last stehend gekennzeichnet, oder die von Ihrem Server gemeldete Auslastung hat sich verdoppelt.

**Pausiert bis … — Ihr Server hat den POS aufgefordert zu warten** bedeutet, dass Ihr Server eine Anfrage abgelehnt und angegeben hat, wann ein neuer Versuch erfolgen soll. Die Kasse wartet wie angefordert, bis zu 15 Minuten.

Fehler, die auftreten, während das Gerät offline ist, zählen nicht: Sie betreffen Ihre Verbindung, nicht Ihren Server.

<Accordion>
<AccordionItem question="Was genau die einzelnen Tempomeldungen auslöst">

| Ende der Tempomeldung | Ihr Server | Die Kasse reagiert |
| --- | --- | --- |
| hat den POS aufgefordert, langsamer zu arbeiten | antwortet mit `429 Too Many Requests` | sofort |
| hat Fehler zurückgegeben | gibt `5xx`-Fehler zurück | nach 3 innerhalb einer Minute |
| bei Anfragen … wurde das Zeitlimit überschritten | antwortet nicht rechtzeitig | nach 3 innerhalb einer Minute |
| hat langsam geantwortet | antwortet langsam | wenn der Median der letzten 10 Antwortzeiten über 2 Sekunden liegt |
| hat eine hohe Auslastung gemeldet | kennzeichnet seine Antworten mit `X-WCPOS-Pressure: high` | bei etwa 6 der letzten 10 |
| hat eine hohe Auslastung gemeldet | meldet mindestens das Doppelte seiner üblichen Auslastung (und mindestens 1) | nach 2 Messwerten in Folge, höchstens 2× |
| Pausiert bis … | sendet bei einer Ablehnung `Retry-After` | sofort, für bis zu 15 Minuten |

Bei einem Server, der seine Antworten mit `elevated` oder `high` kennzeichnet, aber weiterhin schnell antwortet, erscheint **Normales Tempo — Ihr Server meldet eine hohe Auslastung; die Kasse wird erst langsamer, wenn auch seine Antworten langsamer werden**, wie in der Nahaufnahme oben (oder **erhöhte Auslastung** bei der niedrigeren Stufe). Der Header kann eine Drosselung auslösen, sie aber nie allein aufrechterhalten: Die Kasse richtet sich danach, wie schnell Ihr Server tatsächlich antwortet.

</AccordionItem>
</Accordion>

### Was die Drosselung bedeutet {#back-off-steps}

- **Die Kasse prüft seltener auf Änderungen.** Jede Stufe verdoppelt die Wartezeit zwischen den Prüfungen. Wie weit das Tempo gedrosselt werden kann, hängt von Ihrer Einstellung ab: auf etwa 5 Minuten bei **Ausgewogen** und **Echtzeit**, auf 10 Minuten bei **Eco**. Benutzerdefinierte Einstellungen und Pausen werden unten im Detail erläutert.
- **Die Wartung im Hintergrund wartet.** Eine Aufgabe, die lange gewartet hat, führt dennoch einen kleinen Lauf aus, sofern Ihr Server den POS nicht zum Warten aufgefordert hat.
- **Der POS hält die Aktionen des Kassierers nicht zurück.** Suchen, Barcode-Abfragen, das Öffnen eines Datensatzes und das Speichern eines Verkaufs werden durch die Drosselung nie zurückgehalten. Ein überlasteter Server kann sie allerdings trotzdem langsam beantworten.

<Accordion>
<AccordionItem question="Wie weit jede Einstellung gedrosselt wird und welche Wartung weiterläuft">

- **Jede Stufe verdoppelt die Wartezeit zwischen den Prüfungen,** bis auf etwa 5 Minuten: **Echtzeit** kann um den Faktor 32× gedrosselt werden, **Ausgewogen** um 8× und **Eco** um 2× (auf 10 Minuten). Bei einer benutzerdefinierten Einstellung steigt das Intervall auf 5 Minuten oder auf das Doppelte des eigenen Intervalls, wenn das länger ist. Eine `Retry-After`-Pause kann diese Grenzen überschreiten und bis zu 15 Minuten dauern.
- **Die Wartung im Hintergrund wartet.** Die [Hintergrundaufgaben](#maintenance-budgets) werden zurückgestellt. Eine Aufgabe, die das Doppelte ihres üblichen Intervalls gewartet hat (bei der Löschprüfung und der Fingerabdruck-Aufgabe das einfache Intervall), führt dennoch einen Lauf innerhalb ihrer Obergrenze aus, sofern Ihr Server den POS nicht zum Warten aufgefordert hat. Der Lauf der Löschprüfung wird auf 1 Übersichtsseite pro Datensatzart und 1 Detailanfrage begrenzt.

</AccordionItem>
</Accordion>

### Rückkehr zum eingestellten Tempo {#recovery}

Sobald Ihr Server wieder normal antwortet, kehrt die Kasse selbstständig Stufe für Stufe zu Ihrer Einstellung zurück (für eine vom Server gemeldete hohe Auslastung gilt eine eigene Regel, siehe die Details unten). Sie müssen nichts ändern. Die Drosselung erfolgt sofort, die Beschleunigung schrittweise, damit ein instabiler Server nicht ständig zwischen schnell und langsam wechselt.

<Accordion>
<AccordionItem question="Voreinstellungen, Filialwechsel, Neustarts und Serverauslastung">

- **Jede Stufe zurück zum höheren Tempo erfordert 10 fehlerfreie, schnelle Antworten in Folge,** und erst dann, wenn seit der letzten Drosselung der Kasse eine Minute vergangen ist und keine `Retry-After`-Pause läuft. Von 32× aus sind 50 solche Antworten nötig, um zu Ihrer Einstellung zurückzukehren.
- **Beim Wechsel der Voreinstellung bleibt die Drosselung bestehen,** begrenzt auf die Obergrenze der neuen Voreinstellung. Sie lässt sich nicht abschalten: Sie ist bei jeder Voreinstellung aktiv, auch bei **Benutzerdefiniert**.
- **Beim Wechsel der Filiale oder des Kassierers auf derselben Website bleibt sie bestehen.** Jede Website auf dem Gerät hat ihre eigene Drosselung.
- **Beim Schließen der App wird sie zurückgesetzt.** Die Kasse startet mit Ihrer Einstellung und drosselt erneut, wenn Ihr Server weiterhin Probleme hat.
- **Die Serverauslastung wird unabhängig davon behandelt.** Wenn die von Ihrem Server gemeldete Auslastung bei zwei Messungen das Doppelte des üblichen Werts erreicht (und mindestens 1 beträgt), prüft die Kasse halb so oft, bis zwei Messwerte wieder unter das 1.25-Fache des üblichen Werts fallen.

</AccordionItem>
</Accordion>

## Die Kasse bleibt reaktionsfähig {#device-responsiveness}

Die Synchronisierung im Hintergrund darf die Bildschirmanzeige nie ins Stocken bringen. Prüfungen arbeiten in kurzen Abschnitten und legen Pausen ein, damit die Oberfläche reagieren kann. In den Tests der Engine treffen die ersten Ergebnisse einer Liste auch während einer laufenden Prüfung in deutlich weniger als einer Zehntelsekunde ein. Und wenn die Datenbank eine Liste selbst filtern und sortieren kann, verlassen nur die auf dem Bildschirm sichtbaren Zeilen die Datenbank.

<Accordion>
<AccordionItem question="Die gemessenen Werte">

- **Prüfungen pausieren, damit die Oberfläche reagieren kann.** Die Löschprüfung arbeitet in Abschnitten, von denen keiner länger als etwa **30 ms** läuft — deutlich unter den 100 ms, ab denen Menschen eine Verzögerung bemerken. Bei 10,000 Produkten auf der Kasse benötigt eine vollständige Prüfung etwa **68 ms** Rechenzeit, verteilt über 17 oder 18 Pausen. Bei 50,000 Produkten sind es unter 300 ms.
- **Das erste Ergebnis kommt auch während der Synchronisierung schnell.** Die ersten Ergebnisse einer Abfrage treffen während einer Prüfung von 10,000 Produkten weiterhin nach etwa **7–10 ms** ein und während einer Prüfung von 50,000 Produkten nach etwa **40–54 ms**.
- **Nur die sichtbaren Zeilen verlassen die Datenbank,** wenn Filterung und Sortierung darin ausgeführt werden können. Eine Bildschirmaktualisierung überträgt dann zehn Zeilen statt zehntausend. Suchen und Filter, die die Datenbank nicht selbst ausführen kann, werden stattdessen auf der Kasse verarbeitet.

Diese Werte stammen aus den Leistungstests der Engine, gemessen auf einem Computer mit der Datenbank im Arbeitsspeicher.

</AccordionItem>
<AccordionItem question="Wie diese Werte gemessen werden">

Die Tests laufen auf einem Computer mit Apple Silicon und einer Datenbank im Arbeitsspeicher. Außerdem werden sie bei jeder Änderung an der Synchronisierungs-Engine separat in CI ausgeführt. Ihre Grenzwerte liegen etwa 11–18-mal über den gemessenen Werten (3-mal beim Abschnitt von 30 ms) und in CI nochmals dreimal höher. So erkennen sie eine Verlangsamung dieser Größenordnung und schlagen nicht wegen eines langsamen Testrechners an.

</AccordionItem>
</Accordion>

## An einem Live-Shop überprüft {#live-verification}

Die obigen Regeln werden nach der Bereitstellung einer Version auch von Hand an einem echten WordPress-Shop überprüft: Die Kasse stellt **keine** Prüfanfragen, bevor die Produktliste erstmals angezeigt wird, und hält sich danach an die Obergrenzen der Prüfung.

<Accordion>
<AccordionItem question="Was der Live-Test prüft und warum es ihn gibt">

Der Test lädt den POS bei einer fälligen Prüfung neu und überprüft Folgendes:

- Die Kasse stellt **keine** Prüfanfragen, bevor die Produktliste erstmals angezeigt wird, und
- nach der einminütigen Wartezeit ruft die Prüfung höchstens **9** Übersichtsseiten ab und stellt **2** Detailanfragen.

Der Test entstand aus einer tatsächlichen Regression: Eine frühe Entwicklungsversion sendete bei einer einzigen Prüfung **41** Detailanfragen (**1.2 MB**), als eine Kasse ihre Datensätze neu aufbaute. Das daraufhin eingeführte Konzept prüft zuerst Zusammenfassungen und hält die Detailanfragen unter den oben genannten Obergrenzen. Die Tests der Engine setzen diese Grenzen bei jeder Änderung durch.

</AccordionItem>
</Accordion>

## Was die Zahlen nicht aussagen {#honest-limits}

- **Wie lange ein erster Download dauert.** Das hängt fast ausschließlich von den Antwortzeiten Ihres Servers und der Größe Ihres Katalogs ab. In den Tests dauert das Schreiben von 10,000 heruntergeladenen Produkten in die Datenbank der Kasse weniger als 10 ms; die übrige Zeit entfällt auf Netzwerk und Server.
- **Wie viel schneller dies als WCPOS 1.x ist.** Die beiden Konzepte unterscheiden sich zu stark, um sie mit einer einzigen Zahl fair zu vergleichen. [So funktioniert die Synchronisierungs-Engine](./sync-engine.mdx) erläutert die Unterschiede.
- **Welche Werte Ihr eigener Shop erreichen wird.** Die Testwerte stammen von einem Computer mit der Datenbank im Arbeitsspeicher. Deshalb zeigt der Tab „Leistung“, was diese Kasse in den letzten 24 Stunden tatsächlich getan hat, statt eine Prognose abzugeben. Die Datenmenge berücksichtigt nur Antworten, die ihre Größe angeben. Sie kann daher unter dem tatsächlichen Datenverkehr liegen, sogar bei **0.0 MB**.
