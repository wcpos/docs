Diese Seite dokumentiert, welche WCPOS-REST-Endpunkte für die drei Standardrollen in POS-Workflows zugänglich sind:

- `administrator`
- `shop_manager`
- `cashier`

Die Konfiguration von Rollen und Berechtigungen über die Benutzeroberfläche wird unter [Zugriff auf den POS](/1.x/settings/wp-admin/access) beschrieben.

## Zusammenfassung {#summary}

Das standardmäßige Zugriffsmodell sieht wie folgt aus:

- **`administrator`** — vollständiger POS- und Verwaltungszugriff.
- **`shop_manager`** — vollständiger POS- und Verwaltungszugriff, ausgenommen Aktionen für Plugin-Erweiterungen, die Berechtigungen zur Plugin-Installation erfordern.
- **`cashier`** — Zugriff auf den normalen POS-Verkaufsablauf, aber kein Zugriff auf Verwaltung, Einstellungen, Protokolle oder Filialadministration.

Die Endpunktmatrix wird durch Integrationstests überprüft, die denselben Authentifizierungspfad wie die POS-App durchlaufen (WCPOS-Bearer-Zugriffstoken, nicht nur `wp_set_current_user()`). Prüfungen für zulässige Endpunkte bestätigen, dass eine Rolle weder `401` noch `403` erhält. Einige Endpunkte können weiterhin reguläre Daten oder fachliche Fehler wie `400` oder `404` zurückgeben, wenn der Test minimale Testdaten verwendet — auch diese Antworten belegen, dass der Benutzer die Authentifizierungs- und Berechtigungsprüfung bestanden hat.

## Testabdeckung für den Token-Ablauf {#token-expiry-coverage}

| Szenario | Admin | Shop-Manager | Kassierer | Erwartetes Ergebnis |
|---|---:|---:|---:|---|
| Gültiges Zugriffstoken | ✅ getestet | ✅ getestet | ✅ getestet | Zulässige Endpunkte geben weder `401` noch `403` zurück |
| Abgelaufenes Zugriffstoken | ✅ getestet | ✅ getestet | ✅ getestet | Anfrage scheitert an der WCPOS-Authentifizierungsprüfung mit Benutzer `0` |
| Gültiges Refresh-Token nach Ablauf des Zugriffstokens | ✅ getestet | ✅ getestet | ✅ getestet | Neues Zugriffstoken wird ausgestellt und der Zugriff wiederhergestellt |
| Abgelaufenes Refresh-Token | ✅ getestet | ✅ getestet | ✅ getestet | Es kann kein neues Zugriffstoken ausgestellt werden |

## Fehler diagnostizieren {#diagnosing-failures}

Wenn ein Benutzer mit der Standardrolle `shop_manager` einen Fehler wie diesen sieht:

> Anfrage nach der Token-Aktualisierung weiterhin nicht autorisiert – bitte melden Sie sich erneut an

Die Endpunktmatrix zeigt, dass dies **nicht** daran liegt, dass der Standardrolle `shop_manager` grundsätzlich der POS-Zugriff fehlt. Folgende wahrscheinliche Ursachen sollten untersucht werden:

1. Beschädigte Rollen oder Berechtigungen auf der betreffenden Website.
2. Ein Endpunkt, der nicht von der Matrix abgedeckt wird.
3. Das Wiederholungsverhalten des Clients bei veralteten oder abgelaufenen Zugriffstoken.
4. Störungen durch Sicherheits- oder Authentifizierungs-Plugins von Drittanbietern.
5. Pro- oder filialspezifische Zugriffsregeln oder benutzerdefinierter Code.

### Berechtigungsfehler im Vergleich zu Token-Fehlern {#permission-failure-vs-token-failure}

Das POS-Frontend zeigt möglicherweise in beiden Fällen denselben Fehler bei der Token-Aktualisierung an: Es erhält `401` oder `403`, versucht eine Token-Aktualisierung und bleibt auch beim erneuten Versuch nicht autorisiert. Serverseitig unterscheiden sich die beiden Fehlerarten:

Ein **echter Rollen- oder Berechtigungsfehler** sieht in der Regel so aus:

```text
status: 403
current_user: <actual user id>
access token expired: false
```

Ein **Token- oder Authentifizierungsfehler** sieht in der Regel so aus:

```text
status: 403
current_user: 0
access token expired: true or invalid
```

Nutzen Sie diese Unterscheidung beim Eingrenzen von POS-Zugriffsproblemen — ein `current_user` ungleich null deutet auf Berechtigungen hin, während `current_user: 0` auf die Authentifizierungs- oder Token-Ebene hinweist.
