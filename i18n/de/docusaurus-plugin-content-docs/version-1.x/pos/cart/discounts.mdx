WCPOS bietet Kassierern mehrere Möglichkeiten, einer Bestellung spontan einen Rabatt zu gewähren: schnelle Prozent-Schaltflächen, direkte Preisänderungen einzelner Positionen und Rabattgebühren auf Bestellebene. Informationen zu vorkonfigurierten Aktionen mit Nutzungsregeln finden Sie unter [Gutscheine](/coupons) (Pro).

:::info Suchen Sie nach der Rabattsumme?
Ein an der Kasse reduzierter Preis wird als Angebotspreis des Artikels erfasst, nicht als WooCommerce-Rabatt — die systemeigene Summe **Rabatt** ist für Gutscheine reserviert. [Warum Preisänderungen und Gutscheine unterschiedlich erfasst werden](#why-tracked-differently) erläutert das Modell; wenn sich Ihre Summen nach dem Update auf v1.9.0 geändert haben, lesen Sie [Was sich in v1.9.0 geändert hat](#what-changed-in-v190).
:::

## Schnelle Rabatte {#quick-discounts}

Mit Schaltflächen für schnelle Rabatte können Sie den Preis einer einzelnen Position mit einem einzigen Tippen um einen Prozentsatz reduzieren.

Öffnen Sie zum Konfigurieren die [Anzeigeeinstellungen](/pos/cart#display-settings) des Warenkorbs und geben Sie im Feld **Schnelle Rabatte** eine durch Kommas getrennte Liste von Prozentsätzen ein. Beispielsweise erstellt `5,10,15,20` vier Schnellzugriffsschaltflächen.

Die Schaltflächen werden im Ziffernblock angezeigt, der sich öffnet, wenn Sie auf das Feld **Preis** einer Position klicken. Durch Tippen auf eine Schaltfläche wird der Preis dieser Position um den entsprechenden Prozentsatz reduziert; bestätigen Sie mit **Fertig**. Jede Position wird separat rabattiert. Wiederholen Sie dies daher für jede Position, wenn mehrere Artikel rabattiert werden sollen. Es gibt keine Schaltfläche, die die gesamte Bestellung auf einmal rabattiert — verwenden Sie dafür einen [Rabatt auf Bestellebene](#order-level-discounts).

## Rabatte für einzelne Positionen {#line-item-discounts}

Der Preis eines einzelnen Artikels kann direkt im Warenkorb geändert werden:

1. Klicken Sie beim Artikel auf das Feld **Preis**
2. Geben Sie den neuen Preis ein
3. Drücken Sie zur Bestätigung **Eingabetaste**

Dies ist hilfreich bei Preisanpassungen, Mitarbeiterrabatten oder einmaligen Änderungen. Die Gesamtsumme des Artikels wird automatisch anhand von Menge × neuem Preis aktualisiert.

Weitere Informationen zum Bearbeiten von Artikeln im Warenkorb finden Sie unter [Artikel](/pos/cart/line-items).

:::tip Artikel aufteilen
Wenn ein Kunde für Teile desselben Produkts unterschiedliche Rabatte wünscht (z. B. 3 zum regulären Preis und 2 mit Rabatt), aktivieren Sie in den [Anzeigeeinstellungen](/pos/cart#display-settings) des Warenkorbs die Option **Aufteilen**, um einen Artikel in separate Zeilen aufzuteilen.
:::

## Rabatte auf Bestellebene {#order-level-discounts}

Um einen festen Rabatt auf die gesamte Bestellung anzuwenden (statt auf einzelne Artikel), fügen Sie eine **negative Gebühr** hinzu:

1. Klicken Sie unter den Artikeln im Warenkorb auf **Gebühr hinzufügen**
2. Geben Sie einen Namen ein (z. B. „Mitarbeiterrabatt“)
3. Geben Sie den Rabattbetrag als negative Zahl ein (z. B. `-5.00`)

Die Gebühr wird als separate Position angezeigt und reduziert die Bestellsumme. Bei Bedarf können Sie über das Drei-Punkte-Menü den Steuerstatus und die Steuerklasse der Gebühr bearbeiten.

### So wird die Steuer auf eine Rabattgebühr berechnet {#discount-fee-tax}

WCPOS besteuert eine negative Gebühr anhand **der eigenen Steuereinstellungen der Gebühr**: Setzen Sie ihren Steuerstatus auf **Keine**, wird keine Steuer darauf erhoben; bleibt sie **Steuerpflichtig**, wird sie gemäß ihrer eigenen Steuerklasse besteuert. Der eingegebene Betrag wird abgezogen — bei Eingabe von `-10.00` zahlt der Kunde 10 weniger.

Der WooCommerce-Kern verhält sich anders. WooCommerce allein behandelt eine negative Gebühr als Rabatt auf den gesamten Warenkorb und verteilt ihre Steuer auf die Steuerklassen aller anderen Positionen der Bestellung; dabei wird der für die Gebühr festgelegte Steuerstatus ignoriert. Außerdem werden Preise inklusive Steuer nicht berücksichtigt. In einem Shop, in dem **Preise inklusive Steuer eingegeben** auf *Ja* gesetzt ist, würde eine Gebühr von `-10.00` bei einem Steuersatz von 20 % **12.00** abziehen. WCPOS überschreibt dieses Verhalten, sodass die Kasse genau den vom Kassierer eingegebenen Betrag abzieht.

Diese Behandlung gehört zur Bestellung, nicht zur gerade verwendeten App — eine Neuberechnung einer POS-Bestellung über **WP Admin → Bestellungen** ändert daran nichts. Nicht-POS-Bestellungen behalten das Standardverhalten von WooCommerce bei.

:::note Bekannte Einschränkung bei Shops mit Preisen inklusive Steuer
Wenn Ihre Preise Steuern enthalten, ergibt eine Rabattgebühr zwar den korrekten Gesamtbetrag für den Kunden, lässt aber die **in der Bestellung erfasste Steuer unverändert** — der Steuerbetrag ist daher geringfügig höher, als es der reduzierte Betrag streng genommen rechtfertigen würde. Dies geschieht zugunsten der Steuerbehörde, niemals umgekehrt. Wenn die erfasste Steuer für Ihre Buchhaltung wichtig ist, verwenden Sie stattdessen einen [Gutschein](/coupons) für den Rabatt: Gutscheine reduzieren den steuerpflichtigen Betrag und berechnen die darauf entfallende Steuer korrekt neu. Aus genau diesem Grund werden POS-Rabatte auf Bestellebene in einer zukünftigen Version auf Gutscheine umgestellt.
:::

## POS-Rabatte im Vergleich zu WooCommerce-Gutscheinen {#pos-discounts-vs-woocommerce-coupons}

Die Rabatte auf dieser Seite sind spontane Anpassungen, die Kassierer an der Kasse anwenden; WooCommerce-**Gutscheine** sind vorkonfigurierte Aktionen mit Regeln und Nachverfolgung. Hier ist ein kurzer Vergleich:

| | POS-Rabatte | WooCommerce-Gutscheine (Pro) |
|---|---|---|
| **Anwendung** | Schneller Rabatt, Bearbeitung des Zeilenpreises oder negative Gebühr | Einen Gutscheincode im Warenkorb eingeben |
| **Konfiguration** | Direkt durch das Kassenpersonal | Vorab konfiguriert in **WP Admin → Marketing → Gutscheine** |
| **Nachverfolgung** | Als Zeilenpreis erfasst, wie ein Aktionspreis (siehe [Warum](#why-tracked-differently)) | Als Gutscheinrabatt in WooCommerce-Berichten nachverfolgt |
| **Einschränkungen** | Keine — das Kassenpersonal legt jeden beliebigen Preis fest | Nutzungsbeschränkungen, Produkt-/Kategorieeinschränkungen, Mindestbestellwert, Ablaufdatum, E-Mail-Regeln |
| **Am besten geeignet für** | Ad-hoc-Anpassungen, Preisanpassungen | Strukturierte Werbeaktionen, nachverfolgbare Rabatte |

:::tip Was sollte verwendet werden?
Für einmalige Preisanpassungen sind die Rabatte auf dieser Seite einfacher. Wenn die Nutzung von Rabatten in WooCommerce-Berichten nachverfolgt oder Regeln wie Nutzungsbeschränkungen durchgesetzt werden müssen, sollten [Gutscheine](/coupons) verwendet werden.
:::

## Warum Preisänderungen und Gutscheine unterschiedlich nachverfolgt werden {#why-tracked-differently}

WooCommerce kennt genau ein integriertes Konzept für einen Rabatt: den **Gutschein**. Ein Gutschein gehört zur Bestellung — er wird in einem eigenen Feld erfasst, in Berichten in der Spalte **Rabatt** gezählt und hat eigene Regeln wie Nutzungsbeschränkungen und Ablaufdaten.

Ein **Aktionspreis** ist für WooCommerce kein Rabatt. Er ist einfach der aktuelle Preis des Produkts: Wenn ein reduzierter Artikel verkauft wird, erfasst die Bestellung den gezahlten Preis und sonst nichts. Der reguläre Preis erscheint nie in der Bestellung, und Berichte zählen den Verkauf als gewöhnlichen Umsatz — WooCommerce selbst hält nicht fest, dass Kundschaft etwas gespart hat.

Schnellrabatte und Preisänderungen bei Positionen folgen dem Angebotspreis-Modell: Der Artikel wird zum Preis verkauft, den das Kassenpersonal festlegt. Diese Regel erklärt den Rest dieser Seite — die WooCommerce-Gesamtsumme **Rabatt** bleibt bei null, Gutscheine werden auf Grundlage des reduzierten Preises berechnet, und Gutscheine mit „Angebotsartikel ausschließen“ überspringen an der Kasse reduzierte Artikel. (Eine negative Gebühr auf Bestellungsebene ist wiederum etwas anderes: Sie wird als Gebührenposition und nicht als Preisänderung erfasst.)

Auf Belegen erwarten Kundinnen und Kunden besonders, ihre Ersparnis zu sehen. Deshalb erfasst WCPOS bei jeder Position neben dem neuen Preis auch den regulären Preis. Dadurch können auf einem Beleg Ersparnisse durch Angebotspreise und Gutscheinrabatte als getrennte Beträge angezeigt werden, ohne einen davon doppelt zu zählen — und ohne die Bestellsummen oder Berichte von WooCommerce zu ändern.

## Wie POS-Preisänderungen mit Gutscheinen interagieren {#how-pos-price-changes-interact-with-coupons}

Wenn das Kassenpersonal für eine Position einen benutzerdefinierten Preis festlegt (z. B. von 18 $ auf 16 $ reduziert) und anschließend ein Gutschein angewendet wird, wird der Gutschein auf Grundlage des **POS-reduzierten Preises** (16 $) berechnet, nicht auf Grundlage des ursprünglichen Preises (18 $). Dies verhindert, dass Kundinnen und Kunden durch die Kombination eines Kassenrabatts mit einem Gutschein auf Grundlage des ursprünglichen Preises zu viel Rabatt erhalten.

- POS-reduzierte Artikel werden von WooCommerce als „im Angebot“ behandelt. Wenn für einen Gutschein **Angebotsartikel ausschließen** aktiviert ist, werden POS-reduzierte Artikel übersprungen — genauso wie reguläre Angebotsartikel. Entwicklerinnen und Entwickler können dies mit dem Filter `woocommerce_pos_item_is_on_sale` überschreiben.
- Das Entfernen eines Gutscheins belässt die Position beim POS-reduzierten Preis.

:::note Entwicklerreferenz
Technische Details zur Speicherung von POS-Preisüberschreibungen und zu den verfügbaren Filtern finden Sie in der [POS-Rabattreferenz](/reference/pos-discounts).
:::

## Änderungen in v1.9.0 {#what-changed-in-v190}

Wenn Sie von v1.8 aktualisiert haben und die Gesamtsumme **Rabatt** auf Belegen und in Berichten nun **0** anzeigt, ist dies der Grund: Frühere Versionen erfassten eine Preisänderung an der Kasse als WooCommerce-Rabatt, wodurch die Gutscheinberechnung fehlerhaft war — ein zusätzlich angewendeter Gutschein wurde auf Grundlage des ursprünglichen Preises berechnet, wodurch die Bestellung zu stark rabattiert und der Kundschaft zu wenig berechnet wurde. Ab v1.9.0 **ist** der an der Kasse festgelegte Preis der Positionspreis, genau wie WooCommerce einen Angebotsartikel erfasst, und nur Gutscheine zählen als Rabatte. Siehe oben [Warum Preisänderungen und Gutscheine unterschiedlich erfasst werden](#why-tracked-differently).

### Was das für Sie bedeutet {#what-this-means-for-you}

- **Belege** können den erfassten regulären Preis, die Ersparnis zwischen regulärem Preis und Verkaufspreis sowie einen kombinierten Wert für **Insgesamt gespart** anzeigen, der diese Ersparnisse und Gutscheine umfasst. Preisersparnisse bleiben vom WooCommerce-Feld **Rabatt** getrennt.
- **Berichte** zeigen `discount_total = 0`, wenn nur Änderungen der POS-Artikelpreise verwendet wurden. Gezählt werden nur Gutscheinrabatte.
- **Gutscheine** werden jetzt korrekt berechnet, wenn sie zusammen mit POS-reduzierten Artikeln verwendet werden.
- **Die erfassten regulären Preise und Verkaufspreise werden gespeichert** in den POS-Metadaten der Bestellpositionen (`_woocommerce_pos_data`), sodass der Beleg die Ersparnis ermitteln kann, ohne die Rabattsummen von WooCommerce zu ändern.

### Ursprünglichen Preis und Ersparnis auf Belegen anzeigen {#showing-the-original-price-and-saving-on-receipts}

Die aktuell enthaltenen Vorlagen mit Preisangaben zeigen den erfassten regulären Preis und die Ersparnis, wenn ein Produkt im Angebot ist oder sein Preis an der Kasse geändert wird. Sie zeigen auch **Insgesamt gespart**, wenn WCPOS einen vollständigen Wert auf Bestellungsebene berechnen kann. Dieser Gesamtwert kombiniert Ersparnisse gegenüber dem regulären Preis mit Gutscheinrabatten, ohne einen der Werte doppelt zu zählen.

Aus der Galerie kopierte Vorlagen sind bearbeitbare Momentaufnahmen und werden durch WCPOS-Updates nicht überschrieben. Wenn der Beleg vor dieser Änderung erstellt wurde, gibt es folgende Möglichkeiten:

1. Klicken Sie bei einer neuen Kopie der enthaltenen Vorlage auf **Vorlage verwenden**; oder
2. Aktualisieren Sie die vorhandene Vorlage mit den Feldern in der [Referenz zu Belegdaten](/receipts/receipt-data#displaying-regular-price-and-savings).

Die wichtigsten Belegfelder sind:

| Feld | Bedeutung |
|-------|---------|
| `lines[].regular_price_display` | Erfasster regulärer Stückpreis |
| `lines[].selling_price_display` | Verkaufseinzelpreis vor Gutscheinen |
| `lines[].unit_savings_display` | Ersparnis pro Artikel |
| `lines[].line_regular_total_display` | Gesamtbetrag zum regulären Preis für die Position |
| `lines[].line_savings_display` | Gesamtersparnis für die Position |
| `totals.sale_savings_total_display` | Gesamtersparnis zwischen regulärem Preis und Verkaufspreis durch Katalogangebote und Preisänderungen an der Kasse |
| `totals.discount_total_display` | Gesamtrabatt von WooCommerce; normalerweise Gutscheine bei aktuellen Bestellungen |
| `totals.total_saved_display` | Kombinierte Ersparnis zum regulären Preis und WooCommerce-Rabatte |
| `totals.total_saved_complete` | Ob der kombinierte Gesamtbetrag vollständig ist und sicher angezeigt werden kann |

Benutzerdefinierte Vorlagen sollten die Zeile **Insgesamt gespart** absichern, damit sie ausgeblendet wird, wenn historische Preisdaten unvollständig sind oder nichts gespart wurde — das genaue Muster finden Sie in der [Referenz zu Belegdaten](/receipts/receipt-data#totals).

WooCommerce-Berichte bleiben unverändert: Native Rabattgesamtsummen enthalten weiterhin Gutscheine statt aktueller Ersparnisse durch Angebotspreise oder Kassenpreise. Verwenden Sie `totals.total_saved` für Belege und weiterhin [Gutscheine](/coupons), wenn Ersparnisse in Berichten auch als WooCommerce-Rabatte erfasst werden müssen.

## Bekannte Einschränkungen {#known-limitations}

- **Keine automatischen Rabattregeln** — das POS unterstützt keine automatischen Rabatte nach dem Muster „Kaufe 2, erhalte 1 gratis“. Verwenden Sie WooCommerce-Gutscheine für strukturierte Werbeaktionen.
- **Schnellrabatte sind nur prozentual möglich** — es gibt keine integrierte Schnellschaltfläche für Festbetragsrabatte. Verwenden Sie stattdessen eine negative Gebühr oder bearbeiten Sie die einzelnen Preise.
- **Rabattgebühren und Preise inklusive Steuern** — eine Rabattgebühr auf Bestellungsebene berechnet zwar den korrekten Gesamtbetrag, verringert jedoch nicht die in der Bestellung erfasste Steuer. Siehe [So wird die Steuer auf eine Rabattgebühr berechnet](#discount-fee-tax).
