## Bedeutung {#what-this-means}

Der Server des Shops blockiert das Anmeldetoken auf jedem Kanal, den diese App verwenden kann.

Die App hat bestätigt, dass der Shop erreichbar ist, aber der Server (oder eine vorgeschaltete Firewall, ein Proxy oder ein Sicherheits-Plugin) entfernt den Authorization-Header und blockiert das Token auch, wenn es als URL-Parameter gesendet wird. Es gibt keinen dritten Weg, ein Anmeldetoken zu übermitteln. Daher muss dies auf dem Server behoben werden.

## Vorgehensweise {#what-to-do}

Exportieren Sie Diagnosedaten und wenden Sie sich an den Support. Wiederholen Sie den Vorgang nach der oben genannten Änderung; ohne diese Änderung schlägt er erneut auf dieselbe Weise fehl.

## Ihre Daten {#your-data}

Keine Bestell- oder Produktdaten sind betroffen.

## Fehlerbehebung {#troubleshoot}

1. Bitten Sie Ihren Hoster, den Authorization-Header an WordPress weiterzuleiten — unter Apache ist dafür normalerweise nur eine Zeile erforderlich: SetEnvIf Authorization "(.*)" HTTP_AUTHORIZATION=$1.
2. Wenn die Website .htaccess-Rewrites verwendet, behalten Sie die von WordPress generierte RewriteRule-Zeile bei, die HTTP_AUTHORIZATION weiterleitet — Sicherheits-Plugins entfernen sie manchmal.
3. Prüfen Sie bei einem Proxy oder CDN dessen Header-Zulassungsliste: Der Authorization-Request-Header muss an den Ursprungsserver weitergeleitet werden.
4. Wenn eine Web Application Firewall (WAF) URL-Parameter filtert, bitten Sie Ihren Hoster, den Autorisierungsparameter auf /wcpos/-REST-Routen zuzulassen.

## Wo Sie nachsehen können {#where-to-look}

Wenn WCPOS diesen Fehler speichern kann, wird er auf dem Gerät aufgezeichnet, auf dem er aufgetreten ist. Öffnen Sie **Filialzustand → Protokolle** (das Herzschlag-Symbol unten im Navigationsmenü), suchen Sie den mit diesem Code markierten Eintrag und erweitern Sie ihn: Die erweiterte Zeile zeigt die verständlich formulierte Ursache und den zum Zeitpunkt des Fehlers erfassten Kontext. Bei einer Filialanfrage kann dieser Kontext den servereigenen Fehlercode (`serverCode`), den HTTP-`status` oder den `endpoint` enthalten; die angezeigten Felder hängen davon ab, wo der Fehler aufgetreten ist. Verwenden Sie beim Melden eines Problems oben im Protokollbildschirm **Debuginformationen kopieren** (**Debuginformationen teilen** auf Smartphones und Tablets) statt Screenshots: Dadurch werden die App-Version, der Verbindungsstatus und die neuesten Fehler gebündelt. Protokolle werden höchstens 30 Tage aufbewahrt; erfassen Sie sie daher, solange das Problem noch aktuell ist. Kopieren Sie außerdem jeden Browser-Konsolenfehler, der angezeigt wurde, bevor der POS seinen eigenen Protokolleintrag schreiben konnte.
