## Was dies bedeutet {#what-this-means}

Ihr Shop begrenzt vorübergehend die Anfragen, daher wird diese Aktion später erneut versucht.

Warten Sie, bevor Sie es erneut versuchen. Wenn die Begrenzungen anhalten, bitten Sie den Website-Administrator oder das Hosting, die Anfragelimits des Shops zu überprüfen.

## Was zu tun ist {#what-to-do}

Versuchen Sie die Aktion erneut. WCPOS wiederholt dies automatisch.

## Ihre Daten {#your-data}

Die Änderung ist auf diesem Gerät gespeichert, hat Ihren Shop aber nicht erreicht. Wenn dies weiterhin auftritt, wenden Sie sich an die Person, die Ihre WordPress-Website betreut.

## Fehlerbehebung {#troubleshoot}

1. Warten Sie — das POS wartet von selbst ab und versucht es erneut; ein manueller Wiederholungsversuch verlängert die Drosselung nur.
2. Es muss nichts neu eingegeben werden: Die betroffenen Änderungen bleiben auf dem Gerät und gehen bei einem späteren Versuch durch.
3. Wenn der Code weiterhin auftritt, bitten Sie den Website-Administrator herauszufinden, welche Schicht den Status 429 zurückgibt — ein Sicherheits-Plugin, eine CDN- oder Firewall-Regel oder die Limits des Hostings selbst — und den REST-Verkehr des POS zuzulassen.
4. Endpoint und Zeitstempel im aufgeklappten Protokolleintrag helfen dem Administrator, die Drosselung in seinen eigenen Dashboards zuzuordnen.

## Wo Sie nachsehen können {#where-to-look}

Wenn WCPOS diesen Fehler speichern kann, wird er auf dem Gerät aufgezeichnet, das ihn ausgelöst hat. Öffnen Sie **Shop-Zustand → Protokolle** (das Herzschlagsymbol unten im Navigationsmenü), suchen Sie den mit diesem Code gekennzeichneten Eintrag und klappen Sie ihn auf: Die aufgeklappte Zeile zeigt die Ursache in verständlicher Sprache sowie den Kontext, der im Moment des Fehlers erfasst wurde. Bei einer Shop-Anfrage kann dieser Kontext den eigenen Fehlercode des Servers (`serverCode`), den HTTP-`status` oder den `endpoint` enthalten; welche Felder angezeigt werden, hängt davon ab, wo der Fehler aufgetreten ist. Verwenden Sie beim Melden eines Problems **Debug-Infos kopieren** oben im Protokollbildschirm (**Debug-Infos teilen** auf Smartphones und Tablets) statt Screenshots: Damit werden App-Version, Verbindungsstatus und die neuesten Fehler zusammengefasst. Protokolle werden höchstens 30 Tage aufbewahrt — sammeln Sie sie daher, solange das Problem frisch ist. Kopieren Sie außerdem jede Fehlermeldung aus der Browser-Konsole, die erschienen ist, bevor das POS seinen eigenen Protokolleintrag schreiben konnte.

Über das Protokoll in der App hinaus kann dieser Fehler an folgenden Stellen Spuren hinterlassen:

- **Netzwerk-Inspektor** (Web und Desktop): Öffnen Sie die Entwicklertools — drücken Sie F12 im Browser oder wählen Sie **Erweitert → Entwicklertools umschalten** im Menü der Desktop-App — und wechseln Sie zum Tab **Netzwerk**. Befolgen Sie zuerst die Hinweise zum erneuten Versuch auf dieser Seite; wiederholen Sie die Aktion nur, wenn diese Schritte sie als unbedenklich bezeichnen. Eine fehlgeschlagene Anfrage zeigt den HTTP-Status und den unbearbeiteten Antworttext, einschließlich Fehlerseiten, die nie im POS-Protokoll ankommen.
