このページでは、レジ係（またはマネージャー）向けに日次締めの手順を説明します。レポート画面自体の詳細（フィルター、列、サマリーパネルの内容）については、[レポート](/1.x/reports)を参照してください。

:::info Pro機能
レポート画面を使用するには [WCPOS Pro](/1.x/getting-started/pro-license) が必要です。Pro がない場合、日次精算は **WP Admin → WooCommerce → 分析** から行う必要があります。
:::

:::note 手動での現金カウント
WCPOS には、釣銭準備金の入力や「レジ開け／レジ締め」機能は組み込まれていません。シフトの開始・終了を記録する機能、アプリ内でのドロワー計数、自動差異計算の機能はありません。レポート画面には、レジで受け取った**はずの**金額が表示されます。レジ係がドロワーの現金を数え、手動で照合します。このページでは、その手順を説明します。
:::

<ComingSoon>釣銭準備金の入力と正式なシフト開始・終了機能は今後追加予定です。アプリ内で開始時の釣銭準備金を記録し、各販売をシフトに紐づけて、正確な日次合計を算出できるようになります。</ComingSoon>

## 初回の締め作業の前に {#before-your-first-close}

次の事項を決め、どのシフトでも一貫して守ってください。

- **営業開始時の釣銭準備金。** 一般的な小売店のレジでは、釣銭用の少額紙幣や硬貨を $100–$200 用意して営業を開始します。金額を決めて毎日同じ額にすると、日次精算の計算が簡単になります。
- **釣銭準備金の記録場所。** WCPOS では記録されないため、付箋、クリップボードに挟んだ用紙、またはレジで使えるスプレッドシートが必要です。どれを選ぶ場合も、後から精算を監査できるよう、*開始時の釣銭準備金*と*ドロワーの予想残高*を同じ記録に残してください。
- **集計担当者と確認者。** レジ係が数え、マネージャーが確認する二人体制が理想的です。スタッフが一人だけの店舗では、レジ係が両方を担当します。その場合は、その手順を店舗の方針として記録してください。

## レジの開始 {#opening-the-till}

シフト開始時に、次の手順を行います。

1. 金庫から釣銭準備金を取り出し、ドロワーに入れます。
2. 精算シートに釣銭準備金の金額と開始時刻を記入します。
3. WCPOS に正しい店舗でサインインします（複数店舗のサイトの場合）。どの店舗を選ぶかわからない場合は、[マルチ店舗セットアップ](/1.x/stores)を参照してください。

これで完了です。WCPOS はシフト中の売上をユーザーアカウントと選択した店舗に紐づけて記録します。

## シフト中 {#during-the-shift}

締め作業をスムーズにするために、次の点に注意してください。

- **クーポンまたは明細行の割引を一貫して使用してください。** どちらも臨時の調整に使えますが、クーポンはレポートに追跡対象の割引として表示され、明細行の価格変更は表示されません。使い分けについては、[割引](/1.x/pos/cart/discounts)を参照してください。
- **注文は破棄せず、保留してください。** 「POS - Open」の注文（**Save to Server** で保存）は注文一覧やレポートに明確に表示されますが、破棄されたカートは記録が残りません。お客様が戻ったら、保留した注文を再開してください。
- **ドロワー内の現金が多くなったら、シフト中に余剰分を回収してください。** 精算時に計算が合うよう、回収するたびに金額と時刻を記録します。WCPOS は回収を記録しないため、精算シートに記録してください。

## 締め作業の手順 {#the-close-procedure}

<Steps>
  <StepCard number="1" title="販売を停止する">

入口を施錠するか、会計の受付を一時停止して、計数中に新しい取引が発生しないようにします。締め作業中にお客様が来店した場合は、会計する**前に**計数とレポートを完了してください。レポートの対象期間後に売上を追加すると、合計が合わなくなります。

  </StepCard>
  <StepCard number="2" title="ドロワーを計数する">

ドロワーをバックオフィスまたは静かなカウンターに持っていき、すべての金種を数えます。合計を記録してください。これが**実測現金高**です。

シフト中に現金回収や現金での支出（払い戻し、レジからの仕入先への支払い）があった場合は、それらの金額も準備しておいてください。

  </StepCard>
  <StepCard number="3" title="レポート画面を開く">

POS で**レポート**を開きます。レポートがシフトの時間帯を正確にカバーするようにフィルターを設定してください。

- **日付範囲：** *今日*（後日精算する場合は該当する日付）
- **レジ係：** 複数のレジ係が同じレジを使い、自分の売上だけを表示したい場合は、自分のユーザーを選択します
- **店舗：** 現在の店舗が自動的に設定されます
- **ステータス：** デフォルトのままにします（通常は*完了* + *処理中*）

右側の売上サマリーパネルは、フィルターを変更すると更新されます。*決済方法*の下にある**現金**の金額を控えてください。これが**現金売上の期待値**です。

  </StepCard>
  <StepCard number="4" title="現金の照合">

次の計算を行います。

> **ドロワーの予想残高 = 開始時の釣銭準備金 + 現金売上 − 現金での払い戻し − 現金回収/出金**

**実測現金高**と比較してください。一致するはずです。

- **一致した場合：** 問題ありません。精算シートに署名と日付を記入し、現金を回収すれば、現金の照合は完了です。
- **不一致の場合:** 署名する前に、下記の[差異の対処](#variance-handling)を参照してください。

</StepCard>
  <StepCard number="5" title="カード決済の照合">

次にカード決済を確認します。売上サマリーから**カード**の金額（および Stripe Terminal、SumUp、Vipps/MobilePay などの統合決済ゲートウェイの金額）を控えてください。

カード端末で**バッチ合計**を実行します（正確なメニューは端末によって異なりますが、通常は端末の*レポート*または*締め処理*にあります）。次の点を確認してください。

- 同一期間の**端末バッチ合計**と**WCPOS カード合計**を比較します。一致するはずです。
- 手動でバッチ精算する端末を使用している場合は、帰宅する前に**今すぐバッチを精算**してください。Stripe Terminal などの統合型ゲートウェイは自動精算されます。Web チェックアウト経由の Square の設定については、[Web チェックアウト](/1.x/payment/gateways/web-checkout)を参照してください。

</StepCard>
  <StepCard number="6" title="レポートを印刷する">

レポート画面のサマリーパネルで**印刷**をクリックします。通常は、設定済みの印刷ルーティング（[印刷ルーティング](/1.x/hardware/printers#print-routing)を参照）を使用して、レシートプリンターまたはドキュメントプリンターにレポートを送り、紙の記録を出力します。

印刷されたレポートには、店舗情報、期間、項目別合計、支払方法の内訳、および注文テーブルで注文を選択している場合は注文ごとの詳細が含まれます。

  </StepCard>
  <StepCard number="7" title="現金を回収して締める" isLast>

- **翌日分の釣銭準備金**をドロワーに戻します。
- 署名済みの精算シートと印刷したレポートをホチキスで留め、残りの現金と一緒に入金用バッグに入れて金庫に保管します。
- 使用している外部システム（スプレッドシート、会計ソフトウェアなど）を更新します。
- WCPOS アプリを閉じて施錠します。

</StepCard>
</Steps>

## 差異の対応 {#variance-handling}

実測現金高が予想残高と一致しない場合は、締め作業を完了する前に次の項目を順番に確認してください。

1. **ドロワーを再計数する。** 数え間違いは起こるものです。特に硬貨を中心に、もう一度数え直してください。
2. **記録漏れの現金取引がないか確認する。** 別のデバイスやブラウザータブで売上を処理し、この期間に含まれていないものはありませんか。レポートの日付範囲とレジ係フィルターを再確認してください。
3. **保留中／未完了の注文がないか確認する。** 注文一覧を *POS - Open* ステータスで絞り込みます。レジに入力したものの、まだ支払われていない売上がここに表示されます。今すぐ完了するか、その分の差異が生じることを見込んでください。
4. **払い戻しと出金。** 本日の現金での払い戻しと出金が、すべて金額とともに精算シートに記録されていることを確認してください。
5. **クーポンと割引。** 適用した割引が合計に反映されていることを確認します。レポートの*割引合計*行には追跡対象のクーポン割引が表示されます。明細行の価格変更は*純売上*を直接減らします（[割引](/1.x/pos/cart/discounts#why-tracked-differently)を参照）。
6. **お釣りの渡し間違い。** 差異の最も一般的な原因です。小さな差異（$5 未満）は通常これが原因です。大きな差異は調査が必要です。

原因が判明したかどうかにかかわらず、差異を精算シートに記録してください。小さな差異でも記録を残しておく方が、不一致を記録せずに済ませるよりもよい対応です。

## 複数のレジ係・複数店舗の場合 {#multi-cashier-or-multi-store-scenarios}

<Accordion>
  <AccordionItem question="本日、同じレジを複数のレジ係が使用した場合">

次の二つの方法があります。

- **レジ係ごとに締め処理を行う**（最も正確）：各レジ係が締め処理前にレポートを自分のユーザーで絞り込みます。それぞれが受け取った金額を数え、自分の担当分を照合します。シフト交代時にドロワーを引き継ぐことができ、各引き継ぎが簡易的な締め処理になります。
- **その日の営業をまとめて締める**：レジ係フィルターを*すべて*のままにして、営業終了時にドロワーをまとめて精算します。短時間で済みますが、差異が誰の担当中に生じたかを特定しにくくなります。

レポート画面のレジ係フィルターは、内訳表示にも使われるフィルターです。レジ係ごとの専用パネルはありません。

  </AccordionItem>

  <AccordionItem question="本日、同じレジ係が複数の店舗で勤務した場合">

一方の店舗からサインアウトし、もう一方の店舗にサインインします。各セッションは、注文メタデータの `_pos_store` によって正しい店舗に紐づけて記録されます。締め作業時には、レポート画面の**店舗**フィルターを切り替えて、店舗ごとに精算してください。

営業終了時にサイト全体を締める場合は、店舗フィルターを*すべて*に設定し、全体の締め処理も行ってください。店舗ごとの締め処理との照合に役立ちます。

  </AccordionItem>

  <AccordionItem question="店舗ごとに異なる担当者が締め作業を行う場合">

それが通常の運用です。各店舗の締め担当者が自分の店舗にサインインし、その店舗と当日の日付範囲で絞り込んだレポートを実行して、その店舗のドロワーを精算します。サイト所有者は翌朝、全店舗のデータを集約する **WP Admin → WooCommerce → 分析** ですべてを確認できます。

  </AccordionItem>

  <AccordionItem question="締め作業を開始した後に売上が発生した場合">

そのまま今回の締めに含めないでください。次のいずれかで対応します。

- **レポート期間を延長して**その売上を含めます（実測現金高にも新しい売上分を加えます）。または、
- **翌日のレポートに回し**、遅れて発生した売上の現金を翌日の開始時の精算シートに繰越として記録します。

方針を決めたら、一貫して守ってください。対応方法が変わると、帳簿の監査が難しくなります。

  </AccordionItem>
</Accordion>

## ベストプラクティス {#best-practices}

- **毎日締め処理を行ってください。** 一日飛ばすと、二日分の差異を追跡することになり、はるかに難しくなります。
- 取引の少ない日でも**レポートを印刷して保管してください**。紙の記録は、監査や紛争の際に役立ちます。
- **ユーザーアカウントを共有しないでください。** 各レジ係がそれぞれの WordPress ユーザーを使うことで、レジ係フィルターが担当者別レポートで正しく機能します。
- **毎週 WooCommerce の分析と照合してください**(`WP Admin → WooCommerce → Analytics`)。同じデータが異なる形式で表示されます。合計が一致しない場合は、通常、保留中の注文が後から完了されたか、払い戻しが POS ではなく WP Admin で処理されたことが原因です。
- **釣銭準備金を一定に保ってください。** 開始時の釣銭準備金を頻繁に変更すると、計算ミスを招きます。
