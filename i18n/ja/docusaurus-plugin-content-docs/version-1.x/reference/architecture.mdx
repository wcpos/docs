このページでは、開発者や上級ユーザー向けにWCPOSの技術アーキテクチャを説明します。

## 二部構成システム {#two-part-system}

WCPOSは二部構成のシステムとして設計されています：

1. **PHPプラグイン:** サーバーにホストされる比較的小さなプラグインで、[WooCommerce REST API](/reference/wc-rest-api) を POS 固有のエンドポイントで拡張します。

2. **JavaScriptクライアント:** ブラウザー、デスクトップアプリ、または iOS / Android アプリ上でローカルに実行されます。

これは二つの別々の世界と考えることができます：

- _PHP世界_は、WordPressとWooCommerceを使用してデータ管理が行われる場所です。
- _JavaScript世界_は、レジに必要な店舗データのオフライン対応のローカルコピーを保持し、高速な検索と即座の応答に最適化されています。

## データ同期 {#data-synchronization}

:::info v1.10.0 での変更
v1.10.0 では、従来のレプリケーション層が専用の**同期エンジン**に置き換えられました。以下は要約です。詳しい説明は[同期エンジンの仕組み](/reference/sync-engine)にあります。
:::

クライアントはローカルファーストです。すべての画面はデバイスのローカルデータベースを読み書きし、バックグラウンドの同期エンジンがそのデータベースと WooCommerce を収束させます。このエンジンは店舗全体を無条件にミラーリングすることは**ありません**。画面が実際に必要とするものを起点に動作します。

- **変更検出:** POS は条件付きリクエストで軽量な変更ログをポーリングします。更新のない店舗は、本文のない `304` を1回返すだけです。
- **宣言された需要:** 画面が表示している内容を宣言し、エンジンがそれにリクエストが必要か、それともローカルで既に応答できるかを判断します。
- **シードとレーン:** 範囲を限定したカタログのシード、直近の注文のウィンドウ、アイドル時のメンテナンスレーンが、デバイスごとに調整可能なスケジュールでローカルデータを充填・検証します。
- **確実な書き込み:** 販売や編集はローカルにキューイングされて WooCommerce へ送信され、サーバーが拒否したものは目に見える形で復旧できます。

同期される対象: 商品とバリエーション、カテゴリー / タグ / ブランド、顧客、税率、クーポン（Pro）、注文。支払いゲートウェイはチェックアウト時に取得されます。

## アーキテクチャの利点と欠点 {#architecture-pros-and-cons}

| 良い 😊 | 悪い 😟 |
| ------------------------------------------------------------------ | -------------------------------------------------------- |
| ローカルデータの検索は瞬時です | データの同期を保つのは困難です |
| オフラインで利用可能なキャッシュデータ | WooCommerce REST APIに制限されています |
| デスクトップ、iOS、Android用のより良いネイティブアプリを作成できる | WordPressのテーマやフックがPOSアプリをカスタマイズできない |

## ローカルデータベース {#local-database}

クライアントは各デバイスのローカルデータベースにデータを保存します。ウェブアプリとデスクトップアプリは **ワーカー内で動作する OPFS（Origin Private File System）ストレージ**を使用し、モバイルアプリはファイルシステムエンジンを介して同じディスク上の形式を使用します。すべてのプラットフォームが単一のストレージ形式と復旧ツールを共有しています。これにより：

- **永続性:** データはブラウザーの再起動やデバイスの再起動を経ても保持されます
- **パフォーマンス:** ネットワークの遅延なしに高速なクエリが可能です。絞り込み、並べ替え、ページングはストレージ層の内部で実行されるため、UI に届くのは表示中のページの行だけです
- **オフラインブラウジング:** キャッシュデータはインターネットなしでアクセス可能です

サイト + 店舗 + キャッシャーの組み合わせごとに独自のローカルデータベースが作成されるため、1台のデバイス上でキャッシャーや店舗がローカルデータを共有することはありません。アップグレード時にローカルデータベースをその場で移行することはありません。アプリはサーバーから再ダウンロードします。サーバーが常に正式なコピーです。

## チェックアウトアーキテクチャ {#checkout-architecture}

チェックアウトプロセスでは、WooCommerceの注文支払いページをロードするiframe/webviewを使用します。このアプローチは：

- **既存の支払いゲートウェイを活用:** すべてのWooCommerce支払いゲートウェイがPOSで機能できます
- **セキュリティを維持:** 支払い処理はWooCommerceの安全なインフラストラクチャを通じて行われます
- **複雑さを減少:** 支払いゲートウェイの統合を再実装する必要がありません

## API拡張 {#api-extensions}

PHPプラグインは、POS固有の機能のために追加のエンドポイントで WooCommerce REST API を拡張します。これらは専用の `wcpos/v1` および `wcpos/v2` 名前空間の下に登録されます。`wcpos/v2` は v1.10.0 の同期サーフェスを担っており、アプリとプラグインのバージョンが足並みを揃えてリリースされるのはこのためです。詳細は [WooCommerce REST API](/reference/wc-rest-api) を参照してください。
