このページでは、開発者や上級ユーザー向けにWCPOSの技術アーキテクチャを説明します。

## 二部構成のシステム {#two-part-system}

WCPOSは二部構成のシステムとして設計されています。

1. **PHPプラグイン：** サーバー上で動作する比較的小さなプラグインで、[WooCommerce REST API](/1.x/reference/wc-rest-api)にPOS固有のエンドポイントを追加します。

2. **JavaScriptクライアント：** ブラウザー、デスクトップアプリ、またはiOS/Androidアプリでローカルに実行されます。

二つの独立した世界として考えることができます。

- _PHPの世界_ では、WordPressとWooCommerceを使ってデータを管理します。
- _JavaScriptの世界_ では、レジで必要な店舗データのコピーを、オフラインでも使える形でローカルに保持します。高速な検索と即時応答に最適化されています。

## データ同期 {#data-synchronization}

:::info v1.10.0で変更
v1.10.0では、従来のレプリケーション層が専用の **同期エンジン** に置き換わりました。以下はその概要です。詳しくは[同期エンジンの仕組み](/1.x/reference/sync-engine)をご覧ください。
:::

クライアントはローカルファースト方式です。すべての画面がデバイスのローカルデータベースを読み書きし、バックグラウンドの同期エンジンがそのデータベースとWooCommerceの内容を一致させます。エンジンが店舗全体を無条件にミラーリングすることは **ありません**。画面が実際に必要とするデータに基づいて動作します。

- **変更検出：** POSは条件付きリクエストで軽量な変更ログを定期的に確認します。変更のない店舗は、本文のない `304` 応答一つだけを返します。
- **必要なデータの宣言：** 画面が表示内容を宣言し、エンジンはリクエストが必要か、ローカルのデータだけで対応できるかを判断します。
- **シードとレーン：** 範囲を限定したカタログの初期取得、最近の注文を対象とする期間枠、アイドル時のメンテナンスレーンが、デバイスごとに調整できるスケジュールでローカルデータを補充・検証します。
- **永続的な書き込み：** 売上や編集内容はローカルのキューに保存され、順次WooCommerceへ送信されます。サーバーに拒否されたものは画面上で確認し、復旧できます。

同期対象は、商品とバリエーション、カテゴリー/タグ/ブランド、顧客、税率、クーポン（Pro）、注文です。決済ゲートウェイはチェックアウト時に取得されます。

## アーキテクチャの長所と短所 {#architecture-pros-and-cons}

| 良い点 😊 | 悪い点 😟 |
| ------------------------------------------------------------------ | -------------------------------------------------------- |
| ローカルデータを瞬時に検索できる | データの同期を保つのが難しい |
| キャッシュされたデータをオフラインで利用できる | WooCommerce REST APIによる制約を受ける |
| デスクトップ、iOS、Android向けに、より優れたネイティブアプリを作成できる | WordPressのテーマやフックでPOSアプリをカスタマイズできない |

## ローカルデータベース {#local-database}

クライアントは、各デバイスのローカルデータベースにデータを保存します。ウェブアプリとデスクトップアプリでは **ワーカー内で動作するOPFS（Origin Private File System）ストレージ** を使用し、モバイルアプリではファイルシステムエンジンを通じて同じディスク上の形式を使用します。すべてのプラットフォームで保存形式と復旧ツールが共通です。これにより、次のことが実現します。

- **永続性：** ブラウザーやデバイスを再起動してもデータが保持されます
- **パフォーマンス：** ネットワーク遅延のない高速なクエリが可能です。絞り込み、並べ替え、ページ分割はストレージ層の内部で実行されるため、表示するページ分の行だけがUIに渡されます
- **オフライン閲覧：** インターネットに接続していなくても、キャッシュされたデータにアクセスできます

サイト、店舗、レジ係の組み合わせごとに専用のローカルデータベースが作成されるため、同じデバイス上でレジ係や店舗がローカルデータを共有することはありません。アップグレード時にローカルデータベースをその場で移行することはなく、アプリは常に正本となるサーバーからデータを再ダウンロードします。

## チェックアウトのアーキテクチャ {#checkout-architecture}

チェックアウトでは、WooCommerceの注文支払いページを読み込むiframe/webviewを使用します。この方式には、次の利点があります。

- **既存の決済ゲートウェイを活用：** どのWooCommerce決済ゲートウェイもPOSで動作させられます
- **セキュリティの維持：** 決済処理はWooCommerceの安全なインフラを通じて行われます
- **複雑さの軽減：** 決済ゲートウェイとの連携を再実装する必要がありません

## API拡張 {#api-extensions}

PHPプラグインは、POS固有の機能に対応するエンドポイントをWooCommerce REST APIに追加し、専用の `wcpos/v1` および `wcpos/v2` 名前空間に登録します。`wcpos/v2` がv1.10.0の同期機能を担うため、アプリとプラグインのバージョンは足並みをそろえてリリースされます。概要は[WooCommerce REST API](/1.x/reference/wc-rest-api)を参照してください。

### `wcpos/v2` 名前空間 {#wcpos-v2-namespace}

v1.10では、`wcpos/v2` REST名前空間が導入されました。同期はここで処理され、従来 `wcpos/v1` から提供されていたPOSの共通サービスも、現在は `wcpos/v2` から提供されます（`wcpos/v1` のサービスルートは、対応するv2の実装に処理を渡します）。後方互換性のために `wcpos/v1` のルートは引き続き登録されますが、**凍結** されており、現在のクライアントは呼び出しません。

これらのエンドポイントと連携する際の重要な点は、次のとおりです。

- **v2のルートは常に登録されます。** 従来の `woocommerce_pos_sync_api_enabled` オプションは削除され、APIをオン・オフするフラグはなくなりました。
- **公開エンドポイント。** `wcpos/v2/site`、`wcpos/v2/ping`、`wcpos/v2/echo` は公開されています。制約の厳しいホスト向けの[トランスポートフォールバック](/1.x/error-codes)を含め、機能や接続性の確認に使用されます。
- **注文はUUIDを主キーとします。** 通信上の注文識別子はUUIDです。従来の `wooOrderId` フィールドは、注文取得用のデータ構造から削除されました。注文メタデータは単一の正規化処理により型を付けて通信されます。
- サードパーティの同期処理との互換性を確保するため、**明細の価格保存方法を文書化しています**。[POS価格上書きの保存方法](/1.x/reference/pos-discounts#how-pos-price-overrides-are-stored)を参照してください。
- POSの **デフォルトの商品並び順** は、現在 **名前の昇順** です（以前は `menu_order, id`）。
- **従来のメソッドの削除。** `API\Settings` コントローラーの従来のメソッドの一部（例：`get_general_settings()`、`update_access_settings()`、`get_general_endpoint_args()`、`remove_license_transient()`）が削除されました。クラスのエイリアスは残っていますが、これらのメソッドは残っていません。

:::note Proも同じ分割に従います
WCPOS Proも同じV1/V2の分割に従います。共通サービスは `wcpos/v2` に移行し、注文データはv1のまま凍結されます。店舗別の商品価格設定はv2のレーンで処理され、レジの店舗スコープが注文の書き込みに引き継がれるため、複数店舗の注文でも正しい店舗に基づいて価格と税が計算されます。[Pro](/1.x/getting-started/free-vs-pro)を参照してください。
:::
