:::info v1.10.0の新機能
このページでは、**WCPOS v1.10.0** で導入された同期エンジンについて説明します。それ以前のバージョンは、画面ごとに異なるレプリケーションモデルを使用しています。ページ末尾の[v1.10.0での変更点](#what-changed-in-v1100)をご覧ください。
:::

WCPOSはローカルファーストです。すべての画面はデバイス上のデータベースに対して読み書きを行い、**同期エンジン**がそのデータベースとWooCommerceストアをバックグラウンドで収束させ続けます。このページでは、エンジンが何を、いつ取得するかをどのように判断し、売上がどのようにサーバーへ戻るのかを説明します。開発者、インテグレーター、そしてPOSがホスティングに与える負荷を理解したいストアオーナーに役立つ詳細度でまとめています。

## 店舗とレジ係ごとに1つのエンジン {#one-engine-per-scope}

POS は各デバイスで、**サイト + 店舗 + レジ係の組み合わせごとに1つの同期エンジン**を実行します。各エンジンは独自のローカルデータベースを持つため、店舗またはレジ係を切り替えると、共有データの集合をフィルタリングするのではなく、データプレーン全体が切り替わります。レジ係ごとの分離は意図的なものです。同じデバイス上の2人のレジ係がローカルデータを共有することはありません。

スコープの切り替えは**トランザクションとして行われます**。新しい店舗またはレジ係のデータプレーンにデータを読み込み、準備が整ってから確定します。エラーが発生した場合は通知されるため、2つの店舗の中間状態に取り残されることはありません。

アップグレード時にローカルデータベースがその場で移行されることはありません。アプリは新しいデータベースを作成し、常に正となるコピーを保持しているサーバーからダウンロードし直します（[v1.9からのアップグレード](#upgrading-from-v19)を参照）。

Proのマルチストア構成では、すべての同期リクエストが対象のストアを識別します。そのため、レジで編集した価格はWebストアの価格ではなく、そのストアの価格を更新します。

## バックグラウンドで実行される処理 {#sync-lanes}

エンジンがスケジュールに従って行う処理はすべて **レーン**、つまり名前と範囲が定められたバックグラウンド作業の単位です。レーンは次の3つのグループに分類されます:

| グループ | レーン | 既定の実行間隔 |
| --- | --- | --- |
| **プル** | 変更チェック（変更シグナル） | 10秒〜5分（[同期プリセット](/support/store-health#sync-presets)で設定） |
| | 最近の注文、商品カタログのシード、参照データのシード | 約5分 |
| | 顧客のトリクル（アイドル時のみ） | 約5分 |
| **プッシュ** | 書き込みドレイン — キューに入ったローカルの変更を送信 | 約10秒 |
| **メンテナンス** | 整合性および削除の監査、サーバー合計数の更新 | 数分〜約17分ごと |

すべてのレーンには、次の2つの特性があります:

- **各レーンには、1回の実行あたりのリクエスト上限が設定されています。** 1回の実行で無制限のリクエストを発行するレーンはありません。大規模な処理は、再開可能なカーソルを使った上限付きのバッチで行います。これは中核となる設計上の不変条件であり、[同期パフォーマンス](/reference/sync-performance)で詳しく説明しています。
- **メンテナンスはキャッシャーに道を譲ります。** 監査やバックグラウンドの事前読み込みは、レジが販売できる状態になるまでの対話的な処理の後に実行され、その前に実行されることはありません。また、サーバーに負荷の兆候が見られたときに最初に一時停止されるのもこれらの処理です。

上記の間隔は既定値です。チェック間隔とリクエストあたりのレコード数は、POSの **ストアヘルス → パフォーマンス** からデバイスごとに販売者が調整できます。[ストアヘルス](/support/store-health)をご覧ください。

## POSが変更を検知する仕組み {#change-signal}

エンジンは、変更の有無を確認するためにデータを再ダウンロードしません。サーバーが変更ログを保持し、POSは軽量な**変更チェック**をポーリングして、前回の位置から変更があったかどうかだけを確認します。

- **1回のチェックで8つのコレクションを確認します** — 商品、バリエーション、税率、顧客、クーポン、カテゴリー、ブランド、タグです。注文は意図的に変更チェックの対象外です。注文の最新状態は独自の最近の注文レーンで取得するため、商品と注文の更新頻度は異なる場合があります。
- **アイドル状態のレジにかかる負荷はごくわずかです。** エンジンは条件付きリクエストを送信します。変更がなければ、サーバーは本文のない単一の `304 Not Modified` で応答します。店舗が静かなときは、チェックごとにごく小さな応答が1つ返るだけです。
- **チェックの間隔には±20%のジッターを加えます**。そのため、同じサイトにある複数のレジのチェック時刻が分散され、サーバーに一斉にリクエストが集中するのを防ぎます。
- **アイドル時の減衰:** 10分間操作がないと、チェック間隔が延びます（下限は60秒）。タッチ、キー入力、バーコードスキャンの受理といった実際の操作があれば、すぐに通常の間隔に戻り、即座にキャッチアップのチェックが実行されます。減衰は間隔を延ばすだけで、設定値より速くポーリングすることはありません。
- **数日間閉じられていたレジは、履歴を再生するのではなくベースラインを取り直します。** 変更ログがレジの最後の位置から離れすぎている場合、すべての行を再生すると数百件のリクエストが必要になります。そこでエンジンはカーソルを先頭までジャンプさせ、デバイスがすでに保持しているデータの現在のサーバー上の状態を確認し直します。これにより、コストはレジが離れていた期間ではなく、ローカルコピーのサイズに比例します。

## 画面がデータを取得する仕組み {#declared-demand}

v1.10.0 では、画面ごとに独自の同期処理を実行しません。**画面は検索語、フィルター、並べ替え、ページなど表示内容を宣言し、それがリクエストを必要とするかどうかをエンジンが判断します。** 宣言の結果は次の3つのいずれかになります:

- **取得（Fetched）** — エンジンが宣言を満たすために通信を行いました。
- **ローカルで応答（Served locally）** — デバイスがすでに答えを保持していたか、直近の同一の取得結果でカバーできました。
- **上書き（Superseded）** — 画面が先へ進み（スクロールした、フィルターを変更した）、より新しい宣言に置き換えられました。これは通常の動作であり、エラーではありません。

ローカルだけで答えられるフィルターがサーバーまで届くことはありません。また、宣言が成功したからといって、そのコレクションが完全にダウンロードされたことにはなりません。完全性は別途追跡されます（次のセクション）。

すべてが先読みでダウンロードされるわけではなく、起動時にデバイス上に何があるかはコレクションによって異なります。

1. **シードされるもの** — 商品は上限付きのカタログシードによって充填されます。税率は起動時に取得されます（税率がなければPOSはカートの計算ができません）。
2. **オンデマンド＋アイドル時のトリクル** — 顧客には先読みのシードがありません。顧客のトリクルはアイドルの間隔ごとに小さなバッチをダウンロードし、キャッシャーが操作中のときは完全にスキップします。新規または変更された顧客は変更チェックを通じて届きます。
3. **初回オープン時に取得されるもの** — カテゴリー、タグ、ブランド、クーポンは、キャッシャーが最初に開いたときに取得されます。誰も開かないコレクションが、リクエストを発生させることは一切ありません。

バリエーション選択画面では、開くたびに価格と在庫も更新されます。そのため、読み込み済みのバリエーションはすぐに表示され、何日も前の古い在庫が表示されることもありません。

## 「すべてダウンロードされていますか？」— 誠実なカバレッジ {#coverage}

*「5,000件中1,240件の商品」*のような表示には、分母となる**サーバー側**の合計数が必要です。エンジンはコレクションごとに合計数を管理し（およそ15分ごとに更新されます。通常のsyncレスポンスにすでに合計数が含まれているため、専用のリクエストが必要になることはめったになく、たいていコストはかかりません）、次の厳格な誠実性のルールに従います。

- サーバー合計数が古い、または取得できない場合は*確認中…*と表示され、ローカルの件数がひそかに代用されることはありません。ローカルの分母を使えば常に100％と表示され、この数値が明らかにすべきギャップそのものを隠してしまうからです。
- エンジンが完全性を保証できない場合、判定は*不明*となり、UIはその数値をローカルの件数として表示します。
- 注文のカバレッジバーは、サーバー上の**すべての**注文履歴に対して測定されます。一方でレジは意図的に未処理の注文と最近の注文のみを保持します。そのため、正常なレジでも注文は部分的と表示されますが、これは設計どおりです。

これらの数値は **ストアヘルス → データベース** に表示されます。あわせて、最初の商品がデバイスに届いた時点で切り替わる*販売準備完了*のマイルストーンも表示されます。オフラインであっても妨げにはなりません。オフラインで販売できることこそが目的だからです。[ストアヘルス](/support/store-health)をご覧ください。

## 変更がストアに戻る仕組み {#write-path}

ローカルでの書き込み（売上、商品の編集、顧客の更新）はすべて、まずデバイス上の**永続的な送信キュー**に入ります。そしてドレインレーンが数秒ごとにキューをWooCommerceへ送信します。これがオフライン販売を安全にしている仕組みです。接続がない状態で計上した売上はキューに留まり、接続が戻った時点で送信されます。

重要な詳細は次のとおりです。

- **カートへの書き込みは注文ごとに直列化されます。** スキャナーで短時間に連続して読み取った場合も、1件ずつ適用されます。重複する商品の追加は、2行目としてキューに入れず、既存の行にまとめられます。
- **注文の確認応答ではサーバー側のコピーを採用します。** WooCommerceは注文の作成時に明細行へIDを割り当てます。エンジンは確認応答された注文を採用するため、以降の更新は重複行を追加するのではなく、それらの明細行に一致します。採用は保守的に行われ、サーバーがまだ認識していないローカルの編集を上書きすることはなく、注文にのみ適用されます。
- **注文の書き込み競合は1回だけ自動的に解決されます。** 新しいサーバー側の注文データと書き込みが競合した場合、エンジンは整合を取り直して1回だけ再試行します。それでも解決できなければ、何度も黙って繰り返すのではなく、競合を通知して対応を促します。
- **サーバーが恒久的に拒否した書き込みは、自動で再試行されません。** サーバーが返した理由とともに保留され、**店舗の健全性 → データベース**に*"変更がサーバーに届きませんでした"*と表示されます。明示的な操作として**再送信**（現在のレコードからリクエストを再構築するため、その後の修正が反映されます）と**破棄**が用意されています。自動再試行は行われず、復旧操作は常に明示的に実行します。店舗管理者向けの手順は[店舗の健全性](/support/store-health#database)を参照してください。

### 複数のブラウザータブ {#multi-tab}

同じ店舗の Web POS を複数のタブで実行できます。どのタブからも販売を処理でき、書き込みは共有キューに追加されますが、店舗 + レジ係の各スコープで**送信を行うのは選出された1つのタブだけです**。そのタブを閉じると、ブラウザーが次のタブを自動的に昇格させます。異なるレジ係でログインした2つのタブは別々のスコープとなり、それぞれが独自のキューを管理します。

## ローカルストレージ {#local-storage}

Web アプリとデスクトップアプリは **OPFS (Origin Private File System) ワーカー**を介してデータを保存します。iOS アプリと Android アプリは、ファイルシステムエンジンを通じて同じディスク形式を使用します。4つのプラットフォームすべてでストレージ形式と破損復旧ツールを共有します。（以前のバージョンでは、Web で IndexedDB、ネイティブアプリで SQLite を使用していました。）

ローカル店舗データが**読み取れない**場合、WCPOSはチェックアウトをブロックして再読み込みを促します。破損したデータで販売を続けて注文を失うことはありません。また、その状態でバーコードをスキャンすると、無反応になるのではなくエラーが明確に表示されます。復旧ツールがデータを再構築する前に、破損した店舗データによって販売が気付かれずに失われることを防ぎます。

クエリ（セレクター、並べ替え、ページ指定）はデータベース層内で実行されるため、表示中のページの行だけがアプリに渡されます。合成した10,000件の注文データでのテストでは、このプッシュダウンにより、ライブ購読中の書き込みごとの更新コストが約27 msから約0.06 msに下がりました。

## v1.9からのアップグレード {#upgrading-from-v19}

v1.10.0はローカルデータベースを移行せず、**コールド再同期**を実行します。

1. 初回起動時、アプリは新しいローカルデータベースを開き、ストアからダウンロードし直します。すべてのデバイスで一度だけ、完全な再ダウンロードが発生します。
2. データが失われることはありません。同期されるすべてのデータについて、正となるコピーはWooCommerceサーバーです。未送信の変更は、古いデータが整理される**前に**送信されるか、画面に表示されます。アップグレードによって未送信の売上が失われることはありません。
3. **アプリとプラグインは足並みをそろえてリリースされます。** v1.10.0のクライアントは、プラグインのv2同期APIを使用します。どちらか一方だけをアップグレードすると、リクエストは `rest_no_route` エラーで失敗します。このエラーは「もう一方も更新してください」という意味であり、インストールが壊れているわけではありません。

## v1.10.0での変更点 {#what-changed-in-v1100}

| | v1.9.x | v1.10.0 |
| --- | --- | --- |
| 同期単位 | マウントされた画面クエリごとに1つのレプリケーションストリーム | サイト + 店舗 + レジ係ごとに1つのエンジン |
| 取得のきっかけ | 画面のマウント | 画面が必要なものを宣言すること |
| 変更の検出 | 定期ポーリング + 毎時の全件監査 | 変更ログカーソルと条件付き `304` レスポンス |
| サーバー合計数 | 追跡なし | コレクションごとの合計数と、誠実な*確認中…*の状態 |
| 失敗した書き込み | 不透明に再試行 | 永続キュー、目に見える復旧パネル、ひそかな再試行なし |
| 複数タブの Web | 調整なし | スコープごとに選出された1つの送信元 |
| ローカル検索 | 単語の前方一致 | 部分一致（3文字以上） |
| ストレージ | IndexedDB（Web）、SQLite（ネイティブ） | 全プラットフォームでOPFS形式のストレージ |
| 同期のチューニング | 固定 | ストアヘルス内のデバイスごとのプリセットとダイヤル |

エンジンの背後にあるパフォーマンスの考え方（リクエスト上限、サーバー負荷時のバックオフ、実測値）については、[同期のパフォーマンス](/reference/sync-performance)をご覧ください。
