:::info v1.10.0の新機能
このページでは、**WCPOS v1.10.0** で導入された同期エンジンについて説明します。それ以前のバージョンは、画面ごとに異なるレプリケーションモデルを使用しています。ページ末尾の[v1.10.0での変更点](#what-changed-in-v1100)をご覧ください。
:::

WCPOSはローカルファーストです。すべての画面はデバイス上のデータベースに対して読み書きを行い、**同期エンジン**がそのデータベースとWooCommerceストアをバックグラウンドで収束させ続けます。このページでは、エンジンが何を、いつ取得するかをどのように判断し、売上がどのようにサーバーへ戻るのかを説明します。開発者、インテグレーター、そしてPOSがホスティングに与える負荷を理解したいストアオーナーに役立つ詳細度でまとめています。

## 店舗とレジ係の組み合わせごとに1つのエンジン {#one-engine-per-scope}

各デバイスでは、POSは**サイト + 店舗 + レジ係の組み合わせごとに1つの同期エンジン**を実行します。エンジンはそれぞれ独自のローカルデータベースを持つため、店舗やレジ係を切り替えると、共有されたレコード群をフィルタリングするのではなく、データプレーン全体が切り替わります。レジ係ごとの分離は意図的なもので、同じデバイス上の2人のレジ係がローカルデータを共有することはありません。

スコープの切り替えは**トランザクションとして行われます**。新しい店舗またはレジ係のデータプレーンにデータが読み込まれ、準備ができてから切り替えが確定します。エラーが発生した場合も通知されるため、2つの店舗の間で中途半端な状態になることはありません。

アップグレード時にローカルデータベースがその場で移行されることはありません。アプリは新しいデータベースを作成し、常に正となるコピーを保持しているサーバーからダウンロードし直します（[v1.9からのアップグレード](#upgrading-from-v19)を参照）。

Proの複数店舗構成では、すべての同期リクエストが対象の店舗を識別します。そのため、レジで価格を編集すると、オンラインショップの価格ではなく、その店舗の価格が更新されます。

## バックグラウンドで実行される処理 {#sync-lanes}

エンジンがスケジュールに沿って行う処理はすべて**レーン**と呼ばれます。これは、名前と処理量の上限が定められたバックグラウンド処理の単位です。レーンは次の3つのグループに分かれます。

| グループ | レーン | デフォルトの実行間隔 |
| --- | --- | --- |
| **プル** | 変更チェック（変更シグナル） | 10秒〜5分。[同期プリセット](/1.x/support/store-health#sync-presets)で設定 |
| | 最近の注文、商品カタログのシード、参照データのシード | 約5分 |
| | 顧客のトリクル（アイドル時のみ） | 約5分 |
| **プッシュ** | 書き込みドレイン — キューに入ったローカルの変更を送信 | 約10秒 |
| **メンテナンス** | 整合性監査と削除監査、サーバー合計数の更新 | 数分〜約17分ごと |

すべてのレーンには、次の2つの特性があります。

- **各レーンは、1回の実行あたりのリクエスト上限を宣言します。** 1回の実行で無制限にリクエストを発行するレーンはありません。大規模な処理は、再開可能なカーソルを使い、上限付きのバッチで行います。これは設計の中核となる不変条件です。[同期のパフォーマンス](/1.x/reference/sync-performance)で詳しく説明しています。
- **メンテナンスよりレジ係の操作を優先します。** 監査やバックグラウンドの事前読み込みは、レジを販売可能にする対話的な処理が終わってから実行されます。それより先に実行されることはありません。また、サーバーに負荷の兆候が見られたときに最初に一時停止するのも、これらの処理です。

上記の間隔はデフォルト値です。販売者は、POSの**店舗の健全性 → パフォーマンス**で、チェック間隔とリクエストあたりのレコード数をデバイスごとに調整できます。[店舗の健全性](/1.x/support/store-health)を参照してください。

## POSが変更を検知する仕組み {#change-signal}

エンジンは、変更の有無を調べるためにデータをダウンロードし直すことはありません。サーバーが変更ログを保持し、POSは軽量な**変更チェック**をポーリングして、前回の位置から何か変わったかどうかだけを確認します。

- **1回のチェックで8つのコレクションを対象にします** — 商品、バリエーション、税率、顧客、クーポン、カテゴリー、ブランド、タグです。注文は意図的に変更チェックの対象外にしています。注文は専用の最近の注文レーンで最新の状態に保つため、商品と注文の更新は異なるタイミングで届く場合があります。
- **アイドル状態のレジには、ほとんどコストがかかりません。** エンジンは条件付きリクエストを送信します。変更がなければ、サーバーは本文のない `304 Not Modified` を1つ返します。変更のない店舗では、チェックごとにごく小さなレスポンスが1つ返るだけです。
- **チェック間隔には±20%のジッターを加えます**。同じサイトに複数のレジがあっても、リクエストが一斉にサーバーへ集中せず、タイミングが分散されます。
- **アイドル時の減衰：** 10分間操作がないと、チェック間隔を延ばします（下限は60秒）。タッチ、キー入力、バーコードスキャンの受理など、実際の操作があれば、すぐに通常の間隔に戻り、最新状態に追いつくためのチェックを即座に実行します。減衰は間隔を延ばすだけで、設定値より速くポーリングすることはありません。
- **数日間使っていなかったレジは、履歴を再生せず、基準状態を取り直します。** レジの最後の位置から変更ログが大幅に進んでいる場合、すべての行を再生すると数百件のリクエストが必要になります。代わりに、エンジンはカーソルを最新の位置へ移し、デバイスがすでに保持しているデータについて、現在のサーバーの状態を確認し直します。これにより、コストはレジを使っていなかった期間ではなく、ローカルコピーのサイズに比例します。

## 画面がデータを取得する仕組み {#declared-demand}

v1.10.0では、画面ごとに同期を実行しません。**画面は表示内容（検索語、フィルター、並べ替え、ページ）を宣言し、それにリクエストが必要かどうかをエンジンが判断します。** 各宣言は、次の3つのいずれかの結果になります。

- **取得** — 宣言を満たすために、エンジンが通信を行いました。
- **ローカルで応答** — デバイスがすでに必要なデータを保持していたか、直近の同一条件での取得結果で対応できました。
- **上書き** — スクロールやフィルター変更により画面の状態が変わり、新しい宣言に置き換わりました。これは通常の動作であり、エラーではありません。

ローカルでしか処理できないフィルターがサーバーに送られることはありません。また、宣言が成功しても、そのコレクションが完全にダウンロードされたことにはなりません。完全性は別に追跡します（次のセクションを参照）。

すべてのデータをあらかじめダウンロードするわけではありません。起動時にデバイス上にあるデータは、コレクションごとに異なります。

1. **シードされるもの** — 商品は上限付きのカタログシードで取り込まれます。税率は起動時に取得します（税率がなければ、POSはカートの計算ができません）。
2. **オンデマンド＋アイドル時のトリクル** — 顧客はあらかじめシードされません。顧客のトリクルは、アイドル時の実行間隔ごとに小さなバッチをダウンロードし、レジ係が操作している間は実行を完全にスキップします。新規または変更された顧客は、変更チェックを通じて取得します。
3. **初回オープン時に取得されるもの** — カテゴリー、タグ、ブランド、クーポンは、レジ係が初めて開いたときに取得します。誰も開かないコレクションでは、リクエストは一切発生しません。

バリエーション選択画面では、開くたびに価格と在庫も更新します。そのため、読み込み済みのバリエーションは即座に表示でき、何日も前の古い在庫が表示され続けることもありません。

## 「すべてダウンロードされていますか？」— 正確なカバレッジ表示 {#coverage}

*「5,000件中1,240件の商品」*のような表示には、分母として**サーバー側**の合計数が必要です。エンジンはコレクションごとに合計数を管理します。約15分ごとに更新しますが、通常の同期レスポンスにすでに合計数が含まれるため、専用リクエストが必要になることはまれで、通常は追加のコストがかかりません。表示では、次のルールを厳守します。

- サーバーの合計数が古い、または取得できない場合は*確認中…*と表示し、ローカルの件数に勝手に置き換えることはありません。ローカルの件数を分母にすると常に100%となり、本来この数値で示すべき差を隠してしまうためです。
- エンジンが完全性を保証できない場合、判定は*不明*となり、UIにはローカルの件数であることが表示されます。
- 注文のカバレッジバーは、サーバー上の注文履歴**全体**に対する割合を示します。一方、レジは意図的に未処理の注文と最近の注文だけを保持するため、正常なレジでも部分的な取得と表示されるのは設計どおりです。

これらの数値は**店舗の健全性 → データベース**に表示されます。最初の商品がデバイスに届くと切り替わる*販売準備完了*のマイルストーンも表示されます。オフライン販売を可能にすることが目的なので、オフラインでも準備完了になれます。[店舗の健全性](/1.x/support/store-health)を参照してください。

## 変更が店舗に戻る仕組み {#write-path}

売上、商品の編集、顧客の更新など、ローカルでの書き込みはすべて、まずデバイス上の**永続的な送信キュー**に入ります。ドレインレーンが数秒ごとにキューの内容をWooCommerceへ送信します。この仕組みにより、オフラインでも安全に販売できます。接続がない状態で計上した売上はキューに残り、接続が戻ると送信されます。

重要な点は次のとおりです。

- **カートへの書き込みは注文ごとに直列化されます。** スキャナーで連続して読み取っても、1件ずつ適用します。同じ商品を再度追加した場合は、別の明細行をキューに追加せず、既存の同じ明細行に統合します。
- **注文の確認応答では、サーバー側のコピーを採用します。** WooCommerceは注文の作成時に明細行へIDを割り当てます。エンジンが確認応答された注文を採用することで、以降の更新では重複行を追加せず、該当する明細行を更新できます。採用は慎重に行われ、サーバーがまだ受け取っていないローカルの編集を上書きすることはありません。また、この処理は注文にのみ適用されます。
- **注文の書き込み競合は、1回だけ自動で復旧を試みます。** サーバー上の新しいコピーと注文の書き込みが競合すると、エンジンが調整し、1回だけ再試行します。それでも解決できなければ、通知せずに再試行を繰り返すのではなく、解決が必要な競合として表示します。
- **サーバーが恒久的に拒否した書き込みを、通知せずに再試行することはありません。** サーバーから返された理由とともに保留し、**店舗の健全性 → データベース**に*「変更がサーバーに届きませんでした」*と表示します。操作として**再送信**（現在のレコードからリクエストを再構築するため、その後の修正が反映されます）と**破棄**が用意されています。自動で再試行を繰り返すことはなく、復旧は必ず画面上で明示的に操作します。販売者向けの手順は、[店舗の健全性](/1.x/support/store-health#database)を参照してください。

### 複数のブラウザータブ {#multi-tab}

同じ店舗のWeb POSを複数のタブで実行できます。どのタブでも販売でき、書き込みは共有キューに追加されます。ただし、店舗 + レジ係のスコープごとに、**選出された1つのタブだけが送信を担当します**。そのタブを閉じると、ブラウザーが次のタブを自動的に選出します。異なるレジ係としてサインインした2つのタブは別のスコープとなり、それぞれ独自のキューを管理します。

## ローカルストレージ {#local-storage}

Webアプリとデスクトップアプリは、**OPFS (Origin Private File System) ワーカー**を通じてデータを保存します。iOSアプリとAndroidアプリは、ファイルシステムエンジンを通じて同じディスク形式を使用します。4つのプラットフォームはすべて、共通のストレージ形式とデータ破損からの復旧ツールを使用します（以前のバージョンでは、WebでIndexedDB、ネイティブアプリでSQLiteを使用していました）。

ローカルのデータストアが**読み取れない**状態になると、WCPOSはチェックアウトをブロックし、再読み込みを促します。破損したデータで販売を続け、売上が失われるのを防ぐためです。その状態でバーコードをスキャンした場合も、無反応になるのではなく、エラーを明示します。復旧ツールがデータを再構築するまでの間に、破損したデータストアによって売上が気付かれずに失われることを防ぎます。

セレクター、並べ替え、ページ指定といったクエリ処理はデータベース層内で実行されるため、表示中のページの行だけがアプリに渡されます。合成した10,000件の注文フィクスチャでは、このプッシュダウンにより、ライブ購読中の書き込みごとの更新コストが約27 msから約0.06 msに下がりました。

## v1.9からのアップグレード {#upgrading-from-v19}

v1.10.0ではローカルデータベースを移行せず、**コールド再同期**を実行します。

1. 初回起動時、アプリは新しいローカルデータベースを開き、店舗からデータをダウンロードし直します。すべてのデバイスで、一度だけ全データの再ダウンロードが発生します。
2. データは失われません。同期されるすべてのデータの正本は、WooCommerceサーバー上にあります。保留中の未送信の変更は、古いデータを整理する**前に**送信されるか、画面に表示されます。アップグレードによって未送信の売上が失われることはありません。
3. **アプリとプラグインは、足並みをそろえてリリースされます。** v1.10.0のクライアントは、プラグインのv2同期APIを使用します。片方だけをアップグレードすると、リクエストは `rest_no_route` エラーで失敗します。これは「もう片方も更新してください」という意味であり、インストールが壊れているわけではありません。

## v1.10.0での変更点 {#what-changed-in-v1100}

| | v1.9.x | v1.10.0 |
| --- | --- | --- |
| 同期の単位 | マウントされた画面クエリごとに1つのレプリケーションストリーム | サイト + 店舗 + レジ係ごとに1つのエンジン |
| 取得のきっかけ | 画面のマウント | 画面による必要なデータの宣言 |
| 変更の検出 | 定期ポーリング + 毎時の全件監査 | 変更ログカーソルと条件付き `304` レスポンス |
| サーバー合計数 | 追跡なし | コレクションごとの合計数と、状態を正確に示す*確認中…*の表示 |
| 失敗した書き込み | 状況が見えないまま再試行 | 永続キューと復旧パネル。通知のない再試行はなし |
| Webの複数タブ | 調整なし | スコープごとに送信担当を1つ選出 |
| ローカル検索 | 単語の前方一致 | 部分一致（3文字以上） |
| ストレージ | IndexedDB（Web）、SQLite（ネイティブ） | 全プラットフォームでOPFS形式のストレージ |
| 同期の調整 | 固定 | 店舗の健全性でデバイスごとにプリセットとダイヤルを設定 |

リクエスト数の上限、サーバー負荷時のバックオフ、実測値など、エンジンのパフォーマンスに関する考え方は、[同期のパフォーマンス](/1.x/reference/sync-performance)を参照してください。
