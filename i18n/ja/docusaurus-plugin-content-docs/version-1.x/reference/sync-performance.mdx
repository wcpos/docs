このページでは、**WCPOS v1.10.0** で導入された同期エンジンについて説明します。エンジンの動作の仕組みについては、まず[同期エンジンの仕組み](/reference/sync-engine)をご覧ください。
:::

WCPOSのストアの多くは共有PHPホスティング上で動作しています。PHPワーカーはわずかで、RESTリクエストのたびにWordPressのフルブートストラップが走り、セキュリティプラグインがバーストをレート制限します。クライアントが無料だとみなしているリクエストは、ストアフロントの表示を遅くし、レート制限に引っかかり、キャッシャー自身の通信と競合します。しかもその影響は、稼働しているレジとブラウザータブの数だけ倍増します。

v1.10.0の同期エンジンは、これを後付けの課題ではなく設計上の制約として扱います。**販売者のホスティングを守ることは、同期エンジンの仕事の一部です。** このページでは、エンジンが従うルールと、その裏付けとなる測定結果を説明します。

## 4つの基本ルール {#the-four-rules}

エンジンがスケジュールに従って実行する同期処理は、次の4つの不変条件に従います。

1. **コストはカタログの規模ではなく、変更量に応じて増えます。** 大量のデータを取得する前に、必ず低コストのダイジェストまたは早期終了できるチェックを行います。変更のない商品50,000件の店舗を同期状態に保つコストは、変更のない商品500件の店舗とほぼ同じです。
2. **無制限のリクエスト展開はありません。**各バックグラウンドレーンは1回の実行あたりのリクエスト上限を定め、自動テストで強制されます。大規模な処理は、再開可能なカーソルを使った上限付きバッチで実行します。これにより、一度に集中させず、スケジュールに分散して処理します。
3. **メンテナンスがキャッシャーの邪魔をすることはありません。** レジが販売できる状態にするためのリクエストが先に実行され、整合性の監査やバックグラウンドの事前読み込みは、その後のアイドル時間に実行されます。
4. **負荷がかかると、まずメンテナンスが後退します。** サーバーが不調のシグナルを出すと、エンジンはキャッシャーに関わる処理に手を付ける前に、自身のバックグラウンド処理を減速させます。

## 同期がサーバーにかけるコスト {#request-budgets}

定常状態のコストは、**ストアヘルス → パフォーマンス** でデバイスごとに選択する**同期プリセット**によって決まります。

| プリセット | 確認間隔 | 1リクエストあたりのレコード数 | 1日あたりの標準確認回数 |
| --- | --- | --- | --- |
| エコ | 5分 | 25 | 288 |
| バランス（既定） | 60秒 | 50 | 1,440 |
| リアルタイム | 10秒 | 75 | 8,640 |

どちらのダイヤルも重要ですが、共有ホスティングで実際にコストになるのはたいていページの重さです。レコード数の多いページはサーバーの処理時間を実際に消費し、間隔はそれを掛け算するだけです。最大値である100件のページを使うプリセットはありません。これはカスタムのスライダー（間隔5秒〜5分、レコード数10〜100）でのみ設定できます。

プリセットに加えて、次の仕組みがあります。

- **アイドル時の確認は低コストです。**エンジンは条件付きリクエストを送信するため、変更がない場合は本文のない`304 Not Modified`が1つ返されます。リクエスト数は1つのままですが、ペイロードはなく、サーバーの処理も最小限です。
- **チェックには±20％のジッターがかかります。** そのため、多数のレジがバーストとして同期することなく、リクエストを分散します。
- **アイドル状態のレジは減衰します。** 10分間操作がないと間隔が長くなり、バーコードスキャンを含むあらゆる操作で即座に元に戻ります。
- **バックグラウンドの保守処理には上限があります。**ドリフトがない場合、整合性チェックにかかるコストは安価な集計ページ数ページまでで、詳細データの取得は**ゼロ**です。サーバーと一致すると確認できたバケットは完全にスキップされます。ドリフトが見つかった場合も、詳細確認は**1回の実行につき2回まで**に制限され、集中して実行するのではなく、保存済みカーソルから再開します。削除の完全監査は**1回の実行につき11リクエスト**、ダイジェストの初期作成は1回の実行につき5チャンクに制限されます。これらの上限はコードで宣言され、CIで検証されます。

:::note アプリ内の「1日あたりのリクエスト数」は概算です
ストアヘルスでは、設定された間隔から*1日あたり約N件のリクエスト*を推定します。これは標準的な確認頻度であり、上限や予測値ではありません。±20%のジッターにより実際の件数は増減し、`304`もリクエストとして数えられます。アイドル時の減衰によって件数が減るのは、60秒の下限より速いプリセットのみです。デフォルトのバランス型プリセットがさらに遅くなることはありません。
:::

## サーバーが苦しいときのバックオフ {#server-pressure}

エンジンが受け取るすべてのレスポンスは、ストアごとの負荷モニターに送られます。モニターは次の状況に反応します。

- HTTP `429`（即座に反応）
- `5xx`エラーまたは通信障害の繰り返し（1分間に3回）、
- 継続的な遅さ（応答時間の中央値が2秒超）
- `Retry-After` ヘッダー（次回のチェックの下限として厳密に適用されます）

いずれかの条件に達すると、エンジンは**変更確認の間隔を段階的に2倍に延長**し、保守レーンの実行をすべてスキップします。レジ係が行うリクエスト（検索、バーコード照会、チェックアウト）はスロットリングされません。目的は後回しにできる負荷を減らすことであり、販売を遅らせることではありません。

回復の動作は意図的に非対称です。バックオフは即時に行われますが、間隔が短くなるのは**正常な応答が10回連続した後**のみです。不安定なサーバーの確認頻度が速い状態と遅い状態の間で頻繁に切り替わることを防ぎます。また、店舗管理者がより高速なプリセットを選んでも、負荷状態は維持されます。この保護機能は設定されたすべての段階で働き、無効にはできません。

## デバイス側の応答性を保つ {#device-responsiveness}

パフォーマンスのもう半分はレジ自体です。バックグラウンドの同期がUIをカクつかせてはいけません。

- **監査処理はイベントループに制御を返します。** 整合性監査では作業を分割し、チャンクごとに処理を中断することで、連続実行時間を約**30 ms**に抑えます。これは人が遅延を感じる約100 msのしきい値を下回ります。ローカル商品10,000件で監査全体の計算時間は約**68 ms**（17回以上の中断に分散）、商品50,000件でも300 ms未満です。
- **負荷がかかっていても最初の結果はすばやく表示されます。**一括適用や完全監査が同時に実行されていても、最初の結果が表示されるまでの時間に関する契約はCIで固定されています。ベンチマーク環境で、一般的なカタログ規模なら1桁ミリ秒です。
- **画面に表示されるページだけがアプリに渡されます。**フィルター、並べ替え、ページネーションなどのクエリ処理はストレージ層内で実行されるため、画面の更新で移動するのは10行であり、10,000行ではありません。

これらの数値は、エンジンの固定パフォーマンス契約テストスイートから得られたものです。CIで分離して実行し、予算は定常状態での実測値のおよそ10倍に設定されています。低速な実行環境で失敗させるのではなく、桁違いの性能劣化を検出する設計です。

## 実際のストアでの検証 {#live-verification}

サーバーへの配慮のルールは、ユニットテストだけで確認しているわけではありません。実際のWordPressストアに対するエンドツーエンドのライブチェックにより、実際のホスティングで最も重要な不変条件を検証しています。

- ストアを開いたとき、商品カタログが描画されるまでのメンテナンスリクエスト（整合性やダイジェストの通信）は**ゼロ**であること。
- 起動後の待機期間を経た後は、安価な集計ページを数ページ取得し、詳細確認は最大2回までです。

このシナリオは、実際に発生したリグレッションから作られました。開発中の初期ビルドでは、監査がストアを開くたびにデバイスごとに約41件のリクエスト（1.2MB）を発行していました。これを置き換えたダイジェストによるゲート方式の設計では、ずれのない監査は集計ページだけで済み、それ以外は発生しません。この種のバグは現在、レビューの注意深さではなく、CIで宣言された上限によって防がれています。

## 主張しないこと {#honest-limits}

裏付けとなる数値がまだ揃っていないため、このページでは意図的に述べていないことがいくつかあります。

- **「初回同期はX分かかる」というエンドツーエンドの数値はありません。** 初回ダウンロード時間は、主にサーバーの応答時間とカタログの規模によって決まります。デバイス側でレコードを適用するコストは小さく、商品10,000件の一括適用に必要な計算時間は10 ms未満です。大部分を占めるのは通信とサーバーの処理です。
- **「v1.9よりX%高速」という主張はありません。** アーキテクチャが大きく異なるため、単一の比較数値では有益な情報より誤解を招くおそれがあります。構造上の違いは[v1.10.0での変更点](/reference/sync-engine#what-changed-in-v1100)で説明しています。
- 上記のベンチマーク数値は、エンジンのテスト環境（インメモリストレージ、分離された実行環境）での値です。実際のデバイスや店舗によって異なるため、**ストアヘルス → パフォーマンス**では予測値ではなく、レジで過去24時間に計測されたリクエスト数と通常の応答時間を表示します。応答サイズが宣言されていない場合はデータ量に0として加算されるため、データ量の数値は下限値です。

サーバー側のチューニング（ホスティング要件、HPOS、キャッシュ、応答が遅い場合の診断）については、[サーバーのパフォーマンス](/support/performance/server)をご覧ください。
