:::info v1.10.0の新機能
このページでは、**WCPOS v1.10.0** で導入された同期エンジンについて説明します。エンジンの動作の仕組みについては、まず[同期エンジンの仕組み](/1.x/reference/sync-engine)をご覧ください。
:::

WCPOSを利用する店舗の多くは、共有PHPホスティング上で運用されています。PHPワーカーは少数で、RESTリクエストのたびにWordPressの起動処理がすべて実行され、リクエストが集中するとセキュリティプラグインがレート制限をかけます。クライアント側ではコストがかからないように見えるリクエストも、オンラインショップの表示を遅くし、レート制限を作動させ、レジ係自身の通信と競合します。その影響は、稼働するレジとブラウザータブの数に比例して増えます。

v1.10.0の同期エンジンは、この問題を後から対処する課題ではなく、設計上の制約として扱います。**販売者のホスティング環境を守ることも、同期エンジンの役割です。** このページでは、エンジンが従うルールと、その裏付けとなる測定結果を説明します。

## 4つの基本ルール {#the-four-rules}

エンジンがスケジュールに沿って行うすべての同期処理は、次の4つの不変条件に従います。

1. **コストはカタログの規模ではなく、変更量に比例します。** 大量のデータを取得する前に、必ず低コストのダイジェストや早期終了可能なチェックを行います。商品が50,000件ある店舗でも変更がなければ、同期状態を保つコストは、変更のない商品500件の店舗とほぼ同じです。
2. **無制限にリクエストを発行しません。** すべてのバックグラウンドレーンが1回の実行あたりのリクエスト上限を宣言し、自動テストでその遵守を確認します。大規模な処理は、再開可能なカーソルを使った上限付きのバッチで実行します。全件走査も一度に集中させず、スケジュール全体に分散します。
3. **メンテナンスがレジ係の操作を妨げることはありません。** レジを販売可能にするリクエストを先に実行し、整合性監査やバックグラウンドの事前読み込みは、その後のアイドル時間に行います。
4. **負荷がかかると、まずメンテナンスを減速します。** サーバーが不調の兆候を示すと、エンジンはレジ係に関わる処理より先に、自身のバックグラウンド処理の頻度を落とします。

## 同期がサーバーにかけるコスト {#request-budgets}

定常状態のコストは、**店舗の健全性 → パフォーマンス**でデバイスごとに選択する**同期プリセット**によって決まります。

| プリセット | チェック間隔 | リクエストあたりのレコード数 | 日次の公称チェック回数 |
| --- | --- | --- | --- |
| エコ | 5分 | 25 | 288 |
| バランス（デフォルト） | 60秒 | 50 | 1,440 |
| リアルタイム | 10秒 | 75 | 8,640 |

どちらの調整項目も重要ですが、共有ホスティングで実際の負荷を左右するのは、通常ページあたりの処理量です。レコード数の多いページはサーバーの処理時間を消費し、それにチェック頻度が掛け合わされます。最大の100件をページあたりに取得するプリセットはありません。この値は、カスタムのスライダー（間隔5秒〜5分、レコード数10〜100件）でのみ設定できます。

プリセットに加えて、次の仕組みがあります。

- **変更がないときのチェックは低コストです。** エンジンは条件付きリクエストを送るため、変更がなければ本文のない `304 Not Modified` が1つ返ります。リクエストは発生しますが、ペイロードはなく、サーバーの処理も最小限です。
- **チェック間隔には±20%のジッターを加えます**。多数のレジが同時にリクエストを集中させず、送信タイミングを分散します。
- **アイドル状態のレジはチェック頻度を下げます**。10分間操作がないと間隔を延ばし、バーコードスキャンを含む何らかの操作があれば即座に元に戻します。
- **バックグラウンドのメンテナンスには上限があります。** 差異のない整合性チェックでは、最大でも低コストの集計ページを数ページ取得するだけで、詳細データの取得は**ゼロ**です。サーバーと一致することが確認できたバケットは、そのままスキップします。差異が見つかった場合も、詳細調査は**1回の実行につき2回まで**に制限し、一度に集中させず、永続化されたカーソルから再開します。削除監査全体は**1回の実行につき11リクエスト**、ダイジェストの初期化は1回の実行につき5チャンクが上限です。これらの上限はコードで宣言され、CIで遵守を確認しています。

:::note アプリ内の「1日あたりのリクエスト数」は公称値です
店舗の健全性では、設定された間隔から*1日あたり約N件のリクエスト*という目安を算出します。上限や予測値ではなく、公称のチェック頻度として捉えてください。±20%のジッターで実際の回数は増減し、`304` もリクエストとして数えます。アイドル時の減衰で回数が減るのは、間隔の下限である60秒より速いプリセットだけです。デフォルトの「バランス」プリセットがさらに遅くなることはありません。
:::

## サーバーの負荷が高いときのバックオフ {#server-pressure}

エンジンが受け取るすべてのレスポンスは、店舗ごとの負荷モニターに渡されます。モニターは次の状況に反応します。

- HTTP `429`（即座に反応）
- `5xx` エラーや通信失敗の繰り返し（直近1分間に3回）
- 応答の遅さが継続（応答時間の中央値が2秒を超える）
- `Retry-After` ヘッダー（次のチェックまでの待機時間の厳密な下限となります）

いずれかの条件に該当すると、エンジンは段階的に**変更チェックの間隔を2倍に延ばし**、メンテナンスレーンの実行を完全にスキップします。レジ係の操作に伴う検索、バーコード検索、チェックアウトのリクエストには制限をかけません。販売を遅らせるのではなく、後回しにできる負荷を減らすためです。

復旧時の動作は意図的に非対称にしています。バックオフは即時に行いますが、**正常なレスポンスが10回連続する**まで、間隔を段階的に短縮しません。不安定なサーバーでチェック頻度が頻繁に上下するのを防ぐためです。販売者がより高速なプリセットを選んでも、負荷状態は維持されます。この保護機能はどの設定段階でも働き、設定で無効にすることはできません。

## デバイス側の応答性を保つ {#device-responsiveness}

パフォーマンスのもう一つの側面は、レジ自体の動作です。バックグラウンド同期によってUIの動きがカクついてはいけません。

- **監査処理はイベントループに制御を返します。** 整合性監査は処理をチャンクに分け、その合間に制御を返すことで、中断のない最長実行時間を約**30 ms**に抑えます。人が遅延を感じる約100 msのしきい値を下回る値です。ローカルの商品10,000件での測定では、全件監査の計算時間は約**68 ms**で、17回以上にわたって制御を返しながら実行します。商品50,000件でも300 ms未満です。
- **負荷がかかっていても、最初の結果をすばやく返します。** 一括適用や全件監査が同時に走っている場合も、最初の結果を返すまでの時間要件をCIで固定しています。ベンチマーク環境では、一般的なカタログ規模で1桁のミリ秒に収まります。
- **表示中のページだけがアプリに渡されます。** フィルター、並べ替え、ページネーションなどのクエリ処理はストレージ層内で実行されます。そのため、画面更新で渡すのは1万行ではなく10行です。

これらの数値は、エンジンの固定された性能要件を検証するテストスイートから得られたものです。CIの分離された環境で実行し、実測した定常状態より約1桁大きい許容値を設定しています。遅い実行環境で失敗させるためではなく、桁違いの性能劣化を検出するための設計です。

## 実際の店舗での検証 {#live-verification}

サーバーへの配慮に関するルールは、ユニットテストだけで確認しているわけではありません。実際のWordPress店舗に対するエンドツーエンドの検証で、実際のホスティング環境にとって特に重要な次の不変条件を確認しています。

- 店舗を開いた際、商品カタログが描画されるまでのメンテナンスリクエスト（整合性やダイジェスト関連の通信）は**ゼロ**です。
- 起動後の待機時間が過ぎても、取得するのは最大で低コストの集計ページ数ページと、2回までの詳細調査です。

このシナリオは、実際に起きた性能劣化を基に作られました。以前の開発ビルドでは、店舗を開くたびに、監査がデバイスごとに約41件のリクエスト（1.2 MB）を発行していました。代わりに導入した、ダイジェストで詳細取得の要否を判断する設計では、差異のない監査は集計ページの取得だけで済みます。この種のバグは現在、レビュー時の注意だけに頼らず、CIで宣言した上限で防いでいます。

## 主張しないこと {#honest-limits}

裏付けとなる数値がまだないため、このページでは意図的に述べていないことがあります。

- **「初回同期にX分かかる」という全工程の所要時間は示していません。** 初回ダウンロード時間は、主にサーバーの応答時間とカタログの規模によって決まります。デバイス側でレコードを適用するコストは小さく、商品10,000件の一括適用の計算時間は10 ms未満でした。時間の大部分を占めるのは通信とサーバー処理です。
- **「v1.9よりX%高速」とは主張しません。** アーキテクチャが大きく異なるため、単一の比較数値では、役立つ情報を示すより誤解を招くおそれがあります。構造上の違いは、[v1.10.0での変更点](/1.x/reference/sync-engine#what-changed-in-v1100)で説明しています。
- 上記のベンチマーク値は、エンジンのテスト環境（メモリ内ストレージ、分離された実行環境）で測定したものです。実際のデバイスや店舗では結果が異なります。そのため、**店舗の健全性 → パフォーマンス**には、予測値ではなく、過去24時間にそのレジで実測したリクエスト数と代表的な応答時間を表示します。サイズが宣言されていないレスポンスはゼロとして集計されるため、データ量の表示値は下限値です。

ホスティング要件、HPOS、キャッシュ、応答の遅さの診断など、サーバー側の調整については、[サーバーのパフォーマンス](/1.x/support/performance/server)を参照してください。
