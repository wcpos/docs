店舗からレジへの応答が遅いと、会計に時間がかかります。販売時には店舗の応答を2回待ちます。**チェックアウト**を押すと注文が店舗に保存され、**受け取り**を押すと店舗に支払いが記録されてからレシートが表示されます。このページでは、レジで待ち時間が発生する場面、店舗の応答時間の測定方法、変更すべき点を説明します。

:::note レジ係の方へ：測定して担当者に引き継いでください
修正はウェブサイト側で行い、主に WP Admin を使用します。ウェブサイトの管理を担当していない場合は、[テスト販売の所要時間を測定](#time-a-sale)し、このページへのリンクと一緒に測定結果を管理担当者に送ってください。
:::

## テスト販売の所要時間を測定する {#time-a-sale}

変更の効果を確認するため、各変更の前後でテスト販売の所要時間を測定してください。それぞれの測定値は、レジが店舗の応答を待つ時間です。

1. **チェックアウト**を押してから、**受け取り**の表示が**注文を保存中…** でなくなるまでの時間を測定します。
2. 支払いを行い、支払い方法に応じて待ち時間を測定します。
   - **現金、カード、その他レジで記録する支払い** — **受け取り**を押してからレシートが表示されるまで。
   - **カードリーダー** — タイルをタップしてから**端末で処理中**になるまでと、**承認済み**になってからレシートが表示されるまで。お客様がリーダーを操作する時間は除いてください。
   - **レガシータブ** — タブを開いてから**支払いを処理**を押せるようになるまで。
3. [店舗の状態 → パフォーマンス](#store-health)の**標準応答時間**を記録します。

使用する支払い方法ごとに手順2を繰り返し、テストの間に変更する項目は1つずつにしてください。[レジで待ち時間が発生する場面](#where-it-waits)では、各測定値が何を表すかを説明しています。実際の販売に使う端末と接続環境で測定してください。端末やネットワークが違うと、所要時間も変わることがあります。

## レジが店舗の応答を待つ場面 {#where-it-waits}

**チェックアウト** — 注文が店舗に保存されます。会計画面はすぐに開きますが、店舗から応答があるまでテンキーは反応せず、**受け取り**には**注文を保存中…** と表示されます。4秒経つと店舗が応答していないというメッセージが表示されます。[対処方法](#store-not-answering)をご覧ください。

現金、カード、その他レジで記録する支払いの**受け取り** — 店舗に支払いが記録されてからレシートが表示されます。店舗から応答がない場合、レジは1秒、3秒、9秒の間隔で再問い合わせします。それでも応答がない場合は、[対処方法](#payment-not-answered)をご覧ください。

**カードリーダーのタイル** — まず店舗側で決済が作成されます。次にタイルが**端末で処理中**の段階になり、**端末でお客様の操作を待っています**と表示されます。このレジに直接接続したリーダーでは、**リーダーにカードをかざしてください**と表示されます。待機中にレジから店舗への接続が失敗し続けると、タイルにはそのメッセージが表示されたままとなり、**詳細**ログに**接続が不安定です。再試行しています**が追加されます。リーダーが承認すると、店舗で支払いを確認する間はタイルに**承認済み**と表示され、その後レシートが表示されます。[支払いの受け付け](../../pos/checkout/taking-a-payment.mdx#card-reader)をご覧ください。

**レガシータブ** — 店舗から決済ページが送信されます。読み込み中の仮表示が現れ、ページの読み込みが完了するまで**支払いを処理**はグレー表示のままです。読み込まれない場合は、[対処方法](#payment-form-didnt-load)をご覧ください。[レガシータブ](../../pos/checkout/legacy-tab.mdx)もご覧ください。

どの待ち時間も店舗へのリクエストに伴うため、店舗の応答が遅いと、どの販売にも時間がかかります。オフラインの場合、レジで記録する支払いでは待ち時間が発生しません。販売データはこの端末に保存され、店舗との接続が回復したら送信されます。[オフラインモード](../../getting-started/offline.mdx)をご覧ください。

## 店舗の応答を測定する {#measure}

テスト販売では、1件の販売の所要時間を測定します。**店舗の状態**では、店舗がこのレジに1日を通してどのように応答したかを確認できます。

### 店舗の状態 → パフォーマンス {#store-health}

**店舗の状態 → パフォーマンス**には、過去24時間に店舗がこのレジへどれくらいの速さで応答したかが表示されます。

<JourneyShot manifest={manifest} device="tablet" step={1} offsets={[[50, 0], [100, 0], [375, 0], [571, -75], [181, -22], [141, -20], [456, 0]]} alt="店舗の状態のパフォーマンスタブ：標準応答時間を含むステータス行、1時間ごとの稼働状況の帯、エコ・バランス・リアルタイムのカード、2つのスライダー">

1. **店舗の状態** — メニューの下部付近にある脈拍のアイコンです。
2. **パフォーマンス** — このタブです。
3. **ステータス行** — このレジが過去24時間に送信したリクエストと、**標準応答時間**が表示されます。標準応答時間は、それらすべてのリクエストに店舗が応答するまでにかかった時間の平均です。[テスト販売](#time-a-sale)の所要時間と比較してください。
4. **エンジンの稼働状況** — 1時間につき1つのセルが表示されます。黄色は、その時間帯に店舗へのリクエストが少なくとも1回失敗したことを示します。
5. **バランス** — このレジが店舗の変更を確認する頻度です。共有ホスティングや低価格のホスティングでは、**エコ**にすると問い合わせの頻度が下がり、店舗が販売を処理する余力を確保できます。[同期プリセット](../store-health.mdx#sync-presets)をご覧ください。
6. **変更を確認** — 同じ設定を5秒から5分の範囲で調整するスライダーです。
7. **現在** — この設定で発生する1時間あたりのリクエスト数の目安です。

</JourneyShot>

さらに下にある**サーバーの推移**には、サーバー負荷と POS のリクエスト数が並んでグラフ表示されます。起動したばかりのレジでは、両方のグラフに*データがまだ不足しています*と表示され、稼働に伴ってデータが追加されます。

<details>
<summary>サーバーのグラフの見方</summary>

<JourneyShot manifest={manifest} device="tablet" step={2} offsets={[[456, 0], [571, -222], [560, 0], [101, -84], [110, -84]]} alt="パフォーマンスタブの下半分：ペースの行と、起動直後のレジのためまだ空のサーバー負荷および POS リクエストのグラフ">

1. **現在** — この設定で発生する1時間あたりのリクエスト数です。
2. **サーバーの推移** — このセクションの見出しです。
3. **ペース** — **通常のペース**、またはサーバーの応答が遅い、タイムアウトした、エラーが返された場合は**頻度を抑制中**と表示されます。[サーバーの推移](../store-health.mdx#server-load)をご覧ください。
4. **サーバー負荷** — POS だけでなく、サーバー上で動作するすべての処理による負荷です。右側に最新の値が表示されます。値が高いだけでレジの動作が遅くなるわけではありません。**標準応答時間**と併せて確認し、両方をホスティング事業者に伝えてください。
5. **POS リクエスト** — このレジが1時間ごとに送信したリクエスト数です。

</JourneyShot>

</details>

## 保存と支払いを速くする {#saving}

以下の原因を1つずつ確認し、変更するたびに[テスト販売の所要時間を再測定](#time-a-sale)してください。

### 注文ストレージ {#order-storage}

WooCommerce がまだ注文を WordPress の投稿として保存している場合（従来のストレージ）、店舗の規模が大きくなるにつれて会計時の保存に時間がかかるようになります。使用中のストレージを確認し、HPOS に切り替えてください。[注文ストレージ（HPOS）](./order-storage.mdx)をご覧ください。

### 注文の保存時に動作するプラグイン {#2-plugin-interference-during-order-creation}

注文の保存時や支払い時に独自の処理を行うプラグインがあり、レジはその処理を待ちます。たとえば注文を Xero に送信する会計プラグインがあると、販売のたびに Xero からの応答を待つことになります。ウェブサイトのコピー上でプラグインを1つずつ無効化すると、原因を特定できます。

<details>
<summary>原因となるプラグインを特定する手順</summary>

注文ごとに処理を行うことが多いプラグイン：

- 会計・簿記（Xero、QuickBooks）
- 新規注文をきっかけに動作するメールマーケティングツール
- 在庫管理システム
- 送料計算ツール
- 分析・トラッキング

原因を特定するには：

1. [ステージングサイト](../troubleshooting/plugin-conflicts.mdx#before-you-start-use-a-staging-site)で、WooCommerce と WCPOS 以外のすべてのプラグインを無効化します。
2. [テスト販売の所要時間を測定](#time-a-sale)します。
3. 大幅に速くなった場合は、プラグインを1つずつ有効に戻し、そのたびに販売の所要時間を測定して、再び遅くなるものを探します。
4. そのプラグインの開発者に、処理をバックグラウンドで実行できないか確認します。

詳しい手順は[プラグインの競合](../troubleshooting/plugin-conflicts.mdx#step-2-the-plugin-elimination-method)をご覧ください。

</details>

### ホスティング環境 {#hosting}

会計の所要時間だけでなく**標準応答時間**も遅い場合、サーバーのリソースが不足している可能性があります。調査してもらえるよう、[テスト販売](#time-a-sale)の所要時間と**サーバー負荷**の値をホスティング事業者に伝えてください。推奨仕様は[サーバーのパフォーマンス](./server.mdx)をご覧ください。

<details>
<summary>ホスティング事業者に確認すること</summary>

- 販売中の CPU とメモリの使用状況
- PHP のメモリ上限と PHP ワーカー数
- 遅いデータベースクエリと、削除可能な古いデータ
- オブジェクトキャッシュ（本格的に利用する前に POS でテストしてください）
- 上位プランへの変更、または共有ホスティングから VPS への移行

</details>

## レガシータブの決済ページを速くする {#legacy-page}

会計時にウェブページを読み込むのは、**レガシー**タブの決済ゲートウェイだけです。これは、お客様がオンラインで注文の代金を支払う WooCommerce のページを簡素化したもので、毎回ウェブサイトから送信されます。テーマのヘッダー、フッター、レイアウトはすでに除かれていますが、テーマやプラグインが各ページに追加するスタイルとスクリプトは引き続き読み込まれ、ページの遅延や不具合の原因になることがあります。読み込む項目の変更はショップマネージャーが行います。レジでページが読み込まれない場合は、[対処方法](#payment-form-didnt-load)をご覧ください。

<JourneyShot manifest={manifest} device="tablet" step={3} offsets={[[28, 34], [28, 34], [337, -273], [-30, 0], [-30, 0]]} alt="会計画面のレガシータブ：店舗から読み込まれた決済ページ。右上に会計設定ボタン、ページの下に支払いを処理ボタンが表示されています">

1. **支払い** — アプリ内の現金、カード、カードリーダーなどのタイルです。ページは読み込みません。
2. **レガシー** — 店舗独自の決済ページ上で動作する決済ゲートウェイです。
3. **会計設定** — このページで読み込むスタイルとスクリプトを選択するフォームを開きます。周囲のページはウェブサイトから送信されたものです。
4. **支払いを処理** — ページの読み込みが完了するまでグレー表示になります。
5. **✕** — 注文を保持したままカートに戻ります。

</JourneyShot>

このページからスタイルとスクリプトを除外するには：

1. ショップマネージャーまたは管理者として POS にサインインします。レジ係はフォームを開けますが、保存はできません。
2. **チェックアウト**を押し、**レガシー**タブを開いて、決済ページの**会計設定**を押します。
3. スタイルまたはスクリプトのチェックを外すと、除外できます。まずクラシックテーマの `classic-theme-styles` など、テーマのスタイルから始め、次に `selectWoo` など決済ゲートウェイに不要なスクリプトを除外します。
4. **送信**を押し、使用するレガシー決済ゲートウェイごとにテスト決済を行います。

<details>
<summary>会計設定フォームの表示内容</summary>

<JourneyShot manifest={manifest} device="tablet" step={4} offsets={[[28, 34], [-28, 0]]} alt="レガシータブの決済ページで開いた会計設定フォーム：上部に wp_head を無効化と wp_footer を無効化があり、その下にスタイルとスクリプトの一覧が左右に並んでいます。常に除外される項目はグレー表示です">

1. **レガシー** — このフォームが属するタブです。
2. **会計設定** — 決済ページ上に表示されるフォームです。ページ内のすべてのスタイルとスクリプトにチェックボックスがあり、読み込まれるものにはチェックが入っています。

</JourneyShot>

フォームは上から順に3つの部分で構成されています。

- **すべてのスタイルとスクリプトを無効化** — **wp_head を無効化**と**wp_footer を無効化**は、決済フォームに必要なものも含め、ページのヘッダーやフッターが読み込むものをすべて除外します。スタイルやスクリプトが原因かどうかをテストする場合にのみ使用してください。
- 左側の**選択したスタイルを無効化** — スタイルごとに1項目あります。テーマのスタイルには、`twentytwentyfive-style` など、そのテーマにちなんだ名前が付いています。
- 右側の**選択したスクリプトを無効化** — スクリプトごとに1項目あります。

末尾に *POS 決済ページでは常に除外* と表示されるグレーの項目は、すでに除外されており、チェックを入れることはできません。

</details>

:::warning 決済ゲートウェイに必要なものは残してください
スクリプトを除外した後で支払い方法が動作しなくなった場合は、再びチェックを入れて**送信**を押してください。
:::

<details>
<summary>WCPOS が自動的に除外するものと開発者向けの選択肢</summary>

決済ページでは、管理バー、WordPress がページのヘッダーに追加するリンク、および以下の WooCommerce のスタイルとスクリプトが常に除外されます。

- スタイル：`admin-bar`、`woocommerce-general`、`woocommerce-inline`、`woocommerce-layout`、`woocommerce-smallscreen`、`woocommerce-blocktheme`、`wp-block-library`
- スクリプト：`admin-bar`、`wc-add-to-cart`
- WooCommerce Stripe が11.1.1より前のバージョンの場合は、`wc-stripe-upe-classic` のスクリプトとスタイル、および `stripelink_styles` も除外されます。

開発者向け：

- フォームの保存には `manage_woocommerce` 権限が必要です。
- フィルター `wcpos_payment_template_dequeue_style_handles` と `wcpos_payment_template_dequeue_script_handles` を使うと、除外リストにハンドルを追加できます。
- テンプレートを `yourtheme/woocommerce-pos/payment.php` にコピーすると、上書きできます。元のファイルはプラグイン内の [templates/payment.php](https://github.com/wcpos/woocommerce-pos/blob/main/templates/payment.php) です。
- 除外できるのは、`wp_enqueue_style` と `wp_enqueue_script` で追加されたスタイルとスクリプトだけです。テーマやプラグインがコードをページに直接出力している場合は除外できません。開発者にエンキューするよう依頼するか、そのプラグインやテーマのフックを使って除外してください（テーマの場合は子テーマで行います）。

</details>

## 問題が発生した場合 {#goes-wrong}

### 店舗が応答しない {#store-not-answering}

*「店舗が応答していません。このまま待つか、カートに戻ってください。」* 店舗での注文の保存に4秒以上かかっています。そのまま待つか、**✕** を押して注文を保持したままカートに戻ってください。頻繁に表示される場合は、[テスト販売の所要時間を測定](#time-a-sale)し、[保存と支払いを速くする](#saving)に挙げた原因を確認してください。

### 直前の支払いに店舗から応答がない {#payment-not-answered}

*「直前の支払いに店舗から応答がありません。もう一度試して確認してください。二重に請求されることはありません。」* **もう一度試す**を押してください。

### 決済フォームが読み込まれなかった {#payment-form-didnt-load}

*「決済フォームが読み込まれませんでした。店舗への接続を確認してから、再試行してください。」* レガシータブは決済ページの読み込みを90秒待ち、再読み込みしてさらに90秒待った後、処理を中止しました。接続を確認し、**再試行**を押してください。毎回ページの読み込みが遅い場合は、[レガシータブの決済ページを速くする](#legacy-page)をご覧ください。

### 会計設定を変更する権限がない {#no-permission}

*「会計設定を変更する権限がありません。」* レジ係として**会計設定**の**送信**を押した場合に表示されます。ショップマネージャーまたは管理者としてサインインしてください。

### それでも遅い場合 {#still-slow}

これらをすべて試しても会計に10秒以上かかり続ける場合や、プラグインが原因と思われても特定できない場合は、[Discord](https://wcpos.com/discord) で相談してください。**店舗の状態 → ログ**の**デバッグ情報をコピー**を押し、[テスト販売](#time-a-sale)の所要時間と試した対処法を添えて貼り付けてください。[ヘルプとトラブルシューティング](../index.mdx)をご覧ください。

:::info WCPOS Pro の場合
現金とカード以外の決済ゲートウェイには [WCPOS Pro](../../getting-started/pro-license.mdx) が必要です。
:::
