各レジ端末は一日を通してWordPressサイトと通信し、変更の確認、売上の送信、レジ係が検索した情報の取得を行います。POSの体感速度はサーバーの応答速度に左右されます。サーバーの処理が追いつかなくなると、各端末が確認の頻度を下げ、回復後は自動で元に戻します。このページでは、その状況を確認する場所、表示の意味、ホスティング環境で見直す項目を説明します。

画面の表示や動作が気になって、このページを開きましたか？

- **サーバーの推移** の下にある [**頻度を抑制中** または **… まで一時停止**](#pace)。販売は続けられます。バックグラウンドの確認だけが遅くなるため、他のレジでの変更が反映されるまで時間がかかることがあります。ほとんど毎日表示される場合は、まず[負荷の軽いプリセットを選んでください](#fix)。
- [**503**、**429**、**414**のいずれかのエラー](#503-errors)が表示される場合。各コードについて、最初に簡単な対処方法を説明しています。ウェブサイトの管理担当者向けの詳細は、その下の折りたたみ部分にあります。
- [すべての端末で検索や販売処理が遅い](#fix)場合。確認頻度の抑制でこれらの処理が遅くなることはないため、まず端末ではなくサーバーを調べてください。ウェブサイトの管理担当者に[ホスティング事業者に伝える情報](#when-to-seek-help)を渡してください。

## サーバーの状態を確認する {#store-health}

メニュー下部の脈拍アイコンから**店舗の健全性**を開き、**パフォーマンス**を選びます。表示される数値は、この端末だけのものです。

<JourneyShot manifest={manifest} device="tablet" step={1} offsets={[[50, 0], [160, 0], [370, 0], [480, 26], [180, 0], [470, 0]]} alt="店舗の健全性のパフォーマンスタブ：過去24時間のリクエスト数、データ量、標準的な応答時間を示すステータス行、時間別の稼働状況、エコ・バランス・リアルタイムのプリセット">

1. **店舗の健全性** — メニュー下部の脈拍アイコンです。
2. **パフォーマンス** — この端末が店舗の変更を確認する頻度と、サーバーの状態を示します。
3. **過去24時間** — **正常**は、この端末が現在オンラインで同期中であることを示します。続いてリクエスト数、データ量、ミリ秒単位の**標準的な応答時間**が表示されます。この例の2347は約2.3秒です。ほとんど毎日2000を超える場合は、[ホスティング事業者に伝える情報](#when-to-seek-help)に含めてください。
4. **エンジンの稼働状況** — 各セルが1時間を表します。オレンジ色は、その時間帯に少なくとも1件のリクエストが失敗したことを示します。セルにマウスポインターを合わせるかタップすると、件数を確認できます。
5. **エコ** — **バランス**、**リアルタイム**と並ぶ3つのプリセットのうち、最も負荷の低い設定です。ほかの端末の売上をすぐに確認する必要がない端末で選んでください。ウェブサイトの管理担当者から指示がない限り、**リアルタイム**は選ばないでください。[同期プリセット](../store-health.mdx#sync-presets)を参照してください。
6. **現在の状況** — 次回の確認予定を示します。1時間あたりのリクエスト数は、設定で指定した定期確認の回数です。頻度を抑制している間は実際の回数が減るため、この例では次回の確認まで約2分となっています。

</JourneyShot>

## 「サーバーの状態の推移」の見方 {#server-load}

同じタブを下にスクロールします。**サーバーの状態の推移**には、端末の確認ペースと過去24時間のグラフが表示されます。

<JourneyShot manifest={manifest} device="tablet" step={2} maxWidth={710} offsets={[[400, -204], [430, 0], [110, -84], [120, -84]]} alt="確認頻度を抑制中の端末の「サーバーの状態の推移」：オレンジ色のペース表示は、サーバーから高負荷が報告されたため確認間隔を2×に延長していることを示し、サーバー負荷のグラフは午前3:00に59.1まで上昇、POSリクエストのグラフは下降しています">

1. **サーバーの状態の推移** — サーバー負荷にはPOSだけでなく、ウェブサイト、バックアップ、同じホスト上のほかのサイトなど、サーバーで実行中のすべての処理が含まれます。
2. **ペース** — この例では、**頻度を抑制中 — 確認間隔を2×に延長：サーバーから高負荷が報告されました**とオレンジ色で表示されています。この端末は毎分ではなく2分ごとに確認し、サーバーが回復すると自動で元に戻ります。[ペース表示の意味](#pace)を参照してください。
3. **サーバー負荷** — 各時間帯にサーバーが報告した負荷の最大値です。タイトルの横の数値は直近の時間帯のものです。数値を自分で判断する必要はありません。サーバーが負荷を「やや高い」または「高い」と報告すると、ペース表示で知らせます。
4. **POSリクエスト** — 各時間帯にこの端末が店舗に送ったすべてのリクエストです。定期確認に加え、変更のダウンロード、売上の送信、検索が含まれます。そのため、設定で指定した1時間あたりのリクエスト数を大きく上回ることがあります。

</JourneyShot>

2つのグラフを合わせて確認してください。POSリクエストに連動して負荷が上下する場合は、端末が負荷の一因になっている可能性があります。負荷だけが上昇する場合は、ウェブサイト、バックアップ、同じホスト上の別のサイトなど、サーバー上の別の処理が動いています。この画像では、深夜を過ぎると両方の線が同時に下がっています。午前2:00以降は、この端末のリクエストが減り続ける一方で負荷が59.1まで上昇しているため、別の処理が動いており、端末は負荷を抑えるために確認頻度を下げています。

いずれの場合も、両方のグラフのスクリーンショットがホスティング事業者の判断に役立ちます。負荷が低いままなのに**標準的な応答時間**が長い場合、サーバーの処理能力が不足しているわけではありません。まず注文ストレージとプラグインを確認してください（[サーバーの負荷が高い状態が続く場合](#fix)の手順2と3）。

異なる2つの時間帯の測定値が揃うまでは、両方のグラフに**データがまだ不足しています — 端末の稼働に伴い推移が表示されます**と表示されます。端末を稼働させたまま、後でもう一度確認してください。

### ペース表示の意味 {#pace}

次のいずれかが表示されます。これはタブ上部の**正常**というステータスとは別のもので、確認頻度を抑制している間もステータスは正常のままの場合があります。

- **通常のペース** — 設定どおりの頻度で確認しています。
- **通常のペース — サーバーからやや高い負荷が報告されています**（または**高い負荷**） — サーバーは処理が混み合っていると報告していますが、端末は設定どおりの頻度で確認しています。負荷の高い応答が一度あっただけでは頻度は下がりません。高負荷が続く場合にも、端末は頻度を抑制します。直近10回の応答の大半が高負荷を報告すると、応答自体が速くても表示は**頻度を抑制中**に変わります（[各理由の意味](#reasons)を参照）。ほとんど毎日表示されるのでなければ、対処は不要です。
- **頻度を抑制中 — 確認間隔をN×に延長：…** — 確認の頻度を下げています。コロンの後に理由が表示されます。下の[各理由の意味](#reasons)を参照してください。
- **…まで一時停止** — サーバーが再試行の時刻を指定したため、端末はその時刻まで待機します。待機中も販売は続けられます。

確認頻度の抑制中や一時停止中は、表示の色が変わります。どちらもサーバーが回復すると自動で解除されます。ほとんど毎日表示される場合は、[サーバーの負荷が高い状態が続く場合](#fix)を参照してください。

:::note 頻度が下がるのはバックグラウンドの確認だけです
頻度が下がるのは、端末が行う定期的な変更確認とバックグラウンドの確認だけです。検索、バーコード検索、販売処理はすぐにサーバーに送信されます。確認頻度の抑制中は、ほかの端末やWooCommerceで行った変更がこの端末に反映されるまでに時間がかかります。
:::

<Accordion>
<AccordionItem question="各理由の意味、確認頻度の下がり方、回復の仕組み">

<Anchor id="reasons" />

- **サーバーがPOSに頻度を下げるよう要求しました** — サーバー、またはその手前にあるファイアウォールが、「リクエストが多すぎます」（**429**）と一度応答しました。
- **サーバーがエラーを返しました**または**サーバーへのリクエストがタイムアウトしました** — 1分以内にサーバーエラー（**5xx**）またはタイムアウトが3回発生しました。理由には、その3回のうち最後のものが表示されます。
- **サーバーの応答が遅くなっていました** — 直近10回の標準的な応答時間（中央値）が2秒を超えました。
- **サーバーから高負荷が報告されました** — 端末が通常のペースで確認している間に、直近10回の応答の大半でサーバーの高負荷が報告されたか、負荷が1以上の状態で、2回連続の測定値がサーバーの通常の負荷の2倍以上になりました。

そのたびに、確認頻度はそれまでの半分になります。ただし、5分に1回より少なくなることはありません。設定した間隔の2倍のほうが長い場合は、そちらが上限になります。**エコ**では10分に1回です。サーバーが独自の一時停止時間を指定した場合（**Retry-After**ヘッダー）、最大15分まで従います。

回復時は、意図的にゆっくり元に戻します。最後に頻度を下げてから少なくとも1分が経過し、正常な応答が10回得られると、待機時間が再び半分になります。負荷の急上昇は例外で、確認頻度を半分に下げ、それ以上は下げずに、2回連続の負荷測定値がサーバーの通常の負荷から上下4分の1以内に戻るまで維持します。端末を再起動すると、設定した頻度に戻ります。

WCPOS自体も短い一時停止を要求します。サイトでプラグインを更新している間は5秒、同期用テーブルをインストールしている間は30秒です。その際、一時的に **…まで一時停止**と表示されることがあります。

この動作を支えるエンジンのルールについては、[同期パフォーマンス](../../reference/sync-performance.mdx#server-pressure)を参照してください。

</AccordionItem>
<AccordionItem question="負荷の数値の算出元">

サーバーは同期の応答ごとに、直近1分間の平均負荷を報告します。これは、実行中またはプロセッサーの空きを待っていたプロセスの平均数です。サーバーのプロセッサーのコア数と比較してください。4コアのサーバーで負荷が4なら処理能力を使い切っている状態ですが、16コアのサーバーなら軽い負荷です。

**やや高い**と**高い**という表示が、この判断を代わりに行います。WCPOSは負荷をコア数で割り、1コアあたり0.9未満なら低い、1.8以下ならやや高い、それを超えると高いと判断します。共有ホスティングでは、自分のサイトだけでなく、そのマシン上のすべてのサイトが数値に含まれます。

PHPが平均負荷を取得できない場合は、グラフの代わりに**サーバーが負荷を報告していません。このページのほかの機能は引き続き利用できます。** と表示されます。Windowsサーバーや、この機能を無効にしているホスティング環境では正常な状態です。端末はエラーや応答時間も監視しているため、負荷を取得できなくてもペース表示は機能します。

</AccordionItem>
</Accordion>

## サーバーの負荷が高い状態が続く場合 {#fix}

この一覧を上から順に進めてください。後の手順ほど費用がかかります。手順1は端末を操作する方なら誰でも行えます。手順2から4は、店舗のオーナー、開発者、ホスティング事業者など、ウェブサイトの管理担当者向けです。

1. **負荷の低いプリセットを選びます。** ほかの端末の売上を数秒以内に確認する必要がない端末では、**店舗の健全性 › パフォーマンス**を開き、**エコ**を選んでください。ウェブサイトの管理担当者から指示がない限り、**リアルタイム**は選ばないでください。プリセットは端末ごとに保存されます。[同期プリセット](../store-health.mdx#sync-presets)を参照してください。
2. 従来の注文ストレージをまだ使用している場合は、**WooCommerceをHPOSに切り替えます**。注文が多い店舗では、これだけで最も大きな改善が見込めます。従来のストレージを使用している間は、WP Adminの**POS → 設定 → レジ**の上部に警告とWooCommerceの設定へのリンクが表示されます。[注文ストレージ（HPOS）](./order-storage.mdx#switch-to-hpos)を参照してください。
3. **すべてのリクエストを遅くしているプラグインを探します。** ステージングサイトでWooCommerceとWCPOSだけを有効にしてテストし、その後プラグインを1つずつ有効に戻してください。[プラグインの競合](../troubleshooting/plugin-conflicts.mdx#step-2-the-plugin-elimination-method)を参照してください。
4. オブジェクトキャッシュ（RedisまたはMemcached）、PHPワーカーとメモリの増強、共有ホスティングからの移行について、**ホスティング事業者に相談します**。[ホスティング事業者に伝える情報](#when-to-seek-help)を参照してください。

## ホスティング事業者に伝える情報 {#when-to-seek-help}

**頻度を抑制中**や **…まで一時停止**がほとんど毎日表示される場合、標準的な応答時間が2秒を超えたままの場合、またはホスティング事業者のログにメモリエラーが記録されている場合は、ホスティング事業者かWordPress開発者に連絡してください。

端末から次の情報を送ってください。

- **店舗の健全性 → パフォーマンス**を開き、**サーバーの状態の推移**までスクロールした画面のスクリーンショット。
- **店舗の健全性 → ログ → デバッグ情報をコピー**（スマートフォン・タブレットアプリでは**デバッグ情報を共有**）から取得したデバッグレポート。WordPress、WooCommerce、WCPOSのバージョンはすでに含まれています。[ログ](../store-health.mdx#logs)を参照してください。

ウェブサイトの管理担当者から、次の情報も追加してください。

- WP Adminの**プラグイン**で確認できる、有効なプラグインの一覧。
- ホスティングアカウントで確認できる、サーバーのコア数、メモリ容量、ストレージの種類。

ここから先は、ウェブサイトの管理担当者向けの内容です。**503**、**429**、**414**のコードについて調べている場合は、[サーバーが返すエラー](#503-errors)で各コードの簡単な対処方法を最初に説明しています。

## サーバーが返すエラー {#503-errors}

### 503 サービスを利用できません {#503}

サーバー、またはその手前にあるシステムがリクエストを処理できませんでした。端末はバックグラウンドの確認間隔を延ばし、自動で再試行します。サイトでWCPOSを更新中、またはテーブルをインストール中に短時間503が発生するのは正常です。端末は5〜30秒待って処理を続けます。繰り返し発生する場合は、ウェブサイトの管理担当者に[ホスティング事業者に伝える情報](#when-to-seek-help)を渡してください。

<Accordion>
<AccordionItem question="ウェブサイトの管理担当者向け：503発生時の確認事項">

サーバーの負荷と空きメモリ、PHPワーカーを使い切っていないか、PHPのメモリ上限が**256 MB**以上かを確認してください。ホスティング事業者のエラーログには、POSからは確認できない情報が記録されています。

</AccordionItem>
</Accordion>

### 429 リクエストが多すぎます {#429}

ホスティング事業者またはファイアウォールが、1つのアドレスからサイトを呼び出せる頻度を制限しています。端末はすぐに確認頻度を下げ、後で再試行します。店舗の同じルーターに接続された複数の端末は1つのアドレスを共有するため、ほかの端末の売上をすぐに確認する必要がない端末では**エコ**を選んでください。繰り返し発生する場合は、ウェブサイトの管理担当者に[ホスティング事業者に伝える情報](#when-to-seek-help)を渡してください。

<Accordion>
<AccordionItem question="ウェブサイトの管理担当者向け：POSに許可するリクエスト数を増やす">

店舗のアドレスから、POSが呼び出すパス`/wp-json/`へのリクエスト数の上限を引き上げるようホスティング事業者に依頼するか、ファイアウォールの設定を変更してください。

</AccordionItem>
</Accordion>

### 414 URIが長すぎます {#http-414-uri-too-long}

会計画面の**レガシー**タブ内の決済ページで表示されます。このページはアドレスにログイン情報を含めて開きますが、サーバーで許可されるアドレスの長さが足りません。ウェブサイトの管理担当者またはホスティング事業者に、上限の引き上げを依頼してください。

<Accordion>
<AccordionItem question="ウェブサイトの管理担当者向け：アドレスの長さの上限を引き上げる">

- **Apache:** `httpd.conf`に`LimitRequestLine 65536`を設定
- **Nginx:** `nginx.conf`に`large_client_header_buffers 4 65536;`を設定

</AccordionItem>
</Accordion>

## WooCommerceを安全に更新する {#woocommerce-version-compatibility}

WooCommerceの更新によって、まれにPOSが正常に動作しなくなることがあります。まず[ステージングサイト](../troubleshooting/plugin-conflicts.mdx#before-you-start-use-a-staging-site)でWooCommerceを更新してください。また、最新の互換性修正が適用されるよう、WCPOSも最新の状態に保ってください。WCPOS 2.0にはWooCommerce 9.0以降が必要です。

更新後にPOSが正常に動作しなくなった場合は、[Discord](https://wcpos.com/discord)でお知らせいただき、ウェブサイトの管理担当者に元のバージョンへ戻すことを相談してください。更新によって店舗のデータベースが変更される場合があるため、担当者はまずその点を確認し、更新前のバックアップを用意する必要があります。

<Accordion>
<AccordionItem question="ウェブサイトの管理担当者向け：WooCommerceを以前のバージョンに戻す">

WordPress.orgのWooCommerceページにある**詳細を表示**リンクから、以前のバージョンの一覧を確認できます。更新によってデータベースが変更された場合は、更新前のバックアップから復元してください。変更されていなければ、それまで使用していたバージョンをインストールします。まずステージング環境で試してください。

</AccordionItem>
</Accordion>

## 注文ストレージ（HPOS） {#woocommerce-high-performance-order-storage-hpos}

WooCommerceの**高パフォーマンス注文ストレージ**は、投稿と同じテーブルではなく、注文専用のテーブルに注文を保存します。注文が多い店舗では、販売データの保存が大幅に速くなります。店舗で使用しているストレージを確認し、WooCommerce標準のツールで切り替えてください：[注文ストレージ（HPOS）](./order-storage.mdx)。WooCommerceのガイドは[高パフォーマンス注文ストレージ](https://woocommerce.com/document/high-performance-order-storage/)です。

<Accordion>
<AccordionItem question="ホスティング事業者に相談するPHPとWordPressの設定">

これらは設定の目安であり、必須ではありません。サーバーで許可される設定は、ホスティング事業者に確認してください。

```ini
memory_limit = 512M
max_execution_time = 300
max_input_vars = 3000
```

`wp-config.php`で保存する投稿リビジョン数を減らすと、データベースのサイズを抑えられます。

```php
define('WP_POST_REVISIONS', 3);
```

すべてのリクエストを遅くしがちなプラグインには、商品保存時に動作する負荷の高いSEOプラグイン、複雑な在庫管理システム、リアルタイムの分析・追跡機能、WooCommerceのフックに接続する独自コードなどがあります。[プラグインの競合](../troubleshooting/plugin-conflicts.mdx)を参考に、原因を特定してください。

</AccordionItem>
</Accordion>

## ホスティング環境ごとの注意点 {#hosting-specific-notes}

ホスティング事業者やCDNによっては、POSがサイトのREST APIにアクセスするために設定変更が必要です。利用している項目を開いてください。

<Accordion>
<AccordionItem question="GoDaddy">

ウェブサイトのファイアウォールが`/wp-json/`をブロックし、_「'undefined'を受信しました」_などのエラーが発生します。**ウェブサイトセキュリティ › ファイアウォール › 設定 › アクセス制御 › URLパスを許可**に`/wp-json/`を追加してください。

</AccordionItem>
<AccordionItem question="WP Engine">

REST APIを有効にする必要があります。有効にしたうえで、必要に応じてWP EngineのファイアウォールでREST APIのパスを許可してください。

</AccordionItem>
<AccordionItem question="Cloudflare">

ボットファイトモード、攻撃を受けているモード、WAFのチャレンジがRESTリクエストをブロックすることがあります。また、キャッシュから古い応答が返されることもあります。[Cloudflareガイド](../troubleshooting/cloudflare.mdx)に従い、`/wp-json/`に対するWAFの**スキップ**ルールと**キャッシュをバイパス**ルールを追加してください。

</AccordionItem>
<AccordionItem question="WordPress.com">

大きなカタログの商品が9件または10件しか表示されないなど、商品の読み込みに失敗することがあります。セルフホスト型のWordPressを使用してください。

</AccordionItem>
<AccordionItem question="共有ホスティング">

複数の端末を動かすにはPHPワーカー数とメモリ容量が不足しています。VPSまたはマネージドWordPressホスティングに移行してください。

</AccordionItem>
</Accordion>

Wordfenceなどのセキュリティプラグインも、同様にREST APIをブロックすることがあります。[プラグインの競合](../troubleshooting/plugin-conflicts.mdx)を参照してください。
