覚えている単語から数文字ずつ、好きな順序で入力してみてください。入力した語句をすべて含むものだけが一覧に残ります。このページでは、各検索ボックスの検索対象、店舗側と端末側の検索の違い、開発者向けの独自フィールドの追加方法を説明します。見つからない場合は、[検索結果がない場合](#goes-wrong)を参照してください。

各検索ボックスの検索対象：[商品](#products) · [注文](#orders) · [顧客](#customers) · [クーポン](#coupons) · [カテゴリー、タグ、ブランド](#category-tag-brand) · [電話番号](#phone-numbers)

## 入力した語句の一致条件 {#how-a-search-is-matched}

- **すべての語句が一致する必要があります。** 検索文字列はスペースで語句に分割されます。各語句が、[以下に示す](#what-each-screen-searches)商品、注文、顧客の詳細のどこかに含まれている必要があります。語句の順序は問いません。`shirt lovelace` で検索すると、シャツを含む Ada Lovelace の注文が見つかります。
- **単語のどの部分でも一致します。** `saippua` で `Kuorintasaippua` が、`jo` で `Bjorn` が見つかります。ログ画面以外では、最小文字数の制限はありません。
- **大文字・小文字やアクセント記号を区別しません。** `creme` で `Crème` が見つかります。
- **単語内の記号はそのまま扱います。** `0.4`、`K-2`、`3/4`、メールアドレス全体は、それぞれ一つの語句として扱われ、ピリオドやハイフンでは分割されません。

例：

<JourneyShot manifest={manifest} device="tablet" step={1} offsets={[[170, 0], [0, 0], [-60, 0]]} alt="検索欄に wat aim と入力した商品パネル。Aim Analog Watch のタイルが表示され、その下に商品数 1 が表示されています">

1. **商品を検索** — `wat aim` は二つの語句です。それぞれ商品名の単語の一部で、商品名とは逆の順序で入力されています。
2. **Aim Analog Watch** — 両方の語句を含む唯一の商品です。
3. **… 商品** — 一致する商品の件数です。**在庫あり** が有効な間は、在庫切れの商品は数えられません。[検索と絞り込み](../pos/product-panel/search-filtering.mdx#no-match)を参照してください。

</JourneyShot>

入力を止めると、少しして一覧が更新されます。検索欄を空にすると、すべて再表示されます。店舗側から返される結果も同じルールに従いますが、[いくつか違いがあります](#device-and-store)。

<details>
<summary>例外：ログ検索と単語の前後の記号</summary>

- **ログ。** [ログ](../support/logs.mdx)画面では、三文字未満の語句は検索から除外されます。
- **単語の前後の記号。** 括弧や引用符、注文番号の前の `#`、単語の後のカンマやピリオドは省いてください。端末側はこれらを無視します（`(shirt)` で `shirt` が、`#4120` で注文 4120 が見つかります）が、店舗側は入力どおりに検索するため、`#4120` では注文 4120 が見つかりません。

</details>

## 電話番号 {#phone-numbers}

電話番号は、スペース、括弧、ハイフンを入れず、数字だけで入力してください。保存されている番号の表記にかかわらず、数字同士を比較します。

- `0412` で `(04) 1234 5678` が見つかります。
- `412345` で `+61 412-345-678` が見つかります。
- `0412` では `+61 412 345 678` は **見つかりません**。

国番号や先頭の `0` は変換されません。`0412` と `+61 412` は異なる数字の並びです。

## 各検索ボックスの検索対象 {#what-each-screen-searches}

### 商品 {#products}

商品パネルと商品画面：

- 名前、SKU、バーコード。
- バリエーションのある商品は、いずれかの選択肢の SKU またはバーコードが一致した場合にも表示されます。

バーコードには、店舗がバーコード用に使用しているフィールドが使われます。[バーコードフィールド](../settings/wp-admin/general.mdx#barcode-field)を参照してください。バーコードの **スキャン** は検索とは異なり、コードの完全一致で商品を特定してカートに追加します。[バーコードスキャン](../pos/product-panel/barcode-scanning.mdx)を参照してください。

### 注文 {#orders}

注文画面：

- **注文：** 注文番号。
- **請求先：** 名、姓、会社、メールアドレス、電話番号。
- **配送先：** 名、姓、会社、電話番号。
- **商品：** 各明細行の名前と SKU。

明細行は **販売時の名前** で照合されるため、商品名が変わった後も注文を検索できます。配送先の名前を検索するのは、配送や店舗受け取りの注文を受取人の名前で探すことが多く、受取人と支払者が必ずしも同じではないためです。

### 顧客 {#customers}

顧客画面とカートの顧客検索：

- **顧客：** 名、姓、メールアドレス、ユーザー名、税 ID。
- **請求先：** 名、姓、会社、メールアドレス、電話番号。
- **配送先：** 名、姓、会社、電話番号。

### クーポン {#coupons}

クーポン画面とカートのクーポン検索：

- コードと説明。

### カテゴリー、タグ、ブランド {#category-tag-brand}

カテゴリー、タグ、ブランドのフィルター一覧：

- 名前。

## 端末側と店舗側の検索 {#device-and-store}

検索では、まず端末に保存済みのデータを調べるため、結果がすぐに表示されます。**商品**、**顧客**、**注文** は店舗側にも問い合わせるため、この端末にまだダウンロードされていないレコードも見つかります。**クーポン** と **カテゴリー**、**タグ**、**ブランド** の一覧は端末内だけを検索します。オフラインでは、どの検索でも端末にあるデータだけが見つかります。

店舗側でも同じフィールドを同じルールで照合しますが、いくつか違いがあります。

<details>
<summary>注文番号、顧客名、商品 SKU、長い検索文字列での違い</summary>

- **注文番号。** 店舗側は番号が完全に一致する注文を検索し、連番注文番号プラグインが注文に割り当てた番号にも一致します。端末側は、入力した数字を含む番号も検索します。端末では `412` で注文 4120 が見つかります。
- **顧客の表示名。** 店舗側は WordPress が表示する顧客名も照合します。
- **明細行の SKU。** 店舗側は商品の現在の SKU を照合します。端末側は、その注文を最後にダウンロードした時点の明細行の SKU を照合します。
- **長い検索文字列。** 店舗側は最大十個の語句を一つずつ照合します。検索は少数の語句に絞ってください。

</details>

## 検索結果がない場合 {#goes-wrong}

- **何も表示されない** — 各語句に入力ミスがないか確認してください。一つでも一致しない語句があると、すべての結果が表示されなくなります。語句を一つ減らして、もう一度試してください。
- **電話番号が見つからない** — 保存時と同じ数字だけを入力してください。国番号なしで保存した番号なら国番号を省き、国番号付きで保存した番号なら国番号も入力します。
- **オフラインになっている** — 端末に保存済みのレコードだけが見つかります。この端末にどれだけのデータがあるかは、[店舗の状態 → データベース](../support/store-health.mdx#coverage)を参照してください。
- **[ログ](../support/logs.mdx)画面の場合** — 三文字未満の語句は検索から除外されます。
- **商品一覧の件数が少ないまま** — フィルターが有効なままです。[検索と絞り込み](../pos/product-panel/search-filtering.mdx#no-match)を参照してください。

## 開発者向け：検索対象フィールドの変更 {#developers}

<details>
<summary>設定がない理由と、独自フィールドの追加方法</summary>

### 検索フィールドの設定がない理由 {#why-there-is-no-setting}

上記のフィールドは POS と WP Admin の両方で固定されています。レコードのフィールドは入力した語句を含む場合だけ一致するため、検索するフィールドを増やしても誤った結果は返されません。また、対象を固定することで、端末側と店舗側が同じフィールドを検索できます。会員番号など店舗独自のフィールドは、開発者が一つのフィルターで追加できます。

### 店舗側での照合方法 {#store-matching}

- **注文番号** は、WooCommerce の注文 ID と、連番注文番号プラグインが書き込む `_order_number` および `_order_number_formatted` メタデータに対して照合されます。
- **大文字・小文字とアクセント記号** の扱いは、データベースの照合順序に依存します。WordPress の既定の照合順序はどちらも区別しないため、`creme` で `Crème` が見つかります。

### 独自フィールドの追加 {#adding-a-custom-field}

`wcpos_search_fields` は、コレクションの検索定義とコレクションのスラッグを受け取ります。WCPOS 2.0 より前は、このフィルターは `woocommerce_pos_search_fields` という名前でした。旧名も引き続き使用できますが、2.0 以降は非推奨で、早ければ 2.2 で削除されます（[フックの命名](../extensions/index.mdx#hook-naming)を参照）。ユーザーメタに保存された会員番号で顧客を検索できるようにするには、次のようにします。

```php
add_filter( 'wcpos_search_fields', function ( array $search, string $collection ) {
	if ( 'customers' === $collection ) {
		$search['meta'][] = 'loyalty_number';
	}
	return $search;
}, 10, 2 );
```

注文では `$search['posts']['meta']` に追加します。従来のストレージでは投稿メタ、HPOS では注文メタテーブル内でそのキーを検索します。

**顧客** または **注文** に追加したキーは、両方で検索されます。店舗側はクエリで照合し、POS も端末側の検索対象に追加します。これは、`wcpos/v2/site` が店舗側で追加したキーを公開するためです。次の三つの制限があります。

- 端末に渡されるのは、**先頭にアンダースコアがない** キーだけです。`_private` などのキーは店舗側だけで検索されます。
- 後から追加したキーは、POS の次回起動時に反映されます。ブラウザーで再読み込みするか、アプリを開き直してください。
- **商品** または **バリエーション** に追加したキー(`$search['posts']['meta']`)は、店舗側だけで検索されます。

値はレジ係が入力する形で保存し、番号なら数字で保存してください。このフィルターは対象フィールドを追加するもので、語句の一致条件を変更するものではありません。

</details>
