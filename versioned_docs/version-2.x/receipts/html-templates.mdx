An HTML template is a receipt laid out like a web page, with `{{placeholders}}` where the order's details go. The POS fills it in on the device itself, so an HTML template previews and prints even when the connection to your store is down.

Use HTML for browser printing, PDFs, A4 invoices and printers that print web pages. For a receipt printer that takes ESC/POS commands, use a [thermal template](./thermal-templates.mdx) instead.

Go straight to: [Write a template](#write) · [Syntax](#syntax) · [Common patterns](#common-patterns) · [If something goes wrong](#goes-wrong)

## Write a template {#write}

Templates live in **WP Admin → POS → Templates**. Don't start from a blank page:

1. In the **Template Gallery**, press **Use Template** on the card closest to what you want. You get your own copy under **Your Templates**; the gallery original stays as it is.
2. Open your copy. **Fields** lists every placeholder: search it, then **Insert**, so you don't have to remember the names. **Preview** fills the template in with **Sample Data** or one of your POS orders as you type.
3. Change what you need, then press **Update**. Put styles on each element (`style="…"`), not in a `<style>` block: the editor shows a `<style>` block working, but the PDF and the mobile apps remove it. See [Styling](#styling).
4. Turn on **Active**, so the POS offers the template at the till.
5. In the POS, make a sale and pick your template on the paid screen. See [Check it in the POS](#check).

For example, to add a returns line to your copy of **Standard Receipt**, find the footer near the end and add one line after it:

```html
  {{^store.personal_notes}}{{i18n.thank_you_purchase}}{{/store.personal_notes}}
</div>
<!-- the line you add -->
<div style="text-align: center; font-size: 11px;">Returns within 30 days with this receipt.</div>
```

Press **Update**, and every receipt printed with your copy ends with that line under the footer message. Typed text prints exactly as typed, in one language.

### Check it in the POS {#check}

The editor's preview forgives mistakes that the POS doesn't, so a template is ready only once it looks right at the till:

1. Ring up an order like your busiest ones: a discounted line, a taxed product, and a cash payment with change.
2. On the paid screen, pick your template under **Template**.
3. Read the preview: names, prices, discount, tax rows, tendered and change.
4. Print it the way the till will, with **Print Receipt** or **Download PDF**, and check the paper or the file too: the PDF and the mobile apps drop `<style>` blocks.

To check a template without making a sale, put an item in the cart, press **⋮** beside **Checkout**, then **Print**: the same Template picker and preview open for the cart's order. An HTML template previews there even before the order reaches the store; the **Legacy PHP Template** asks you to sync the order first. See [Receipts at Checkout](./at-checkout.mdx).

:::tip Keep the original
Every **Use Template** makes a fresh copy. While you experiment, make two copies (*Receipt v1*, *Receipt v2*) and switch between them at the till.
:::

## Syntax {#syntax}

The placeholders use [Mustache](https://mustache.github.io/mustache.5.html), a small template language. It has no logic of its own. It does three things: fills in a value, repeats a block for each item in a list, and shows or hides a block.

### Variables {#variables}

Put a field's name in double curly braces:

```html
<h1>{{store.name}}</h1>
<p>Order #{{order.number}}</p>
<p>Total: {{totals.total_display}}</p>
```

A field ending in `_display` is the money already formatted for your store (`$12.50` rather than `12.5`). The [Receipt Data Reference](./receipt-data.mdx) lists every field.

### Escaping {#escaping}

`{{field}}` prints the value as plain text: a `<` in a product name shows as `<`, never as HTML. Three braces, `{{{field}}}`, print it as HTML. That HTML is still cleaned before it prints (see [Styling](#styling)), so a field can never add a script.

### Sections (Loops and Conditionals) {#sections-loops-and-conditionals}

`{{#section}}...{{/section}}` repeats the block for each item in a list, or shows it once when the value is there.

<details>
<summary>Example: one row per line item</summary>

```html
{{#lines}}
<div class="line-item">
  <span>{{name}} × {{qty}}</span>
  <span>{{line_total_display}}</span>
</div>
{{/lines}}
```

</details>

Inside a section, a name is looked up on the current item first, then outside it. That is why `{{i18n.tendered}}` works inside `{{#payments}}`. `{{.}}` is the current item itself, for a list of plain text such as `store.address_lines`.

### Inverted Sections {#inverted-sections}

`{{^section}}...{{/section}}` shows the block when the value is missing, empty, `false` or `0`.

<details>
<summary>Example: customer name, or "Guest checkout"</summary>

```html
{{#customer.id}}
  <p>Customer: {{customer.name}}</p>
{{/customer.id}}
{{^customer.id}}
  <p>Guest checkout</p>
{{/customer.id}}
```

</details>

### Localised Labels {#localised-labels}

`{{i18n.key}}` prints a label in your store's language, so one template works in every store.

<details>
<summary>Example: a translated Subtotal label</summary>

```html
<th>{{i18n.subtotal}}</th>
<td>{{totals.subtotal_display}}</td>
```

</details>

The labels follow the store's WordPress language, not the language the cashier has chosen in the app. Every key is in the [i18n reference](./receipt-data.mdx#i18n).

<details>
<summary>What the POS doesn't support</summary>

- **Partials** (`{{> name}}`) print nothing in the POS. Put everything in one template.
- **Lambdas** (functions in place of values) aren't possible: the receipt data holds plain values only.
- **Comments** (`{{! a note }}`) and changed delimiters (`{{=<% %>=}}`) work as in any Mustache.

</details>

## Common Patterns {#common-patterns}

### Store Header {#store-header}

`store.address_lines` holds the address already split into lines. Loop over it rather than joining the address fields yourself.

<details>
<summary>Example: logo, name, address, phone and tax IDs</summary>

```html
<div style="text-align: center;">
  {{#store.logo}}<img src="{{store.logo}}" alt="{{store.name}}" style="max-width: 200px;" />{{/store.logo}}
  <h1 style="margin: 8px 0;">{{store.name}}</h1>
  {{#store.address_lines}}<div>{{.}}</div>{{/store.address_lines}}
  {{#store.phone}}<div>{{store.phone}}</div>{{/store.phone}}
  {{#store.tax_ids}}<div>{{label}}: {{value}}</div>{{/store.tax_ids}}
</div>
```

</details>

The logo comes from the store's settings, not the template. See [Customise Your Receipt](./customise.mdx).

### Line Items with Discounts {#line-items-with-discounts}

A line's `discounts` is the discount as a positive number, or `0` when there is none. Mustache treats `0` as empty, so `{{#discounts}}...{{/discounts}}` shows the block only on a discounted line.

<details>
<summary>Example: each line with its discount</summary>

```html
{{#lines}}
<div class="line-item" style="display: flex; justify-content: space-between;">
  <div>
    <div>{{name}} × {{qty}}</div>
    {{#discounts}}
      <div style="font-size: 0.9em;">
        <s>{{line_subtotal_display}}</s> −{{discounts_display}}
      </div>
    {{/discounts}}
  </div>
  <div>{{line_total_display}}</div>
</div>
{{/lines}}
```

</details>

`line_subtotal_display` is the line before discounts, `line_total_display` after. For sale prices and savings, see [Displaying regular price and savings](./receipt-data.mdx#displaying-regular-price-and-savings).

### Tax Summary {#tax-summary}

`tax_summary` has one row per tax rate. `rate` is a percentage, such as `10`. It can be empty (a 0% rate, or a receipt printed offline), so the `{{#rate}}` guard keeps a bare `(%)` off the receipt.

<details>
<summary>Example: one row per tax rate</summary>

```html
{{#tax_summary}}
<div class="tax-line" style="display: flex; justify-content: space-between;">
  <span>{{label}}{{#rate}} ({{rate}}%){{/rate}}</span>
  <span>{{tax_amount_display}}</span>
</div>
{{/tax_summary}}
```

</details>


### Payment Details {#payment-details}

Tendered and change come from your store. A receipt printed while the POS is offline has neither, so the `{{#tendered}}` block is skipped; a reprint after the order syncs shows them.

<details>
<summary>Example: payments with tendered and change</summary>

```html
{{#payments}}
<div class="payment" style="display: flex; justify-content: space-between;">
  <span>{{method_title}}</span>
  <span>{{amount_display}}</span>
</div>
{{#tendered}}
  <div style="display: flex; justify-content: space-between;">
    <span>{{i18n.tendered}}</span><span>{{tendered_display}}</span>
  </div>
  <div style="display: flex; justify-content: space-between;">
    <span>{{i18n.change}}</span><span>{{change_display}}</span>
  </div>
{{/tendered}}
{{/payments}}
```

</details>


### Barcodes and QR Codes {#barcodes-and-qr-codes}

Use the same elements as [thermal templates](./thermal-templates.mdx). The value goes inside the element, and the POS draws the code in its place.

<details>
<summary>Example: Code 128, EAN-13 and a QR code</summary>

```html
<!-- Code 128 barcode of the order number -->
<barcode type="code128" height="40">{{order.number}}</barcode>

<!-- EAN-13 of each product, when your SKUs are EAN numbers -->
{{#lines}}<barcode type="ean13" height="30">{{sku}}</barcode>{{/lines}}

<!-- QR code: size sets how big, 4 by default -->
{{#order.payment_url}}<qrcode size="4">{{order.payment_url}}</qrcode>{{/order.payment_url}}
```

</details>

- **Always set `type`.** Without it, the POS draws Code 128 and the store's PDF draws a QR code.
- **`type` can be a placeholder**, such as `type="{{presentation_hints.order_barcode_type}}"`, because the placeholders are filled in before the codes are drawn.
- **Use `<qrcode size="…">` for QR codes.** `<barcode type="qrcode">` (or `qr`) also draws one, but the POS sizes it from `height` and the PDF from `size`, so the two don't match.
- **Pick from these types:** `code128`, `code39`, `code93`, `ean13`, `ean8`, `upca`, `upce`, `codabar`, `itf` and `qrcode`. The POS can draw other [bwip-js types](https://github.com/metafloor/bwip-js/wiki/Supported-Barcode-Types) such as `pdf417`, but the editor preview and the PDF draw those as Code 128.

Use EAN-13 only when the SKU is a valid EAN product code. For order numbers, use Code 128. If the value doesn't fit the type, the POS shows a **Barcode error** or **QR code error** block with the value in it. Fix the value or pick a type that takes it. The PDF prints the bare value instead.

## Styling {#styling}

The receipt is cleaned before it prints, so a template can never run code: scripts, `<link>` and `<meta>` tags and `on…` attributes are removed wherever it prints. The store's PDF and the mobile apps also remove `<style>` blocks and `<head>`. Style each element **inline**, as the gallery templates do:

```html
<div style="font-family: monospace; font-size: 12px; max-width: 300px; margin: 0 auto;">
  <div style="text-align: center; margin-bottom: 16px;">
    <strong style="font-size: 16px;">{{store.name}}</strong>
  </div>
  <div style="display: flex; justify-content: space-between; font-weight: 700; border-top: 1px solid black; padding-top: 8px;">
    <span>{{i18n.total}}</span>
    <span>{{totals.total_display}}</span>
  </div>
</div>
```

:::warning The editor preview doesn't clean
The template editor shows a `<style>` block working. The PDF and the mobile apps remove it, and the receipt prints unstyled there. Keep every style inline.
:::

:::tip Designed for black and white
Receipts are usually printed on black-and-white thermal or laser printers. Use **font weight, whitespace, type size and horizontal rules** for hierarchy rather than coloured fills. Coloured backgrounds and grey text either disappear or print as muddy halftones.
:::

:::tip Need a thermal-paper look without a thermal printer?
Press **Use Template** on the **Narrow Receipt** card in the gallery. It's a monospace layout 72 mm wide that prints cleanly from the browser, on printers that print web pages (Sunmi and iMin devices), and on standard paper. For a raw ESC/POS printer, use a **Simple Thermal Receipt** (58mm or 80mm) instead.
:::

## Best Practices {#best-practices}

- **Use `_display` fields** for money: they carry your store's currency format.
- **Use `{{i18n.*}}` labels** instead of typed text, so the template works in every store's language.
- **Wrap optional fields in sections**, `{{#field}}...{{/field}}`, so nothing prints when they're empty.
- **Start from a gallery template** rather than a blank page.
- **Check it in the POS** on a real order, with a discount, a tax line and a cash payment, before the till relies on it.

## If something goes wrong {#goes-wrong}

**Styles show in the editor but not on the receipt.** A `<style>` block is removed in the PDF and the mobile apps. Move the styles inline. See [Styling](#styling).

**A field prints nothing.** Check its name against the [Receipt Data Reference](./receipt-data.mdx); a misspelt or unknown field prints empty, with no error. Inside a section, the name is looked up on the current item first.

**The receipt shows a Barcode error block.** The value doesn't fit the barcode type. See [Barcodes and QR Codes](#barcodes-and-qr-codes).

**Tendered and change are missing.** The receipt was printed offline. Reprint it once the order has synced. See [Offline Mode](../getting-started/offline.mdx).

**The template isn't in the till's Template list.** It isn't **Active**, or a store has its own template list. See [Customise Your Receipt](./customise.mdx#per-store-assignments).

**The editor's preview says "Template rendering error".** A section isn't closed, or a closing tag doesn't match its opening one. Every `{{#x}}` and `{{^x}}` needs its own `{{/x}}`.
