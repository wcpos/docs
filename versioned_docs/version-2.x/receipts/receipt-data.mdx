To print or email a receipt, see [Receipts and the Paid Screen](./at-checkout.mdx). To choose a receipt template, or have AI change one for you, see [Customise Your Receipt](./customise.mdx). This page is for editing a template's code by hand.

Every receipt template, HTML or thermal, prints from the same receipt data: the store, the order, the items, the totals and the payments. This page lists every field a template can use, and shows how to print it.

**Jump to:** [Find a field](#field-reference) · [Common examples](#common-recipes) · [If something goes wrong](#if-something-goes-wrong)

## Print a field {#print-a-field}

Write the field's path between double braces: `{{store.name}}`, `{{order.number}}`, `{{totals.total_display}}`. For a list, such as the items, wrap the row in a section and it repeats once per item:

```mustache
{{#lines}}
  {{name}} x {{qty}} —
  {{line_total_display}}
{{/lines}}
```

The same section hides its contents when the field is empty, zero or false, so `{{#customer.id}}…{{/customer.id}}` prints only for a named customer. To print money, use the field that ends in `_display`; see [Currency fields](#currency-fields).

To try a field:

1. Open the template in **WP Admin → POS → Templates** ([Edit it by hand](./customise.mdx#option-3--edit-it-by-hand) has the details).
2. Type the field where it should print, or insert it from the field list beside the code.
3. Check the preview below the code, then click **Update** to save.

Receipts print offline too: the app builds a copy of the receipt data from the order on the device.

<Accordion>
  <AccordionItem question="Why receipts can differ">

### Where the data comes from {#where-the-data-comes-from}

Your store's server builds the receipt data for each order, and the app builds a shorter copy from the order on the device: it has no `cashier`, no store opening hours, notes or policies, and no `totals.paid_total` or `totals.change_total`. An HTML or thermal template opens at once from the device's copy and switches to the server's when it arrives; offline, the device's copy is the one that prints, so those fields print empty. A legacy PHP template is always rendered by the server. That's why a template uses the fields below and never PHP order methods. A few fields print only when the server renders the template, as it does for a PDF download; [If something goes wrong](#if-something-goes-wrong) lists them.

  </AccordionItem>
</Accordion>

## Field reference {#field-reference}

### Top-level sections {#top-level-sections}

| Section | What it holds |
|---------|---------------|
| `order` (object) | Order identity, status, dates, note, and payment URL information |
| `store` (object) | Store identity, address, contact details, tax IDs, logo, hours, and footer text |
| `cashier` (object) | User who processed the order |
| `customer` (object) | Customer display name, addresses, and tax IDs |
| `lines` (array) | Product line items |
| `fees` (array) | Fee rows |
| `shipping` (array) | Shipping rows |
| `discounts` (array) | Coupon/discount rows |
| `totals` (object) | Order totals, payment totals, refund summary, and item counts |
| `tax` (object) | Tax display mode flags for section guards |
| `tax_summary` (array) | Per-rate tax summary rows |
| `has_tax_summary` (boolean) | Convenience guard for `tax_summary` |
| `payments` (array) | Payment rows |
| `refunds` (array) | Refund records applied to the order |
| `fiscal` (object) | Fiscal snapshot fields populated by fiscal integrations |
| `register` (object) | The register that took the sale: `id` and `name`. Empty strings when unknown |
| `software` (object) | The software that issued the receipt: `name` (`WCPOS`), `plugin_version`, `app_version`, `app_build`, `platform` |
| `presentation_hints` (object) | Formatting and renderer hints |
| `i18n` (object) | Translated labels for bundled and custom templates |

### Tax ID objects {#tax-id-objects}

`store.tax_ids` and `customer.tax_ids` contain objects with the same shape:

| Field | Type | Description |
|-------|------|-------------|
| `type` | string | Identifier such as `eu_vat`, `de_steuernummer`, `au_abn`, `br_cpf`, `us_ein`, or `other` |
| `value` | string | Tax ID value to print |
| `country` | string/null | ISO country code; null for `eu_vat` and `other` |
| `label` | string | Localised display label, resolved before rendering |

Example:

```mustache
{{#store.tax_ids}}
  {{label}}: {{value}}
{{/store.tax_ids}}
```

### Displaying regular price and savings {#displaying-regular-price-and-savings}

For a unit-price layout, show the recorded regular price, selling price, and saving like this:

```mustache
{{#lines}}
  {{#unit_savings}}
    <span style="text-decoration: line-through;">{{regular_price_display}}</span>
    <span>{{selling_price_display}}</span>
    <span>{{i18n.savings}}: -{{unit_savings_display}}</span>
  {{/unit_savings}}
{{/lines}}
```

Use the line-total fields when quantity matters:

```mustache
{{#lines}}
  {{#line_savings}}
    <span style="text-decoration: line-through;">{{line_regular_total_display}}</span>
    <span>{{i18n.savings}}: -{{line_savings_display}}</span>
  {{/line_savings}}
{{/lines}}
```

`selling_price` is the price before coupons. Use `unit_price` or `line_total` for the final amount after WooCommerce discounts.

:::note Reprinting orders created before v1.9.0
Older WCPOS orders may already include the regular-to-selling-price reduction in `discounts`. If your custom template prints both line savings and line discounts, use `savings_in_discounts` to avoid showing the same reduction twice:

```mustache
{{#lines}}
  {{#line_savings}}
    <span style="text-decoration: line-through;">{{line_regular_total_display}}</span>
    {{^savings_in_discounts}}
      <span>{{i18n.savings}}: -{{line_savings_display}}</span>
    {{/savings_in_discounts}}
  {{/line_savings}}
  {{#discounts}}
    <span>{{i18n.discount}}: -{{discounts_display}}</span>
  {{/discounts}}
{{/lines}}
```

If the template does not print a line-level `discounts` row, keep showing `line_savings` even when `savings_in_discounts` is true. The bundled templates handle this distinction automatically.
:::

Use `total_saved` when you want one customer-facing figure for everything saved. Do not calculate it by adding `discount_total` and `sale_savings_total` in the template: orders created before v1.9.0 may already include their POS price saving in WooCommerce's discount total. The canonical `total_saved` field detects and removes that overlap.

Savings totals are `null` and `total_saved_complete` is false when any product line lacks enough recorded price data for a reliable aggregate. Guard the row with `total_saved_complete`, then use `total_saved` to hide a zero value:

```mustache
{{#totals.total_saved_complete}}
  {{#totals.total_saved}}
    <span>{{i18n.total_saved}}: {{totals.total_saved_display}}</span>
  {{/totals.total_saved}}
{{/totals.total_saved_complete}}
```

The bundled templates print **Total saved** from the tax-inclusive variant, `totals.total_saved_incl_display`, inside a single `{{#totals.total_saved_incl}}` guard. That one guard is enough because the value is `null` when the price history is incomplete and zero when nothing was saved.

## How the prices relate {#price-model}

One product line carries several prices, and the names make sense once you see them on the money itself. This is the espresso line from the sample order — a $17.00 product on sale for $14.50, with a 10% coupon on top:

<PriceFlow
  caption="Espresso Beans — one unit (the order has two)"
  scaleLabel="regular price 17.00"
  segments={[
    { kind: 'paid', amount: 13.05, label: "13.05 paid" },
    { kind: 'coupon', amount: 1.45, label: "1.45" },
    { kind: 'savings', amount: 2.5, label: "2.50" },
  ]}
  summary={[
    { label: "Sale savings across the order", value: '`totals.sale_savings_total` = 5.00' },
    { label: "All coupon discounts across the order", value: '`totals.discount_total` = 5.28' },
    { label: "Savings + discounts, legacy overlap removed", value: '`totals.total_saved` = 10.28' },

Sale savings and coupon discounts are different things: sale savings compare the selling price with the recorded regular price, while `discounts` is WooCommerce's own coupon arithmetic. WooCommerce order totals and reports only ever contain the coupon part — which is why `total_saved` exists as the one customer-facing figure that combines both.

## Extending receipt data {#extending}

A plugin can add its own fields to the receipt data through the `wcpos_receipt_data` filter.

<Accordion>
  <AccordionItem question="The filter — its arguments, the six modes and an example">

WCPOS keeps the contract above vendor-neutral. When a plugin needs the receipt to know something WooCommerce does not model, it adds that itself through the `wcpos_receipt_data` filter, the same way plugins filter WooCommerce's own order totals. The filter runs on every receipt the server builds: live receipts, fiscal snapshots at payment time, PDF downloads, and legacy PHP templates. Before WCPOS 2.0 this filter was named `woocommerce_pos_receipt_data`; that name still works but is deprecated since 2.0 and is removed in 2.2 at the earliest (see [Hook naming](../extensions/index.mdx#hook-naming)).

The third argument, `$mode`, says which document is being built: `live`, `fiscal`, `refund`, `preview` (sample receipts in the template editor and gallery), `closure` or `xreport` (register closure and X-report documents). In `preview`, `closure` and `xreport` the order is an unsaved one whose ID is `0`; a plugin that needs a saved order should return `$data` unchanged when `$order->get_id()` is `0`.

```php
add_filter( 'wcpos_receipt_data', function ( array $data, WC_Abstract_Order $order, string $mode ) {
    foreach ( $data['discounts'] as &$row ) {
        if ( 'smart_coupon' === $row['discount_type'] ) {
            $row['gift_card'] = true;
        }
    }
    return $data;
}, 10, 3 );
```

A template can then guard on the new key like any other section:

```
{{#discounts}}
  {{#gift_card}}Gift Card{{/gift_card}}{{^gift_card}}{{i18n.discount}}{{/gift_card}}{{#label}}: {{label}}{{/label}}
{{/discounts}}
```

Keys defined in the schema should keep their documented types. Added keys are not part of the schema, so they do not appear in the template editor's field picker, and fiscal snapshots only carry what the filter added at the time the order was paid. The filter is available from WCPOS 1.10.8.

  </AccordionItem>

  <AccordionItem question="Which receipts print an added key">

Every added key reaches the receipts the server renders itself: PDF downloads and legacy PHP templates. HTML and thermal templates rendered in the POS app rebuild the data first: a key added inside `order`, `store`, `cashier` or `customer` comes through, but a key added anywhere else, such as on the discounts row above, is left out. {/* pending: monorepo#3363 */} On a live receipt with a fiscal snapshot, the fiscal identity, `register` and `software` are copied from the snapshot after the filter runs, so changing them in this filter has no effect; enrich the snapshot instead.

  </AccordionItem>
</Accordion>

## If something goes wrong {#if-something-goes-wrong}

**A row prints `$0.00` on one receipt and nothing on another.** Some `_display` fields, such as `totals.change_total_display`, `totals.refund_total_display` and `payments[].tendered_display`, are empty at zero when the server renders the receipt, and `$0.00` when the app does. Guard the row with the number instead, so it hides in both: `{{#totals.change_total}}…{{/totals.change_total}}`.

**The Total saved row is missing.** `totals.total_saved_complete` is false: at least one item has no recorded regular price, so the saving can't be worked out. Orders rung up before WCPOS 1.9.0 are the usual case.

**The total is less than the customer paid.** The store shows prices excluding tax, so `totals.total` is the total before tax. Print `totals.total_incl_display` for the amount charged.

**A field prints in the PDF download but not in the POS.** Templates rendered in the app rebuild the data first and leave out a few fields, which print only in PDF downloads and legacy PHP templates. Print a field from the list below only in those, or guard it with a section so the POS receipt leaves it out. {/* pending: monorepo#3363 */}

<Accordion>
  <AccordionItem question="Fields that differ between PDF and POS receipts">

- `lines[].attributes`, `lines[].total_refunded_display` and `lines[].unit_subtotal_display` (with its `_incl` and `_excl` twins)
- `software.platform`
- `presentation_hints` other than `display_tax`, `prices_entered_with_tax`, `rounding_mode`, `locale` and `order_barcode_type`
- customer tax IDs of the German, Dutch, French, UK company and Swiss types
- keys a plugin adds outside `order`, `store`, `cashier` and `customer`; see [Extending receipt data](#extending)

  </AccordionItem>
</Accordion>

## Versions {#versions}

The receipt data has its own version number, separate from the plugin's. Newer fields are missing from older receipts, such as a fiscal snapshot taken before the field existed, so guard them with a section.

| Version | Added |
|---------|-------|
| 1.1 | Regular price, selling price and savings for each item, and the order's savings totals, including **Total saved**. None of them change the order totals or WooCommerce reports |
| 1.2 | `discounts[].discount_type` |
| 1.3 | `customer.first_name` and the customer display labels in `i18n` |
| 1.4 | `register`, `software`, the fiscal document fields (`fiscal.document_type`, the `is_…` flags, `sale_time`, `received_at`, `sale_tz`, `sale_counter`, `corrects`) and their `i18n` labels |
