## What this means {#what-this-means}

Your store refused this change, so it hasn't reached the store.

Read the store's reason. If **Store health → Database** lists the change, fix the record and tap **Send again**, or **Discard** it. If not, the store's version was restored — make the change again if it's still needed (see [SYNC202](/error-codes/SYNC202)). Nothing retries a refused change on its own.

## Your data {#your-data}

Don't clear this device's data — it may hold changes your store doesn't have yet. A refused change that is listed in **Store health → Database** stays there until you send it again or discard it. A refused edit to an existing product, variation, customer or coupon is usually undone automatically and logged as [SYNC202](/error-codes/SYNC202) instead. If it shows as this code and the change is listed in **Store health → Database**, the automatic undo didn't happen — treat it like any other listed change below. If this keeps happening, use **Copy debug info** in **Store health → Logs** and contact WCPOS support.

## Troubleshoot {#troubleshoot}

### At the till {#at-the-till}

1. Read the store's reason — it is on [the log entry](#log-entry), and on the change's row in **Store health → Database**.
2. Open **Store health → Database**. If the change is not listed there, the store's version was already restored on this device and there is nothing to send — see [SYNC202](/error-codes/SYNC202). Fix what the reason names, then make the change again if it's still needed.
3. If it is listed — an order, a record created on this device, or a catalogue edit whose automatic undo didn't happen — the refused change is under **"… changes never reached your server"** with your store's reason on its row. Fix what the reason names on the record itself, for example a field on the order, while the change stays listed.
4. Back in **Store health → Database**, tap **Send again** on that row. It rebuilds the change from what is now on this device and sends it.
5. If the change is no longer wanted, tap **Discard** instead: the store's version is kept. Read the confirmation first — for a record the store never saved, discarding deletes it from this device.

### On the store {#on-the-store}

For the site administrator.

1. If the reason says the user is not allowed to make the change, their role lacks that task — see [AUTH201](/error-codes/AUTH201).
2. If the reason mentions a field the POS does not show, open the same record in WP Admin — another plugin may add validation the POS cannot see.
3. If it is still refused, use **Copy debug info** in **Store health → Logs** and contact support.

## Find the entry in the log {#log-entry}

Every code is logged in **Store health → Logs**. Press **Errors**, then tap the entry with this code to open it under its row. The picture shows an example entry, AUTH201; on your till the entry shows this page's code.

<JourneyShot manifest={logs} device="tablet" step={3} offsets={[[17, 28], [549, -9], [-54, -97], [131, 0], [101, 0], [-33, 0]]} alt="An error entry opened under its row in Store health → Logs: what the server said, what to do, Open record, the Help link, the event code with Copy, and the record, operation and request">

1. **Errors** — the filter that's on.
2. **The entry** — the code in **Status** is its error code.
3. **What happened and what to do** — what your store said, when it said something, then one line on what to do. When it matters, a warning comes first, such as **Payment has been taken — don't charge again.** or **Don't clear this device's data**.
4. **Help** — opens the code's page in these docs.
5. **Open record** — opens the order, product or customer the entry is about, when this till has it, your store has WCPOS Pro, and you're allowed to edit it.
6. **Copy** — copies the whole entry for support. The rows under it are for support; you don't need to read them.
