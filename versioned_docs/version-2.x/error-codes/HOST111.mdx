## Fix it at the till {#at-the-till}

1. Send whoever looks after your website a link to this page.
2. Meanwhile, use the desktop or mobile app. They don't need these browser settings.
3. Once it's fixed, reload the web app, enter **Your store's address** and press **Connect**.
4. **If it connects:** carry on selling in the browser.
5. **If the red text shows again:** the settings are still wrong. Tell them again.

{/* source: step 1 error-registry.json:1801 (the fix is on the store's side); step 2 error-registry.json:1806; step 3 core.json:482, :477, url-input.tsx:44-47 (typing clears the error); steps 4-5 connect-probes.ts:409-413 (the same check runs again on Connect, use-site-connect.ts:235-260) */}

## Is anything lost? {#your-data}

No. No order or product data is affected, and nothing on this device or on your store changed.

## If it keeps happening {#keeps-happening}

Your store's browser access settings are wrong, so the browser hides its answers from the web app. Only whoever looks after your website can fix them.

{/* source: error-registry.json:1800-1801 */}

<details>
<summary>For whoever looks after your website</summary>

The store answers, but its CORS response headers are wrong: duplicated, set to the wrong origin, or missing on error responses. The browser hides the real answer, which also masks every other error behind a generic network failure.

1. Look for a second CORS layer (a plugin and the web host's config both adding headers) and remove one. A duplicated Access-Control-Allow-Origin is fatal in the browser.
2. On nginx, end `add_header` lines with `always`, so CORS headers reach 4xx and 5xx responses too.
3. If a CDN or proxy adds CORS headers, make sure they don't conflict with WordPress's own.
4. Aim for exactly one Access-Control-Allow-Origin, on every status code.

{/* source: error-registry.json:1801, :1803-1805 */}

</details>
