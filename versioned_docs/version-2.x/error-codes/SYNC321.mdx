## What this means {#what-this-means}

Some data didn't sync this time.

This code appears in two forms — the log row's title says which one you have:

- **"Sync partial"** (record titles): some records synced and the named records did not. Nothing to do if the next sync clears it. If **Store health → Database** lists changes that need attention, settle them there.
- **"Gave up on a stuck data request"**: the sync engine's data-request lane stopped making progress on one request, so after a generous wait the app abandoned that request rather than let it block everything queued behind it. Nothing needs retrying by hand — the sync engine re-issues the request automatically — and it often follows a stalled local database call, logged separately as [SYNC181](/error-codes/SYNC181).

## Your data {#your-data}

Don't clear this device's data — it may hold changes your store doesn't have yet. For a gave-up data request, nothing was changed — an abandoned request is re-issued automatically. If this keeps happening, use **Copy debug info** in **Store health → Logs** and contact WCPOS support.

## Troubleshoot {#troubleshoot}

### At the till {#at-the-till}

1. For a **"Gave up on a stuck data request"** entry, no action is needed unless a screen stays stuck. Then reload the app — reload the browser tab on web, or close and reopen the app on desktop and mobile.
2. For a partial sync, nothing to do if the next sync clears it. If it doesn't, open **Store health → Database**: records that still did not sync appear at the top.
   - The **"… records need attention"** callout names the first one with its reason (fix it and the next one appears), and the **"… changes never reached your server"** and **"… changes were held"** panels list theirs. The records that did sync need nothing.
3. Settle each listed record by its own reason. In the callout, **Fix record** (where shown) opens the record to edit it; a refused change is corrected on the record itself ([SYNC201](/error-codes/SYNC201)); for a held change, choose which version to keep ([SYNC221](/error-codes/SYNC221)).
4. Then send them again: **Retry** in the callout (this runs a sync), or **Send again** on the record's row in the panels.
   - A record the callout says *can't download from your store* has no **Retry** — see [SYNC331](/error-codes/SYNC331).
5. If a record still does not sync, use **Copy debug info** in [**Store health → Logs**](#log-entry) and contact support.

## Find the entry in the log {#log-entry}

Every code is logged in **Store health → Logs**. Press **Errors**, then tap the entry with this code to open it under its row. The picture shows an example entry, AUTH201; on your till the entry shows this page's code.

<JourneyShot manifest={logs} device="tablet" step={3} offsets={[[17, 28], [549, -9], [-54, -97], [131, 0], [101, 0], [-33, 0]]} alt="An error entry opened under its row in Store health → Logs: what the server said, what to do, Open record, the Help link, the event code with Copy, and the record, operation and request">

1. **Errors** — the filter that's on.
2. **The entry** — the code in **Status** is its error code.
3. **What happened and what to do** — what your store said, when it said something, then one line on what to do. When it matters, a warning comes first, such as **Payment has been taken — don't charge again.** or **Don't clear this device's data**.
4. **Help** — opens the code's page in these docs.
5. **Open record** — opens the order, product or customer the entry is about, when this till has it, your store has WCPOS Pro, and you're allowed to edit it.
6. **Copy** — copies the whole entry for support. The rows under it are for support; you don't need to read them.
