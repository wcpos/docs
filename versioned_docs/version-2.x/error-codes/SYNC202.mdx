## What this means {#what-this-means}

Your store refused this change, so this device went back to the store's version.

The change wasn't saved. Read the store's reason, fix what it names, then make the change again.

This happens with edits to existing products, variations, coupons and customers. When your store permanently refuses one — for example because a value is invalid, or the signed-in user isn't allowed to make that change — WCPOS doesn't keep the refused edit waiting. It puts the store's version back on this device, so the till sells from the same details your store has. The log entry names the record and carries the store's reason.

## Your data {#your-data}

Nothing else changed. Your store still has its own version, unchanged, and this device shows that version again. If the store has deleted the record, it is removed from this device instead. Only the refused edit is gone, so make it again once the reason is fixed. Sales and orders are not affected, and an edit you made to the same record after the refused one is kept and still sends.

## Troubleshoot {#troubleshoot}

### At the till {#at-the-till}

1. Expand [the log entry](#log-entry) and read the store's reason: it says what the store refused and which record it belongs to.
2. Fix what the reason names. If it is a value — for example a price, a SKU, an email address, or a required field left empty — work out the correct value.
   - If the reason says the user isn't allowed to make the change, the account's role lacks that task: see [AUTH201](/error-codes/AUTH201).
3. Open the record (if the store has deleted it, there is nothing to change), make the change again with the corrected value, and save. Once it syncs, check the record shows your change.
4. A new record created on this device that the store refused is not reverted — there is no store version to go back to. It stays listed in **Store health → Database** under **"… changes never reached your server"**; see [SYNC201](/error-codes/SYNC201).

### On the store {#on-the-store}

For the site administrator.

1. If the reason mentions a field the POS does not show, open the same record in WP Admin — another plugin may add validation the POS cannot see.
2. If the store keeps refusing the change, use **Copy debug info** in **Store health → Logs** and contact support.

## Find the entry in the log {#log-entry}

Every code is logged in **Store health → Logs**. Press **Errors**, then tap the entry with this code to open it under its row. The picture shows an example entry, AUTH201; on your till the entry shows this page's code.

<JourneyShot manifest={logs} device="tablet" step={3} offsets={[[17, 28], [549, -9], [-54, -97], [131, 0], [101, 0], [-33, 0]]} alt="An error entry opened under its row in Store health → Logs: what the server said, what to do, Open record, the Help link, the event code with Copy, and the record, operation and request">

1. **Errors** — the filter that's on.
2. **The entry** — the code in **Status** is its error code.
3. **What happened and what to do** — what your store said, when it said something, then one line on what to do. When it matters, a warning comes first, such as **Payment has been taken — don't charge again.** or **Don't clear this device's data**.
4. **Help** — opens the code's page in these docs.
5. **Open record** — opens the order, product or customer the entry is about, when this till has it, your store has WCPOS Pro, and you're allowed to edit it.
6. **Copy** — copies the whole entry for support. The rows under it are for support; you don't need to read them.
