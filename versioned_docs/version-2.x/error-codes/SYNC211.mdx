## What this means {#what-this-means}

Your store refused a value it was sent.

The store's reason names the value. Correct it where you entered it, then save again. Usually the value belongs to a record — a product, customer or order — but this code can also come from a settings or sign-in request the store refused; then correct it on that screen.

## Your data {#your-data}

Don't clear this device's data — it may hold changes your store doesn't have yet. A refused edit to an existing product, variation, customer or coupon is usually undone automatically and logged as [SYNC202](/error-codes/SYNC202) instead. If it shows as this code and the change is listed in **Store health → Database**, the automatic undo didn't happen — treat it like any other listed change. A settings or sign-in request leaves nothing to save.

## Troubleshoot {#troubleshoot}

### At the till {#at-the-till}

1. Expand [the log entry](#log-entry) and read the store's reason: the reason names the value.
2. Correct the value where you entered it — common causes are a value out of range, a rejected format or a required option left empty — then save again.
   - If the change is not listed in **Store health → Database**, the store's version was restored, so make the change again with the corrected value.
   - If it is still listed under **"… changes never reached your server"** in **Store health → Database** after you correct it, tap **Send again** on its row.
3. If the record is instead listed under **"… changes were held"** with *"Your store required a current version"*, no value is at fault — decide between **Send again** and **Discard device change** as described in [SYNC221](/error-codes/SYNC221).
4. If it was a settings or sign-in request, correct the value on the screen where you entered it and save again.

### On the store {#on-the-store}

For the site administrator.

1. If a named value looks correct in the POS, compare it with the same record in WP Admin — plugin-added validation on the store can reject values the POS considers fine.

<details>
<summary>Technical detail</summary>

The log entry also shows the endpoint: the endpoint shows whether the value came from a record or from a settings or sign-in request.

For a settings or sign-in request, the browser's developer tools (Network tab) — or **Advanced → Toggle Developer Tools** in the desktop app — show the store's response when the details are not in the POS log.

</details>

## Find the entry in the log {#log-entry}

Every code is logged in **Store health → Logs**. Press **Errors**, then tap the entry with this code to open it under its row. The picture shows an example entry, AUTH201; on your till the entry shows this page's code.

<JourneyShot manifest={logs} device="tablet" step={3} offsets={[[17, 28], [549, -9], [-54, -97], [131, 0], [101, 0], [-33, 0]]} alt="An error entry opened under its row in Store health → Logs: what the server said, what to do, Open record, the Help link, the event code with Copy, and the record, operation and request">

1. **Errors** — the filter that's on.
2. **The entry** — the code in **Status** is its error code.
3. **What happened and what to do** — what your store said, when it said something, then one line on what to do. When it matters, a warning comes first, such as **Payment has been taken — don't charge again.** or **Don't clear this device's data**.
4. **Help** — opens the code's page in these docs.
5. **Open record** — opens the order, product or customer the entry is about, when this till has it, your store has WCPOS Pro, and you're allowed to edit it.
6. **Copy** — copies the whole entry for support. The rows beside and under it (event code, record, operation, request, details) are for support too; you don't need to read them.

</JourneyShot>
