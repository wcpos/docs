## What this means {#what-this-means}

This device asked the store for data far more often than normal.

Nothing to do — nothing was lost. Nothing was slowed down or blocked — this is a detection-only alarm. Sustained request floods usually indicate an app problem (a screen re-requesting the same data in a loop) rather than anything you did. If it keeps appearing, tap **Copy debug info** and send it to WCPOS support so the loop can be found and fixed.

## Your data {#your-data}

Nothing was lost — no order or product data is affected. If this persists, use **Copy debug info** in **Store health → Logs** and contact WCPOS support.

## Troubleshoot {#troubleshoot}

### At the till {#at-the-till}

1. Keep working — this is a detection-only alarm. WCPOS does not slow, queue or drop any request, and no order or product data is affected.
2. If the code appears once and stops, no action is needed. If it repeats, note which screen was open and which action you were taking when it appeared.
3. Use Copy debug info while the event is still in the log window and contact WCPOS support; the export lets support trace the request loop.

## Find the entry in the log {#log-entry}

Every code is logged in **Store health → Logs**. Press **Errors**, then tap the entry with this code to open it under its row. The picture shows an example entry, AUTH201; on your till the entry shows this page's code.

1. **Errors** — the filter that's on.
2. **The entry** — the code in **Status** is its error code.
3. **What happened and what to do** — what your store said, when it said something, then one line on what to do. When it matters, a warning comes first, such as **Payment has been taken — don't charge again.** or **Don't clear this device's data**.
4. **Help** — opens the code's page in these docs.
5. **Open record** — opens the order, product or customer the entry is about, when this till has it, your store has WCPOS Pro, and you're allowed to edit it.
6. **Copy** — copies the whole entry for support.
