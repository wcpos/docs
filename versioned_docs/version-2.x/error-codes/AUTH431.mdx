**Do this now:** send whoever looks after your website a link to this page, even if your website opens normally.

## Fix it at the till {#at-the-till}

1. Send whoever looks after your website a link to this page.
2. Your website can open normally in a browser. The block is only on the part the POS reads.
3. Once they've fixed it, press **Connect** again.
4. **If it connects:** press **Sign in with WordPress** and carry on.
5. **If the red text shows again:** the block is still there. Tell them again.

## Is anything lost? {#your-data}

No. Nothing on this device or on your store changed. The app stopped before it saved your store.

{/* source: dataSafety no-impact, error-registry.json:1735; use-site-connect.ts:252-254 throws before saveSiteData at :276 */}

## If it keeps happening {#keeps-happening}

A security plugin hides your store's REST API, or a firewall rule blocks it. Only whoever looks after your website can change that.

{/* source: error-registry.json:1738, :1740-1741 */}

<details>
<summary>For whoever looks after your website</summary>

The app tried the REST API at `/wp-json/...` and at WordPress's fallback `/?rest_route=...`. Neither answered.

1. If a plugin such as WP Hide hides or renames `/wp-json/`, allow `/?rest_route=` too. The app falls back to it by itself.
2. Check firewall (WAF) rules matching `wp-json` or `rest_route`, and allow the store's own REST API.
3. If a maintenance page answers REST requests with HTML, switch it off for the REST API.
4. Test: `https://your-store.com/?rest_route=/` must return JSON, not a 403 or the homepage.

{/* source: connect-probes.ts:596-624 (path first, then the rest_route form); error-registry.json:1738, :1740-1743 */}

</details>
