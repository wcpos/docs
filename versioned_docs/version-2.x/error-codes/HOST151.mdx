## What this means {#what-this-means}

Your host's cache could show one person's data to another, so WCPOS won't connect.

Nothing on this device is lost. Ask your host to stop caching the store's API (both `/wp-json/` and `?rest_route=` addresses), then reconnect.

A caching layer is serving stored REST API responses without checking who is asking: the app sent two differently-authenticated probes and received the first probe's answer both times. On a live store this means one cashier could see another's data, so connecting is blocked until the cache excludes the store's API. This is a hosting-layer problem — WordPress itself always answers per-user.

Before raising this error the app retries with a unique cache key on every request. When that retry proves the key defeats the cache, the app connects and keeps sending the key, so you only see this error when the retry could not prove a safe connection either.

## Your data {#your-data}

Nothing on this device is lost. WCPOS refuses to connect rather than risk showing one person's data to another; anything already on this device stays there and sends once it connects.

## Troubleshoot {#troubleshoot}

**For your host or site admin** — the app already retried with a unique cache key and still could not prove a safe connection, so the cache has to be fixed on the host:

1. Exclude the store's REST API paths (/wp-json/ and /?rest_route=) from page caching — on LiteSpeed disable REST caching or add a no-cache rule; on WP Engine extend the WooCommerce exclusion to /wp-json/wcpos and the ?rest_route= form; on Sucuri set the caching level to honor Cache-Control.
2. The store's API already sends Cache-Control: no-store and Vary: Authorization — the cache layer is ignoring them; point the host at those headers.
3. After changing cache settings, purge the cache, then reconnect.
