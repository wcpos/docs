## What this means {#what-this-means}

Your host's cache can replay one person's store data to another.

Nothing on this device is lost. The host's cache is handing out stored answers without checking who is asking, so on a live store one cashier could see another's data. If WCPOS gets past the cache, it connects and this entry is a warning that the cache still needs fixing. If it can't prove a safe connection, WCPOS doesn't connect until the cache is fixed.

## Your data {#your-data}

Nothing on this device is lost. If WCPOS couldn't prove a safe connection, it doesn't connect rather than risk showing one person's data to another; anything already on this device stays there and sends once it connects.

## Troubleshoot {#troubleshoot}

### At the till {#at-the-till}

1. Ask your host to stop caching the store's answers, and tell them the code, HOST151.
2. Once your host has changed the cache settings and purged the cache (see On the store), reconnect if WCPOS didn't connect.

### On the store {#on-the-store}

For your host or site admin — the cache has to be fixed on the host, even if WCPOS connected by working around it.

1. Exclude the store's REST API paths (/wp-json/ and /?rest_route=) from page caching.
   - On LiteSpeed, disable REST caching or add a no-cache rule.
   - On WP Engine, extend the WooCommerce exclusion to /wp-json/wcpos and the ?rest_route= form.
   - On Sucuri, set the caching level to honor Cache-Control.
2. The store's API already sends Cache-Control: no-store and Vary: Authorization — the cache layer is ignoring them; point the host at those headers.
3. After changing cache settings, purge the cache.

<details>
<summary>Technical detail</summary>

A caching layer is serving stored REST API responses without checking who is asking: the app sent two differently-authenticated probes and received the first probe's answer both times. This is a hosting-layer problem — WordPress itself always answers per-user.

When this happens the app retries with a unique cache key on every request. If that proves the key gets past the cache, WCPOS connects and keeps sending the key — this entry is then a warning that the cache still needs fixing. If it can't prove a safe connection, WCPOS doesn't connect until the cache is fixed.

The host must stop caching the store's API (both `/wp-json/` and `?rest_route=` addresses).

</details>

## Find the entry in the log {#log-entry}

Every code is logged in **Store health → Logs**. Press **Errors**, then tap the entry with this code to open it under its row. The picture shows an example entry, AUTH201; on your till the entry shows this page's code.

1. **Errors** — the filter that's on.
2. **The entry** — the code in **Status** is its error code.
3. **What happened and what to do** — what your store said, when it said something, then one line on what to do. When it matters, a warning comes first, such as **Payment has been taken — don't charge again.** or **Don't clear this device's data**.
4. **Help** — opens the code's page in these docs.
5. **Open record** — opens the order, product or customer the entry is about, when this till has it, your store has WCPOS Pro, and you're allowed to edit it.
6. **Copy** — copies the whole entry for support. The rows under it are for support; you don't need to read them.
