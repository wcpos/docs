The POS reads and saves your store through your WordPress site's REST API. Another plugin that blocks, caches or rewrites those requests can stop the till signing in, downloading products or saving a sale. This page helps you find that plugin, and lists the ones we already know about.

:::note For the person who manages your website
Most fixes on this page are made in WP Admin or with your host. If you're a cashier, show this page to whoever looks after the website.
:::

:::tip Check the list first
If you know which plugin changed, look it up in [Known plugin conflicts](#known-plugin-conflicts) before you start switching plugins off. Don't know which plugin? Start with [a staging site](#before-you-start-use-a-staging-site).
:::

## Signs of a plugin conflict {#signs-of-plugin-conflicts}

It may be a plugin conflict if, after a plugin was added or updated:

- **The login window shows an error or a blank page.**
- **The app says "The WordPress REST API on this site requires authentication"**, or shows another plugin's message saying only signed-in users can use the REST API.
- **The site shows "There has been a critical error on this website"**, in the POS or in WP Admin.
- **Products, orders or customers stop downloading**, or a sale won't save to the store.
- **A gateway's payment page on the Legacy tab looks broken**, or its buttons do nothing.
- **Everything is slow**, or requests time out. A slow checkout has its own page: [Checkout Performance](../performance/checkout.mdx).

## Before you start: use a staging site {#before-you-start-use-a-staging-site}

:::warning Don't troubleshoot on your live site
Switching plugins off on the site your till uses can stop sales and change your web store. Do it on a staging site.
:::

### What is a staging site? {#what-is-a-staging-site}

A staging site is a copy of your website where you can test changes without your customers or your till seeing them. Most hosts make one in a few clicks from the hosting dashboard.

### If your host doesn't offer staging {#if-your-host-doesnt-offer-staging}

Ask your host how to copy the site. If they have no way to, it's worth moving to a host that does: you'll want staging for every plugin, theme, WordPress and WooCommerce update, not only for this. WP Engine, SiteGround, Kinsta and Cloudways all include it.

## Step 1: Look for a fatal error {#step-1-check-for-fatal-errors}

A crash usually names the plugin that caused it. Look there first:

1. **The POS log.** Open **Store health** from the drawer, choose **Logs**, then **Errors**. See [Logs](../logs.mdx).
2. **The WooCommerce fatal error log.** Follow [Critical Error](./critical-error.mdx) to find it in WP Admin.
3. **Read the file path.** A line such as `wp-content/plugins/<plugin-name>/…` names the plugin.

If the error names a plugin other than WooCommerce or WCPOS, switch that one off on your staging site and try again. If nothing names a plugin, go on to Step 2.

## Step 2: Switch plugins off, then back on one by one {#step-2-the-plugin-elimination-method}

Use this when there's no fatal error, or when the problem is slowness.

### 2.1 Note what goes wrong {#21-create-a-baseline}

1. **Open your staging site** in the POS.
2. **Do the thing that fails**, and write down exactly what you see: the message, the screen, how long it takes.
3. **For slowness**, note the times in the [Logs](../logs.mdx) so you can compare later.

### 2.2 Switch off everything except the POS {#22-disable-all-plugins-except-essential-ones}

**Keep these active:**
- WooCommerce
- WCPOS
- WCPOS Pro, if you have it

**Switch off everything else:**
1. Go to `WP Admin > Plugins`.
2. Tick every other plugin.
3. Choose **Deactivate** from **Bulk actions**.
4. Click **Apply**.

### 2.3 Try again {#23-test-the-issue}

1. **Clear every cache**: your host's, your CDN's and any caching plugin's.
2. **Do the thing that failed.** Does it work now?
3. **For slowness**, compare the times with the ones you noted.

**It works now:** a plugin is the cause. Go to 2.4.

**It still fails:** this test hasn't found the cause. Next, check:
- your server's resources and firewall: see [Server Performance](../performance/server.mdx)
- your theme: see [Step 3](#step-3-check-for-theme-conflicts)
- a service in front of your site, such as [Cloudflare](./cloudflare.mdx)

### 2.4 Switch plugins back on one by one {#24-enable-plugins-one-by-one}

1. **Activate one plugin.**
2. **Try again.**
3. **Still works:** activate the next one and try again.
4. **Fails again:** the plugin you just activated is the conflict.

Start with the kinds of plugin most likely to clash, so you find it sooner:
1. **Security and login plugins**: Wordfence, Sucuri, Solid Security and similar
2. **Caching and optimisation plugins**
3. **Payment gateways**
4. **Other WooCommerce extensions**
5. **SEO plugins**
6. **Everything else**

### 2.5 Write down what you found {#25-document-your-findings}

1. **The plugin's name and version.**
2. **What it breaks**, in the words you noted in 2.1.
3. **Whether a newer version is out.**

You'll need these for [Step 4](#step-4-resolving-plugin-conflicts) and if you [contact support](#getting-help).

## Step 3: Check your theme {#step-3-check-for-theme-conflicts}

The POS screens don't use your theme, so a theme rarely breaks the till. It can still break the pages WordPress draws for the POS:

- a gateway's payment page on the checkout's **Legacy** tab, and the web store checkout the [Web Checkout](../../payment/gateways/web-checkout.mdx) gateway sends customers to
- WP Admin screens, including the POS settings

### Test with a default theme {#test-with-a-default-theme}

1. **On your staging site**, switch to a default WordPress theme, such as Twenty Twenty-Five or Twenty Twenty-Four.
2. **Try again.**
3. **It works now:** your theme is the cause. Tell the theme's developer what breaks.

## Step 4: Fix the conflict {#step-4-resolving-plugin-conflicts}

Once you know the plugin, try these in order.

### Option 1: Update it {#option-1-update-the-plugin}

1. **Look for an update.** The conflict may already be fixed.
2. **Update on staging first**, and try again.
3. **Then update your live site.**

### Option 2: Exclude the POS from it {#option-2-exclude-the-pos}

Most clashes are fixed in the other plugin's settings, without switching it off. See [What to exclude](#what-to-exclude), and the fix for your plugin under [Known plugin conflicts](#known-plugin-conflicts).

### Option 3: Find an alternative {#option-2-find-an-alternative}

1. **Look for another plugin** that does the same job.
2. **Try it on staging.**
3. **Move its settings across** before you switch.

### Option 4: Tell the plugin's developer {#option-3-contact-plugin-developer}

Send them:
- the plugin's version, and your WordPress, WooCommerce and WCPOS versions
- what breaks, with the exact message
- the steps to make it happen

### Option 5: Get a developer to work around it {#option-4-custom-solution}

For a plugin you can't do without, a WordPress developer can often stop the part that clashes from running on POS requests and POS pages, using the plugin's own hooks.

## What to exclude {#what-to-exclude}

Almost every fix below is the same move: tell the other plugin to leave the POS alone, rather than switching it off. These are the addresses to exclude from firewalls, caching, script optimisation and login rules:

| Address | What the POS uses it for |
| --- | --- |
| `/wp-json/wcpos/` | Everything the POS reads and saves |
| `/wp-json/` | Finding your store when the app connects |
| `/pos` | The POS in a web browser. This is the default; your site may use another **POS base** under `WP Admin > Settings > Permalinks` |
| `/wcpos-auth/` | The app's login window |
| `/wcpos-checkout/` | A gateway's payment page on the **Legacy** tab, and receipts |

:::note The app's login window doesn't use the WordPress login page
The desktop and mobile apps sign in on WCPOS's own form at `/wcpos-auth/`, in a separate window. Plugins that change the WordPress login page, such as a custom login address, two-factor codes, a captcha or email-only login, don't apply to it. They do apply when you open the POS in a web browser, which sends you to your normal WordPress login first.
:::

## Common conflicting plugin types {#common-conflicting-plugin-types}

### High-risk plugin categories {#high-risk-plugin-categories}

| Kind of plugin | What it can do to the POS |
| --- | --- |
| **Security and firewall** | Block REST API requests, lock out the till after many requests, or stop the sign-in |
| **Caching and optimisation** | Serve stale answers to the POS, or break scripts on the pages WordPress draws for it |
| **Login, membership and access** | Close the REST API to anyone not signed in, or change how users sign in |
| **Page builders and front-end injectors** | Load their scripts and overlays into a gateway's payment page |
| **Anything that runs when an order or product is saved** | Slow every sale, or make a sale fail to save |

### Lower-risk plugin categories {#lower-risk-plugin-categories}

Contact forms, social media, analytics and content plugins rarely touch the POS. [WooCommerce Tax](../../integrations/woocommerce-tax.mdx) works with it: POS sales get the same automated rates as your online orders.

## Known plugin conflicts {#known-plugin-conflicts}

These plugins have been reported to clash with WCPOS. Open yours to see what goes wrong and the fix, then make the fix on your staging site first.

### Security & login plugins {#security-and-login-plugins}

These are the most common cause. They block the requests the POS makes, so the app can't connect, sign in or download your store.

<details>
<summary>Wordfence: the POS can't connect or download</summary>

**What goes wrong:** its firewall blocks the POS's REST API requests.

**Fix:** allow `/wp-json/wcpos/` in the firewall. Allow only the POS's routes, not the whole REST API.

</details>

<details>
<summary>Really Simple Security: REST API blocked or redirected</summary>

**What goes wrong:** it blocks REST API access, or forces redirects.

**Fix:** turn off its REST API restrictions in the plugin's **Advanced** settings.

</details>

<details>
<summary>Solid Security (iThemes Security): REST API blocked or till locked out</summary>

**What goes wrong:** it blocks the REST API, or locks the till out as a brute-force attack.

**Fix:** allow the POS's routes and your server's own IP address. Avoid allowing IP addresses site-wide.

</details>

<details>
<summary>Sucuri: the POS can't connect or download</summary>

**What goes wrong:** its firewall blocks REST API requests.

**Fix:** allow `/wp-json/wcpos/` in the Sucuri dashboard.

</details>

<details>
<summary>Force Login, and other plugins that close the REST API: "requires authentication"</summary>

**What goes wrong:** the app says _"The WordPress REST API on this site requires authentication"_, or shows the plugin's own message saying only signed-in users can use the REST API.

**Fix:** let visitors who aren't signed in reach the REST API, or at least `/wp-json/` and `/wp-json/wcpos/`.

</details>

<details>
<summary>Security Optimizer: web browser POS asks for the custom login URL</summary>

**What goes wrong:** opening the POS in a web browser stops at a message to use the custom login URL.

**Fix:** log in to WP Admin through your custom login URL first, then go to `/pos`.

</details>

<details>
<summary>Jetpack CRM Client Portal: users can't sign in</summary>

**What goes wrong:** users can't sign in to the POS.

**Fix:** switch off the Client Portal extension only, not all of Jetpack CRM.

</details>

### Performance, caching & optimisation plugins {#performance-caching-optimisation-plugins}

<details>
<summary>WP Rocket, Autoptimize, Hummingbird, Smush: Legacy payment pages break</summary>

**What goes wrong:** deferring or minifying JavaScript breaks gateway payment pages on the **Legacy** tab.

**Fix:** exclude `/wcpos-checkout/` and `/pos` from JavaScript optimisation.

</details>

<details>
<summary>LiteSpeed Cache: desktop app reloads at checkout</summary>

**What goes wrong:** the desktop app reloads over and over at checkout.

**Fix:** update WCPOS and LiteSpeed Cache, purge the cache, and exclude `/wcpos-checkout/` and `/pos` from caching.

</details>

### Page builders & front-end injectors {#page-builders-front-end-injectors}

These load their scripts and overlays into the payment page that a gateway on the **Legacy** tab opens inside the POS. That page has a **Checkout Settings** button that removes scripts and styles from it: see [A Gateway's Payment Page Looks Wrong](../../pos/checkout/troubleshooting.mdx#checkout-settings-troubleshooting).

<details>
<summary>Elementor: payment methods won't open</summary>

**What goes wrong:** `elementor-frontend.js` breaks the payment page: payment methods won't open.

**Fix:** in **Checkout Settings**, remove Elementor's frontend script under **Disable Selected Scripts**, or stop Elementor loading it on `/wcpos-checkout/`.

</details>

<details>
<summary>Omnisend, and other marketing plugins: payment page layout breaks</summary>

**What goes wrong:** their scripts break the payment page's layout and payments.

**Fix:** in **Checkout Settings**, remove their scripts under **Disable Selected Scripts**.

</details>

<details>
<summary>MyStickyElements, Complianz: buttons or a banner cover the payment page</summary>

**What goes wrong:** sticky buttons or a cookie banner cover the payment page.

**Fix:** set them to leave out `/wcpos-checkout/`, or remove their scripts in **Checkout Settings**.

</details>

### WooCommerce extensions & other plugins {#woocommerce-extensions-other-plugins}

<details>
<summary>Stripe Tax: doesn't work with POS orders</summary>

**What goes wrong:** it doesn't work with orders created through the REST API, which is how the POS saves every order.

**Fix:** there's no workaround. [WooCommerce Tax](../../integrations/woocommerce-tax.mdx) is the automated tax that works with the POS.

</details>

<details>
<summary>WP Activity Log: database fills up, store slows</summary>

**What goes wrong:** it logs every change the POS makes, so the database fills up and the store slows down.

**Fix:** switch it off, or leave POS products and orders out of its logging.

</details>

<details>
<summary>MailerLite: server error (500) when a sale saves</summary>

**What goes wrong:** with both MailerLite Signup Forms and the MailerLite WooCommerce integration active, the server runs out of memory and returns a server error (500) when the POS saves an order.

**Fix:** deactivate both to confirm, then contact MailerLite.

</details>

<details>
<summary>The Courier Guy Shipping: orders won't save</summary>

**What goes wrong:** the POS can't save orders: a server error.

**Fix:** go back to the plugin's previous version, or contact its developer.

</details>

<details>
<summary>Mollie: Direct Bank Transfer missing</summary>

**What goes wrong:** it hides Direct Bank Transfer from the POS checkout.

**Fix:** update Mollie.

</details>

<details>
<summary>CTX Feed: 403 errors on the POS settings page</summary>

**What goes wrong:** 403 errors now and then on the POS settings page.

**Fix:** deactivate it to confirm. There's no known setting that fixes it.

</details>

<details>
<summary>Barcode scanner plugins: orders won't save or show</summary>

**What goes wrong:** they break the order data the REST API sends, so orders won't save or show.

**Fix:** switch them off. The POS reads barcodes itself: see [Barcode Scanning](../../pos/product-panel/barcode-scanning.mdx).

</details>

<details>
<summary>PixelYourSite, PixelMySite: critical error</summary>

**What goes wrong:** a critical error: _call to a member function `is_type()` on bool_.

**Fix:** switch it off.

</details>

<details>
<summary>Google Listings & Ads: critical error, WCPOS class not found</summary>

**What goes wrong:** a critical error saying a WCPOS class was _not found_.

**Fix:** delete every WCPOS plugin, then install only the latest WCPOS Pro.

</details>

<details>
<summary>WooCommerce Subscriptions: blocks the Pro upgrade from 1.7 or older</summary>

**What goes wrong:** it blocks WCPOS Pro's upgrade step.

**Fix:** deactivate Subscriptions, activate WCPOS Pro and let the upgrade finish, then reactivate Subscriptions.

</details>

:::warning Stripe Terminal: leave it off in WooCommerce payments
Switch Stripe Terminal on only for the POS, in `WP Admin > POS > Settings > Checkout`. It doesn't need to be on in `WP Admin > WooCommerce > Settings > Payments`. Switched on there, it shows on your web store's checkout, where it has broken the checkout for online customers. See [Stripe Terminal](../../payment/gateways/stripe-terminal.mdx).
:::

### Server-level conflicts {#server-level-conflicts}

<details>
<summary>Security headers set by your web server: POS stuck on its logo, or blank pages</summary>

A `Content-Security-Policy` or `X-Frame-Options` line in `.htaccess`, Nginx or your host's panel.

**What goes wrong:** the POS stays on its logo, or a Legacy tab payment page or a receipt shows blank.

**Fix:** leave out `/pos`, `/wcpos-auth/` and `/wcpos-checkout/`, or allow `cdn.wcpos.com` and `cdn.jsdelivr.net` in `script-src` and `style-src`. WCPOS removes these headers from its own pages when WordPress or a plugin adds them, but it can't remove a header your web server adds.

</details>

<details>
<summary>GoDaddy Website Firewall: "Received 'undefined'"</summary>

**What goes wrong:** it blocks `/wp-json/`, with _"Received 'undefined'"_.

**Fix:** allow the `/wp-json/` path in the firewall: see [Server Performance](../performance/server.mdx#hosting-specific-notes).

</details>

### Conflicts WCPOS handles itself {#handled-by-wcpos}

<details>
<summary>Plugins that used to clash and need nothing from you now</summary>

Keep WCPOS up to date and these need no setting:

- **Security headers from plugins.** Wordfence, LiteSpeed Cache and other plugins can add a `Content-Security-Policy` that stops the POS loading. WCPOS removes `Content-Security-Policy` and `X-Frame-Options` from its own pages. A developer who needs a policy there can set one with the `wcpos_content_security_policy` filter.
- **JWT Authentication plugins.** They used to reject the POS's sign-in token, so every request after login failed with a 403. WCPOS now clears their error when it has signed the request in itself; other plugins' errors still come through.
- **Image Prioritizer.** It fills the `Link` header that apps use to find a WordPress site. When that header doesn't name your site's REST API, the app looks for it at `/wp-json/` instead. If the app still says _"Site does not seem to be a WordPress site"_, deactivate it.
- **Plugins that run when a product is saved** (Jetpack, Astra, Xero and others). Older WCPOS versions made them add duplicate rows on every request. That was fixed in 1.8.12, and the upgrade removed the duplicates.

</details>

## Prevention tips {#prevention-tips}

### Regular maintenance {#regular-maintenance}

1. **Keep plugins up to date.**
2. **Delete plugins you don't use**, rather than leaving them deactivated.
3. **Test every update on staging** before your live site.
4. **Watch your server's speed** with [Server Performance](../performance/server.mdx).

### Choosing plugins {#plugin-selection-best-practices}

1. **Pick plugins that are kept up to date**, with good reviews.
2. **Don't run two plugins that do the same job.**
3. **Check the plugin says it's tested with your WooCommerce version.**
4. **Add plugins one at a time**, and check the till after each.

### What to send {#when-contacting-support}

1. **Your active plugins**, with versions. `WP Admin > Tools > Site Health > Info` lists them, with a **Copy site info to clipboard** button.
2. **Your WordPress, WooCommerce and WCPOS versions.**
3. **What goes wrong**, in the words you noted.
4. **What you've already tried.**
