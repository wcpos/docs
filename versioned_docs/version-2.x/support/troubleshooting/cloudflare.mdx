Cloudflare sits in front of some stores and can ask visitors to pass a security check. The WCPOS app cannot always pass it, and then it cannot connect to your store or sync. The store owner, or whoever manages the site's Cloudflare account, fixes it by changing the Cloudflare setting responsible. This page shows which setting and how.

## At the till {#at-the-till}

- **Security check window on the desktop app:** tick the box in the window within two minutes. The app carries on, and Cloudflare lets it through for 30 minutes (unless the owner has changed that) before it asks again.
- **HOST121 on the iPad, iPhone or Android app:** these apps cannot pass Cloudflare's check. The app stays blocked until the store owner makes the change below.
- **Either way,** send this page to the store owner. The window keeps you selling today; only the store owner's change stops it coming back.

## Signs that Cloudflare is blocking the app {#how-to-recognise-it}

- **"This store's hosting setup is blocking the app"** on the connect screen, with error code [HOST121](../../error-codes/HOST121.mdx).
- A small window titled **Security check for your-store.com** opens on the desktop app while it connects or syncs.
- **"Your store is behind Cloudflare"** at the top of **WP Admin > POS > Settings > General**. The plugin shows this notice whenever your site runs through Cloudflare, as a warning before anything goes wrong.
- Cloud printing stops, and the printer card under **WP Admin > POS > Settings > Cloud Print** says **"A security service (like Cloudflare or a firewall plugin) is blocking WCPOS Cloud Print"**. The [relay](../../receipts/cloud-printing.mdx#relay) reaches your store the same way the app does, so the fix below fixes printing too.
- Older app versions reported **"Site does not seem to be a WordPress site"** or **"The site took too long to respond"** on a store that opens fine in a browser.

## Check it from a computer {#check}

The rest of this page is for the store owner. Open a terminal (Terminal on a Mac, PowerShell on Windows) and run this, with your store's address in place of `your-store.com`. On Windows, type `curl.exe` in place of `curl`.

```bash
curl -sI https://your-store.com/wp-json/
```

Read the first lines of the answer:

| You see | It means |
| --- | --- |
| `403` and `cf-mitigated: challenge` | Cloudflare is blocking the app. Carry on below. |
| `200` and `content-type: application/json` | Cloudflare is letting this computer through. If the app still fails, see [Plugin Conflicts](./plugin-conflicts.mdx). |
| `404` | Your site does not use pretty permalinks. Run the check again on `'https://your-store.com/?rest_route=/'` (keep the quotes). |

If WordPress lives in a subfolder, include it: `https://example.com/shop/wp-json/`.

<details>
<summary>How the desktop app gets past the check</summary>

The app talks to your store's REST API, the part of WordPress that answers apps with data. A web browser passes Cloudflare's check without you noticing; an app usually cannot. When Cloudflare answers with a check instead of data, the desktop app opens a hidden browser window and tries to pass the check on its own. If Cloudflare wants a tick box, the window appears and waits two minutes. Cloudflare then lets the app through for the time set in **Challenge Passage** (30 minutes by default), and the check comes back after that. The iPad, iPhone and Android apps have no such window.

</details>

## Find the Cloudflare feature that is blocking it {#which-feature}

Open your site in the Cloudflare dashboard and check which of these is on. The fix depends on which one it is.

- **Bot Fight Mode** (Free plan)
  - Where: **Security > Settings**, filter by **Bot traffic**.
  - Fix: turn it off. No rule can exempt the app from it ([why](#bot-fight-mode)).
- **Super Bot Fight Mode** (Pro plan and above)
  - Where: **Security > Settings**, filter by **Bot traffic**.
  - Fix: [add a Skip rule](#add-a-skip-rule).
- **Custom rules** or **managed rules** that challenge visitors
  - Where: **Security rules**.
  - Fix: [add a Skip rule](#add-a-skip-rule).
- **Under Attack Mode**
  - Where: **Quick Actions** on the site's overview, or the **Security level** setting under **Security > Settings**.
  - Fix: turn it off once the attack has passed. To keep it on for the rest of the site, add a **Configuration Rule** (**Rules > Overview > Create rule > Configuration Rule**) with the [Skip rule's expression](#add-a-skip-rule), and set **I'm Under Attack** to off.

The Cloudflare plugin for WordPress does not manage any of these. They live in the Cloudflare dashboard.

## Add a Skip rule for the REST API {#add-a-skip-rule}

A Skip rule tells Cloudflare not to challenge requests to your store's REST API. Your store stays protected: WordPress still checks every login and permission on those requests.

1. In the Cloudflare dashboard, open your site, go to **Security rules** and choose **Create rule > Custom rules**.
2. Under **Rule name**, enter `WCPOS REST API`.
3. Under **When incoming requests match**, choose **Edit expression** and paste:

   ```text
   (starts_with(http.request.uri.path, "/wp-json/")) or (http.request.uri.path eq "/" and (starts_with(http.request.uri.query, "rest_route=") or http.request.uri.query contains "&rest_route="))
   ```

   If WordPress lives in a subfolder, such as `https://example.com/shop`, use `/shop/wp-json/` and `/shop/` in place of `/wp-json/` and `/`.

   <details>
   <summary>What the expression matches</summary>

   The first half matches the API's normal address, `/wp-json/`. The second half matches the fallback address, `/?rest_route=/`, and only on the site's home address, so a page that happens to carry `rest_route=` in its link keeps its protection.

   </details>

4. Under **Then take action**, choose **Skip**.
5. Tick **All remaining custom rules** and **All Super Bot Fight Mode rules**. Under the other components to skip, tick **Security Level**. Tick **All managed rules** only if a managed rule is the one challenging the app. Leave the entries marked **(Previous version)** alone.
6. Choose **Deploy**. If other custom rules challenge or block visitors, drag this rule above them in the **Security rules** list. Managed rules always run after custom rules, so their order does not matter.

Run the [check](#check) again. The answer should be `200` with `content-type: application/json`, and no `cf-mitigated` line.

### If Bot Fight Mode is on {#bot-fight-mode}

Bot Fight Mode on the Free plan ignores Skip and Allow rules: Cloudflare's own documentation says no rule can bypass it. If the check still shows `cf-mitigated: challenge` after you add the Skip rule, and **Bot Fight Mode** is on, turn it off under **Security > Settings**, filter **Bot traffic**. To keep bot protection, move to the Pro plan and use **Super Bot Fight Mode**, which the Skip rule above does exempt.

## Stop Cloudflare caching the API {#caching}

Cloudflare can also keep a copy of the REST API's answers, and the app then shows old products, prices and orders. The Skip rule only turns off security checks; it does not change caching. If you cache HTML pages or use Automatic Platform Optimization (APO), add a **Cache Rule** with the same expression and set it to **Bypass cache**.

## Still blocked? {#still-blocked}

- Open the Skip rule and check it is deployed, not saved as a draft (**Save as Draft**).
- Check that no IP Access rule blocks or challenges the shop's internet connection.
- Other services in front of your site can block the app in the same way. See [Plugin Conflicts](./plugin-conflicts.mdx#server-level-conflicts) for security plugins and firewalls, and the [hosting notes](../performance/server.mdx#hosting-specific-notes) for GoDaddy, WP Engine and other hosts.
