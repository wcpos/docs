"There has been a critical error on this website." is WordPress's own message when your website crashes: a PHP error stopped it before it could answer the POS. The fault is on the website, not on the till. A change that didn't reach your store stays saved on the till until the website is fixed, so don't clear the till's data meanwhile.

## At the till {#at-the-till}

:::warning Don't clear this till's data
The error's entry in Logs says so too: "Don't clear this device's data — it may hold changes your store doesn't have yet." Clearing it loses them. Wait for the website to be fixed, then try again.
:::

1. Taking a payment? Follow the page for the checkout code in the message, [CHECKOUT101](../../error-codes/CHECKOUT101.mdx) or [CHECKOUT201](../../error-codes/CHECKOUT201.mdx), before you try again: with CHECKOUT201 the sale may have gone through. For anything else, try the action once more. A crash can be a one-off.
2. If it fails again, open **Store health** from the pulse icon at the foot of the menu, then **Logs**, and press **Errors**.
3. Tap the **SYNC131** entry to open it. It tells you whether your data is safe, and **Help — SYNC131** opens the code's page.
4. Press **Copy debug info** and send it, with the time it happened, to whoever looks after your website.

## Where you see it {#where-you-see-it}

- **On the till**, as a message after the action that failed, with the code [SYNC131](../../error-codes/SYNC131.mdx): your store had an error and didn't finish the request.
- **In the store's own reason**, where the POS shows one, such as at checkout or on a change your store refused. The reason is WordPress's sentence, or the PHP error itself when your website shows error details, such as *Allowed memory size of 134217728 bytes exhausted in wp-includes/class-wpdb.php:2324*.
- **At checkout**, the message carries a checkout code instead, which says what happened to the payment: [CHECKOUT101](../../error-codes/CHECKOUT101.mdx) when the cart is safe to try again, [CHECKOUT201](../../error-codes/CHECKOUT201.mdx) when the POS can't tell whether the sale went through. Follow that page before you charge again.
- **In a browser**, when the website crashes while the POS page itself loads. WordPress shows its own error page in place of the POS.
- **In Store health → Logs**, as an error entry with **SYNC131** in the **Status** column.

## Find the cause on your website {#find-the-cause}

This part needs someone who can sign in to WP Admin.

1. Go to **WooCommerce → Status → Logs** and open the newest **fatal-errors** log from around the time of the failure. A crash almost always leaves its PHP error there.
2. Read the first line of the error and the file it names. A file under `wp-content/plugins/` names the plugin it belongs to; one under `wp-content/themes/` names the theme.
3. If the crashes started after a plugin or theme update, undo that update or deactivate the plugin or theme. If they started after a PHP upgrade, ask your host to check that change. [Plugin Conflicts](./plugin-conflicts.mdx) shows how to find the plugin at fault.
4. Nothing in WooCommerce's logs? Ask your host for the server's PHP error log for the same time.
5. Once it's fixed, go back to the till. For a payment, check the checkout code's page before you charge again. For anything else, try the action again: the change is still saved there.

**WP Admin > POS > Settings**, **Logs** under **Tools**, shows **Fatal errors detected — view in WooCommerce logs** whenever a fatal-errors log exists. The link opens WooCommerce's logs filtered to fatal errors.

:::tip The email from WordPress
When a plugin or theme causes the crash, WordPress emails the site's admin address: **Your Site is Experiencing a Technical Issue**. Its link signs you in to WP Admin in recovery mode, where you can deactivate the plugin at fault even when WP Admin won't open normally.
:::

### Errors you may find {#common-errors}

**Allowed memory size of … bytes exhausted.** PHP ran out of memory. Ask your host to raise PHP's memory limit.

**An error in another plugin's file.** Some plugins are known to clash with the POS. Look for it under [Known plugin conflicts](./plugin-conflicts.mdx#known-plugin-conflicts), with its fix.
