A response error means your store's website answered the POS with nothing, or with something that isn't data: an error page, a PHP warning or a security check. The fault is on the website, not the till.

## At the till {#at-the-till}

:::warning Don't charge twice
After **CHECKOUT211**, the customer may already have paid. Open the order and check its status before you take payment again. The steps are on the [CHECKOUT211](../../error-codes/CHECKOUT211.mdx#troubleshoot) page.
:::

1. **Check the action finished.** Look for the sale, product or customer you were saving. If it's there, carry on.
2. **Try once more.** A one-off failure often clears on the next try. After **CHECKOUT211**, only once the order shows it isn't paid.
3. **Still failing?** Open **Store health → Logs** and press **Copy debug info** (**Share debug info** in the phone and tablet apps). [Find the error](#find-the-error) below shows where. Send it with the error code to whoever looks after your website, or to WCPOS support.

Don't clear this device's data to make the error go away. It may hold changes your store doesn't have yet. See [Clear Local Data](./clear-local-data.mdx).

## Find the error {#find-the-error}

Open **Store health** and go to **Logs**. Tap **Errors** to see only the problems, then tap a row to open it.

<div className="pinned-legend">

1. **Store health** — the heartbeat icon in the side bar. A red badge counts errors you haven't read. On a phone, it's in the menu at the top left.
2. **Logs** — everything this device did and every problem it met, kept for up to 30 days. See [Logs](../logs.mdx).
3. **Errors** — shows only the rows that need attention. The code at the end of each row names the problem.
4. **The opened row** — what the store said, what to do next, and under **Request** the status the store answered with. This example is a refused change (`403`). A response error ends in **SYNC131**, **SYNC151** or **CHECKOUT211**, often with a `500`.
5. **Help** — opens the page for that error code.
6. **Copy** — copies this one entry, to paste into a message to support.
7. **Copy debug info** — copies a report of this device and its recent errors. In the phone and tablet apps it reads **Share debug info**.

</div>

## What the codes mean {#codes}

Older versions of WCPOS showed a response error as `Cannot read properties of undefined (reading 'data')`. Now the row in Logs ends with one of these codes:

- **[SYNC131](../../error-codes/SYNC131.mdx): Your store had an error and didn't finish this request.** The website failed while handling the request, or sent back a page instead of data.
- **[SYNC151](../../error-codes/SYNC151.mdx): Your store's reply had stray text in it, which WCPOS tried to clean up.** A plugin or theme printed text, often a PHP warning, in front of the data. The POS removed it; check the action finished.
- **[CHECKOUT211](../../error-codes/CHECKOUT211.mdx): The store returned no checkout result, so the order status is unknown.** The sale was sent, but no answer came back. The order may exist and may be paid.
- **[HOST121](../../error-codes/HOST121.mdx): A bot-protection page is answering instead of the store's API.** A firewall or security service answered for your store. The POS checks for this when you connect the store; later, the same page shows as SYNC131. See [Cloudflare](./cloudflare.mdx).

A red bar that reads **Something went wrong:** followed by technical text is a different problem: part of the screen failed to draw. Close it with the **X**. See [CLIENT151](../../error-codes/CLIENT151.mdx).

## Find the cause on the website {#find-the-cause}

These steps are for whoever looks after your WordPress site.

<details>
<summary>For the site admin: the error log, the reply and what it tells you</summary>

### Read the store's error log {#error-log}

1. In WP Admin, go to **WooCommerce → Status → Logs**.
2. Open the newest `fatal-errors` log from around the time of the error. A PHP crash leaves a line there naming the plugin or file.

The POS plugin's own log, **POS → Settings → Logs**, shows **Fatal errors detected — view in WooCommerce logs** when there are any. See [Critical Error](./critical-error.mdx).

### Read the reply itself {#read-the-reply}

1. Open the POS in a desktop browser at `yourdomain.com/pos`. In the desktop app, use **Advanced → Toggle Developer Tools** instead.
2. Open the developer tools: right-click the page and choose **Inspect**, or press `Ctrl + Shift + I` (`Cmd + Option + I` on a Mac).
3. Go to the **Network** tab and repeat the action that failed. Never repeat a payment whose result you don't know: check the order first, as in [Don't charge twice](#at-the-till).
4. Click the failed request, shown in red or with a `5xx` status, and read its **Response**.

### What the reply tells you {#what-the-reply-tells-you}

- **`Warning:`, `Notice:` or `Deprecated:` text before the `{`.** A plugin or theme is printing PHP messages into every reply. Turn off on-screen PHP messages (`WP_DEBUG_DISPLAY` set to `false`), then fix or replace the plugin. See [Plugin Conflicts](./plugin-conflicts.mdx).
- **"There has been a critical error on this website".** PHP crashed. Read the fatal-errors log above. See [Critical Error](./critical-error.mdx).
- **A security check or "verify you are human" page.** A firewall or bot protection is answering for the store. Allow the store's REST API through. See [Cloudflare](./cloudflare.mdx).
- **Nothing at all, with a `500`, `502`, `503` or `504` status.** The server ran out of memory or time. Ask your host for the PHP error log and your limits. See [Server Performance](../performance/server.mdx#503-errors).

</details>
