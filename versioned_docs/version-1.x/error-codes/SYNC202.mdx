## What this means {#what-this-means}

Your store refused this change, so this device went back to the store's version.

The change wasn't saved. Read the store's reason, fix what it names, then make the change again.

This happens with edits to existing products, variations, coupons and customers. When your store permanently refuses one — for example because a value is invalid, or the signed-in user isn't allowed to make that change — WCPOS doesn't keep the refused edit waiting. It puts the store's version back on this device, so the till sells from the same details your store has. The log entry names the record and carries the store's reason.

## Your data {#your-data}

Nothing else changed. Your store still has its own version, unchanged, and this device shows that version again. If the store has deleted the record, it is removed from this device instead. Only the refused edit is gone, so make it again once the reason is fixed. Sales and orders are not affected, and an edit you made to the same record after the refused one is kept and still sends.

## Troubleshoot {#troubleshoot}

1. Expand the log entry and read the store's reason: it says what the store refused and which record it belongs to.
2. Fix what the reason names. If it is a value — for example a price, a SKU, an email address, or a required field left empty — work out the correct value. If the reason says the user isn't allowed to make the change, the account's role lacks that task: see [AUTH201](/error-codes/AUTH201).
3. Open the record (if the store has deleted it, there is nothing to change), make the change again with the corrected value, and save. Once it syncs, check the record shows your change.
4. A new record created on this device that the store refused is not reverted — there is no store version to go back to. It stays listed in **Store health → Database** under **"… changes never reached your server"**; see [SYNC201](/error-codes/SYNC201).
5. **Site admin:** if the reason mentions a field the POS does not show, open the same record in WP Admin — another plugin may add validation the POS cannot see. If the store keeps refusing the change, use **Copy debug info** on the **Logs** tab and contact support.
